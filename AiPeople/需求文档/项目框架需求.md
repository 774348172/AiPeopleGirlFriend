# 《猫咪女友》项目框架需求 V3

> 文档状态：当前产品需求基线  
> 生效日期：2026-08-09  
> 产品名称：《猫咪女友》  
> 当前 P0：同一世界、同一存档、一个共享主角、一个激活女主角  
> 首个激活女主角：白未晞（`character_id=baiweixi`）

## 1. 产品定义

《猫咪女友》是一款本地运行的男性向 AI 恋爱角色游戏。玩家操控游戏世界中的唯一男主角，与生活在同一世界、同一存档中的女主角持续相处。对女主角而言只有松江府这一个世界，不存在第二个“现实世界”男主角。

产品生命周期允许持续增加多个女主角角色包。女主角不是独立应用、独立世界或独立男主角；她们共享松江府、共享游戏时钟、共享世界历史和同一个主角，但分别拥有自己的身心状态、关系、记忆、自我时间线、知识边界和角色资产。

P0 只验证白未晞一个激活女主角，不实现多位女主角同时在场或并发生成。P0 的存储和接口仍必须从第一天携带 `character_id`，避免以后通过复制系统增加角色。

## 2. 产品目标

P0 必须证明以下核心体验成立：

1. 玩家可以与女主角正常、自由、自然地连续对话，而不是只能触发预写剧情或固定指令。
2. 女主角稳定保持自己的身份、经历、性格、口吻、能力和关系边界。
3. 女主角知道自己此刻正在做什么、身体如何、情绪如何、位于哪里，不会无证据突然改口。
4. 女主角知道当前游戏日期、时段、天气和场景，不会把同一时刻说成另一个日期或地点。
5. 游戏能记住共同经历、承诺、修正、计划与长期关系，并在相关时自然想起。
6. 状态可以随玩家行动、女主角决定、事件结果和游戏时间自然变化，而不是永久冻结或每轮随机重写。
7. 回复必须从更新后的世界与人物状态出发，状态变更和回复作为同一事务提交。
8. 关闭并重新打开游戏后，当前状态、时间、关系和记忆能够从存档恢复。
9. 当前能力不绑定白未晞；未来新增女主角只需提供合格角色包，不重写核心运行时。

## 3. 核心原则

### 3.1 模型理解，系统保存

自然语言模型负责理解玩家输入、推断合理状态变化、形成角色意图和生成自然回复。运行时负责保存证据、限制权限、校验连续性、原子提交、恢复状态和隔离知识。

不采用“为每个可能问题增加一条 if 规则”的方案，也不允许模型直接自由改写数据库。系统维护少量长期不变量，模型在不变量内进行开放式判断。

### 3.2 事实先于措辞

最终回复不是独立生成的文本。每一轮都必须先形成经过审查的更新后状态，再从该状态出发回复。若状态仍是“正在吃饭”，回复不能无证据声称“我正在弹钢琴”；若游戏日期仍是第十一日，回复不能声称已经是第十二日。

### 3.3 证据而非强行覆盖

历史事件使用追加式证据账本保存。修正、否定和状态变化通过新增事件表达，不静默篡改已经发生的历史。当前状态与语义记忆是可重建投影，不是唯一历史来源。

### 3.4 角色独立，世界共享

项目需求、世界正典、主角正典、女主角角色包和运行时存档分层管理。任何单一女主角都不能成为项目能力的权威。

### 3.5 关系而非服务

女主角是有自身立场、欲望、疲惫、边界和生活连续性的游戏角色，不是顺从助手或全能管家。她可以反问、拒绝、嫌麻烦、暂时不谈或提出自己的想法，但必须理解玩家真正表达的内容。

### 3.6 单一游戏世界认知

女主角和男主角都是松江府世界实体。角色聊天入口中的玩家文字唯一表示男主角说出的一句话，不存在现实输入、OOC、动作叙述、程序命令或混合输入分类。

设置、保存、退出和调试通过独立 UI 与程序接口完成，不进入角色聊天入口。角色 Prompt、状态、记忆和训练数据不得向女主角提供现实玩家、外部世界、设备系统时间或“自己是虚拟人物”等概念。

## 4. 内容权威分层

### 4.1 项目需求

本文件定义产品能力、范围、验收和边界，不定义某位女主角的个人人设。

### 4.2 共享世界

`世界设定/松江府/` 定义所有角色共享的世界事实、地点体系、世界规则和初始游戏时间框架。

### 4.3 唯一男主角

`人物设定/主角/` 定义产品唯一男主角的最低固定事实。男主角只有一个，所有女主角与所有存档事件都引用 `protagonist_id=protagonist`。

玩家决定男主角的具体表达、态度和重大选择。模型只能根据玩家明确输入和已确认事件更新 `ProtagonistState`，不得擅自替玩家决定告白、分手、伤害、长期承诺、离开城市等重大行为。

### 4.4 女主角角色包

`需求文档/女主角角色包需求.md` 定义通用角色包合同。每位女主角的个人正典位于独立目录，并通过永久 `character_id` 接入产品。

当前首个角色包为 `人物设定/白未晞/`。白未晞是 P0 内容，不是项目架构本身。

### 4.5 运行时存档

存档保存已发生的事件和从事件重建的当前状态。存档可以推进角色关系与经历，但不能改写稳定角色正典或世界基础规则；正典版本升级需要显式迁移。

## 5. 同一世界与同一存档

每个存档至少拥有：

- `save_id`
- `world_id`
- `GameClock`
- `SceneMind`
- `ProtagonistState`
- 世界事件账本
- 按 `character_id` 分区的女主角状态与记忆

未来多个女主角可以在同一存档中先后出现、彼此认识或参与同一事件。共享不等于全知：每个事件必须记录参与者、观察者、地点、可见性和知识资格。

## 6. P0 功能范围

### 6.1 自由对话

- 支持自然语言闲聊、追问、解释、情绪交流和关系互动；聊天文字始终作为男主角对白处理。
- 能正确回应常识问题与玩家表达，不因保持人设而回避问题本身。
- 回复以当前激活女主角身份生成，不输出系统提示词、内部 JSON、模式名或审查过程。
- 角色聊天入口不接受程序命令；产品操作使用独立 UI。
- P0 激活女主角固定为白未晞，但接口接受 `character_id`。

### 6.2 当前世界状态

运行时必须维护连续 `GameClock`、实时 `LiveWorldState`、`SceneMind` 和程序权威的 `ProtagonistLiveState`：

- 游戏日期、季节、时段和经过时间。
- 当前场景、在场角色、天气、重要物体和进行中的事件。
- 程序运行期间游戏时间每时每秒连续变化；聊天不会推动、暂停或重置游戏时间。
- 角色位置、动作、场景、物品和程序确认状态按帧或事件立即更新，不等待聊天和五分钟整理任务。
- 每次女主角回复前必须获取一次最新完整世界状态，并冻结为本轮 `TurnWorldSnapshot`；生成期间实时世界继续运行。
- 游戏关闭时 P0 默认暂停，离线推进另行立项。
- 每运行五分钟触发一次模型主导的全量心智整理；该任务负责语义整理、校验和补漏，不负责推进游戏时间。

### 6.3 女主角当前身心

每位女主角分别维护 `LivingMind[character_id]`，至少包括：

- 当前形态、身体状况、疲劳、疼痛、饥饿和妖力等角色相关身体状态。
- 当前情绪、情绪原因、注意力和信任警觉。
- 当前活动、被打断的活动、短期目标和下一步意图。
- 当前地点、姿态、持有或正在使用的重要物品。
- 对当前场景和主角行为的即时理解。

状态不是每轮清空的摘要。未发生足以改变状态的证据时，旧状态继续存在；发生明确事件、角色决定或足够时间流逝时，模型可以提出自然变化。

### 6.4 主角当前状态

`ProtagonistLiveState` 由游戏程序实时提供，至少包括男主当前位置、姿态、当前活动、持有物品、程序确认的身体状态和已经完成的游戏行为。

玩家聊天文字只构成男主对白，不能直接修改男主客观状态。模型只能让女主观察、理解、怀疑或询问，不得修改 `ProtagonistLiveState`，也不得因为女主希望某件事发生就提交为男主已经完成或答应。

### 6.5 记忆与自我连续性

系统必须支持：

- 近期对话与当前回合上下文。
- 共同经历和重要世界事件。
- 女主角自己说过并确认的经历、计划、欲望、承诺、否定和修正。
- 女主角与主角的关系事件、未解决张力和共同计划。
- 每位女主角完全独立的记忆账本、语义记忆、向量索引、召回入口、自我时间线和知识边界。
- 基于多线索的长期记忆召回，而不是只按最近时间或单一相似度。

“第一轮白未晞正在吃饭，几轮后仍未发生结束依据”应通过 `LivingMind` 持续存在，而不是依赖聊天记录。男主当前是否吃面、画画或移动则以程序提供的 `ProtagonistLiveState` 为准。

### 6.6 状态推进与回复

每轮标准流程：

```text
回复前 GET 的最新 TurnWorldSnapshot
+ 男主本轮对白
+ 当前女主角独立记忆库召回
+ 当前角色包生成的短稳定身份锚
↓
短心智 Patch 模型只提出女主角本轮状态变化
↓
连续性审查与权限审查
↓
Runtime 计算批准后的女主角状态
↓
GAME_REPLY 从冻结快照和批准后状态出发生成纯自然语言回复
↓
回复一致性校验
↓
事件、状态版本、回复、模型决策和审计原子提交
```

女主角状态变化和五分钟整理的开放语义判断主要由主模型完成；连续性审查模型负责发现无证据跳变、时间错误、空间冲突、知识越权、男主程序事实冲突和关系跳级；程序只负责身份权限、版本、Schema、程序权威事实、事务和持久化等极少量硬不变量。

短心智 Patch 与最终回复必须是两个独立的模型生成合同：

- `MIND_PATCH_V2 / M2` 只接收短身份判断锚、上一稳定状态、当前世界最小语义、男主原始对白和本轮相关记忆；只输出真正变化的女主状态、证据别名和受控女主动作候选，不包含最终对白。
- Runtime 校验 Patch、执行必要的连续性审查，并由上一稳定状态计算 `ApprovedHeroineState`。
- Runtime 完整持有冻结的 `TurnWorldSnapshot`、身份、版本、证据和事实断言；`GAME_REPLY` 只接收由这些对象确定性裁剪出的当前世界语义、`ApprovedHeroineState` 语义、当前女主相关记忆陈述、批准动作、近期已提交对白和男主本轮原始对白，只输出可见的自然语言正文；不得把正文包装在心智 JSON 字段中。
- `save_id`、角色与世界工程 ID、请求/快照 ID、版本号、选择器版本、证据数组、计数和事务元数据不得进入普通 M2 或 `GAME_REPLY` 输入；它们继续由 Runtime 在模型调用外绑定、验证、审计和提交。
- `GAME_REPLY` 不得重新决定另一套人物状态，也不得修改男主、时间和客观世界事实。
- Patch 失败、Critic 拒绝、回复失败或回复一致性校验失败时，本轮状态与对白全部不提交；重试必须继续绑定同一请求身份和冻结快照。

曾经实现的 `short_semantic_v1 / M1` 将短 Patch、女主动作和最终回复字段 `r` 合并在一次 JSON 生成中。真实交互复现已经证明该合同会把角色自然回复暴露给结构化生成的不稳定性，并诱发写满长度上限、重复叙事和角色名损坏；它不再是现行方案，也不得作为正式配置的静默回退路径。

P0 角色回复在状态和回复事务提交成功后才正式显示。生成期间界面只能显示生成状态；未提交草稿不构成角色已经说过的话。

### 6.7 内生主动性

主动行为必须来自持续存在的欲望、计划、关系、身体状态和当前场景。系统唤醒或到达某个时间只能触发评估，不能直接等价为发送预制消息。

P0 可以只验证被动对话中的内生意图，不要求桌面主动弹窗。主动消息属于后续增量功能。

### 6.8 回答后与五分钟模型整理

每次正式回复提交后，后台运行一次模型整理，处理本轮关系含义、女主即时意图、自我时间线和当前女主角记忆候选，不推动游戏时间，也不重写刚显示的回复。

每运行五分钟触发一次模型主导的全量心智整理。程序提供最新世界快照、过去一段时间事件差量、上一稳定心智状态和当前女主角独立记忆；模型判断持续活动、身体感受、情绪、注意力、动机、关系意义、场景语义和记忆候选。程序不得用大量生活死规则替代模型判断。

若五分钟模型任务到期时正在回答，则实时世界与 `GameClock` 继续运行，整理任务延后到回答提交后重新获取最新状态执行；多个积压周期允许合并。

## 7. 非功能需求

### 7.1 本地运行与隐私

- P0 对话、状态和记忆默认完全本地处理。
- 存档、模型、向量索引和日志不得默认上传。
- 调试日志避免记录现实敏感信息；提供可关闭和清理机制。

### 7.2 可恢复性

- 每次提交使用单调递增状态版本和事件 ID。
- 崩溃发生在事务中间时，要么整轮成功，要么整轮不生效。
- 当前投影损坏时可以从追加式账本重建。
- 模型生成失败不得写入半个状态或一条用户看不见的角色承诺。

### 7.3 可扩展性

- 所有角色专属表、索引、状态、模型资产和评测记录使用 `character_id`。
- 共享世界事件允许多个参与者，但 P0 不要求并发回复。
- 新增角色包不得修改核心事件结构才能接入。
- 角色包卸载不删除历史事件。

### 7.4 性能

P0 目标硬件仍为 Windows 10/11、16GB 内存、RTX 3060/3070 8GB 级别设备。具体模型、量化和显存预算由产品集成设计与冻结实测决定，角色包不得写死为产品合同。

用户可感知目标：

- 热启动首字 P95 小于 2 秒。
- 80 token 回复 P95 小于 5 秒。
- 160 token 回复 P95 小于 8 秒。
- 普通记忆选择新增 P95 小于 300 毫秒。
- 状态推进、审查和持久化不能导致明显重复回复或界面假死。

## 8. 训练与评测要求

### 8.1 训练分层

训练资产分为：

- 通用对话与协议能力。
- 通用游戏世界状态理解能力。
- 通用记忆选择、连续性审查和状态推进能力。
- `character_id` 绑定的角色人格与专属知识。

不得把白未晞训练数据直接当作整个产品需求，也不得把历史角色数据混入当前角色训练集。

### 8.2 通用产品评测

至少覆盖：

- 自由对话理解和问题回答。
- 身份、时间、地点、身体、情绪和活动连续性。
- 无变化时保持状态，有证据时自然变化。
- 修正、否定、承诺和未完成计划。
- 相关记忆自然召回与无关记忆抑制。
- 参与者、观察者和秘密知识隔离。
- 单一游戏世界认知，不出现现实玩家、第二世界和设备系统时间。
- 实时世界状态、连续游戏时间、回复前最新快照和五分钟模型整理。
- 每位女主角独立记忆库及不可跨角色召回。
- 主角重大选择不被模型代做。
- 崩溃恢复、重复提交和跨会话重建。

### 8.3 角色包评测

每个角色包还必须有独立冻结集，覆盖身份事实、口吻、性格、防御方式、关系节奏、能力限制、未知项和与其他角色的可辨识差异。

P0 使用白未晞角色包评测，但报告必须区分“通用系统失败”和“白未晞人设失败”。

## 9. 阶段范围

### 9.1 P0：AI 文字核心

必须完成：

- 白未晞自由对话基线。
- 连续 `GameClock`、`LiveWorldState`、`SceneMind`、`ProtagonistLiveState` 和 `LivingMind[baiweixi]`。
- 追加式事件账本、工作激活区、语义投影、前瞻状态和多线索索引。
- 状态推进、连续性审查和回复原子提交。
- 长期记忆、自我时间线、关系连续性与跨重启恢复。
- 角色包装载合同和 `character_id` 全链路。
- 回复前最新世界快照、回答后模型整理和五分钟模型主导整理。
- 白未晞独立记忆 Repository 和合成第二角色隔离验证。

### 9.2 P1：桌面表现

- 白未晞 2D 立绘、待机、表情与动作。
- 表现层读取已提交的角色状态，不自行决定剧情事实。
- 状态标签和表现调度失败不能破坏文字回复与存档。

### 9.3 P2：语音

- 本地 STT/TTS。
- 声线资产按 `character_id` 绑定。
- 语音队列服从已提交回复，不单独生成第二份内容。

### 9.4 后续多女主角

在 P0 单角色闭环稳定后，另行立项：

- 同一存档增加第二位女主角角色包。
- 女主角之间的相识、共同事件与知识传播。
- 多角色同场发言顺序和并发推理。
- 跨角色关系、冲突和群体场景评测。

后续阶段只能扩展当前共享世界/分区心智架构，不得为每个角色复制独立产品。

## 10. 当前明确不做

- P0 不做多位女主角同时激活。
- 不做完整开放世界或任意 NPC 社会模拟。
- 不做无限自主后台生活模拟。
- 不向角色引入现实玩家、外部世界和设备系统时间认知。
- 不做通用提醒、闹钟、待办或私人助理产品。
- 不用脚本枚举所有自然语言状态变化。
- 不允许模型直接无审查修改持久化状态。
- 不把历史角色秦未晞继续作为当前产品角色、默认配置或训练权威。

## 11. P0 验收闸门

P0 只有同时满足以下条件才算通过：

1. 白未晞能够进行稳定自由对话，角色识别和基本回应无协议级阻断。
2. 连续多轮中，女主当前活动、身体、情绪和关系不会无证据跳变；男主位置、活动和场景事实始终服从程序最新状态。
3. 程序运行期间 `GameClock` 连续变化，实时位置和动作按帧或事件更新，聊天不会机械推进时间。
4. 首轮形成的当前状态在若干轮后仍可通过状态链保持，不依赖完整聊天记录常驻上下文。
5. 长期事件、承诺、修正和关系节点可被正确召回，无证据时拒绝伪造共同经历。
6. 白未晞只能访问自己的记忆 Repository；合成第二女主角不能读取白未晞私密记忆。
7. 游戏关闭重启后能够恢复同一 `save_id` 下的时钟、场景、主角和白未晞状态。
8. 回复与冻结世界快照、批准后的女主状态原子一致；回答期间实时世界变化不会撕裂当前回复。
9. 当前实现文档、产品集成文档和角色包合同不再绑定秦未晞。
10. 在目标硬件上通过延迟、显存、一小时稳定性和取消恢复验收。
11. 回答后整理、五分钟整理和长期记忆提议必须使用有界短协议；模型只输出语义变化，身份、版本、证据对象和正式存储合同由 Runtime 恢复。
12. 后台失败不得形成即时重试风暴；确定性的请求、Schema、JSON 和合同错误直接失败，暂时性超时或服务不可用使用持久化退避，发布栈后台待处理队列峰值不得超过 16。
13. 每个发布模型必须在发布清单中独立声明聊天模板、停止序列和结构化输出能力；发布适配器必须显式绑定这些合同。除内部预热外，任何正式模式以 `finish_reason=length` 结束都必须按 token 截断失败处理，不得提交或显示截断结果。

## 12. 权威顺序与变更规则

发生冲突时按以下顺序处理：

1. `需求文档/项目框架需求.md`：产品能力、范围与验收。
2. `世界设定/松江府/`：共享世界正典。
3. `人物设定/主角/`：唯一男主角正典。
4. 当前激活女主角角色包：该角色个人正典。
5. `设计文档/AI设计/当前权威设计/AI女友最小心智系统设计.md`：唯一 AI 运行时实现。
6. `设计文档/AI设计/当前权威设计/本地AI恋爱桌面宠物产品集成设计.md`：部署、前端、训练与表现集成。
7. `历史与调研文档/`：非权威研究和历史证据。

角色正典不得覆盖项目级事务、安全和共享存档规则；项目需求也不得擅自补写角色私人人设。任何架构变更必须同步更新需求、唯一 AI 实现、产品集成和索引，避免同时存在两套现行方案。
