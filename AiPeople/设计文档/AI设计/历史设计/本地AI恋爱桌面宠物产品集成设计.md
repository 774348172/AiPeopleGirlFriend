# 《猫咪女友》本地产品集成设计 V4

> 文档状态：当前产品集成权威  
> 生效日期：2026-08-09  
> AI 运行时唯一权威：`AI女友最小心智系统设计.md`  
> 当前 P0 激活角色：白未晞（`character_id=baiweixi`）
> 2026-08-14：前台 M2 与 `GAME_REPLY` 已切换到角色包短锚和确定性最小语义投影。

## 1. 设计目标

本文件定义《猫咪女友》的本地模型部署、角色包装载、桌面宿主、训练工件、2D 表现、语音和进程集成。它不定义第二套记忆、关系或状态架构。

产品生命周期允许增加多个女主角角色包。所有角色共享一个世界、一个存档和唯一男主角；P0 只激活白未晞，不实现多角色同时生成。

## 2. 分层架构

```text
Desktop Host / Game UI
├─ 角色聊天入口（所有文字均为男主对白）
├─ 独立设置、存档、退出与调试 UI
├─ 提交后回复显示与模拟打字
├─ 角色选择与角色包管理（P0 固定白未晞）
└─ 2D / STT / TTS（后续阶段）
        ↓
RelationshipRuntime / WorldMindRuntime
├─ Continuous GameClock / LiveWorldState
├─ ProtagonistLiveState / WorldStateProjection
├─ WorldStateProvider.getLatestSnapshot()
├─ LivingMind[character_id]
├─ 追加式事件账本与投影
├─ HeroineMemoryRepository[character_id]
├─ 回合状态推进、回答后整理与五分钟模型整理
├─ 连续性审查
└─ 原子提交
        ↓
Local Model Services
├─ 主生成模型
├─ Embedding 模型
├─ Reranker
├─ STT（P2）
└─ TTS（P2）
        ↓
Content Packages
├─ 世界包：songjiangfu
├─ 主角包：protagonist
└─ 女主角包：baiweixi，未来可增加
```

前端只通过统一运行时接口读写对话和已提交状态，不直接拼接记忆、改人物状态或决定剧情事实。

## 3. 角色包注册与加载

### 3.1 注册表

每个可用女主角通过 manifest 注册：

```yaml
character_id: baiweixi
display_name: 白未晞
package_version: 1.0.0
world_id: songjiangfu
protagonist_id: protagonist
canon_path: 人物设定/白未晞/
assets:
  dialogue_adapter: null
  evaluation_manifest: null
  portrait_manifest: null
  voice_manifest: null
compatibility:
  runtime_schema: 2
```

所有路径由 manifest 明确声明，不通过“秦”“白未晞”等目录名猜测。发布工件必须记录 SHA256、模型格式、量化、基础模型版本和角色包版本。

### 3.2 启动顺序

进入存档时：

1. 校验运行时 schema。
2. 加载 `world_id=songjiangfu` 世界正典。
3. 加载 `protagonist_id=protagonist` 主角正典。
4. 读取存档角色注册表。
5. 加载 `active_character_id` 的角色包和专属资产。
6. 重放或校验事件账本与投影。
7. 启动本地模型服务并完成健康检查。
8. 恢复已提交的当前场景和角色状态。

P0 仅接受 `active_character_id=baiweixi`。找不到角色包时必须阻止进入并显示错误，不允许自动回退到历史秦未晞模型、默认人格或无角色助手。

### 3.3 同一存档

存档目录建议：

```text
saves/<save_id>/
  save_manifest.json
  ledger/
  projections/
    world/
    protagonist/
    heroines/<character_id>/
  indexes/
    shared/
    heroines/<character_id>/
  transactions/
```

共享事件可以包含多个角色，但角色私密投影、关系和记忆索引按 `character_id` 分区。角色包卸载不删除账本历史。

## 4. 模型方案

### 4.1 主生成模型

P0 当前工程候选可以继续使用本地 4B 级中文模型验证，但产品合同不把某个基础模型、LoRA 名称、GGUF 文件或训练条数绑定为永久架构。

正式工件必须通过 manifest 冻结：

- 基础模型与精确版本。
- tokenizer 与聊天模板。
- 角色适配方式。
- 合并与量化流程。
- 上下文长度和采样参数。
- 文件 SHA256。
- 目标硬件真实延迟、显存和稳定性证据。

角色专属权重必须带 `character_id`。通用状态推进或审查能力应尽量保持角色中立；角色人格能力由角色包正典、角色训练数据和可选适配资产提供。

### 4.2 模型调用协议

主模型支持唯一心智设计定义的模式：

- `MIND_PATCH_V2 / M2`
- `WORLD_CONTINUITY_REVIEW`
- `GAME_REPLY`
- `POST_REPLY_WORLD_MIND_RECONCILE`
- `FIVE_MINUTE_WORLD_MIND_RECONCILE`
- `MEMORY_PROPOSE`
- `SELF_TIMELINE_PROPOSE`
- `RELATIONSHIP_PROJECT`
- `MOTIVE_EVALUATE`

结构化语义模式通过独立 Schema、停止条件和 Decoder 隔离。`MIND_PATCH_V2 / M2` 只生成短 Patch，不包含回复正文；`GAME_REPLY` 不使用 JSON Grammar，只生成自然语言正文。两次调用之间由 Runtime 计算并冻结 `ApprovedHeroineState`。

前台推理输入采用职责最小化：M2 使用角色包生成的短身份判断锚与最小动态状态帧；`GAME_REPLY` 使用短身份表达锚、冻结快照与批准状态的确定性自然语义投影、相关记忆陈述、批准动作和正常对话消息。完整正典、完整 Runtime JSON、工程 ID、版本、证据数组、计数和事务字段保留在 Runtime 调用外，不发送给普通前台模型。

推理服务内部可以流式接收 `GAME_REPLY` token，但 P0 前端永远只接收通过一致性校验并与状态、事件和审计原子提交后的最终文本。Patch、Critic 或回复任一阶段失败都不能显示草稿或提交部分状态。已否决的 `short_semantic_v1 / M1` 合并合同不得成为正式模式或静默回退。

### 4.3 Embedding 与 Reranker

每个 `HeroineMemoryRepository[character_id]` 内部保持两阶段链路：

1. CPU 侧预计算向量和多线索粗召回。
2. 对合法候选中的稳定 Top32 做学习式批量重排。

当前候选可以继续实测 `bge-small-zh-v1.5` 与 `Qwen3-Reranker-0.6B`，但正式上线以冻结 manifest 和真实指标为准。模型替换不得改变“先打开当前女主角独立 Repository，再在库内召回和重排”的合同。

### 4.4 推理服务

推理服务需要：

- 本地离线启动。
- 模型服务内部支持流式 token，但 P0 在事务提交前不向玩家显示角色正文。
- 取消与超时。
- 每种模式独立 token 预算。
- 单存档前台事务串行化。
- 后台任务可暂停和去重。
- 模型健康检查和可执行错误信息。
- 模型工件与角色包版本记录。

P0 可以使用单进程或多进程实现，但必须测量完整 CUDA context、KV cache、分配器和跨框架重复开销，不能只相加模型文件大小。

## 5. 前端实现

### 5.1 前端边界

前端负责：

- 文本输入、发送、生成状态、提交后显示、模拟打字和取消。
- 显示当前角色、游戏时间、存档和连接状态。
- OOC 命令与游戏内输入的明确入口。
- 模型加载、恢复、错误和重试提示。
- P1 表现层和 P2 语音队列。

前端不负责：

- 自己维护另一份人物状态。
- 根据关键词直接改变表情以外的剧情事实。
- 把未提交生成文本显示为已经发生。
- 直接读取全部私密记忆拼进 prompt。
- 在 P0 模拟第二个激活女主角。

### 5.2 P0 最小界面

- 当前激活女主角：白未晞。
- 当前存档与游戏时间。
- 对话记录和输入框。
- 生成中、取消、重试和恢复状态。
- 角色回复生成完成并原子提交后才显示；提交前只显示“正在回应”。
- 可选开发面板：只在调试模式显示 `save_id`、`character_id`、事务 ID 和状态版本，不显示模型内部思考。

### 5.3 角色选择

P0 UI 不需要角色选择器，可以固定显示白未晞。底层接口仍提供角色注册表和 `active_character_id`。未来增加角色时，角色选择只改变激活对象和场景事件，不创建新男主角或新世界。

## 6. 2D 表现（P1）

### 6.1 资源绑定

每位女主角的以下资源由 `character_id` 绑定：

- 基础立绘。
- 表情与动作。
- 猫形、人形或其他角色合法形态。
- 服装和场景适配。
- 资源版本与兼容矩阵。

白未晞的形态、耳尾显示和伤势表现必须读取已经提交的 `LivingMind[baiweixi]`，不能由前端随机切换成与文本不同的状态。

### 6.2 表现标签

表现意图不得要求 `GAME_REPLY` 把对白正文重新包装进 JSON。P1 可以采用以下两种受控来源之一：

- 从已经批准并提交的 `LivingMind` 和女主动作候选映射表现标签。
- 使用独立、可失败的表现元数据提议器；失败只降级为纯文字，不影响对白与存档。

提交后的表现事件可以是：

```json
{
  "character_id": "baiweixi",
  "emotion": "guarded_affection",
  "pose": "sitting",
  "gesture": "tail_curl",
  "reply_event_id": "evt_heroine_reply_..."
}
```

标签必须通过白名单映射到已有资源，并引用已经提交的回复事件，而不是保存第二份回复正文。标签解析失败时只显示文字，不影响事务和存档。

### 6.3 调度

- 先确认事务提交，再播放动作和语音。
- 新消息可以中断非关键表现。
- 表现层不得补写角色未说出的行动。
- 同一状态版本只播放一次关键剧情表现，避免重连重复。

## 7. 语音（P2）

### 7.1 STT

- 本地语音识别转成玩家输入后，仍经过 `INPUT_GROUND`。
- STT 低置信度的时间、否定和角色名必须允许玩家确认。
- 原始音频默认不上传，保存策略可配置。

### 7.2 TTS

- 声线和参数由 `voice_manifest(character_id)` 加载。
- TTS 只朗读已经提交的最终回复。
- 生成取消时清理未播放队列。
- 声线不可用时回退到文字，不替换成另一女主角声线。

## 8. 训练流水线

### 8.1 通用与角色专属分离

```text
通用协议/状态轨迹/审查数据
→ 通用能力训练或提示合同

角色包正典 + 角色专属数据
→ character_id 专属训练 manifest
→ 角色适配候选
→ 角色专属评测

两者组合
→ 同一运行时端到端冻结评测
```

不得把历史角色数据混入白未晞数据。任何混合训练都必须有显式来源标记、用途和污染检查。

### 8.2 角色训练 manifest

至少记录：

- `character_id`
- 角色包版本与正典哈希。
- 数据文件、样本数、生成器版本和清洗报告。
- 基础模型、训练配置和随机种子。
- 防泄漏、事实冲突和其他角色污染检查。
- 评测集版本。
- 输出模型和量化工件 SHA256。

训练条数是工程参数，不是质量标准。是否发布由冻结自动评测、人工盲测、长聊和运行时连续性共同决定。

### 8.3 评测分层

报告必须分开：

- 通用自由对话质量。
- 世界与人物当前状态连续性。
- 长期记忆和知识隔离。
- 角色人格忠实度。
- 模型协议、延迟、显存和稳定性。

这样才能判断失败来自角色数据、基础模型、状态运行时、记忆选择器还是前端集成。

## 9. 性能与资源预算

目标环境：Windows 10/11、16GB 内存、RTX 3060/3070 8GB 级别设备。

P0 阻塞目标：

- 总显存峰值低于 5120 MiB。
- 热启动首字 P95 小于 2 秒。
- 80 token 回复 P95 小于 5 秒。
- 160 token 回复 P95 小于 8 秒。
- 普通记忆选择新增 P95 小于 300 毫秒。
- 连续一小时对话无进程泄漏、重复事务或不可恢复卡死。

测量必须包括主模型、KV cache、reranker 权重与激活、CUDA context、框架分配器、桌面壳和同时运行的其他 GPU 组件。

P1 增加 2D 后需重新测量；P2 加入 STT/TTS 后总峰值目标低于 6144 MiB，并提供按需加载和回退到纯文字的降级路径。

## 10. 进程与事务

- 桌面宿主负责启动、健康检查和关闭模型服务。
- 每个前台回合绑定唯一 `transaction_id`。
- 用户取消只取消未提交事务。
- 生成、状态推进、审查或持久化失败时显示明确阶段和重试入口。
- 崩溃恢复先检查事务日志，再重放账本，最后验证投影版本。
- 后台记忆与投影任务按 `transaction_id` 去重，新消息到达时暂停。
- 模型服务重启不改变 `active_character_id` 或游戏时钟。

## 11. 单一世界与产品 UI 边界

角色聊天入口只接收男主角对白，不解析程序命令、OOC、动作叙述和现实输入。保存、加载、设置、退出与调试通过独立 UI 或程序接口完成，不发送给角色模型。

前端不得把现实玩家、外部世界或设备系统时间写入角色 Prompt、女主状态、关系和记忆。女主每次回复前只通过 Runtime 获取当时最新 `TurnWorldSnapshot`，不从 UI 自行拼接男主位置和时间。

## 12. 实施阶段

本文件服从 `AI聊天核心施工优先级总纲.md` 的 `WMR-00` 至 `WMR-08` 排序：

1. `WMR-00～01`：冻结 V6 基线，接入存档身份和白未晞角色包。
2. `WMR-02～03`：建立实时世界、连续 GameClock、男主状态、语义投影、最新快照与 FakeModel 原子回合。
3. `WMR-04～05`：建立女主独立记忆 Repository、真实状态推进、同模型 Critic 和最终回复。
4. `WMR-06～07`：实现回答后整理、五分钟模型整理、长期轨迹和跨重启恢复。
5. `SYS-12S`：完成 Patch-only M2、批准状态和纯文本 `GAME_REPLY` 的前台协议修正。
6. 后台收敛：回答后整理和五分钟整理已接入 `B1`，长期记忆生产调用已从兼容 `R1` 切换为 `R2`；隔离 GPU 长测中 B1/R2 无结构或合同失败，R2 作业 59/59 完成，队列峰值 10 并排空。
7. `WMR-08 / SYS-12`：当前先修复或更换 7B 模型产物，使其通过 GAME_REPLY 最小探针；随后修复 M2 非法 Patch 的整轮失败，并治理进程树 RSS 增长和组合 GPU 峰值。全部达到门槛后才重跑冻结发布栈。
8. P0 文字核心通过后进入 P1 2D 和 P2 语音。

> 发布候选（2026-08-14）：默认 llama.cpp 工件为白未晞 Qwen2.5-7B Q5_K_M。运行时兼容层现已从发布清单逐模型读取 `chatml`、`<|im_end|>/<|im_start|>` 和 `json_schema`，启动时显式绑定模板、每次请求发送 stop，并拒绝所有正式模式的 `finish_reason=length`。复验中 M2/B1/R2 短协议通过；GAME_REPLY 仍出现角色续写、外语碎片和乱码，真实一回合四次打满 360 token 后被拒绝。同一 GGUF 走原始 Ollama Modelfile 也打满 64 token 并续写男主，剩余阻塞属于模型产物，不得进入 10/60 轮或一小时验收。

P0 使用一个不发布的合成第二角色包验证同存档隔离；第二位正式女主角另行立项，多角色同时在场另行研究。

## 13. 关键风险

- 旧秦未晞路径、提示词、模型或数据仍被默认配置加载，污染白未晞。
- 前端和运行时各维护一份状态，导致文字、立绘和存档不一致。
- 状态推进与回复分开提交，造成跨重启矛盾。
- 多角色扩展时先做 UI 角色切换，却没有独立 Repository 和知识隔离。
- 把白未晞当前模型工件误写为所有未来角色必须使用的产品格式。
- 为降低延迟绕过连续性审查或更新后状态，重新退化为“只看聊天记录生成回复”。
- 把现实玩家、第二世界或设备系统时间写入角色上下文，破坏单一世界认知。
- 把五分钟整理错误实现成程序生活规则引擎，或错误用来推动 GameClock。

## 14. 明确边界

- 本文件只负责产品集成，AI 记忆、状态和关系以唯一心智设计为准。
- P0 只有一个激活女主角白未晞，但所有接口和资产必须带 `character_id`。
- 产品名称为《猫咪女友》，不再以历史角色命名。
- 秦未晞相关 GGUF、LoRA、评测和训练包只能作为历史实验资产，不得成为当前默认产品合同。
- 新增角色包不意味着新增应用、世界、男主角或独立存档。
- `GameClock` 在程序运行时连续变化，聊天与时间推进无因果关系；五分钟任务只整理心智与错漏。
- P0 Critic 复用同一主模型的独立模式，独立审查模型必须凭性能和质量证据另行变更。
