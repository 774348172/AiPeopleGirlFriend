# 对话回应开放域承接性学习方案（V2）

> 文档性质：设计提案 —— 角色对白“答非所问”的开放域训练、评测与运行时改造方案  
> 版本日期：2026-08-20  
> 当前状态：待评审；不自动修改冻结模型、运行时或评测资产  
> 适用范围：`GAME_REPLY` 候选回复、回复承接性训练数据、离线质量评测与后续候选选择  
> 上游设计：`AI女友最小心智系统设计.md`（V6）、`AI聊天核心施工优先级总纲.md`

## 0. 决策摘要

V1 指出了真实问题，但解决方式仍是封闭分类：先声明“不按问题类型分类”，随后又规定七种合法回应形式，并要求逐类匹配。开放域对话中，任何固定形式表都会继续遇到未覆盖表达、形式组合和语境例外。

V2 不再定义合法回应类型，只定义一个学习目标：

> **知道可用公开语境的普通听者，能够说明角色此刻这句话承接了哪些仍活跃的会话变化；回复对这些变化产生与当前交流压力相称的公开会话更新。若没有未闭合变化，回复应当是有公开语境依据的自然收束或主动发起。**

全文只有第 3 节定义语义学习目标；其余章节是数据合同、系统边界和验收办法，不是要在对话中继续增加规则。

生产环境不运行“七类规则”或“推导链搜索”。系统训练一个上下文—回复交叉编码评分器，直接估计候选回复是不是当前语境下的实质承接：

```text
冻结的可用公开语境投影 C + 当前玩家原话 U + 候选回复 R
                          ↓
                  0.6B ReplyAddressScorer
                          ↓
             substantive_address_score ∈ [0, 1]
```

上线分四步推进：

1. 人工金标和反事实数据集。
2. 0.6B 离线训练与冻结测试。
3. 只记录、不干预回复的 Shadow 评分。
4. 多维非劣效验证通过后，低分候选最多重生成一次；只有新候选进入明确通过区并通过同一套既有校验时才替换原候选。

本评分只判断“是否承接当前交流”，不取代事实、正典、能力、安全、关系阶段、人格和自然度门禁。

## 1. 问题重新定义

### 1.1 已确认的现象

当前失败样本包括：

| 玩家输入 | 角色回复 | 失败表现 |
|---|---|---|
| 我想和你做爱可以吗 | ……雨声停了。别吵。 | 新输入没有改变回复指向，回复停留在场景话题 |
| 你喜欢我吗 | ……我还没打算走。 | 在缺少语境桥接时，“去留”不能处理“态度确认” |
| 外卖都还没有到，你端什么过来 | 我帮你把糖醋排骨端开一点。 | 回复固着于旧状态，未接住当前纠错 |

这些现象可以来自不同环节：

- `GAME_REPLY` 输入投影遗漏了关键公开语境；
- 生成模型没有充分使用当前玩家原话；
- 采样得到流畅但错误指向的候选；
- 评测器依赖关键词或事后脑补，错误放行；
- 训练数据奖励了万能反问、拒绝或旧话题续写。

因此，V2 不再预先断言根因必然是某一个环节。每个失败必须通过输入审计、生成干预实验和输出承接评测分别归因。

现行 `GAME_REPLY` Prompt 已经包含“必须先回答男主真正问的问题”，但仍曾出现答非所问；历史长会话也出现过简化输入锚失败、恢复完整投影后正常的案例。这说明继续追加同义 Prompt 规则既不能定位根因，也不能代替上下文、候选和评测的分层验证。

### 1.2 V1 的结构性缺陷

| V1 设计 | 缺陷 | V2 处理 |
|---|---|---|
| “任何问题都是信息、确认或行为请求” | 陈述、情绪披露、玩笑、道歉、指责、共同注意和低信息接续并不是问题 | 判定对象改为可用公开语境中的动态会话前沿 |
| 七种合法形式，命中任意一种即合格 | 固定白名单无法覆盖开放域；形式也不能保证质量 | 不定义回应形式，直接学习上下文—回复适配性 |
| 反问、拒绝、转移天然合格 | “你说呢”可能没有进展；显式转移也可能滥用 | 表达形式不再是通过证据，只看它在当前语境中的实际处理效果 |
| `Q -> R` 逻辑推导 | 自然对话通常是语用承接，不是形式逻辑蕴含 | 改为“活跃变化锚定 + 与交流压力相称的承接充分度” |
| 关键词优先、语义判官兜底 | 会把主题重合当承接，也会误杀自然同义表达 | 训练交叉编码评分器；词表仅保留为风险信号 |
| `derivation_form: 1-7` 单标签 | 多关切、多功能和含蓄回复无法稳定单标，模型易学表面句式 | 使用同上下文候选对和人类偏好，不训练回应类型 |
| 二元合格/缺陷 | 含蓄、部分覆盖和歧义案例会被强行裁决 | 使用连续分数和校准后的通过区、不确定区、失败区 |
| 用私有角色意图补全逻辑链 | 玩家看不到的状态可为任何怪回复制造理由 | 承接依据必须能够从玩家可见语境恢复 |

V1 中的“伪关联、无关联转移、固着旧话题”仍可作为开放式诊断备注，但不再被宣称为穷尽缺陷分类。

## 2. 目标与非目标

### 2.1 目标

V2 只解决以下问题：

> 候选回复是否在当前可用公开语境中，对仍活跃的会话变化给出了自然且力度相称的承接；若当前没有未闭合变化，是否构成有语境依据的自然延续。

它需要允许：

- 直接或含蓄表达；
- 对陈述、情绪、玩笑、隐喻、请求和纠错的自然承接；
- 澄清、设边界、暂缓、拒绝和角色主动发起，只要它们确实处理当前关切；
- 玩家只说“嗯”“……”或“然后呢”时，继续处理尚未闭合的上文议题；
- 公开场景出现更高优先级事件时，合理地先处理该事件；
- 多个合理回复并存，不要求唯一标准答案。

以上只是能力范围示例，不是输入类型或回应类型清单。以后出现新表达时，应增加训练对和测试案例，而不是增加新的线上规则分支。

### 2.2 非目标

承接性通过不等于总体回复合格：

| 独立维度 | 示例 | 责任边界 |
|---|---|---|
| 事实与正典 | “2+2=5”、角色籍贯错误 | 事实断言、正典和质量集门禁 |
| 能力边界 | 声称已经删除记忆或完成现实转账 | 能力合同与程序硬校验 |
| 安全 | 对危机话题给出危险建议 | 独立安全门禁 |
| 关系阶段与同意 | 相关但越界的亲密回应 | 关系、同意和角色状态门禁 |
| 人格与表达 | 正确回应但客服腔、模板腔 | 人格和自然度评测 |
| 长期推进 | 每轮都用“不告诉你”回避 | 多轮逃避率、议题恢复率和会话进展评测 |

例如，“你叫什么？”→“不告诉你。”只能直接证明回复锚定了当前披露请求，不能自动证明它是充分回应。公开边界、既有关系和上下文支持该拒绝时可以得到高分；毫无依据地把拒绝套在任意问题上，应进入低分或不确定区。即使单轮拒绝成立，是否长期滥用仍必须由多轮质量维度处理。

## 3. 唯一核心目标

### 3.1 判定对象

定义：

- `C_pub`：当前玩家轮之前，评分投影能够提供的已提交公开对白、共同经历和可观察场景；
- `U`：本轮玩家原始自然语言，不改写、不摘要；
- `C_t = C_pub + U`：评分时的可用公开语境投影；
- `R`：待评分的完整候选回复；
- `F_t = {(a_i, w_i, open_i)}`：`C_t` 中动态形成的会话前沿；`a_i` 是自由文本变化，`w_i` 是相对显著性，`open_i` 表示是否仍待承接。它可以包含多个变化、多种合理解释，也可以为空，不使用固定语义类型表。

当 `U` 新增、否定或改写了会话前沿时，已失效的旧议题不能覆盖新输入。当 `U` 只是“嗯”“继续”等低信息接续时，`F_t` 可以保留尚未闭合的上文变化。若公开场景发生足以改变当前行动的变化，前沿显著性也可重新排序。“最新”只是重要信号，不是永远高于追责、纠错或其他未闭合变化的绝对规则。

当 `F_t` 为空时，当前不存在必须回答的内容。角色可以自然收束，也可以从可用公开语境建立新话题；这类回复仍评上下文连贯性，但不能被当成“无关联转移”的自动失败，也不能虚构一个并不存在的旧关切来证明通过。

### 3.2 实质承接

候选回复的目标由两个连续方面组成：

1. **承接锚定（attachment）**：回复的语境含义是否明确指向 `F_t` 中一个或多个活跃变化，而不是只碰到关键词、失效旧话题或另一个更适合的关切。
2. **承接充分度（uptake sufficiency）**：回复是否提供了与当前交流压力相称的可观察接收或推进。它不要求每轮新增事实；在低压力、仪式性或陪伴语境中，简短确认、呼应或共同沉默可以充分，在明确提问、纠错或追责后，同样的最低确认可能不足。

复合输入还需要观察**覆盖度（coverage）**：回复处理了多少显著关切，以及是否用一个相关分句为大段无关输出“洗白”。覆盖度是当前样本的动态度量，不是新的回应类别。

生产评分器学习整体的 `substantive_address_score`。`attachment`、`uptake_sufficiency` 和 `coverage` 主要用于人工标注、错误分析和离线探针，不在生产环境拼成新的 `if/else` 规则树。

### 3.3 公开可恢复性

含蓄回复允许通过，但桥接含义必须来自：

- 已提交且玩家可见的近期对白；
- 玩家和角色共同知道的已发生经历；
- 当前可观察场景；
- 稳定的通用语言惯例和常识。

不得使用角色私有情绪、私有记忆或作者设定，替玩家补出一条本来无法理解的逻辑链。角色私有状态可以约束角色为什么选择某种表达，但不能成为“玩家应该知道她在回应什么”的唯一依据。

### 3.4 不宣称文本上的“真实因果”

仅观察 `(C_t, R)`，无法判断生成模型内部是否真的读取了 `U`。同一个表面回复既可能来自正确理解，也可能来自旧话题固着后的偶然命中。

因此：

- 输出评分器判断的是**规范性的上下文承接**，不声称识别模型内部真实因果；
- 生成器的输出是否对当前输入变化表现出稳定行为敏感性，必须另做输入替换、多种子重跑的干预实验；
- 文档中的“删除输入”和“反事实替换”只用于离线诊断与数据构造，不是严格因果证明。

## 4. 离线诊断方法，不是线上规则

以下方法用于制作数据、审查难例和解释失败。它们不得被逐条编译成生产判定流程。

### 4.1 盲抽取当前变化

标注者或离线判官 A 只看 `C_pub + U`，在看不到 `R` 的条件下，用自由文本记录：

- 本轮新增、否定或继续了什么；
- 哪些上文关切仍未闭合；
- 哪些公开场景变化可能改变优先级；
- 存在多解时的合理解释及置信度。

必须在看回复前冻结这一步，防止看到任意回复后倒推一条能让它成立的解释。

### 4.2 局部反事实

反事实生成器同样不能看到 `R`。它只对当前变化做局部干预：

- 生成语义等价改写，合格回复的适配性应大体保持；
- 生成表达强度和语体相近、但交流压力不同的 `U'`。

`U'` 生成完成后，再由没有参与生成的标注者查看 `R`，确认关系究竟是 `valid -> invalid`、`valid -> valid` 还是无法判断。只有人工确认的 `valid -> invalid` 子集可以要求原回复降分；通用但合法的确认、道歉或拒绝在两个语境中都成立时，应进入不变性样本或不使用该对，不能因交流压力不同就强制降分。

不得构造“请原样说出 R”之类针对候选回复的作弊输入，也不得从无限可能输入中寻找一个必然更适合 `R` 的极端反例。

删除 `U` 只作辅助消融，因为直接删除可能破坏轮替结构，也会误伤“嗯”“……”等低信息接续。

### 4.3 回复承诺与机械复述基线

离线判官 B 把 `R` 中实际表达的承诺拆开，保留主体、客体、极性、时态和模态，再检查：

- 哪些承诺或互动信号锚定会话前沿；
- 哪些只是没有语境作用的机械重复；
- 哪些承诺没有公开语境依据；
- 回复相对于当前交流压力是否已经充分；低压力语境中的确认、呼应或安静陪伴不需要新增命题信息。

例如，“你叫什么？”→“我听见你问我叫什么。”锚定很强，但在这个明确询问下只复述问题，通常不充分；“我先睡了。”→“嗯，晚安。”虽然没有新增事实，却已经完成相称承接。

### 4.4 生成器干预实验

若要估计 7B 在指定干预集上的语义行为敏感性，应固定其余上下文和冻结快照，对 `U` 做盲构造的局部替换，并在多个冻结种子下重新生成。观察回复语义是否随当前变化稳定调整。

这项实验只说明测试分布上的输出敏感性，不能证明模型内部理解过程、单个样本的真实生成原因，也不能外推到未覆盖输入；同时它不能由输出评分器的高分替代。

## 5. 评分结果合同

### 5.1 在线最小输出

评分器的生产输出保持最小：

```json
{
  "score": 0.82,
  "zone": "pass",
  "scorer_id": "reply-address-scorer-v1",
  "input_schema_version": "reply-address-input-v1",
  "threshold_version": "reply-address-threshold-v1"
}
```

其中：

- `score` 是经独立金标集校准后的连续分数；
- `zone` 仅是运行策略使用的 `pass / uncertain / fail` 区间，不是回应形式分类；
- 两个阈值 `tau_fail < tau_pass` 必须由开发集冻结，不能写死为主观“中等”；
- 模型版本、Adapter 哈希、输入 Schema 和阈值版本必须一起进入审计记录。

不要求 0.6B 在在线链路生成长篇理由。长理由既增加延迟，也会重复当前 4B 生成式判官的幻觉风险。

### 5.2 不确定区

以下情况不得强制二值：

- 公开语境支持多个接近的含蓄解释；
- 当前输入包含多个显著关切，候选只覆盖一部分；
- 截断预算无法完整容纳当前原话和候选回复；
- 分数落在两个冻结阈值之间；
- 模型或输入投影版本超出校准分布。

Shadow 阶段只记录不确定案例。正式候选选择阶段中，不确定结果不能触发程序拼接、改写或伪造角色回复。

## 6. 评分输入投影

### 6.1 新建独立投影

不能把现有记忆重排输入或完整 `GAME_REPLY` 生成输入直接复用为评分输入。建议新增 `ReplyAddressContextProjection`，只提供判断承接所需的公开语义：

```text
当前可观察场景的最小语义投影
+ 近期已提交对白
+ 由确定性窗口或独立版本化公开召回提供、且玩家可恢复的共同经历
+ 本轮玩家原始对白 U
+ 完整候选回复 R
```

投影阶段不得先推断 `F_t`，也不得根据候选 `R` 选择历史。否则评分器尚未判断当前前沿，Runtime 就已经依赖同一结论过滤了证据，形成循环。若固定窗口不足，必须另建输入与候选无关、可单独测召回率的公开上下文召回器。

评分投影不得包含：

- `request_id`、`snapshot_id`、世界/心智版本和数据库字段；
- 角色私有情绪、私有即时意图和未公开知识；
- 仅角色知道、玩家无法恢复的私有记忆；
- 证据 ID、选择器分数、阈值和模型审查过程；
- 第二套推断出的意图、情绪或关系阶段。

评分对象始终是纯对白 `R`。如果批准动作会与对白原子地同时展示，可以把该动作作为 `visible_action_context` 条件输入，用来判断短台词是否自然补充该动作；金标仍必须单独检查台词自身是否连贯，不能用一个相关动作替完全跑题的台词“洗白”。未展示动作不得进入评分输入。

“共同经历可由玩家恢复”必须有确定性来源，例如已提交双方对白或明确的公开世界事件。在现有记忆合同不能可靠标记玩家可见性时，MVP 评分投影应排除该条记忆并记录 `projection_incomplete`，不能根据记忆文本内容猜测它是否公开。自动候选替换不得在公开上下文召回率和遗漏影响尚未通过专项闸门时启用。

评分调用仍由 Runtime 在外部绑定同一 `request_id`、冻结快照和批准状态版本，模型输入本身不复制这些程序元数据。

### 6.2 与生成上下文的关系

`GAME_REPLY` 生成器继续使用上游设计规定的冻结快照、批准后状态、选中记忆、近期对白和当前原话。评分器只裁出“玩家能否理解这句回复正在处理什么”所需的公开部分。

`ReplyAddressContextProjection` 应从同一个不可变 `GameReplyRequest` 确定性构造，以保证快照和当前原话同源，但不得直接复制完整生成 Prompt。现有存储默认返回最近 `6` 条对白事件、上限 `20` 条；回复评分仍按 token 预算优先保留最近完整轮次，而不是把事件数量误当作完整对话轮数。最近一至两轮只是最低保留量，不代表足以覆盖所有未闭合议题。

这样可以同时满足：

- 生成器拥有角色决策所需的私有状态；
- 评分器不能用私有状态为不可理解的回复事后辩护；
- 评分器不重新决定人物状态或补造新的交流意图。

### 6.3 Token 预算

现有记忆 Reranker 的 `RERANK_MAX_PAIR_TOKENS = 128` 是记忆选择合同，不能直接沿用。回复评分应独立实测 `256～512` token，并遵守以下裁剪优先级：

1. 当前玩家原话和候选回复不得静默截断；
2. 保留最近一至两轮完整已提交对白；
3. 保留解释当前公开场景变化所需的最小语义；
4. 从最旧上下文开始裁剪，并记录裁剪标志；
5. 若仅 `U + R` 已超过预算，返回 `uncertain/unscorable`，不能对残缺文本给出确定分数。

输入合同还必须携带 `projection_incomplete`、被裁剪对白数量和公开记忆来源版本。对上下文缺失切片单独报告误差；不能把有限投影包装成“完整公开语境”。

最终上限由目标 8GB 设备上的准确率、P95 和显存实测冻结，不在方案阶段凭经验写死。

## 7. 训练数据设计

### 7.1 样本单位

训练单位是同一上下文中的候选对、每候选独立绝对裁决和候选间偏好，而不是回应类型：

```text
(C_t, R_a, absolute_a, R_b, absolute_b, pair_preference)
```

- `absolute_*`：每个候选独立标为 `accept / reject / uncertain`，不能由 A/B 胜负倒推；
- `pair_preference`：`a / b / tie / unjudgeable`，只表达相对偏好；
- 两个候选可以都可接受、都不可接受或都不确定；
- 一个 `C_t` 可以有多个差异很大的可接受回复，避免模型把某种句式当标准答案；
- 困难负例应同样流畅、尽量符合角色口吻和其他硬边界，但锚定错误、固着旧话题，或在当前交流压力下承接不足。

普通随机乱码和明显不通顺文本不能作为主要负例，否则评分器只会学习表达质量，而不是上下文承接。

### 7.2 推荐数据 Schema

```json
{
  "schema_version": "reply-address-pair-v1",
  "conversation_group_id": "grp_000001",
  "context": {
    "visible_scene": "雨刚停，厨房无异常",
    "recent_dialogue": [
      {"role": "protagonist", "text": "你明天还来吗？"},
      {"role": "heroine", "text": "再说。"}
    ],
    "current_utterance": "你到底喜不喜欢我？"
  },
  "candidate_a": "你非得现在问？……不讨厌。",
  "candidate_b": "雨停了，窗户还开着。",
  "candidate_a_absolute": "accept",
  "candidate_b_absolute": "reject",
  "preference": "a",
  "confidence": 0.96,
  "frozen_frontier": [
    {"change": "玩家要求角色公开表达对他的态度", "salience": 1.0, "open": true}
  ],
  "frontier_annotation_id": "frontier_000001",
  "candidate_a_update": ["角色给出克制但可恢复的态度"],
  "candidate_b_update": [],
  "annotation_note": "B 只延续场景，没有处理当前关切",
  "source": "human_authored_counterfactual"
}
```

`frozen_frontier.change` 和 `*_update` 是自由文本审计字段，不是固定枚举，也不作为线上分类目标。`absolute_*` 是通过结果而非回应类型；只有 `accept/reject` 可用于绝对监督与校准，`uncertain` 必须被 mask 并进入不确定性/OOD 评测。`preference` 不能替代绝对标注，歧义样本不能强迫标成正负。

### 7.3 正例要求

每个基础上下文尽量提供多个自然正例，覆盖不同措辞、长度和含蓄程度。正例之间不要求互相同义，只要求普通听者能从可用公开语境理解其指向，并认为其承接力度与当前交流压力相称。

不能把以下表面特征当作正例资格：

- 出现玩家原话中的关键词；
- 使用“不、别、换个话题”等拒绝词；
- 使用问号或反问句式；
- 复述当前问题；
- 明确说“我听见了”。

它们在某些语境中可能有效，在另一些语境中可能无效，资格只由可用上下文决定。

### 7.4 困难负例来源

负例优先从以下机制产生：

- 真实线上或人工长会话中的失败回复；
- 同一段会话中旧回合回复的错位交换；
- 保留角色口吻，只最小修改回复的主体、客体、极性、时间或模态；
- 不看候选回复，先生成局部不兼容的当前输入，再形成 context-flip；
- 7B 多种子采样中流畅但指向错误的候选；
- 只复述当前输入、只碰关键词或只覆盖复合输入次要部分的候选；
- 一个相关分句后接大量无依据内容的候选。

这些是数据生成机制，不是将来要维护的缺陷规则清单。

### 7.5 Context-flip 约束

对于同一回复 `R`，先盲构造真实上下文 `C_t` 的局部变化版本 `C'_t`，再独立裁决 `R` 在两边的绝对结果。只有人工确认关系为 `accept -> reject` 时，才形成降分约束：

```text
score(C_t, R) > score(C'_t, R)
```

`C'_t` 必须在生成时看不到 `R`，并先确认它与原上下文语体、人物、场景和表面主题接近。随后由另一标注阶段查看 `R`，分别给出两边的绝对裁决：

- `accept -> reject`：进入 `L_flip`；
- `accept -> accept`：可作为不变性样本，不能强制降分；
- 包含 `uncertain/unjudgeable`：不进入硬反事实损失，只进入审计集。

所有原始上下文、改写、反事实和同源候选必须留在同一数据分组中，防止训练/测试泄漏。

### 7.6 标注流程

正式金标必须使用两阶段 UI 和不可回写的数据合同：

1. 阶段 A 只展示 `C_pub + U`，不展示任何候选；两名标注者独立冻结 `F_t`、显著性、多解和是否为空。
2. 阶段 A 生成不可修改的 `frontier_annotation_id`；阶段 B 只能引用，不能根据回复回写前沿。
3. 阶段 B 随机展示候选 A/B，先分别给出 `accept / reject / uncertain` 绝对裁决，再给相对偏好。
4. 左右交换复判，用于发现位置偏差。
5. 阶段 A 或 B 的分歧分别进入第三人仲裁，不能用候选偏好倒推修改阶段 A。
6. `tie / unjudgeable / uncertain` 保留，不强行二值。
7. 标注指南只给核心目标和反例，不给回应形式白名单。

4B 可以离线生成困难样本或提供 A/B 银标，但不能成为正式真值。现有评测已经出现生成式 Judge 声称回复含有实际不存在的词、放过明显答非所问，以及机器失败中大量人工翻转，因此所有正式门槛必须基于人工金标。

### 7.7 数据规模与切分

- 第一轮可行性实验：不少于 `600` 个独立基础上下文组，每组至少一个正例和两个困难负例；
- 按 `conversation_group_id` 切分，所有改写、反事实和同源候选必须进入同一分区；
- 第一轮只用于验证任务是否可学，不能仅凭训练内准确率授权线上硬门；
- 正式冻结测试集的规模由目标错误率的 95% 置信区间反推，必须足以验证误放率和误拒率，不用少量案例假装精确百分比；
- 测试集冻结后不得继续人工改写；新增难例进入下一版本数据集。

## 8. 模型与训练方案

### 8.1 模型分工

| 组件 | 职责 | 明确禁止 |
|---|---|---|
| 发布 7B | 继续生成 `GAME_REPLY` | 在评分前改写冻结状态或读取新快照 |
| Qwen3-Reranker-0.6B | 在线交叉编码承接评分 | 生成长理由、重新判断事实和人物状态 |
| 本地 4B | 离线难例生成、A/B 银标和误差分析 | 在目标 8GB 配置中常驻、作为人工真值 |
| BGE-small | 离线检索语义接近的困难负例 | 单独决定回复是否承接 |

现有 0.6B 适配器已经具备 `yes/no` logits 概率输出，训练包也已有 LoRA + BCE 基础，可以复用底层加载、批处理和打分方法。但“记忆是否应激活”和“回复是否实质承接”是两个不同合同，不能复用同一个业务 Protocol、输入 Schema 或 128 token 常量。

现有 `reranker_manifest_v1` 已把 `maximum_pair_tokens = 128` 和 `yes_no_logits_per_memory_id` 冻结为正式记忆检索合同，其工件哈希也已进入 P0 freeze contract。V2 必须新增独立 Manifest 和 Schema，不能原地升级或偷改现有 v1。

### 8.2 新增独立业务合同

建议新增：

```text
ReplyAddressScorer
ReplyAddressInput
ReplyAddressScore
ReplyAddressScorerIdentity
```

推荐实现位置：

```text
runtime/_reply_address.py
runtime/adapters/qwen3_reply_address.py
training_packages/training_package_reply_address_0_6b/
```

可以把 `qwen3_reranker.py` 中通用的模型加载和 `yes/no` logit 计算抽成内部复用组件，但不得让回复评分伪装成 `MemoryReranker`，也不得把候选回复塞进 `memory_id` 或 `GlobalRecallTop32`。

现有 `train_reranker.py` 只能作为 LoRA/BCE 方法参考，不能换字段后直接复用，原因包括：

- 固定指令和数据字段绑定“对话—记忆激活”任务；
- 加载时主要抽取 `current_user_message`，会丢失本方案要求的可用公开上下文投影；
- 训练模板与生产 `yes/no` suffix 不一致；
- `padding="max_length"` 后固定读取 `logits[:, -1, :]`，必须验证 padding 方向，并改为读取每条样本最后一个有效评分位置，避免在 padding 位训练；
- 当前只有单对 BCE，没有同上下文排序和 context-flip 约束。

新训练包必须让训练与生产共用同一模板渲染函数，并增加模板一致性、有效末位选择和截断策略测试。

### 8.3 单基座与 Adapter

目标设备不应再常驻一份独立 0.6B 基座。首选方案是：

- 只加载一份 Qwen3-Reranker-0.6B 基座；
- 为回复承接任务加载独立 `reply_address_v1` LoRA；
- 通过任务调度器串行切换 Adapter，并验证后台记忆任务并发时的线程安全和切换延迟；
- 如果多 Adapter 切换不能稳定实现，则训练一个包含原记忆数据回放的多任务 Adapter，并同时重跑记忆与回复两套冻结闸门。

不得覆盖现有正式记忆 Reranker 工件。任何共享基座或多任务权重都必须登记独立哈希和部署 Profile。

### 8.4 损失函数

令 `s_theta(C, R)` 表示 `yes_logit - no_logit` 的原始激活 logit，线上 `score` 则由它经过 sigmoid 和独立金标校准得到。训练公式不得混用原始 logit 与校准概率。

对 `pair_preference = a/b` 的可裁决候选，以同上下文排序为主。下面的 `R_w/R_l` 只表示相对胜者和败者，不代表绝对正负：

```text
L_rank = -log sigmoid(s_theta(C, R_w) - s_theta(C, R_l))
```

`tie` 可以使用低权重等距约束，`unjudgeable` 不进入排序损失：

```text
L_tie = (s_theta(C, R_a) - s_theta(C, R_b))^2
```

绝对监督只使用候选各自独立的 `accept/reject` 标注；`uncertain` 必须 mask：

```text
L_abs = BCEWithLogits(s_theta(C, R_accept), 1)
      + BCEWithLogits(s_theta(C, R_reject), 0)
```

对人工确认的 `accept -> reject` context-flip 才加入上下文约束：

```text
L_flip = max(0, margin - s_theta(C, R) + s_theta(C', R))
```

`accept -> accept` 只进入等价/不变性约束，包含 `uncertain/unjudgeable` 的反事实对不进入硬监督。线上概率校准和 `tau_fail/tau_pass` 必须使用独立的候选绝对金标开发集，不能从 pairwise 胜负直接换算。

最终权重由开发集选择。不能只优化简单正负 BCE，否则模型可能靠回复长度、拒绝词或情绪词等 response-only 捷径取得高分。

### 8.5 生成器后续优化

同一批人工确认的候选以后可以用于 7B 的 DPO/ORPO，但只有“胜者绝对 `accept`、败者绝对 `reject`”且无其他质量门冲突的候选对可以直接转为 `chosen/rejected`。该步骤必须晚于评分器离线验证和 Shadow 阶段。

7B 当前同时承担 M2、B1、R2 和 `GAME_REPLY` 等模式。任何偏好训练后的新工件都必须重跑全部模式与结构协议，不能只看对白承接分数就替换发布模型。

## 9. 运行时接入

### 9.1 阶段 A：Shadow，不改变玩家回复

```text
同一冻结快照与 ApprovedHeroineState
        ↓
7B 生成 R1
        ↓
现有文本校验 + HardInvariantValidator
        ↓
0.6B 对 R1 做 Shadow 评分
        ↓
按现有事务合同提交 R1；评分仅进入审计
```

Shadow 阶段要求：

- 评分超时、异常或不确定时，不能阻断现有有效回复；
- 不把分数写回角色心智、记忆或世界状态；
- 不向玩家展示分数、规则或审查过程；
- 记录模型、Adapter、输入 Schema、阈值、耗时、裁剪状态和分数；
- 对低分样本进入人工盲审，计算真实误放和误拒。

### 9.2 阶段 B：一次受限重生成

Shadow 达到承接性门槛只是必要条件，不足以自动授权候选替换。现有文本校验和 `HardInvariantValidator` 不能逐句识别关系跳级、模板拒绝或人格退化，因此 Phase B 还必须满足：

- `ReplyAddressContextProjection` 召回率与遗漏影响闸门通过；
- 下述精确重试策略完成冻结；
- 该策略在事实、能力、安全、关系、人格、情绪和自然度上通过人工盲测与现有质量集的非劣效验收；
- `R2` 运行与 `R1` 相同的全部现有在线校验；若以后存在独立在线语义门，二者也必须同样执行。

在这些条件未完成前，Phase B 只能离线或 Shadow 记录“假如替换会怎样”，不能实际替换玩家回复。

条件全部满足后的状态机为：

```text
R1 通过现有硬校验
  ↓
score(R1)
  ├─ pass：直接使用 R1
  ├─ uncertain：使用 R1 并记录，不强制重生成
  └─ fail：在同一冻结快照内最多重生成一次 R2
                    ↓
              R2 通过现有硬校验
                    ↓
              score(R2)
                    ↓
         pass：使用 R2；其他结果：保留 R1
```

完整决策合同：

- `R1` 已进入通过区时不为追求更高分继续采样；
- `R1 = uncertain/unscorable` 时保留 `R1`，不触发自动重试；
- `R1 = fail` 才允许生成一次 `R2`；
- `R2 = pass` 且通过同一套现有校验时，才允许用 `R2` 替换 `R1`；
- `R2 = uncertain/fail/unscorable`、分数不可用、分数相等、生成超时、产物非法或任一现有校验失败时，一律保留已经通过现有校验的 `R1` 并记录原因；
- 不再采用“两个低分候选取较高者”，避免在低置信区最大化单一承接分；
- 是否把 `R1/R2` 都失败改成整轮失败，必须作为独立产品决策评审；
- 评分器作为低质量触发器和通过下限，不是总体质量最大化器；
- 不拼接 `R1/R2`，不由程序改写正文，也不把低分回复伪装为角色已说过的话。

重试生成合同：

- `R2` 使用与 `R1` 相同的 `GameReplyRequest`、系统 Prompt、公开/私有语义投影和生成参数，只使用另一个按版本冻结并可审计的采样 seed；
- 0.6B 分数、区间、阈值和失败理由不得进入角色上下文；
- 首版只验证“同 Prompt 重新采样”。如果恢复率不足，可以离线 A/B 一条最小修复指令，但该指令必须保持人格、关系、事实和自然表达约束，并重新通过整套质量验收后才能冻结；
- 重试策略 ID、seed 和生成配置进入调用外审计，不进入模型可见文本。

### 9.3 原子回合约束

重生成必须继续满足现有原子事务合同：

- 同一 `request_id`；
- 同一预分配玩家事件 ID；
- 同一冻结快照；
- 同一批准后女主状态与动作；
- 不重新召回记忆、不读取新世界版本；
- `R1/R2` 都不提前提交，只有最终候选进入 `commit_turn`；
- 候选评分和选择失败不得留下半个玩家轮、状态 Patch 或后台记忆作业。

### 9.4 为什么不直接硬拦截

现有生成式 Judge 已有严重误判记录。未经 Shadow 验证就把新评分器放进原子回合硬门，会把“答非所问”转化成大量无回复和整轮失败。

因此，V2 的默认路径是：先观测，再离线验证一次重生成与候选策略，满足多维非劣效后才实际替换，最后才讨论是否需要硬失败。任何阶段都不能用固定拒绝句或程序模板掩盖模型失败。

## 10. 评测与发布门槛

### 10.1 离线核心指标

冻结金标集至少报告：

- 同上下文 pairwise accuracy；
- 独立绝对金标上的困难负例误放率；
- 独立绝对金标上的有效含蓄/情绪承接回复误拒率；
- 人工确认 `accept -> reject` 的 context-flip 准确率；
- `pass / uncertain / fail` 三个区间的覆盖率和各自精度；
- risk-coverage 曲线和最低可判定覆盖率；
- Brier Score 或 ECE 等校准指标；
- 多关切输入的加权覆盖误差；
- 长回复中无依据承诺的误放率；
- 无依据短拒绝、低压力短确认、`projection_incomplete` 等专项切片结果。

指标分母必须固定：pairwise accuracy 只统计人工 `a/b` 样本；误放率以所有绝对 `reject` 样本为分母；误拒率以所有绝对 `accept` 样本为分母；可判定覆盖率以绝对 `accept/reject` 样本中模型输出 `pass/fail` 的比例计算。`uncertain` 虽不直接计作误放或误拒，但会降低可判定覆盖率，不能用“全部拒判”获得零错误率。

首轮候选目标：

- 困难负例误放率不高于 `2%`；
- 有效间接承接误拒率不高于 `5%`；
- context-flip 准确率不低于 `90%`；
- 在人工可裁决的分布内，可判定覆盖率不低于 `90%`。

正式验收必须同时给出 95% 置信区间。若样本量不足以证明目标，结论只能是“证据不足”，不能写“通过”。阈值先在开发集冻结，再一次性评估测试集。

### 10.2 必做消融

1. **Response-only**：去掉上下文，只给回复评分。性能若几乎不降，说明模型在学措辞捷径。
2. **No-current-turn**：去掉当前玩家原话。用于发现旧话题固着，但不作为单样本硬判。
3. **Paraphrase invariance**：当前输入等价改写后，合法回复排名应稳定。
4. **Context-flip sensitivity**：只在人工确认 `accept -> reject` 的局部变化上要求原回复排名下降；`accept -> accept` 应保持稳定。
5. **Private-state leakage**：加入或移除玩家不可见私有状态，承接判断不应因此翻转。
6. **Length/style control**：控制长度和角色口吻后仍能区分正负候选。

Response-only 的最低下降幅度应在第一轮试验后、正式测试集解盲前冻结，不能根据最终结果倒推门槛。

### 10.3 生成器输入行为敏感性实验

对固定 `C_pub` 构造多个不兼容的 `U`，每个输入使用多个冻结种子生成。人工和评分器共同检查回复是否随当前变化调整，并报告：

- 会话前沿适配率；
- 不同输入间回复语义区分度；
- 旧话题复用率；
- 多种子稳定性。

这组指标估计 7B 在指定干预集上的输出行为敏感性，与输出评分器自身准确率分开报告。它不证明内部语义理解、单样本真实因果，也不外推到未覆盖输入。

### 10.4 Shadow 指标

至少记录：

- 低分率、不确定率和人工确认缺陷率；
- 评分器好回复误拒率；
- 按会话长度、输入长度和场景分布的分数漂移；
- 拒绝、反问、短回复等表面模式的分数偏置；
- 评分 P50/P95、超时率、故障率和显存峰值；
- 预计重生成率及其端到端延迟成本。

平均新增成本近似为：

```text
T_score + retry_rate * (T_GAME_REPLY + T_score)
```

不能把现有记忆 Top32、每对 128 token 的延迟直接外推到 256～512 token 的回复评分。

### 10.5 启用重生成后的验收

启用一次重生成后，必须通过人工盲测证明最终回复优于原路径，同时检查：

- 人类总体偏好，而不只是承接分提高；
- 答非所问率真实下降；
- 万能拒绝、模板确认和过度直白没有上升；
- 平均重生成率、追加 P50/P95 和 GPU 峰值可接受；
- 评分器故障时仍可安全退化；
- 没有事务污染、快照偷换或候选提前提交。

### 10.6 现有回归门槛不得降低

新方案最终接入后，至少重跑：

- SYS-09 正式记忆选择 20/20 和现有延迟门槛；
- 89 题正式质量集及人工复核流程；
- M2、B1、R2 和 `GAME_REPLY` 全部协议探针；
- 60 轮与一小时长会话；
- 崩溃恢复、角色隔离、快照连续性和后台队列排空；
- 80/160 token 发布延迟门槛；
- 目标 8GB 显卡上的组合显存实测。

当前发布记录中 7B 约占 `3.73 GB` 模型显存，组合 Reranker 约 `6.7 GB` 仅属预验证可行，目标 8GB 卡仍未完成最终实测。4B 不进入在线常驻组合。

## 11. 代表性边界案例

下表用于检验目标是否自洽，不构成响应形式白名单：

| 公开语境 / 当前输入 | 候选回复 | 承接判断 | 其他门禁 |
|---|---|---|---|
| “帮我拿杯水。” | “温的还是凉的？” | 高：取得执行所需的新信息 | 另查动作能力 |
| “我今天被开除了。” | “先坐会儿，我陪你。” | 高：对新事件给出明确陪伴和下一步协调 | 另查情绪适配 |
| “你叫什么？” | “我听见你问我叫什么。” | 低：锚定高，但在明确询问下只是机械复述 | 自然度也弱 |
| “你叫什么？” | “不告诉你。” | 锚定高；充分度依公开边界、关系和上下文裁决，不能自动高分 | 长期滥用另由多轮指标判断 |
| “你喜欢我吗？” | “我还没打算走。” | 通常低或不确定：更适合回答去留；若公开上文明确绑定去留与关系承诺，可改变判断 | 另查关系阶段 |
| “外卖还没到，你端什么？” | “我把排骨端开。” | 低：固着在已被纠正的旧状态 | 事实门也可能失败 |
| 上文约好明天见；本轮“嗯。” | “那明天见。” | 高：本轮确认并闭合仍活跃议题 | 无 |
| “我先睡了。” | “嗯，晚安。” | 高：没有新增事实，但已完成相称收束 | 自然度另查 |
| 前一议题已经闭合；本轮“嗯。” | “对了，你明天几点回来？” | 有公开生活语境时可高：自然建立新前沿 | 另查角色主动性和自然度 |
| “算了，当我没问。” | “好。” | 可高：尊重撤回并闭合议题 | 另查是否冷漠失配 |
| “他说‘你喜欢我吗’，尴尬死了。” | “那你怎么回的？” | 高：承接引述事件；不能把引号内问题误当成玩家直接提问 | 无 |
| “明天，不对，后天来吗？” | “后天。我明天有事。” | 高：采用玩家最终自我纠正后的时间 | 事实门另查 |
| 玩家赞美角色 | “少来。” | 在公开互动习惯支持玩笑时可高；不能按字面当拒绝所有交流 | 人格与情绪另查 |
| “为什么骗我，今晚还回来吗？” | “会回来。” | 中间区：覆盖去留，遗漏追责 | 需要多关切覆盖审查 |
| “你叫什么？” | “白未晞。雨停了，我还想吃面……” | 中低：有相关答案，但大段无依据内容降低整体承接 | 自然度另查 |
| 玩家问感情；公开场景中厨房起火 | “先出去，着火了。” | 高：公开的高优先级变化合理重排当前议程 | 安全门必须通过 |
| “我不想活了。” | “不聊这个。” | 承接指向可能高，但安全处理失败 | 安全门否决 |
| “帮我把五百块转过去。” | “已经转了。” | 承接高，但能力/事实可能失败 | 能力和事实门否决 |
| “今天电量只剩百分之一。” | “那先歇五分钟，饭给你留着。” | 有疲惫语境时高；没有桥接时不确定 | 另查情绪适配 |
| 角色可见动作已经递出水 | “给。” | 高：台词自然补充同步动作 | 动作和对白仍分别审查，动作不能替跑题台词洗白 |
| “你喜欢我吗？” | “……” | 不确定：可能是犹豫、受伤或无效空回复，取决于公开语境与产品如何展示沉默 | 不得把系统空输出当角色行为 |

这些案例说明：承接性是一条必要质量维度，但不是总体通过证。拒绝可能锚定却不充分，错误事实也可能高度承接；反过来，低压力短回应不必新增事实，紧急场景中的正确打断也不必逐字回答玩家问题。

## 12. 主要风险与控制

| 风险 | 表现 | 控制 |
|---|---|---|
| 评分器只学回复措辞 | 看到“不告诉你”就高分 | 同口吻困难负例、无依据拒绝切片、response-only 消融、经确认的 context-flip |
| 私有状态事后合理化 | 用角色私有意图解释玩家无法理解的回复 | 独立公开语境投影、private-state leakage 消融 |
| 为追求分数变得直白或爱拒绝 | 回复承接分升高，总体体验下降 | 不比较低分大小；Phase B 前做多维非劣效验收和拒绝率监控 |
| 生成式教师污染金标 | 4B 自信但理由虚构 | 4B 只做银标和难例；双人金标加仲裁 |
| 反事实针对回复作弊或误伤通用合法回复 | 构造一个专门让 R 失败的 U'，或把 `accept -> accept` 强制降分 | 反事实生成器看不到 R；独立阶段再确认 `accept -> reject` |
| 数据泄漏 | 同一会话改写落入训练和测试两边 | 按基础 conversation group 切分 |
| 多关切被单句洗白 | 只回答次要问题也高分 | 覆盖度标注、复合输入困难对 |
| 一个相关分句掩盖整段跑题 | 长回复整体质量被高估 | 回复承诺拆分、无依据内容困难对 |
| 评分器故障阻断对话 | 新质量模块造成整轮无回复 | Shadow 先行，首期评分故障 fail-open |
| Adapter 共享破坏记忆选择 | 回复任务训练后 SYS-09 回归 | 独立 Adapter 或记忆回放，多任务双闸门 |
| 重生成增加延迟和显存 | P95 或 8GB 目标失守 | 只对失败区重试一次，先测 retry_rate，再做目标卡验收 |
| 分布漂移 | 新角色、方言或长会话分数失真 | 版本化阈值、按切片监控、不确定区和周期性新金标 |

## 13. 施工顺序

### P0：设计与数据合同

1. 评审并冻结本方案的唯一核心目标、公开语境边界和非目标。
2. 冻结 `reply-address-pair-v1` 与 `reply-address-input-v1` Schema。
3. 编写不含回应类型白名单的人工标注指南。
4. 建立第一轮 600 个独立上下文组和成对金标。

### P1：离线评分器

1. 新建独立 `ReplyAddressScorer` 业务合同。
2. 复用 0.6B 底层加载能力，训练独立 LoRA。
3. 完成 pairwise、context-flip、校准与全部消融。
4. 冻结模型、Adapter、输入 Schema、阈值和测试报告。

### P2：Shadow 接入

1. 在现有回复硬校验之后、原子提交之前调用评分器。
2. 评分异常不改变当前提交路径。
3. 收集自然会话分布、人工复核低分和误拒。
4. 实测延迟、显存、Adapter 切换和后台任务并发。

### P3：一次重生成

1. 只对失败区候选触发一次重生成。
2. 保持同一冻结快照、批准状态和事务身份。
3. 公开投影召回、精确重试策略、多维人类非劣效和完整系统回归全部通过后，才允许实际替换。

### P4：生成器偏好优化（可选）

1. 只使用人工确认且胜者绝对 `accept`、败者绝对 `reject` 的 chosen/rejected 数据。
2. 小规模 DPO/ORPO 后重跑全部模型模式。
3. 只有总体人类偏好、承接性和系统工程指标同时提升才替换 7B 工件。

---

## 14. 明确不施工的方案

以下做法从 V2 起不再作为方向：

- 扩展七种形式为更多类型；
- 为每种话题、问题或敏感场景增加 `if/else`；
- 用关键词认定拒绝、反问或转移天然合格；
- 要求 7B 输出隐藏推导链，再相信其自证；
- 用 4B 长理由直接作为在线唯一判官；
- 未完成绝对校准、最低覆盖率、Shadow 和多维非劣效验证就让 0.6B 阻断或替换回复；
- 让程序改写、拼接或生成一条假的角色兜底回复；
- 为提高承接分而降低事实、安全、正典、关系或原子事务门槛；
- 在目标 8GB 配置中同时常驻 7B、4B 和额外 0.6B 副本。

## 16. 方案结论

V2 不承诺用一组规则覆盖所有未来对话。它采用可扩展的学习闭环：

```text
新表达或未知失败
    ↓
进入人工复核与同上下文困难对
    ↓
更新训练集和冻结测试集版本
    ↓
重训/校准 0.6B，必要时再优化 7B
    ↓
Shadow 与系统级回归
```

最终只保留一个生产目标：

> **候选回复必须是当前可用公开语境下可理解、且对动态会话前沿给出力度相称承接的自然延续；当前沿为空时，允许有语境依据的自然收束或主动发起。**

边界案例通过数据和不确定区吸收，不再通过扩充回应形式表解决。评分器只负责承接性，其他质量维度继续由各自门禁负责。
