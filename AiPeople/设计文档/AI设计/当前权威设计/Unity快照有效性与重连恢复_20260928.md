# Unity 快照有效性与重连恢复（2026-09-28）

本轮承接《Unity人物位置动作回执与实体快照_20260928.md》，落实权威状态闭环 A 块的快照来源、过期、防回放与重连恢复。完整 A 块仍未全部完成；本轮不开放模型动作、不训练模型、不实现全屋存档恢复。

## 合同与行为

1. 新 Unity 包发送 `schema_version=2`、`source=unity_main_thread`、实例启动 UTC 毫秒和主线程采集 UTC 毫秒。门窗等同轮场景字段也随这份 WorldInput 提交。使用现实时间检验传输有效性，不用游戏时钟判断网络快照年龄。
2. 正式后端在取得对话锁后再检查快照：采集距接收最多 30 秒，最多容许向未来偏差 5 秒。排队期间过期同样拒绝，不能因为入队时有效就继续生成。过期/重复/倒退返回 409，流式入口返回对应 error 事件；不调用模型，不提交对白，不凭旧记忆猜当前事实。
3. 新增追加式 migration 015，按存档保存最后接受的实例、启动时间、序号、采集/接收时间与后端运行 ID。该记录与世界更新在同一事务内提交或回滚；旧世界/对白/记忆不删除。
4. 同一实例要求启动时间固定、序号严格增加、采集时间不倒退。实例切换要求新启动时间严格晚于已接受实例；旧实例即使刷新采集时间、增大序号，也不能覆盖新实例。当前产品为同机单后端、单活动游戏实例；这不是不可信客户端的身份认证协议。
5. `/api/status` 返回 `game_observation`：current / stale / unknown、来源、采集/接收时间、年龄、原因和版本。超过 30 秒未更新显示 stale；后端重启后即使数据库快照很新也先显示 stale，直到收到新的合法采集。
6. stale / unknown 时，状态响应隐藏上次位置、持有物、门窗、动作等动态事实，人物活动显示待同步。历史和防回放记录仍保留在数据库；只读查询不延长有效期、不清除版本、不反复写未知状态。
7. 新采集通过校验后恢复 current。Unity 每次发送都重新采集，不重发之前的动作或自动补做旧动作；Unity 重启后以新场景实际状态为准。例如上次拿着的杯子在重启后回到桌上，新的事实会替代旧持有记录。
8. 旧平面 WorldInput 仅保留开发/迁移兼容。一旦存档接入正式 Unity 快照，不能再用省略快照的默认场景覆盖它。旧版无时间字段的结构快照需要升级 Windows 客户端；旧存档仍可读，但升级前的快照不被标成实时。

来源是程序侧已登记的枚举，不是模型自行评估可信度。传入模型的来源说明明确“本轮采集、历史对白不能覆盖”；本轮有效性采用拒绝过期请求策略，不让模型猜测失联场景。

- 使用独立 `snapshotlife20260928` 存档、独立 SQLite 和发布包副本完成三阶段真实联调，正式存档不变：

## 边界与下一步

后续进展：统一游戏时钟与动作计时已继续落地，见[Unity统一游戏时钟与动作计时_20260928.md](Unity统一游戏时钟与动作计时_20260928.md)。新的正式快照为 schema 3，包含 game_clock；本文件保留本轮 schema 2 生命周期设计与验收记录。

- 这是**采集有效期**，不是 TCP 连通性探针。当前没有后台心跳，空闲超过 30 秒也显示待同步；下一次发送会重新采集恢复。异常退出最迟在本轮有效期结束后不再展示旧动态状态。不要把 stale 直接写成“游戏一定已退出”。
- 对话使用接收时有效的固定快照，不会在生成中途换成另一份世界状态；之后人物继续移动，不倒改这一轮已经冻结的输入。
- 本地系统时钟大幅倒退/偏差会拒绝输入，避免把未来或旧实例误认为新实例。不会自动放宽阈值；分布式多机接入需要单独设计时钟/服务端会话协议。
- 这是整份观测的生命周期，尚非每件物品/每个传感来源独立的 known/unknown/stale。房间未知边界仍沿用上一轮明确未知结果。
- 不实现 Unity 场景跨重启存档、取消动作、模型动作权限、完整容器库存、预约报告确认、统一游戏时间或家电身体状态。

建议下一步统一 Unity 动作计时与后端 GameClock，让暂停、倍速和动作完成使用同一时间源；再扩展实际实现的家具设备与身体状态。
