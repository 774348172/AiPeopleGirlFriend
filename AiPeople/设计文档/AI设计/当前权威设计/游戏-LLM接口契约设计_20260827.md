# 游戏-LLM 接口契约设计（2026-08-27）

> 状态：**权威设计（2D 游戏前提）** | 日期：2026-08-27
> 依据：《Harness组装与单次判断设计_20260827.md》、《动作执行闭环施工方案_2D游戏前提_20260827.md》
> 前提：产品为 2D 游戏，出租屋世界由程序构建，拥有实体（面等）、可执行动作与当前世界状态。**游戏是世界的唯一事实源与执行者；LLM runtime 是神经层（投影、校验、转发）；模型是大脑（语义判断、叙述）。**
> 本文定义三者之间的接口契约：事实源与投影方向、状态字段划分、动作接口、玩家输入通道、待定决策点。
> **无意图记账（2026-08-27）**：承诺跟踪完全由世界状态承担（进行中动作 + 实体即账本），runtime 不建任何承诺表。

## 一、总体关系

```
玩家(2D 游戏操作/打字)
   ↓ 玩家输入通道（§六）
游戏(2D 世界：实体/位置/动画/动作执行/进行中动作)
   ↓ 状态投影（§二/§五）
LLM runtime(白名单校验/提议转发/对话管线)
   ↓ 判断契约（Harness 设计 §三）
模型(语义判断/叙述)
   ↓ 提议 actions（§四 转发通道）
LLM runtime → 游戏（执行请求）
```

## 二、单一事实源与投影方向

- **游戏世界状态是唯一事实源**：实体（含面）、女主/男主位置与活动、进行中动作、剩余时间，一律以游戏为准；
- **投影方向单向**：游戏 → runtime（对话快照时读取）。runtime 不写游戏世界（除 §四 转发通道的显式执行请求）；
- LLM runtime 侧的世界状态（snapshot 的 `protagonist` / `scene.item_states` / `pending_actions`）定义为**游戏状态的投影视图**，不再作为独立维护的第二套世界；
- 玩家输入同样经游戏进入（§六），不绕过游戏直接改世界。

## 三、状态字段划分（模型可见状态的两类来源）

| 字段 | 来源 | 说明 |
|---|---|---|
| 女主位置 / 场景 / item_states / 男主位置与活动 | **游戏投影** | 世界事实，模型只读 |
| `current_activity` | **游戏投影**（进行中动作期间） | 她在 2D 世界真的在煮面；动作外由模型自管 |
| `form` | 游戏投影（若游戏表现猫形/人形）或模型自管（纯叙述时） | 按游戏能力定 |
| `emotion` / `attention` / `immediate_intent` | **模型自管**（mind_patch） | 内部状态，游戏不感知 |
| motive / knowledge | 模型自管 | 内部状态 |

划分原则：**世界能表现的事实归游戏投影；世界表现不了的内心归模型自管**。两类的冲突（如游戏显示她在厨房，模型 mind_patch 说她在卧室）由 Critic（可选审查）或上下文一致性兜底。

### 3.1 心情字段设计（模型自管，无规则约束）

心情（emotion）当前**没有外部游戏消费者**（2D 世界不显示心情），其唯一消费者是模型自身——因此：

- **自由文本，不量化**：心情是模型写给自己看的状态，枚举/数值化没有受益者，反而损失"嘴硬心软"这类混合情绪的粒度；
- **无语义规则**：心情变化的一致性由三个机制保证，而非规则——① 上下文锚（每轮区块 4 可见上一轮心情，自然连贯）；② 训练分布（角色情绪模式由训练数据教）；③ 可选 Critic（模型判断，审查"无依据跳变"）；
- **仅两条机械约束**（防格式问题，非语义规则）：① 短文本长度上限（schema 160 字）；② 变更须带证据引用（机械存在性检查；"依据够不够"的语义判断归 Critic）；
- **例外（显示层投影）**：若未来游戏需要在 UI 显示心情（表情/心情条），单独建立**显示层投影**（如 `emotion_label: happy/angry`），由显示层从文本/语气推导或模型附带输出——与模型内部自由文本分离，两层互不污染；游戏剧情若需按信任度等数值分支，同样由游戏侧自己的数值系统承担，不读模型文本。

## 四、动作接口

### 4.1 动作定义导出（游戏 → runtime）

游戏导出每个动作的契约（单一来源，runtime 不自造）：

```yaml
cook_meal:
  description: "走到厨房做饭，双手被占用，大约需要 20 分钟"   # 含语义约束，模型读取
  duration_game_seconds: 1200                               # 游戏模拟时长
  effects: {item_states: {桌上: "一碗热汤面"}}               # 游戏执行结果
  params: {}
move_to:
  description: "走向某处，路上可以被叫住"
  duration_game_seconds: 60
  effects: {location: target}
  params: {target_location_id: {required: true}}
```

- runtime 的 `action_manifest` 消费该导出（校验一致性：id 集合、字段结构）；
- 训练评测与运行时看到同一份动作清单。

### 4.2 提议转发（runtime → 游戏）

- 模型判断契约 `actions` 字段 → runtime 白名单校验（§3.2）→ **转发给游戏执行**；
- 游戏可拒绝（资源冲突、玩家操作冲突等）→ 拒绝原因回注下一轮上下文（模型自然圆场）；
- 游戏执行中的动作进入游戏自己的模拟循环（动画/计时/到期生成实体），runtime 不干预；
- 玩家在游戏中打断（如点击角色、触发对话）→ 由游戏决定打断语义（含被叫住的走路），结果随投影回注。

## 五、状态投影契约（游戏 → runtime 快照）

每次对话回合前，runtime 从游戏读取并投影：

| 投影项 | 来源字段（游戏） | 用途（上下文区块） |
|---|---|---|
| `pending_actions` | 进行中动作 + 剩余秒数 | 区块 6（模型判断冲突/打断依据） |
| `scene.item_states` | 场景实体 | 区块 2（世界状态） |
| `protagonist`（男主位置/活动/身体） | 男主状态 | 区块 3 |
| 女主位置 / `current_activity` | 女主状态 | 区块 4 |
| 到期完成（面实体生成） | 游戏模拟循环 | 下一轮快照自然可见 → 模型基于事实承接 |

- 投影时机：每回合快照（现有 `TurnWorldSnapshot` 构建点）；
- 投影语义：快照是**冻结视图**（本回合内不变，防模型引用漂移）；
- **实体来源不设实体属性规则**：实体投影只有存在性（"桌上：一碗热汤面"），**不携带 created_by / created_at 等来源属性**。实体来源问题（谁做的/何时做的/用什么做的）由模型侧机制承担：① 短期——对话历史（她说"我去煮碗面"）；② 中期——r1 记忆沉淀（煮面事件 → "我今天傍晚给男主煮了一碗热汤面"的 shared_experience 记忆，被问时召回）；③ 推理——14B 模型将"桌上的面"与记忆/历史关联作答。理由与心情字段一致（§三.1）：来源的唯一消费者是模型，属性补漏会无限延伸（谁→何时→用什么→锅在哪），故交模型侧机制，不写规则。

## 六、玩家输入通道

- 玩家在 2D 游戏中的操作（移动、拾取、对话打字）由游戏收集，随对话请求一并传入 runtime；
- 现有 `ensure_world` 手动 API 为占位实现，最终由游戏驱动（游戏状态即投影，无需手动更新）；
- 玩家操作导致的立即世界变化（如玩家拿起物品）由游戏执行，随投影进入上下文。

## 七、待定决策点（接口实现时定）

1. **投影拉取方式**：对话回合前同步拉取（简单，推荐 P0）vs 游戏事件推送（实时性强，P1 可选）；
2. **游戏动作与对话的并行**：煮面动画进行中玩家打字对话——对话回合照常进行，`pending_actions` 提供剩余时间即可；
3. **动作清单的存放**：游戏侧配置文件导出 vs 运行时配置引用（推荐前者，游戏为单一来源）；
4. **女主 form 的投影**：取决于 2D 游戏是否表现猫形/人形切换（未定则归模型自管）。
