# Harness 组装与单次判断设计（2026-08-27，2D 游戏前提版）

> 状态：**权威设计（施工依据）** | 日期：2026-08-27
> 依据：《游戏-LLM 接口契约设计_20260827.md》（执行归游戏，runtime 只做投影/校验/转发）、《动作执行闭环施工方案_2D游戏前提_20260827.md》、《训练数据与运行时能力边界_JUDGE_TURN零样本动作协议与V5事实对齐_20260830.md》
> 参照实现：opencode（多部分消息 + 工具调用分离 + 结果回注）、DeepSeek Harness（轮次流程）、Claude Code
> 本设计将前台"三次调用"（M2 → Critic → GAME_REPLY）改为**单次判断**主流程：Harness 组装全部上下文 → 模型一次判断（回复 + 状态变化 + 动作提议）→ 程序机械记账。Critic 降级为可配置的定向审查。

## 一、总体流程

```
玩家输入（经游戏）
  → 【Harness 组装】游戏状态投影 + 记忆召回(r1) + 男主状态 + 女主状态
                     + 进行中动作 + 可用动作列表(游戏导出) + 对话历史 + 角色设定
  → 【模型一次判断】输出单 JSON：reply + mind_patch + actions
  → 【程序记账】解析 → 机械校验 → 提议转发(游戏执行) → 心智 patch 应用
              → 同一事务提交(心智+事件) → r1 记忆排队
  → 游戏模拟循环：到期动作完成(实体生成) → 状态投影 → 下一轮上下文可见
```

## 二、上下文包（Harness 组装，8 个区块）

固定组装顺序，动态数据来自游戏投影：

| # | 区块 | 来源 | 动态性 |
|---|---|---|---|
| 1 | 角色设定（人设/风格合同/信念） | 角色包 `system_prompt`（现有） | 静态 |
| 2 | 世界状态（场景/位置/物品账） | **游戏投影**（`item_states` 读游戏，接口契约 §五） | 动态 |
| 3 | 男主状态（位置/活动/身体） | **游戏投影** | 动态 |
| 4 | 女主状态（心智/关系/动机） | 游戏投影（位置/current_activity）+ 模型自管（情绪等），字段划分见接口契约 §三 | 动态 |
| 5 | 记忆召回 | r1 管线 `selected_memory_frame`（现有） | 动态 |
| 6 | **进行中动作**（动作/剩余时间） | **游戏投影**（`pending_actions` 读游戏进行中动作，接口契约 §五） | 动态 |
| 7 | **可用动作列表**（id+描述+时长） | **游戏导出**（接口契约 §四），runtime 消费渲染 | 静态 |
| 8 | 对话历史（最近 N 轮） | `list_recent_dialogue`（现有） | 动态 |

**预算策略**：区块 2-7 永远完整（均为短文本，合计数百 token）；超预算只截区块 8（对话历史）。

**区块 6/7 是模型判断的依据**：
- 区块 6：模型看到"泡脚中（剩 10 分钟）"，对并发/打断作常识判断（泡脚时被喊去跑步 → 自然拒绝/圆场）；数据来自游戏进行中动作投影；
- 区块 7：动作 id + **自然语言描述（含语义约束，如"占用双腿""可被打断"）** + 时长——模型读描述 + 世界状态自行判断可行性、冲突、顺序、打断。**约束写在描述文本里，程序不解析语义**；清单由游戏导出（接口契约 §四）。

**无意图记账**：承诺的跟踪完全由世界状态承担——进行中动作（区块 6）与实体结果（区块 2）本身就是账本；口头承诺靠对话历史 + 训练纪律（承诺收口），runtime 不建任何承诺表。

## 三、模型输出契约（单次判断，单 JSON）

```json
{
  "reply": "回复文本（必填）",
  "mind_patch": {
    "living_mind": {"current_activity": "...", "emotion": "...", "attention": "..."},
    "relationship": {"trust": "..."},
    "motive": {"key": "value"}
  },
  "actions": [
    {"action_id": "move_to", "params": {"target": "kitchen"}}
  ]
}
```

字段语义：

- `reply`：角色回复文本（必填）；
- `mind_patch`（可选）：女主角**自省**状态变化——心智由模型维护（V6 §19.3），程序只做机械校验与版本化应用；心情等自省字段为**自由文本、模型自管、无语义规则**（设计原则与例外见《游戏-LLM 接口契约设计》§三.1）；
- `actions`（可选，0-N）：**语义即工具调用**——模型只输出 `action_id + params`（不带 schema，schema 在区块 7 已声明）；每个动作由程序**独立**校验、独立转发、独立回注（拒绝原因进下一轮上下文），不对整批做全有全无。

> 注：早期版本契约含 `intention_resolutions` 字段（意图记账），2026-08-27 已删除；代码中该字段保留但**惰性未使用**，后续代码清理时移除。

**格式遵循策略**（零样本，对齐训练边界文档）：契约由 prompt 定义 + prompt 内输出示例；程序 schema 校验失败 → 回注错误信息重试 1 次；仍失败 → 本次回合**降级为纯文本回复**（actions/mind_patch 丢弃），记录评测标签。

## 四、程序记账层（模型判断之后，纯机械）

1. **解析**：严格 schema 校验（见 §三 格式遵循策略）；
2. **动作机械校验**：`action_id` 存在于游戏导出清单 + `params` 结构合法——**仅此两条，无任何语义规则**（能不能做、冲不冲突、打不打断 = 模型判断 + Critic 兜底）；
3. **动作转发**：合法动作转发游戏执行（接口契约 §四）；执行中 `pending_actions` / `current_activity` 由游戏投影（接口契约 §三），**runtime 不模拟动作、不写动作事件表**；
4. **心智 patch 应用**（版本化，现有机制）；
5. **同一事务提交**：心智 + 事件 + r1 记忆排队（现有 coordinator 锁 + 事务）；
6. **到期完成（游戏模拟循环）**：游戏执行动作到期 → 实体生成（面在桌上）→ 下轮快照投影可见（区块 2/6），模型基于真实状态承接（"饭好了"）；**runtime 无扫描逻辑**。

## 五、模型判断与程序记账的边界

| 层 | 管什么 |
|---|---|
| **模型判断**（语义） | 能不能做（常识）、与进行中动作冲不冲突、要不要打断、动作先后顺序、被拒后怎么圆场、承诺怎么收口（叙述层面） |
| **程序记账**（机械） | 白名单存在性（防幻觉）、参数结构、提议转发、事务原子性 |

**不写任何语义规则代码**；语义约束通过区块 7 的动作描述文本传递。**不建任何承诺/意图表**——世界状态（进行中动作 + 实体）即账本。

## 六、审查策略（可选，默认关闭）

- 默认：单次判断 + 程序机械校验；
- 开关开启时：`actions` 非空 或 `mind_patch` 变化较大 → 触发一次**定向审查**（复用现有 Critic，模型判断，非规则）：核对提议动作与游戏投影状态的语义一致性、叙述状态事实是否存在；
- 审查结果 approve / reject（回注） / revise。

## 九、验收标准

1. 单次判断输出契约格式遵循率（评测，目标 ≥ 98%）；
2. 区块 7 注入后，模型零样本调用合法 `action_id`；游戏导出清单增删动作后行为随之变化（不重训）；
3. 冲突场景（泡脚中被喊去跑步）模型自然处理；开关开启时 Critic 可兜底；
4. 游戏完成煮面后，下轮上下文出现面实体，模型基于事实承接（"饭好了"）；
5. 被游戏拒绝的动作 → 回注 → 模型下轮自然圆场；
6. 回归：chat01/02/diagnostic120 无回归。
