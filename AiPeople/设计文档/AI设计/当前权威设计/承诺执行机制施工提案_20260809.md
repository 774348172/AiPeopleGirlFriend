# 承诺执行机制施工提案（2026-08-09）

> 状态：**施工提案，待项目负责人立项** | 日期：2026-08-09
> 依据：《承诺式回复与执行能力一致性研究_20260809.md》（生成器侧分析目录）
> 问题：训练数据教会模型"有上下文就随口承诺"（数据 71-77% 承诺悬空），
> 而运行时没有任何"承诺→执行"闭环 —— 承诺悬空导致出戏（她说"我去做饭"，饭永远不来）。
> 本文把运行时侧 5 项条款细化为可施工提案。当前 V6 前台合同已经修正为
> `MIND_PATCH_V2 / M2 -> Critic -> ApprovedHeroineState -> GAME_REPLY`；本提案施工时必须服从该合同，不得把承诺状态与回复重新合并进 M1。

## 一、目标与边界

**目标**：让"女主角在对话里承诺做某事"在运行时形成可追溯、可兑现/可收口的闭环，消除承诺悬空。

**边界**（与需求一致）：
- 不做通用提醒、闹钟、待办或私人助理产品（需求 §10）
- 不恢复阶段 6 的 reminder/待办方向；只追踪"关系承诺/共同计划"的建立→完成/取消/missed
- 女主动作的执行主体是模型 patch（程序"不得写死"生活规则，V6 §19.3），程序只做**入账 + 强制回 cue + 审查**

## 二、改动点（5 项）

### 2.1 GAME_REPLY 合同：承诺收口条款

`AI女友最小心智系统设计.md` §16 GAME_REPLY 输出合同增加一条禁止/要求：

```text
- 已提出但未落实的承诺（"我去做饭""我帮你拿药"）不得悬空：后续轮必须自然处理
  （落实 / 圆场 / 转移 / 明确搁置），不得假装已发生（见 Critic 审查）。
```

**性质**：prompt 合同层（软约束 + 后续 Critic 硬审查兜底）。改动点：GAME_REPLY 输出合同段落。

### 2.2 WORLD_CONTINUITY_REVIEW：承诺悬空审查项

§21 Critic 审查项新增第 10 项：

```text
- 承诺悬空：上一轮提出的未完成承诺（在 MotiveState.pending_intentions 有记录），
  本轮若玩家追问或相关语境出现，不得无理由忽略；"把没做的说成已做"依旧拒绝。
```

**性质**：Critic 审查（模型软校验，与既有 9 项同性质）。改动点：审查项清单 + 对应困难负样本。

### 2.3 MotiveState.pending_intentions：承诺入账 + 强制回 cue

`§12.3 MotiveState` 扩展：

```yaml
pending_intentions:
  - intention_id: "int-0001"
    text: "我去给你做饭"
    evidence_event_id: "ev-xxxx"      # 承诺所在的角色消息事件
    created_at: "..."
    status: pending | fulfilled | cancelled | missed
    resolved_at: null
```

**确定性程序职责**（非模型）：
- POST_REPLY 阶段对已提交角色回复运行语义承诺候选提议（可以复用阶段 6 状态转换与证据绑定内核，
  见 2.5；只解析**女主角侧**承诺，玩家侧承诺按 V6"玩家输入一律为对白"合同不建状态机）
- 入账后，下一轮 MIND_PATCH_V2 / FIVE_MINUTE_RECONCILE 的输入注入
  `unresolved_plans`（已有该输入字段，当前为空）→ 促使模型自然兑现或收口
- FIVE_MINUTE_RECONCILE 输出合同增加对每条 pending 意图的判定：
  `fulfilled`（须有 LivingMind 活动或世界状态证据）/ `cancelled` / `missed`（超时未处理）

**性质**：模型提出开放语义候选，程序负责入账、证据绑定、状态转换和注入，后续模型负责兑现/收口决策。不得用承诺句式关键词直接创造语义承诺。改动点：MotiveState schema、POST_REPLY 语义提议、FIVE_MINUTE 输出合同、上下文注入。

### 2.4 heroine_diegetic_actions：schema 与能力边界校验

`§15.2` 的 `heroine_diegetic_actions`（当前空壳）定义：

```yaml
heroine_diegetic_actions:
  - action: "move_to_kitchen"        # 枚举（与 2D 表现层动作集对齐，P0 允许空）
    target: "kitchen"
    intent_ref: "int-0001"           # 关联 pending_intention（若有）
```

- **能力边界校验（程序）**：action 必须在角色包能力集内（白未晞定稿 §7.3 能力/代价/限制），
  游戏无执行系统的动作（付款/点外卖/网购/离场办某事）不在枚举内 → 禁止输出为 diegetic_action，
  只允许出现在对话文本（表达意愿而非承诺执行）。
- P0（纯文字）阶段：枚举可为空集，仅作 schema 占位；动作的"执行"表现为
  `LivingMind.current_activity` patch + 后续轮文本落实。

**性质**：程序 schema + 能力边界白名单。改动点：§15.2 schema、角色包能力集声明、
P1 表现层动作集对齐。

### 2.5 复用阶段 6 承诺状态机内核

阶段 6 `_prospective_parser.py` + `_plans.py`（P0-23/P0-24 全绿）已实现
proposed/confirmed/due/completed/cancelled/missed 状态机，但：
- 只解析**玩家侧**承诺（"我答应你X"）—— 需改为解析**女主角侧**承诺（"我去做饭"）
- 含 reminder/待办方向 —— 按需求 §10 删除，只保留 promise/shared_plan 语义
- 状态机本身可复用（追加式转换、证据关联、到期处理与恢复逻辑）

**性质**：代码复用 + 方向裁剪。改动点：parser 主语侧切换、reminder 裁剪、接入 2.3。

## 三、验收标准

1. **入账**：角色回复含承诺句式（"我去…/我来…/我帮你…/给你…吧"）→ POST_REPLY 提取入账
   `pending_intentions`（带证据 event_id），失败事务不残留（对齐需求 §7.2 原子性）
2. **回 cue**：下一轮输入注入 unresolved_plans；玩家追问"饭呢"时 Critic 不得忽略
3. **兑现/收口**：FIVE_MINUTE 对每条 pending 给出 fulfilled/cancelled/missed；
   fulfilled 须有活动/世界状态证据；超时未处理 → missed（可自然收口圆场）
4. **能力边界**：付款/点外卖等无执行系统动作不得进入 diegetic_actions；
   对话文本中的此类表达只作为意愿（"以后请你"）而非承诺执行（"我帮你付"）
5. **回归**：现有 eval 套件（chat01/02/diagnostic120）无回归；新增"承诺悬空"失败标签
   的评测用例（需求 §8.2 承诺与未完成计划覆盖）
