# 程序施工计划：权威状态闭环 V1

> 状态：A 块部分施工完成（截至 2026-09-29）；B/C/D 块未在本轮验收
> 日期：2026-09-11
> 上游权威：《游戏-LLM 接口契约设计 V2》
> 适用范围：当前 `plain_reply_v1/GAME_REPLY` 前台、正式游戏状态接入、玩家事实报告、动作来源和后台任务消费
> 明确排除：重新训练 LoRA、增加常驻校验模型、开放语义规则树、恢复 `ReplyFocus`、把 `JUDGE_TURN` 切成前台协议

## 一、施工目标

本计划只补齐程序闭环，不以程序理解所有自然语言，也不以固定 60 轮满分为目标。

完成后必须成立：

1. 正式聊天服务能够读取结构化游戏状态，而不是只接收一段场景文本；
2. 游戏事件、预约、物品、动作结果和 unknown 能进入下一轮 `GAME_REPLY_CONTEXT_V1`；
3. 玩家自由文本不会静默覆盖权威世界；
4. 玩家事实报告具有 `reported / confirmed / unknown / stale` 生命周期和来源；
5. 动作定义由游戏侧提供，runtime 不再维护第二份动作真相源；
6. 训练、评测和正式 API 使用同一个上下文渲染器；
7. 后台记忆任务在前台空闲时可被同一个模型实例消费，不增加第二个常驻 Gemma；
8. 所有确定性保证由无大模型合同测试验证。

本计划不承诺模型对白永远正确。它保证的是模型错误不能污染世界，结构化事实不会因为程序链路缺失而丢失。

## 二、当前实现基线

### 2.1 已完成，禁止重复施工

- `plain_reply_v1` 已是正式前台协议；
- Gemma NF4 + 白未晞 Adapter 已接入；
- `GAME_REPLY_CONTEXT_V1` 已有共享渲染器；
- 玩家、白未晞和第三方对白参与者已正确分离；
- 世界快照、对话、心智版本、模型决策和记忆任务已支持 SQLite 原子提交；
- 前台已经支持流式输出和启动预热；
- 前台交互期间已有后台任务互斥机制；
- 旧 Adapter 回退配置继续保留。

### 2.2 已有骨架但未接入正式入口

- `GameWorldInterface` 和 `StubGameWorld`；
- `pending_actions / player_fact_reports / unknown_facts` 快照字段；
- 玩家报告保持 `pending_confirmation` 的桩逻辑；
- 动作执行、完成和拒绝回注测试；
- 后台调度和持久化队列。

### 2.3 当前关键缺口

- 正式 `BaiWeixiChatService` 没有传入 `game_world`；
- 正式 `WorldInput` 只有地点、活动、身体、手持物和场景文本；
- 预约、实体、动作结果、unknown 和事实来源没有正式输入合同；
- 玩家报告没有正式提交、确认、纠正和失效 API；
- runtime 的动作清单仍为本地静态 `ACTIONS`；
- `HardInvariantValidator` 不读取回复正文，不能证明对白事实正确；
- 后台执行在正式服务中永久关闭，尚无正式空闲消费入口；
- 当前 60 轮脚本直接注入测试事实，不是生产状态写回端到端测试。

## 三、施工原则

1. **先程序，后模型**：本计划不训练模型，也不改 Adapter。
2. **结构化来源才可硬判断**：不为自由文本增加关键词判定树。
3. **先接入，再扩展**：先支持当前测试中实际使用的物品、预约、动作和 unknown，不建设通用知识图谱。
4. **状态与对白分离**：对白生成失败不回滚已经由游戏确认的外部事件；对白也不能创建游戏事实。
5. **迁移可回退**：数据库只做追加式 migration，不修改或删除现有对话和记忆记录。
6. **同一模型实例**：后台任务与前台共享当前 Gemma，前台到来时后台让路。
7. **先假模型合同测试**：结构闭环先用 fake model 验证，不消耗 GPU，不用回复质量掩盖程序缺陷。

## 四、施工块划分

本计划分为四个可独立验收的施工块。每块内部一次完成代码、migration、合同测试和文档状态更新，不拆成零散单文件施工。

## A 块：正式结构化世界接入

2026-09-29 进展：Unity schema 5 为门窗、室内灯光和白未晞移动状态增加逐项事实记录（稳定 ID、current/unknown/stale、来源、采集时间和快照版本）；后端保留 schema 4 兼容，严格校验新事实、拒绝同一存档的协议降级，只将 current 值投影为当前事实，unknown/stale 进入明确未知区。状态接口可读取逐项记录，整份快照过期时隐藏各项旧值。后端相关 45 项测试与 Unity 场景事实 8 项测试通过；Windows 客户端和配对后端候选目录已构建，并在本机完成自动启动、壁纸挂载、小窗真实模型对话（未知窗户回答不知道）和正常退出，异机验收尚未执行。厨房设备继续使用既有结构状态，完整实体登记和预约仍未完成，A 块不可标记验收通过。

2026-09-28 进展：已接入人物实际位置、执行器动作回执、有限实体快照，并补齐整份快照的来源、过期与重连恢复，以及 Unity 统一游戏时钟与动作计时。见《Unity人物位置动作回执与实体快照_20260928.md》《Unity快照有效性与重连恢复_20260928.md》《Unity统一游戏时钟与动作计时_20260928.md》。预约、每项事实已知性、全实体登记等仍未完成，不能把 A 块整体标为验收通过。下文设计基线与完整验收范围保留。

### A1 目标

让正式聊天服务获得完整、版本化、只读的游戏快照，并把当前事实投影给 `GAME_REPLY_CONTEXT_V1`。

### A2 最小数据合同

正式游戏快照至少包含：

```json
{
  "snapshot_version": 12,
  "game_time": "day-18 20:10",
  "location": {
    "id": "apartment_living_room",
    "label": "出租屋客厅"
  },
  "protagonist": {
    "location_id": "apartment_living_room",
    "activity": "交谈",
    "body": "正常",
    "held_item_ids": []
  },
  "entities": [
    {
      "entity_id": "blue_thermos",
      "kind": "item",
      "current_state": "在厨房水槽旁",
      "status": "current",
      "source": "game_state"
    }
  ],
  "appointments": [
    {
      "entity_id": "dentist_appointment",
      "status": "cancelled",
      "scheduled_at": null,
      "source": "appointment_system"
    }
  ],
  "pending_actions": [],
  "recent_feedback": [],
  "unknown_facts": []
}
```

字段只服务当前产品，不在本块建设任意谓词系统。`source` 是来源标识，不是自由文本可信度推理。

### A3 实现范围

- 新增正式游戏快照 DTO 和严格 schema 校验；
- 为正式服务实现 `GameWorldInterface` 适配器，或将现有持久化世界提供器收敛到同一接口；
- `BaiWeixiChatService` 创建 runtime 时必须传入正式 `game_world`；
- `/api/status` 和 `/api/chat` 使用相同存档、世界版本和角色身份；
- 当前物品、预约、动作反馈和 unknown 通过 snapshot 进入共享渲染器；
- 保留旧 `WorldInput` 兼容入口，但标记为开发/迁移接口，不再代表完整生产世界；
- 快照版本倒退、身份不匹配或字段非法时拒绝更新，不伪造默认事实。

### A4 主要文件

- `AiPeople/tools/baiweixi_chat_app.py`
- `AiPeople/runtime/world_mind/game_interface.py`
- `AiPeople/runtime/world_mind/world_state.py`
- `AiPeople/runtime/world_mind/state.py`
- `AiPeople/runtime/world_mind/model_payloads.py`
- `AiPeople/runtime/world_mind/persistence.py`

### A5 验收

- 正式 API 写入“牙医预约已取消”，下一轮模型输入必含该当前状态；
- 物品位置更新后旧位置不再出现在当前事实区；
- unknown 能进入 `[明确 unknown]`；
- 状态版本倒退和跨存档输入被拒绝；
- 模型回复内容不能改变快照和权威世界；
- 旧存档升级后仍可读取。

### A6 停止条件

若必须先解析任意玩家自然语言才能完成 A 块，立即停止并缩回结构化 API；A 块不负责自然语言理解。

## B 块：玩家事实报告生命周期

### B1 目标

把“玩家说了什么”和“游戏确认发生了什么”分开保存，避免模型一句“记住了”成为世界写回。

### B2 状态机

```text
reported -> confirmed
reported -> unknown
reported -> stale
confirmed -> stale
unknown -> confirmed
```

禁止：

```text
模型对白 -> confirmed
后台记忆摘要 -> confirmed
关键词命中 -> confirmed
```

### B3 最小记录

```json
{
  "report_id": "report-001",
  "save_id": "save-001",
  "actor_id": "protagonist",
  "subject_id": "spare_key",
  "predicate": "location",
  "value": "desk_middle_drawer",
  "status": "reported",
  "source_text": "我把钥匙放进书桌中间抽屉了。",
  "source_event_id": "dialogue-event-001",
  "created_world_version": 12,
  "confirmed_by_event_id": null
}
```

`predicate` 只允许当前产品已声明的有限字段，不设计开放语义本体。

### B4 实现范围

- 追加式数据库 migration；
- 正式提交、确认、标记 unknown、纠正和 stale 接口；
- 幂等 `report_id` 和版本检查；
- `reported` 进入 `[本轮玩家事实报告]`，不能进入 `[当前权威事实]`；
- `confirmed` 由游戏状态反映，并保留原始来源链；
- 后台记忆读取时保留状态，不得把 reported 改写成 confirmed；
- 首版只接收结构化报告。自动从任意自然语言抽取报告另行评审，不属于本块。

### B5 验收

- reported 提交后不改变物品位置；
- confirmed 必须引用有效游戏事件或结构化确认操作；
- 同一报告重复提交不产生重复记录；
- stale 报告不会作为当前事实渲染；
- unknown 不会被渲染成否定事实；
- 后台记忆整理前后状态等级不提升；
- 玩家纠正后新状态下一轮可见，旧状态保留为有时间关系的历史证据。

### B6 停止条件

如果实现开始依赖“出现我、你、放、拿”等关键词决定主体和动作，停止施工；那已经越过程序可确定边界。

## C 块：动作来源与Prompt边界收口

### C1 目标

统一动作真相源，并让 Prompt 正确区分玩家报告与客观世界。

### C2 实现范围

- 将 `runtime/world_mind/action_manifest.py` 的静态 `ACTIONS` 改为游戏导出清单的消费适配器；
- runtime 只验证 `action_id`、参数结构和清单版本；
- 游戏负责接受、拒绝、执行、完成和效果；
- `plain_reply_v1` 不新增模型动作 JSON；玩家游戏操作通过结构化游戏接口进入；
- `judge_v1` 继续作为后台/专用路径，不升级为前台；
- 修正 `GAME_REPLY_EVIDENCE_BOUNDARY_V1`：
  - 删除重复约束；
  - 明确 reported 可用于回应但不是已确认世界；
  - 允许一般建议和常识解释；
  - 禁止把建议包装成已发生事实；
- 更新旧注释中“实体来源完全交给记忆和模型推理”的过时表述。

### C3 验收

- 游戏增删动作后 runtime 无需改代码即可同步；
- 非法动作和缺少参数仍被机械拒绝；
- 动作完成前不能通过结构化状态显示为 completed；
- Prompt 不再把 pending report 描述成权威更新；
- “钥匙放外面是否安全”允许一般建议，不因无当前事实而被强制回答不知道；
- 训练生成器和生产渲染器 golden test 同步通过。

### C4 停止条件

不为“建议、反问、纠正、玩笑”等建立程序分类器；Prompt 只声明语义边界，不编译成规则树。

## D 块：真实端到端合同与后台消费

### D1 目标

证明正式产品链路成立，而不是再次直接把脚本事实塞给模型。

### D2 端到端合同测试

使用 FastAPI 正式入口、临时数据库和 fake model，覆盖：

1. 结构化游戏事件写入；
2. `/api/chat/stream` 发起真实回合；
3. runtime 从正式 `game_world` 读取冻结快照；
4. `GAME_REPLY_CONTEXT_V1` 包含当前事实、reported、unknown 和历史；
5. 回复提交与记忆任务入队原子完成；
6. 下一轮看到更新后的世界版本；
7. 模型生成失败不产生半个数据库回合；
8. 流式中断不产生未提交的存档回复；
9. 不同存档和对话互不污染。

测试必须保存模型实际输入，不能只检查最终字符串。

### D3 后台消费

- 复用现有 `WorldBackgroundScheduler` 和同一个 Gemma 实例；
- 前台有等待者或正在生成时，后台不得启动新的模型工作；
- 前台到来时，后台在安全边界让路，不中断数据库事务；
- 空闲后消费 reconcile 和 R1 memory 队列；
- 进程退出时保留未完成任务，重启后恢复；
- 不启动第二个常驻 Gemma，不增加第二份模型显存；
- 暂不追求后台实时完成，只保证最终可消费和不阻塞前台。

### D4 验收

- 连续对话后队列不是永久增长；
- 前台期间后台模型调用数为零；
- 空闲后任务能够完成；
- 后台失败不会回滚已提交对白；
- 同一 4090 上只有一个 Gemma 权重实例；
- 热请求首字延迟相对当前基线无显著退化；
- 正式端到端测试不再使用测试脚本直接注入的 `authoritative_facts` 代替游戏状态。

### D5 停止条件

若同实例后台消费仍导致前台首字明显恶化，保持持久化队列但不引入第二个 GPU 模型进程；先评审 CPU、定时维护窗口或手动整理方案。

## 五、不纳入本轮的可选项

以下事项只有完成 A-D 后才允许单独立项：

- `REPLY_FACT_CHECK_V1` Shadow；
- 小模型事实/承接评分；
- 自动从自由文本抽取玩家事实报告；
- 校验失败后重生成；
- 确定性事实核心或模板回复；
- 前台 `JUDGE_TURN`；
- 新 LoRA、DPO/RPO 或训练数据扩充；
- 为固定 60 轮错误追加专用规则。

这些功能不是完成权威状态闭环的前置条件。

## 六、施工顺序与依赖

```text
A 正式结构化世界接入
  -> B 玩家事实报告生命周期
  -> C 动作来源与 Prompt 收口
  -> D 正式端到端合同与后台消费
```

- A、B 完成前，不做新的 60 轮模型测试；
- C 完成前，不宣称训练与生产语义边界完全一致；
- D 完成前，不宣称正式程序已实现世界状态闭环；
- A-D 全部通过后，先做程序级故障注入，再决定是否需要新的模型质量测试。

## 七、每块交付物

每块必须同时交付：

1. 实现代码；
2. 追加式 migration（如涉及持久化）；
3. 不加载大模型的合同测试；
4. 失败与回退测试；
5. 设计实现状态更新；
6. 明确列出仍未实现的部分。

不得只提交接口或测试桩后宣称该块完成。

## 八、最终完成定义

只有同时满足以下条件，才能将“权威状态闭环”标记完成：

- 正式服务实际传入并使用 `GameWorldInterface`；
- 物品、预约、动作、unknown 和来源可由真实结构化输入进入快照；
- 玩家报告全生命周期持久化并通过合同测试；
- runtime 不再拥有独立静态动作真相源；
- Prompt 与 `reported / confirmed / unknown / stale` 含义一致；
- 正式 API 端到端测试覆盖写入、投影、生成、提交和下一轮；
- 后台队列能在不增加第二个 Gemma 的前提下最终消费；
- 数据库原子性、存档隔离和版本冲突测试通过；
- 文档明确承认自然语言对白仍存在概率性错误。

完成上述程序闭环后，再根据人工真实体验决定模型是否需要训练。程序闭环缺失期间，不再用重训模型补偿状态输入和写回问题。
