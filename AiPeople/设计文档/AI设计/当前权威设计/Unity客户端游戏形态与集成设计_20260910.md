## 0. 一句话形态

她住在你的 Windows 桌面里：**3D 出租屋房间铺满整个桌面背景**（桌面图标之后），你工作时互不打扰；桌面底部**常驻一条对话条**显示她最近说的话。想聊天时点对话条（或按热键）→ **弹出一个独立的小对话窗**（她的立绘 + 对话历史 + 输入框，可拖动、记住位置）：**房间与桌面完全不变、不遮挡任何程序**；收起（`Esc` / 点击小窗外部）后焦点立刻交还。她的回复同时更新到常驻条并冒气泡提示。没有对话时她也会自己生活：在屋里走动、靠着纸箱坐着、望着窗外，夜里回纸箱睡觉。所有对白与状态仍来自后端已提交事务，客户端不自行决定剧情事实；她的"自主行为"只是**环境表现**，不产生任何未提交的剧情事实。

## 1. 定位与合规

- 形态定位：**Windows 桌面背景程序（Desktop Diorama）**——房景渲染在壁纸层，另有对话浮层、气泡通知与托盘菜单（细节见 §6.1/§6.2）。这是需求文档 P1「桌面表现」的 3D 化最终形态：表现层读取已提交状态、不自行决定剧情事实（《项目框架需求》§9.2）的原则不变。
- **不打扰纪律**：主进程（壁纸）**永不**拦截键鼠、不抢焦点、不遮挡任何窗口；全屏应用（游戏/影视）前台时自动暂停渲染。唯一获取键盘焦点的界面是**对话小窗**（独立进程），且只由用户显式动作唤出（点击常驻对话条 / 全局热键），收起即归还焦点。**v2.3 明确作废 v2.1 的"全屏会话态"**（点击后把整个房间窗口抬成全屏）——实机验证该形态会遮挡桌面程序，不符合产品预期。
- **自主行为边界**：环境行为（游走/待机变体/看窗/夜间睡觉）由表现层调度，**不写剧情事实、不产生记忆、不推进关系、不进入投影**；剧情相关行动仍只能来自模型提议（§4.3）。
- 首版世界沿用世界正典最小范围：**出租屋（主场景）+ 街角咖啡厅 + 连接街道**（先做出租屋）。
- P0 边界继续有效：不做开放世界、战斗、关卡、经济系统；不做无限的剧情性自主生活模拟（自主性仅限 §6.2 环境行为）。
- 本地运行、隐私、原子提交、`character_id` 全链路等产品级要求由后端承担，客户端不复制。

## 2. 总体架构（两阶段）

```
阶段 A（现状协议，零后端改动）
  Unity（表现层 + 男主输入通道）
    ├─ 3D 场景与角色表现（读已提交状态）
    ├─ 对话 UI（流式 NDJSON）
    └─ 每轮上报男主状态 WorldInput
  ⇅ HTTP 127.0.0.1:8767
  后端 baiweixi_chat_app（plain_reply_v1，程序持有世界）

阶段 B（目标形态：游戏持世界，动作闭环）
  Unity（世界唯一事实源 + 执行者）
    ├─ 世界状态：女主/男主位置、进行中动作、物品实体、计时
    ├─ 动作执行：动画、时长、到期生成实体（如面）
    └─ GameWorldProjection 投影 + 玩家输入
  ⇅ 本地 HTTP/WS（端口待定 D2）
  后端 WorldMindRuntime(game_world=远端游戏代理)
    └─ 白名单校验、提议转发、上下文投影、事务与记忆
```

- 阶段 A 能独立交付价值（对话 + 状态读取 + 男主状态），也是阶段 B 的通信层基础，不浪费。
- 阶段 B 的前置是后端 `game_world` 接线（`runtime/world_mind/runtime.py` 已支持）；前台协议已决策切换 `JUDGE_TURN`（§4.4），动作提议通道的启用时间取决于模型侧交付。

## 3. 阶段 A：表现层与输入通道

### 3.1 线协议（现行生产接口，照此实现客户端）

- `GET /api/health`：就绪检查（model/adapter/protocol/background_execution）。
- `POST /api/status` `{save_id, world?}` → 返回 `save_id`、`game_time`、`world`（version、location_id、location_label、activity、body、held_item、scene）、`heroine`（version、living_mind：emotion/attention/current_activity/immediate_intent、relationship：stage/trust）、`reconcile_queue`、`memory_queue`。
- `POST /api/chat/stream` `{save_id, text, world}` → NDJSON 逐行事件：`{"type":"delta","text":…}` 逐字输出、`{"type":"done","value":…}` 提交结果、`{"type":"error"}` 失败。
- 规则：**只有 `done` 到达才代表回复已提交**；生成期间只显示"正在说"状态，半截草稿不得展示为她说的话（对齐《项目框架需求》§6.6）。

### 3.2 Unity 侧模块（阶段 A）

| 模块 | 职责 |
|---|---|
| `DialogueClient` | UnityWebRequest/HttpClient 调 8767；NDJSON 增量解析；取消与超时；错误重试不重复提交 |
| `GameStateModel` | 缓存 `/api/status` 结果：游戏时间、女主心智/关系、场景描述；供 HUD 与表现调度读取 |
| `SceneView` | 出租屋场景渲染、镜头、昼夜/天气氛围（按 `game_time` 与场景描述表现） |
| `CharacterActor` | 白未晞在场表现：位置/姿势/表情/待机（阶段 A 以静态模型或立绘占位，见 §7） |
| `PlayerController` | 移动/靠近/交互（递物、开灯、关窗）→ 合成男主状态 |
| `ChatUI` | 对话气泡/输入框/生成中状态；关系与心情的轻量展示 |

### 3.3 男主状态来源

每轮对话前，`PlayerController` 把玩家在场景中的真实状态合成为 `WorldInput`：

```json
{
  "location_id": "apartment_table",
  "location_label": "出租屋餐桌旁",
  "activity": "坐着休息",
  "body": "有些疲惫，没有受伤",
  "held_item": "",
  "scene": "窗外下着雨，屋里亮着暖灯"
}
```

字段与默认值以 `tools/baiweixi_chat_app.py::WorldInput` 为唯一来源；客户端不得自行新增字段或语义。

## 4. 阶段 B：游戏持世界与动作执行（目标形态）

### 4.1 事实源与投影方向

对齐《游戏-LLM 接口契约设计》§二/§五：

- 游戏（Unity）是**世界唯一事实源与执行者**：女主/男主位置、进行中动作、物品实体、计时以游戏为准；
- 投影单向：游戏 → runtime（每回合快照读取），runtime 不写游戏世界（动作执行请求除外）；
- 实体投影只有存在性（"桌上：一碗热汤面"），不携带来源属性；
- 模型自管字段（emotion/attention/immediate_intent/motive/knowledge）不进入游戏；游戏投影字段（位置/活动/item_states/pending_actions）不进入模型的自由改写范围。

### 4.2 进程拓扑（D2 已决：Unity 为世界服务端）

- **已实施（2026-09-11，M3）**：Unity 启动时在 `127.0.0.1:8770` 暴露游戏世界服务（`GET /game/health|actions|project`、`POST /game/execute_action|player_fact_report`）；后端以 `runtime/world_mind/remote_game_world.py` 的 `RemoteGameWorld` 实现 `GameWorldInterface`（`project()` / `execute_action()` / `submit_player_fact_report()` + `fetch_action_manifest()`），注入 `WorldMindRuntime(game_world=...)` 启用。
- 备选（未采用）：后端为服务端，Unity 作为客户端轮询/长连接接收动作请求——与"游戏是主进程与执行者"的契约方向相反，需更多运行时协调。
- 安全：仅绑定 127.0.0.1；后续可沿用启动握手/令牌思路（参考 `AIPEOPLE_SHUTDOWN_TOKEN` 模式）。

### 4.3 动作清单与执行（P0 三动作）

动作定义按契约应**由游戏导出、runtime 消费**（当前清单在 `runtime/world_mind/action_manifest.py`，阶段 B 需翻转来源方向，列为施工项）：

| action_id | 语义 | 游戏侧执行 | 时长 | 完成效果 |
|---|---|---|---|---|
| `cook_meal` | 走到厨房做饭，双手被占用 | 走向厨房 → 烹饪循环动画 | 1200 游戏秒 | 桌上生成"一碗热汤面"实体 |
| `move_to` | 走向某处，路上可以被叫住 | 寻路 + 行走动画（可被打断） | 60 游戏秒 | 位置更新 |
| `pick_up_item` | 拿起场景中的某个物品 | 伸手/拾取动画 | 60 游戏秒 | 物品归属更新 |

执行规则：

- 游戏可拒绝（玩家占用厨房、资源冲突等），拒绝原因经下一轮 `project().recent_feedback` 回注，模型自然圆场；
- 到期完成由**游戏模拟循环**负责（runtime 无扫描逻辑）；
- 打断语义由游戏决定（如被叫住的走路、点击角色触发对话）；
- 女主行动是**响应式**的：只执行模型提议的动作、时间推进与打断，不做自主日程模拟（P0 明确不做无限自主后台生活）。

### 4.4 前台协议切换（D1，已决：切换 JUDGE_TURN）

- **2026-09-10 决策：前台协议切换为 `JUDGE_TURN`**（单次判断含 `reply + mind_patch + actions`）。
- 职责边界：**模型侧工作（重训、重新冻结输入/输出、训练数据、评测集与回退资产）由 AI/模型线负责，不在本文与 Unity 客户端的责任范围内**；本文只依赖其交付的 `actions` 输出契约与启用时间。
- 客户端侧要求：动作提议通道按"即将启用"设计——动作校验、转发、执行、拒绝回注、实体生成与投影链路先行施工并可独立测试（用桩提议驱动），**启用时间以模型侧交付为准**；在模型侧交付前，不得以任何方式伪造动作来源或绕过白名单。
- 引用：《Harness组装与单次判断设计》§1.1（协议切换需重新冻结，不能只改配置项）。

## 6. 表现规范与桌面外壳

### 6.1 桌面外壳（v2.3：双进程）

**进程与职责**

| 进程 | 职责 | 窗口 |
|---|---|---|
| **主进程（壁纸）** | 3D 房间与白未晞、环境行为；常驻对话条与新回复气泡；与后端 8767 的唯一通信出口；游戏世界服务（8770）；对外提供小窗所需的本地 UI 接口（`/ui/*`）；系统托盘；全局热键；管理小窗进程生命周期 | 无边框全屏，经 Win32 挂载到桌面图标视图**正下方**（系统壁纸之上、桌面图标之下） |
| **小窗进程（对话）** | 立绘 + 对话历史 + 输入框；拖动与位置记忆；`Esc` / 点击小窗外部收起；只与主进程通信（不直连后端） | 约 900×420 无边框窗口，默认底部居中（可拖动、记住位置）；随主进程启动并常驻后台（隐藏），唤出瞬现 |

**交互约定**

- 唤出：点击常驻对话条，或全局热键 `Ctrl+Alt+B`；退出：小窗菜单 / 托盘菜单 / `Ctrl+Alt+Q`（三者等效，均联动关闭两个进程，退出后桌面完全恢复）；单实例约束（重复启动只唤出既有实例）。
- 回复呈现三处：常驻条（最近一句）+ 桌面气泡（新回复到达提示，不抢焦点）+ 小窗（完整历史与生成中状态）。
- 提交语义不变：流式生成期间小窗显示"正在说…"，只有后端 `done` 才定稿为她说的话；小窗崩溃不影响主进程与存档。
- 位置记忆：小窗拖动后的位置写入外壳设置，下次在原位弹出（多显示器按同屏记忆）。

**壁纸挂载（主进程，已在 Win11 25H2 实机验证）**

- 无边框全屏 + `WS_CHILD` + `SetParent` 到图标宿主，并 `SetWindowPos(hwnd, SHELLDLL_DefView, …)` **紧贴图标视图正下方**；
- 校验标准：我们的窗口必须正好是图标视图的下一个 z 序窗口，否则判定失败并降级（绝不遮挡桌面）；
- 降级链：WorkerW → Progman 置底 → 普通窗口（1600×900，可最小化）；热键注册失败时不进壁纸层（避免无交互/无退出入口）。

**性能纪律（常驻程序硬要求）**

- 主进程渲染上限 30 FPS；前台存在全屏应用时暂停渲染（保留 1Hz 服务心跳，游戏世界服务在独立线程继续）；
- 空闲降频；连续 8 小时运行内存/句柄增长须可忽略；**不注入、不挂钩任何其它进程**（仅使用 `GetAsyncKeyState` 轮询与 `RegisterHotKey`）；
- 2026-09-14 响应性实施细化：服务心跳的 1Hz 不等于 Unity 主线程必须 1 FPS。主壁纸空闲 15 秒后降至最多 15 FPS；完整遮挡或锁屏时相机与 Canvas 停绘，仍以最多 15 FPS 处理命令。小窗隐藏时保留此前低延迟修复后的 30 FPS、Canvas 停绘和轻量可见性查询。小窗可见、对白生成、人物行走或门窗运动时保持活跃帧率；实际节能与唤醒延迟须分别验证，不得把功能通过当成 8 小时长跑通过。
- 2026-09-14 解锁桌面补验：最终 v2 在本机 RTX 4090 上通过活跃/空闲、工作区及全屏覆盖停绘、恢复与小窗唤醒的 16 项短时证据检查；6 次小窗原生可见延迟 89–113ms，HTTP 隐藏 218–250ms。正常绘制阶段主/隐藏小窗工作集约 405/230MiB，小窗使用后约 286MiB；专用 GPU 合计约 377MiB。原生挂载与 12 次门窗转换复验通过。完整数据和口径见 `UnityClient/output/apartment-performance/RESULTS.md`；真实小窗/房间面板首帧、目标 12GB 与后端同跑、8 小时稳定性尚未验收。
- 2026-09-14 真实 UI 补验：最终 UiVerified 包在本机完成 3 轮真实热键/鼠标开关与面板切换、12 次门窗操作；内容 Unity 帧 104–168ms、点击隐藏约 5–7ms、房间状态帧约 13ms。历史文字增加区域裁剪，房间显示时隐藏历史，避免越界。测量区分输入事件、Unity 帧末和 GPU 读回，不声称显示器扫描延迟；诊断识别样式与正常工具窗口样式分别复验。25 项回归通过，报告 `UnityClient/output/ui-latency/RESULTS.md`。仍须目标 12GB 与后端同跑及 8 小时稳定性验收。
- 2026-09-14 用户决策覆盖：本轮跳过 8 小时稳定性测试，保留“未测试”事实，不将其作为继续施工的前置条件。目标硬件与真实后端同跑的证据边界不变。
- 双进程内存预算：主进程约 400MB + 小窗进程约 300MB（已确认接受）。

**输入与字体**：中文输入只发生在小窗（系统输入法，`Esc` 收起即归还焦点）；壁纸层纯展示；发布前替换为随包授权的 CJK 字体（见 §7）。

### 6.2 桌面层布局（v2.0 首版）

- 房景**铺满所选显示器**（默认主显示器，托盘可切换）；镜头为固定居住视角（带轻微呼吸感），她保持面向镜头的自然朝向；
- 房景采用**完整实时 3D 房屋**，不是把整屋烘焙成一张 2D 背景：墙体、房间、门窗、阳台、地面、家具和可交互物均保留空间几何；桌面模式默认固定机位，但场景必须支持第一人称/调试机位和角色在全屋内移动；
- **对话入口（常驻条）**：底部居中**始终可见**，显示她最近一句；无对白时显示"点这里和我说话（Ctrl+Alt+B）"。点击 → 唤出对话小窗（**房间不消失**，仍在壁纸层渲染）；
- **新回复提示**：她说话或完成动作时，在常驻条旁冒气泡（不抢焦点），托盘图标同步提示；
- **环境行为**（自主，见 §9 M6）：屋内游走、纸箱边坐、望窗、伸懒腰等变体，按间隔（≥90s，可在托盘关闭）挑选；**存在进行中动作或对话生成中时一律不发起**，并立即回 Idle；
- **昼夜**：按时段表现（沿用 6.3）；夜间（23:00–07:00 游戏时间）她回纸箱边、环境光转暗、行为频率降低。

### 6.3 室内表现（沿用 v1.0）

- **场景**：出租屋为老旧小户型的完整实时 3D 两室一厅；建筑结构按模块化 Prefab 组装，至少包含狭窄玄关、客厅、主卧、次卧、厨房、卫生间和小阳台。必备陈设：门（她习惯先确认出口）、窗（雨/阴天）、餐桌椅、厨房与锅具、床、**最初收留她的纸箱**（不可移除道具）。
- **时间与天气**：按 `game_time` 与 `scene` 描述表现昼夜与天气；首版锚点＝第一年秋季第 11 日傍晚、阴、雨后潮湿。
- **白未晞**：人形常态（银白长发、白猫耳尾、雪花纹白蓝眼）；**当前服装为正典"男主宽大上衣+长裤"，不是女仆装**；不做持续卖萌；耳/尾触摸是她明确的反感项，需做成"可触发戒备反应"的交互点而非福利。
- **UI**：对话浮层与气泡为准（§6.1）；状态展示从简（游戏时间、关系阶段、生成中状态）；设置等操作走托盘与独立界面，不进入角色聊天入口（《项目框架需求》§3.6）。

## 8. 显存与性能预算

- 目标硬件：Windows 10/11、16GB 内存、**12GB 显存级别 GPU**（与后端共享）；8GB 档位不再作为本设计的预算前提（如需兼容，另行立项画质降级档）。
- 后端组合推理（Gemma NF4 + reranker）预验证约 6.7GB；**游戏渲染预算上限按 ≤4GB 设计**：1080p~1440p、URP、可用中等阴影与后处理、仍避免无节制的实时阴影堆叠；最终以目标硬件实测为准。
- 延迟：状态拉取 <50ms；对白首字沿后端目标（热启动 P95 <2s）；游戏层不得引入阻塞式等待（流式渲染 + 提交后定稿）。
