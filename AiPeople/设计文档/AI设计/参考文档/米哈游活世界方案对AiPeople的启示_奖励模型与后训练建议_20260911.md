## 一、结论

米哈游方案不会要求 AiPeople 推翻当前权威架构。它反而支持当前已经确定的基本边界：

1. 游戏程序拥有客观世界状态；
2. 记忆系统保存经历、关系、来源和有效状态；
3. Agent 负责形成意图和提出行动；
4. 角色模型负责语言、人格与交互节奏；
5. 概率模型不能成为权威事实源或游戏执行结果。

该方案对 AiPeople 最重要的新启示不在运行时增加模型链，而在训练与评测侧补齐第五层：

> 建立“人工标准 -> 多维评价 -> 真实偏好数据 -> 后训练 -> 封存评测 -> 生产错误回流”的质量闭环。

当前项目反复训练但质量不稳定，并不只是训练数据数量不足。更根本的问题是：过去主要训练“模型应该输出什么”，但还没有稳定解决“多个看似合理的回答中，为什么这个更好、那个更差，以及这个判断是否与人工标准一致”。

近期建议保持现有程序施工顺序，先完成权威状态闭环；模型侧优先研究 `SFT + DPO/chosen NLL`。在数据和评价体系得到证实前，不直接建设完整 RLHF、在线 OPD、常驻奖励模型或每轮串行审核链。

## 二、外部方案带来的架构启示

### 2.1 “活人感”是系统效果，不是单模型效果

外部方案把 AI NPC 拆成游戏体验、Agent、角色模型、长期记忆、后训练、评测和研发工具等多个系统。这说明：

```text
游戏世界
  -> 提供确定事实和执行结果
记忆系统
  -> 提供有效经历、关系和知识边界
Agent
  -> 形成本轮意图并提出动作
角色模型
  -> 生成自然对白
评价与后训练
  -> 度量质量并形成改进数据
```

仅靠扩大 LoRA 数据，无法补偿世界状态未传入、事实未写回、第三方说话人渲染错误或训练与生产入口不一致。这与当前权威设计的状态闭环方向一致。

### 2.2 事实正确与角色自然必须分开

外部方案强调对话节奏、张力、留白、言外之意和长期人格生长。这些适合定义角色表现的上限，但不能替代事实底线。

AiPeople 应坚持：

```text
事实与主体正确 -> 硬性准入
回应本轮意图   -> 硬性准入
行动状态真实   -> 硬性准入
角色自然度     -> 通过准入后的排序指标
情感与节奏     -> 通过准入后的排序指标
```

事实正确但答非所问仍然不合格；角色味道很好但事实错误也不合格。软风格分不能补偿事实、主体、意图覆盖或动作完成状态错误。

### 2.3 记忆不能只是聊天记录检索

外部方案明确指出，仅存储和检索历史容易产生涣散与漂移。当前项目应继续区分：

- `confirmed` 当前权威事实；
- `reported` 玩家报告但尚未确认的事实；
- `unknown` 当前缺少证据；
- `stale` 已被当前状态替代的旧事实；
- 角色亲历事件；
- 人物关系与情感变化；
- 稳定人格和偏好；
- 第三方证言及其来源。

这些记忆不应作为同权重文本混在一个检索池中。当前事实、旧事实、来源和主体需要在投影阶段显式区分。

### 2.4 Agent 意图与游戏执行结果必须分开

开放式 Agent 可以提出：

```json
{
  "intent": "提醒玩家赴约",
  "proposed_action": "create_reminder"
}
```

但只有游戏接口确认执行后，角色才能说“提醒已经设置”。模型提出、角色承诺、程序批准、动作执行和动作完成是五种不同状态。

因此，外部方案中的自主行为不能被理解为让模型自由改写世界。当前权威设计中“模型提议、游戏执行、结果回注”的动作闭环应继续保持。

## 三、奖励模型对 AiPeople 的意义

### 3.1 奖励模型是什么

奖励模型可以理解为一个回复质量评价器。它接收：

```text
生产上下文 + 玩家本轮输入 + 候选回复
```

输出总体分数、多个维度分数或两个回复之间的偏好，例如：

```json
{
  "fact_consistency": 0,
  "direct_answer": 0,
  "subject_attribution": 1,
  "persona_naturalness": 0.8,
  "dialogue_coherence": 0.6,
  "unsupported_claim": true
}
```

若事实正确性为零，即使人格自然度较高，这个回复也不能作为好样本。

### 3.2 示例

生产上下文：

```text
当前预约：星期六上午十点
旧预约：星期五下午，状态 stale
玩家：所以我还是星期五下午去，对吗？
```

候选回复：

- A：“不是，是星期六上午十点。”
- B：“嗯，你按时去就行。”
- C：“不是，是星期六上午十点，到时候我陪你去。”

评价：

- B 没有纠正错误前提，事实使用和直接回答失败；
- A 事实正确、直接、没有无依据扩展，可以合格；
- C 前半正确，但“我陪你去”需要角色能力、意愿或程序状态依据，不能因前半正确而自动通过；
- 如果存在多个事实合格的候选，再比较白未晞自然度、语气和节奏。

### 3.3 Hybrid Reward 的可用分层

外部方案提到 rule、scalar 和 rubric 组成的 Hybrid Reward。对 AiPeople 可解释为：

| 层 | 适合判断 | 是否可作为确定性保证 |
|---|---|---|
| Rule 规则 | JSON 格式、必填字段、动作 ID、状态版本、确定性结构冲突 | 只对封闭结构可保证 |
| Scalar 标量 | 人工好差、自然度、总体偏好强弱 | 不可保证，标准可能漂移 |
| Rubric 生成式评价 | 是否回答问题、主体是否正确、是否自然、是否新增无依据事实 | 不可保证，Judge 也会误判 |

建议使用四层评价：

1. **确定性合同层**：格式、字段、动作白名单、事务和状态版本；
2. **封闭事实评价层**：对白是否与本轮明确注入的预约、位置、动作结果冲突；
3. **开放语义评价层**：是否答非所问、是否自然、是否像白未晞、是否机械复述；
4. **人工校准层**：持续检查自动评价的误判、漏判和口径漂移。

第一层可以阻断。第二层只有在封闭切片内经过封存集证明后才能评审主动干预。第三层初期只能用于离线筛选、归因或 Shadow。第四层决定评价系统是否仍符合用户真实标准。

### 3.4 奖励模型适合做什么

- 在同一上下文的多个候选中选择更好的回复；
- 发现明显坏样本并送入人工复核；
- 从真实失败回复构建 `chosen/rejected`；
- 为 DPO 或 RLHF 提供偏好信号；
- 分别报告事实、主体、意图覆盖、自然度和人格问题；
- 检测新 Adapter 相比裸基座新增了哪些错误。

### 3.5 奖励模型不能做什么

- 不能保证所有开放回复正确；
- 不能理解并裁决无限自然语言事实；
- 不能替代游戏状态和动作执行器；
- 不能未经人工校准就成为训练数据或发布的最终裁判；
- 不能因为一个总体高分掩盖严重事实错误；
- 不能默认作为每轮前台串行审核模型，否则会增加延迟、显存或服务复杂度，并引入新的误杀。

## 四、后训练框架对 AiPeople 的启示

### 4.1 过去训练方式的不足

仅使用监督答案的训练主要回答：

> 在这个输入后，应该提高哪段文本的概率？

但它不能充分回答：

> 为什么这个自然但含糊的答案，比另一个明确纠正事实的答案差？

过去重复训练仍出现 unknown 处理不当、主体错位、答非所问、旧事实复活和 Adapter 破坏基座逻辑能力，说明只增加标准答案不能稳定表达所有相对偏好。

### 4.2 建议的数据飞轮

```text
正式 GAME_REPLY_CONTEXT_V1 输入
  -> 裸基座、旧 Adapter、当前 Adapter 生成真实候选
  -> 人工按统一标准审核
  -> 记录错误类型和严重性
  -> 构造 chosen/rejected 偏好对
  -> 独立复核与家族去重
  -> SFT 或 DPO/chosen NLL 小规模训练
  -> 封存集和基座非劣化测试
  -> 通过后扩大
  -> 生产失败继续回流
```

这一流程与“发现错误就凭感觉补数据并重跑 60 轮”不同。每次训练必须能够回答：

1. 要改善哪个冻结指标；
2. 使用了哪些真实失败类型；
3. 哪些能力必须保持不退化；
4. 结果是否优于同输入裸基座和旧 Adapter；
5. 新增了哪些回归。

### 4.3 近期推荐路线

在状态闭环完成后，模型训练建议按以下顺序评审：

1. 保留经过复审的 SFT 数据，学习白未晞人格、自然表达和必要事实纪律；
2. 使用生产同构输入收集模型真实负样本，不以教师凭空编写的简单错误替代；
3. 人工确定正确且自然的 `chosen` 和模型真实错误 `rejected`；
4. 使用 DPO 并加入 chosen NLL/SFT loss，避免只拉开相对差距而降低正确回复本身概率；
5. 保留 known、unknown、普通聊天、人格和逻辑能力集；
6. 分别报告事实硬门、答题率、人格自然度、基座非劣化和首字延迟；
7. 只有离线偏好训练达到瓶颈，且评价器经过人工校准后，再评审在线 RLHF/OPD。

## 五、术语解释

### 5.1 SFT

`SFT` 全称 `Supervised Fine-Tuning`，即监督微调。

训练数据通常是输入和标准答案：

```text
输入：当前预约是星期六，星期五已经失效。玩家问星期五去对吗？
答案：不是，现在是星期六上午十点。
```

训练目标是提高标准答案 token 的概率。LoRA/QLoRA 通常承载的就是这种训练。

优点：

- 实现简单、相对稳定；
- 适合角色语气、常见行为和输出格式；
- 不需要独立奖励模型。

局限：

- 一个输入通常只有一个标准答案，容易把同义好答案当成未学习目标；
- 不直接说明哪些错误答案为什么更差；
- 数据冲突会被直接学入模型；
- 只能提高正确概率，不能保证未见表达全部正确。

### 5.2 RLHF

`RLHF` 全称 `Reinforcement Learning from Human Feedback`，即基于人类反馈的强化学习。

经典流程：

```text
人工比较多个候选
  -> 训练奖励模型
  -> 奖励模型为新回复评分
  -> 使用 PPO 等强化学习算法优化回复模型
```

优点：

- 可以表达自然度、帮助性、人格等复杂偏好；
- 不要求每个输入只有唯一标准答案；
- 可以利用候选之间的相对优劣。

局限：

- 训练和工程复杂、成本高；
- 奖励模型错误会被策略模型放大；
- 容易产生 Reward Hacking，即模型学会讨好评分器而不是真正改善；
- 需要严格的 KL 约束、保持集、在线采样和稳定性监控；
- 不适合作为当前项目未经前置验证的第一步。

### 5.3 DPO

`DPO` 全称 `Direct Preference Optimization`，即直接偏好优化。

它使用同一输入下的成对数据：

```json
{
  "prompt": "生产上下文和玩家问题",
  "chosen": "不是，现在是星期六上午十点。",
  "rejected": "嗯，你按时去就行。"
}
```

DPO 直接提高 `chosen` 相对于 `rejected` 的概率，一般不需要单独训练奖励模型，也不需要 PPO rollout。

优点：

- 比经典 RLHF 简单；
- 适合使用已有人工好差审核；
- 很适合针对模型真实错误建立偏好边界。

局限：

- 标错偏好对会直接训练出错误倾向；
- 过于简单或人工编造的 rejected 不能代表模型真实失败；
- 离线数据覆盖不到的情况仍可能失败；
- 单纯 DPO 只关心相对差距，可能需要 chosen NLL/SFT loss 保持正确答案的绝对概率和语言质量；
- 仍需基座能力保持集和封存泛化评测。

### 5.4 Chosen NLL

`NLL` 是 `Negative Log-Likelihood`，即负对数似然。`chosen NLL` 表示在做偏好训练时，同时继续监督 chosen 正确答案本身。

可简单理解为：

```text
DPO：让 chosen 比 rejected 更可能
chosen NLL：让 chosen 自己也保持足够可能
```

两者组合可以减少“只是把 rejected 压低，但 chosen 本身也变差”的风险。

### 5.5 OPD

外部图片使用了 `OPD`，但没有给出英文全称。它不像 SFT、RLHF、DPO 那样具有唯一公认含义。不同资料中可能用于指在线偏好蒸馏、在线偏好优化，或者团队内部方法。

仅根据图片上下文，可以确认：

- 它位于后训练链路较后阶段；
- 它与 Hybrid Reward 和偏好优化有关；
- 它可能使用当前模型新生成的候选继续形成反馈并优化。

不能仅凭长图确定具体损失函数、采样方式或算法全称。若按“在线偏好优化”作概念理解，它与离线 DPO 的主要区别是：

```text
离线 DPO：训练始终使用预先收集的 chosen/rejected
在线偏好：训练过程中持续生成新候选、评价、再训练
```

在线方法更容易覆盖模型当前真实错误，但成本更高，也更依赖评价器质量。除非取得原始论文、代码或团队技术说明，否则不得把某一种公开 OPD 实现直接认定为图片中的方法。

### 5.6 Reward Model 与 Verifier

`Reward Model` 通常输出偏好分数，用来比较回复总体质量；`Verifier` 通常针对某个可核验目标输出通过、失败或置信度。

对当前项目：

- 白未晞自然度、情商和节奏更接近 Reward Model 问题；
- 明确预约是否冲突、动作是否有执行依据更接近封闭 Verifier 问题；
- 开放聊天中的“是否完全正确”不适合伪装成确定性 Verifier。

## 六、建议新增但暂不施工的设计资产

如果用户裁决采纳本建议，后续可以单独设计以下文档，不直接塞入程序接口契约：

1. 《角色回复多维评价与人工校准规范》；
2. 《真实负样本与 chosen/rejected 偏好数据合同》；
3. 《SFT-DPO-chosen NLL 小规模可证伪试验计划》；
4. 《基座能力保持集与 Reward Hacking 防护规范》；
5. 《生产错误回流与封存评测数据飞轮设计》；
6. 《在线 RLHF/OPD 进入条件与停止条件》；
7. 《奖励模型离线使用、Shadow 使用与前台使用边界》。

其中前三项是近期可能需要的最小集合，后四项只有在前三项实验证明有净收益后才有施工价值。

## 七、对当前权威文档的建议

### 7.1 当前不需要修改的部分

以下原则应保持不变：

- 游戏状态是客观事实源；
- 自由文本不能静默覆盖权威世界；
- 模型和校验模型均为概率组件；
- `REPLY_FACT_CHECK_V1` 默认只运行 Shadow；
- 训练、评测和生产共用 `GAME_REPLY_CONTEXT_V1`；
- 不以规则穷举无限自然语言；
- 不为固定 60 轮测试添加专用规则。

### 7.2 后续可以补充的部分

程序状态闭环完成后，可在训练边界和生成器权威设计中补充：

1. 将事实硬门、意图覆盖和角色自然度分成不可互相补偿的评价维度；
2. 定义真实负样本的来源、版本、生产上下文哈希和人工审查证据；
3. 定义 `chosen/rejected` 对必须同输入、同模型版本或明确记录来源；
4. 规定奖励模型、Rubric Judge 和人工标准之间的校准流程；
5. 规定 DPO 前后的基座非劣化门和 Reward Hacking 检查；
6. 把评价结果用于离线数据飞轮，而不是默认接入每轮前台回复。

这些内容适合形成独立后训练权威文档，再由程序接口契约引用其边界。它们不应改变游戏世界的事实所有权。

## 八、建议决策

建议按以下顺序裁决：

1. 继续执行现有《程序施工计划：权威状态闭环 V1》，不因外部方案中断；
2. 同意研究一套独立的多维评价规范，但不立即训练奖励模型；
3. 状态闭环完成后，从真实生产同构输入收集一批模型实际负样本；
4. 先做小规模 `SFT + DPO/chosen NLL` 可证伪实验；
5. 只有偏好训练显示稳定净收益，才扩大数据和重新训练；
6. 只有离线偏好方法达到明确瓶颈，且评价器人工校准可靠，才讨论完整 RLHF 或在线 OPD。

本建议的核心不是“增加更多模型”，而是先建立一个不会反复改变口径的评价和训练闭环。
