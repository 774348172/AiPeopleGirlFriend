# LoRA 4B 前台最小输入优化提案：SYS-12S 后

> 性质：待审核优化提案，非权威设计、非施工指令。  
> 日期：2026-08-13。  
> 适用主干：`MIND_PATCH_V2 / M2 -> ApprovedHeroineState -> GAME_REPLY 纯自然语言 -> 原子提交`。  
> 本文只优化发给 LoRA 微调后 4B 模型的前台输入，不改变实时世界、女主独立记忆、连续 GameClock、条件 Critic 和原子提交合同。

## 1. 问题确认

当前一个普通玩家回合至少调用同一个本地 4B 模型两次：

```text
第一次：MIND_PATCH_V2 / M2
第二次：GAME_REPLY
```

高风险 Patch 才会在两次调用之间增加连续性审查。

当前实现虽然已经缩短了 M2 输出，并把 `GAME_REPLY` 改为纯文本输出，但两次调用的输入仍包含明显冗余：

- M2 前面仍附带完整世界、男主、角色正典和表达风格。
- `GAME_REPLY` 会读取接近完整的程序运行时对象，包括存档、身份、快照、版本、证据、计数和重复事实投影。
- 同一稳定角色信息每轮重复发送，而白未晞 LoRA 已经学习了大量稳定人格与正典。
- 审计和事务需要的数据被误当成模型理解所需的数据。

需要重新区分：

```text
LoRA 权重中已学习的稳定能力
每轮必须提供的动态语义事实
必须留在程序调用外的工程元数据
```

## 2. 核心结论

LoRA 微调不能替代动态上下文，但可以显著缩短每轮稳定角色提示。

推荐原则：

> LoRA 负责稳定人格、表达习惯和常驻正典；Runtime 只向模型提供此刻变化的语义事实；程序在调用外持有身份、版本、证据和事务元数据。

不是“因为做了 LoRA，所以什么都不输入”，也不是“为了工程可审计，把完整 Runtime 对象都输入模型”。

## 3. LoRA 可以承担的稳定内容

白未晞角色专属 LoRA 可以主要承担：

- 姓名、成年猫妖身份和基本来历。
- 外观、性格、语言风格和关系表达习惯。
- 清冷、戒备、感激、渴望温暖和家的稳定人格张力。
- 不机械卖萌、不使用助手腔等稳定表达偏好。
- 稳定能力边界和已批准正典。
- 松江府世界中长期不变的基础常识。

这些内容不需要每轮重新发送完整角色包全文。

但是 LoRA 不是权威数据库。为了防止小模型身份漂移，每次模式调用仍建议保留一个很短的稳定身份锚，例如：

```text
你是白未晞，生活在松江府的成年猫妖。保持清冷、自然、克制但不回避明确问题。
```

多角色产品中，该身份锚必须由当前激活角色包和模型工件身份共同绑定，不能只相信模型自报身份。

## 4. 每轮必须动态提供的内容

LoRA 无法提前知道或持续保存以下内容，因此每轮仍必须由 Runtime 提供：

- 当前游戏时间。
- 当前地点和场景语义。
- 男主当前的位置、活动、身体状态和持有物中与本轮有关的部分。
- 女主上一稳定状态或批准后的当前状态。
- 本轮召回的当前女主相关记忆。
- 近期已提交对白。
- 男主本轮原始对白。
- 当前允许表达的女主动作候选。

这些内容决定“此刻真实发生了什么”，不能依赖模型参数记忆。

## 5. 不应发送给模型的内容

以下内容应继续存在于 Runtime、日志、验证器和数据库中，但不应进入普通 M2 或 `GAME_REPLY` 模型输入：

- `save_id`
- `world_id`
- `protagonist_id`
- `character_id`
- `request_id`
- `snapshot_id`
- `live_world_version`
- `mind_state_version`
- `approved_mind_state_version`
- `selector_version`
- `projection_counts`
- 完整事件 ID、记忆 ID 和证据 ID
- 数据库版本、事务 ID 和哈希
- 同一个男主状态的多份重复文本与结构投影
- 只用于回复后程序校验的事实断言副本

模型不需要复制或理解这些字段。程序根据当前冻结输入在调用外绑定它们，并在模型返回后执行一致性验证。

## 6. 第一次调用：M2 最小输入

### 6.1 M2 真正需要什么

M2 只判断当前女主自身状态是否发生有意义变化，并提出有限动作候选。它需要：

- 极短角色判断锚。
- M2 固定码表与输出合同。
- 女主上一稳定状态。
- 当前最新世界语义。
- 男主当前原始对白。
- 本轮相关记忆。
- 已有动态动机和知识中与本轮有关的条目。

M2 不负责语言风格和最终对白，因此不需要完整角色生平、完整男主职业史、完整世界正典或对白文风说明。

### 6.2 推荐输入

稳定 System 前缀：

```text
你是白未晞。只判断你自己的状态是否变化，不生成回复。
M2 固定码表和结构约束……
```

动态 User 帧：

```json
{
  "p":"M2",
  "s":[
    "人形",
    "伤势恢复中",
    "平静但仍有戒备",
    "注意男主",
    "坐在窗边",
    "回应男主",
    "早期共同生活",
    "初步信任",
    "担心被赶走"
  ],
  "w":[
    "D10 21:00",
    "出租屋客厅",
    "餐桌旁",
    "正在吃面",
    "有些疲惫",
    "夜晚下雨"
  ],
  "u":"你是谁"
}
```

有相关记忆时再增加：

```json
"m":[[2,4,"男主在雨夜救下了她"]]
```

### 6.3 M2 不再输入

- 角色完整故事全文。
- 所有长期正典。
- 男主完整背景。
- 表达风格和对白长度规则。
- `save_id`、`snapshot_id`、版本号和完整证据 ID。
- 与本轮无关的动机、知识和记忆。

### 6.4 M2 输出保持不变

无变化：

```json
{"c":[],"a":[]}
```

有变化：

```json
{"c":[[2,"有些警觉",[1]]],"a":[["抬头看向男主",[1]]]}
```

M2 仍采用严格 Schema。Runtime 继续负责别名绑定、Patch 编译、版本补齐和硬不变量校验。

## 7. 第二次调用：GAME_REPLY 最小输入

### 7.1 GAME_REPLY 真正需要什么

`GAME_REPLY` 只从批准后的自己出发，对男主说一句自然语言。它需要：

- 短身份和表达锚。
- 当前时间与场景。
- 与回复有关的男主当前状态。
- `ApprovedHeroineState` 的有效语义投影。
- 本轮相关记忆陈述。
- 近期正常 `user/assistant` 对白。
- 本轮允许表达的女主动作。
- 男主本轮原始对白作为最后一条 `user` 消息。

### 7.2 推荐 System 输入

```text
你是白未晞，生活在松江府的成年猫妖。
保持清冷、自然、克制，但必须先回答男主真正问的问题。
只输出你真正说出口的话，不输出动作旁白、分析、字段或内部规则。

[当前世界]
时间：第10天 21:00
地点：出租屋客厅，夜晚下雨
男主：在餐桌旁吃面，有些疲惫

[你此刻的状态]
形态：人形
身体：伤势恢复中
情绪：平静但仍有戒备
注意：男主
活动：坐在窗边
意图：回应男主
关系：早期共同生活，已有初步信任，仍担心被赶走

[相关记忆]
无

[允许表达的动作]
无
```

然后追加近期正式对白：

```text
user: ……
assistant: ……
```

最后一条：

```text
user: 你是谁
```

模型只输出：

```text
我叫白未晞，是只猫妖。你救回来的那只白猫。
```

### 7.3 GAME_REPLY 不再输入

- 完整 Snapshot JSON。
- `mode=GAME_REPLY` 的对象字段。
- 存档、世界、角色和请求 ID。
- 世界版本和心智版本。
- 记忆选择器版本和来源 ID 数组。
- `projection_counts`。
- 程序事实断言的重复副本。
- 已由程序批准但与回复无关的完整动态映射。

### 7.4 自然语义投影不是模型决策

Runtime 只做确定性投影：

```text
完整程序对象
-> 选择本轮允许给模型看的字段
-> 使用固定模板渲染为简短语义视图
```

投影器不得：

- 根据关键词替模型判断情绪。
- 改写关系阶段语义。
- 自动补造女主意图。
- 总结出原状态中不存在的新事实。

它只能裁剪、重命名和格式化已经批准的数据。

## 8. 稳定前缀与缓存

推荐将输入分为稳定和动态两部分：

```text
M2 稳定前缀
  = 短身份锚 + M2 固定协议

M2 动态帧
  = 当前状态 + 最新世界 + 当前对白 + 相关记忆

GAME_REPLY 稳定前缀
  = 短身份锚 + 表达边界

GAME_REPLY 动态帧
  = 当前世界 + 批准状态 + 相关记忆 + 近期对白 + 当前对白
```

稳定前缀应尽量保持字节一致，以利用 llama.cpp Prompt Cache。角色包版本或协议版本变化时才更换前缀。

不能为了缓存而把已经过时的当前状态放入稳定前缀。

## 9. 模型与程序的最终边界

### 9.1 模型负责

- M2：判断女主是否自然变化、变化语义和动作候选。
- `GAME_REPLY`：从批准状态和当前世界出发自然回复。
- 理解动态事实之间的语义关系。

### 9.2 程序负责

- 存档、世界、男主和女主身份。
- 当前冻结快照和实时世界读取。
- 字段裁剪和确定性语义投影。
- 证据别名到真实 ID 的映射。
- 版本、事务、日志和审计。
- Patch 校验、条件 Critic 和原子提交。
- 回复与男主活动、位置、时间和批准状态的一致性校验。

程序不得因为输入缩短而重新引入关键词人格规则。

## 10. 不建议采用的极端方案

### 10.1 每轮什么都不输入

仅依赖 LoRA 直接发送“你是谁”会丢失当前世界、状态、记忆和关系连续性，只能得到静态角色聊天模型。

### 10.2 每轮发送完整 Runtime 对象

虽然审计最直接，但会增加输入 token、破坏自然理解、增加字段泄漏和机械复述风险，也浪费 4B 模型容量。

### 10.3 把动态状态写进 LoRA

当前活动、情绪和关系随存档持续变化，不能通过重新训练权重维护；否则每个存档都需要不同模型。

### 10.4 删除所有稳定身份锚

LoRA 仍可能发生身份漂移或受上下文干扰。保留一个短身份锚的成本很低，收益明显。

## 11. 建议施工范围

本方案获得批准后，建议作为一个完整施工块处理：

1. 新建 M2 最小 System Prompt Composer。
2. 新建 `GameReplyContextProjection`，从完整 Runtime 对象生成简短只读语义视图。
3. 修改 `build_game_reply_messages()`，不再序列化完整 `game_reply_payload()`。
4. 保留完整对象供 Runtime 校验、审计和原子提交，不删除数据库字段。
5. 增加投影器单元测试，证明不丢失当前时间、男主活动、批准女主状态和相关记忆。
6. 增加禁止字段测试，证明 ID、版本、计数和证据结构不会进入模型输入。
7. 用固定请求分别对比旧输入和最小输入的 token、首字、完整回复、身份稳定和事实一致性。

## 12. 验收指标

至少记录：

- M2 输入 token。
- `GAME_REPLY` 输入 token。
- Prompt Cache 命中情况。
- 首 token、完整回复和端到端延迟。
- M2 Patch 正确率和结构成功率。
- 当前时间、地点、男主活动和身体状态一致率。
- 批准女主状态一致率。
- 记忆使用正确率和无证据虚构率。
- 身份直答率。
- 内部字段泄漏率。
- 角色自然度和机械复述率。

最小输入不能只以 token 更少为通过标准。若状态、记忆或角色质量下降，则应恢复必要语义字段，而不是恢复工程 ID 和完整对象。

## 13. 当前建议结论

当前 LoRA 4B 前台输入可以明显缩短：

```text
M2：短身份锚 + 固定协议 + 最小动态状态帧
GAME_REPLY：短身份锚 + 自然语义当前认知视图 + 正常对白
程序外：完整身份、版本、证据、审计和事务对象
```

该方向保留了 V6 的持续状态、实时世界、独立记忆和原子提交能力，同时减少小模型读取内部工程结构的负担。

在正式施工前，需要先审核 M2 最小字段和 `GameReplyContextProjection` 的字段清单；审核通过后再同步权威设计和施工计划。
