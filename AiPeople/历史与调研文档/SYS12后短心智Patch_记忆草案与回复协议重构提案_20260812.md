# SYS-12 后短心智 Patch、记忆草案与回复协议重构提案

> 状态：待讨论、待裁决，不是当前权威设计，不直接指导施工。
>
> 形成原因：SYS-12 证明当前本地 4B 模型可以较快完成普通短文本生成，但不适合在每轮中反复生成接近最终存储结构的长 JSON。本文只提出协议重构方向；确认后才回写 V6 权威设计、施工计划和 Runtime 合同。

## 1. 要解决的问题

当前系统把模型的开放语义判断和程序的确定性数据管理混在了同一输出协议里：

- `TURN_MIND_ADVANCE` 不仅判断女主是否变化，还要复制版本、快照、证据 ID、空字段和世界断言。
- `WORLD_CONTINUITY_REVIEW` 在修订时可能再次输出完整 Patch。
- `GAME_REPLY` 不仅生成对白，还要输出快照、心智版本和程序已经知道的世界断言。
- `MEMORY_PROPOSE` 不仅判断什么值得记住，还要直接生成接近最终记忆对象的时间、证据、置信度和关系结构。

这使模型承担了两类性质不同的工作：

```text
开放语义工作：理解、判断、选择、表达
确定性工程工作：ID、版本、时间格式、证据物化、Schema 复制、数据库身份
```

重构目标不是减少人物心智和记忆能力，而是把两类工作重新分开：

> 模型只输出不可由程序提前确定的最小语义决定；程序把这些语义决定编译成完整、可验证、可持久化的 Runtime 对象。

## 2. SYS-12 实测诊断

### 2.1 心智推进

真实运行中：

| 指标 | 观测值 |
|---|---:|
| 输入 | 944～1122 token |
| 输出 | 423～520 token |
| 首个内容 | 首次约 1.4～2.0 秒；相同请求重试约 57～60 毫秒 |
| 完整输出 | 约 19.6～24.2 秒 |

相同请求重试时，输入前缀已被缓存，首个内容接近 60 毫秒，但完整输出仍约 23 秒。这说明主要瓶颈不是输入解析，而是模型被要求生成约 500 token 的结构文本。

### 2.2 记忆提议

真实运行中：

| 指标 | 观测值 |
|---|---:|
| 输入 | 551 token |
| 输出 | 359～360 token |
| 首个内容 | 首次约 1.1 秒；相同请求重试约 54～57 毫秒 |
| 完整输出 | 约 15.4～16.0 秒 |

记忆提议同样主要慢在输出。模型几乎每次写满 360 token，用约 15 秒生成嵌套对象，随后还可能因 JSON 截断或时间格式错误整体作废。

### 2.3 正式回复

真实运行中：

| 指标 | 观测值 |
|---|---:|
| 输入 | 2560～2611 token |
| 输出 | 162～176 token |
| 首个内容 | 约 4 秒 |
| 完整输出 | 约 12～13 秒 |

`GAME_REPLY` 同时受到三个因素影响：

1. 每轮重新处理较大的角色、世界、心智和记忆上下文。
2. 输出不是单纯对白，而是带版本和世界断言的 JSON。
3. 程序必须等完整 JSON 结束并校验后，才能取得 `text` 并显示。

此前约两秒的短回复探针重复使用固定短提示，能够复用提示词缓存，只证明模型具有短文本生成速度，不能代表当前完整 `GAME_REPLY` 合同。

## 3. 重构原则

### 3.1 语义最小化

模型只回答以下问题：

- 当前女主是否发生了有意义的心理、身体、活动、关系、动机或知识变化。
- 发生变化时，变化后的语义是什么，依据是哪条已提供信息。
- 当前女主应该如何自然回应。
- 哪些已经发生的内容值得形成长期记忆。

### 3.2 Runtime 编译

程序负责：

- `save_id`、`world_id`、`character_id` 和独立女主记忆库身份。
- `snapshot_id`、父版本、目标版本和事务 ID。
- 未变化字段从上一稳定状态继承。
- 最新男主位置、活动、游戏时间和世界版本断言。
- 证据别名到真实事件 ID、位置、原文和哈希的映射。
- 明确游戏时间到 RFC3339 的转换。
- 记忆 ID、版本、状态、索引和数据库提交。

程序不得根据关键词替模型决定情绪、关系、动机或记忆语义。

### 3.3 不复制确定性信息

模型输出中取消：

- `schema_version` 和 `mode` 的反复复制。
- `snapshot_id`、心智版本、世界版本和游戏时间的反复复制。
- 程序刚刚提供给模型的男主状态断言。
- 所有未变化字段的 `null` 占位。
- 长 UUID、完整事件 ID 和完整记忆 ID。

### 3.4 证据别名

程序在每次调用前建立短别名：

```json
{
  "e0": "本轮男主对白与冻结世界快照",
  "e1": "上一轮正式对白事件",
  "m0": "召回的相关记忆"
}
```

模型只输出 `e0`、`e1` 或 `m0`。程序在编译阶段映射回真实 ID，并拒绝不存在的别名。

### 3.5 以语义数量限制复杂度

协议优先限制“最多几项变化、几条记忆、几个动作”，而不是先写死一个紧贴正常输出的 token 上限。Token 上限仍然存在，但正常 P95 输出必须保留至少 30%～50% 余量。

## 4. 推荐的前台终态：一次语义回合

### 4.1 主干

普通回合不再默认串行执行“长心智 JSON、长 Critic JSON、长回复 JSON”三次调用。推荐终态为：

```text
PreparedTurnFrame
  = 上一稳定女主状态
  + 最新冻结世界快照
  + 男主当前对白
  + 精简相关记忆
  + 证据别名
        |
        v
FOREGROUND_SEMANTIC_TURN（一次模型调用）
  = 短心智变化
  + 女主动作候选
  + 从变化后的自己出发生成的对白
        |
        v
Runtime 编译完整 Patch 与世界断言
        |
        v
硬不变量校验
        |
        v
必要时触发短连续性审查
        |
        v
原子提交状态变化与对白
        |
        v
显示正式回复
```

模型按“先变化、后回复”的顺序生成，因此对白在自回归上下文中已经看见本轮变化结果，满足：

```text
上一刻的自己 + 当前对白 + 最新世界 + 相关记忆
-> 更新后的自己
-> 从更新后的自己出发回复
```

### 4.2 推荐输出草案

有变化：

```json
{
  "changes": [
    {
      "field": "emotion",
      "value": "有些担心，但不愿表现得太明显",
      "evidence": ["e0"]
    },
    {
      "field": "immediate_intent",
      "value": "提醒男主慢一点吃",
      "evidence": ["e0"]
    }
  ],
  "actions": [],
  "reply": "慢一点吃，别又呛着。"
}
```

无变化：

```json
{
  "changes": [],
  "actions": [],
  "reply": "嗯，我在听。"
}
```

该对象只承载模型的语义决定，不是最终数据库对象。

### 4.3 Runtime 编译结果

程序从短输出和冻结输入中生成完整对象：

```text
CompiledHeroineMindPatch
+ ReplyFactAssertions
+ TurnEvent identity/version
+ Evidence bindings
+ Atomic commit metadata
```

模型不再输出程序已经知道的 `snapshot_id`、版本、男主位置、男主活动和游戏时间。

### 4.4 `GAME_REPLY` 的重构

`GAME_REPLY` 必须纳入本次重构，不能只缩短心智和记忆协议。

推荐终态中，`GAME_REPLY` 的语义职责并入一次前台语义回合，模型只生成 `reply` 正文，不生成世界断言和事务元数据。

如果迁移阶段暂时保留独立 `GAME_REPLY`，则其合同应改为：

```text
输入：缓存的稳定角色前缀 + 精简动态 ReplyFrame
输出：纯女主对白文本
```

独立模式同样不得继续输出：

- `schema_version`
- `mode`
- `snapshot_id`
- `approved_mind_state_version`
- `reply_state_assertions`

这些字段都由程序从冻结快照和批准状态生成。

### 4.5 输入压缩

前台输入只保留一份权威表达：

- 男主状态不同时以 `world_state.protagonist_text` 和完整结构重复发送。
- 女主状态只发送当前有效投影，不发送数据库身份和历史计数。
- 记忆只发送当前回答真正需要的语义陈述和短别名，不发送物化元数据与完整证据对象。
- 世界、男主和角色正典组成稳定前缀，作为可缓存部分。
- 每轮变化的时间、位置、活动、当前心智和对白组成短动态帧。

后台模型任务不得无必要地破坏前台稳定前缀缓存；具体缓存隔离方式需要在施工前通过 llama.cpp 实测决定。

## 5. 短心智 Patch 协议

### 5.1 模型负责

- 判断是否变化。
- 选择变化字段。
- 给出变化后的自然语言语义。
- 指出变化依据。
- 提出女主自己的动作候选。

### 5.2 模型不负责

- 复制上一状态。
- 输出所有未变化字段。
- 写父版本、目标版本或快照 ID。
- 复制世界事实断言。
- 把证据别名展开成长 ID。
- 修改男主、游戏时间和客观场景。

### 5.3 变化字段

字段集合仍由 Runtime 定义，但模型只输出真正变化的项。初步候选为：

```text
form
body
emotion
attention
current_activity
immediate_intent
relationship.stage
relationship.trust
relationship.unresolved_tension
motive.<key>
knowledge.<key>
```

最终是否允许一轮修改多个字段、普通回合最大变化数和高影响字段审查策略，仍需后续裁决。

### 5.4 连续性审查

连续性审查也改为短决定，不再复制完整修订 Patch：

```json
{"decision":"approve"}
```

或：

```json
{
  "decision": "revise",
  "drop_changes": [1],
  "reason": "该关系变化没有足够依据"
}
```

Runtime 按变化索引删除或替换候选，再编译完整 Patch。

是否每轮都调用 Critic，存在两条候选路线：

1. 保守迁移：暂时每轮调用短 Critic，先验证协议正确性。
2. 推荐终态：硬不变量每轮校验；仅在存在状态变化、高影响变化、矛盾信号或抽样审计时调用语义 Critic。

第二条路线能显著降低正常回合延迟，但必须先用冻结测试证明不会降低连续性质量。

## 6. 简单记忆草案协议

### 6.1 模型负责

- 判断事件是否值得进入当前女主的长期记忆。
- 生成简洁、可独立理解的记忆陈述。
- 判断记忆种类、主体、确定性和时间关系。
- 选择证据别名。
- 必要时指出与已有记忆的语义关系。

### 6.2 推荐输出草案

普通事实：

```json
{
  "memories": [
    {
      "kind": "player_fact",
      "statement": "男主不喜欢香菜",
      "subject": "protagonist",
      "certainty": "asserted",
      "time_relation": "atemporal",
      "evidence": ["e0"]
    }
  ]
}
```

未来事件：

```json
{
  "memories": [
    {
      "kind": "future_event",
      "statement": "男主明天下午准备去咖啡厅",
      "subject": "protagonist",
      "certainty": "asserted",
      "time_relation": "future",
      "time_expression": "明天下午",
      "evidence": ["e0"]
    }
  ]
}
```

无长期价值：

```json
{"memories":[]}
```

与已有记忆存在关系时，才增加可选字段：

```json
"relation": {"type":"refines","target":"m0"}
```

### 6.3 程序物化

程序负责把草案转换成现有完整记忆表示：

- 填充存档、世界和女主身份。
- 生成 `memory_id`、版本、提议批次和顺序。
- 将 `e0` 映射到真实事件、原文、位置和哈希。
- 根据冻结 `GameClock` 解析明确时间表达。
- 维护生效、替代、冲突、索引和重建信息。

### 6.4 时间边界

模型不输出 RFC3339 时间。

程序只解析能够确定解释的游戏时间表达，例如“明天下午”可以相对当前游戏时间解析。无法唯一确定的表达不猜测：

```text
time_relation = future
time_expression = 过几天
resolution = ambiguous
start_at = null
```

模糊时间是合法语义，不应导致整条记忆提议失败。

### 6.5 后台失败隔离

`MEMORY_PROPOSE` 是后台派生任务，任何模型协议失败都不得终止前台对话 Runtime：

```text
提议失败
-> 记录可诊断失败
-> 进入去重的可恢复任务队列
-> 有界重试或等待下一批事件合并
-> 前台对话、世界时间和已提交状态继续运行
```

失败时不产生记忆，也不允许程序通过关键词伪造长期记忆。

## 7. 协议与存储分层

重构后明确区分三层：

```text
模型语义草案
  短、允许失败、不可信
        |
        v
Runtime 编译对象
  身份完整、时间规范、证据绑定
        |
        v
持久化对象
  版本化、可索引、可恢复、可审计
```

最终存储结构可以继续保持完整能力，但不得反向要求小模型逐字段生成相同结构。

## 8. 初步性能预算

以下是待实测目标，不是已经通过的指标：

| 协议 | 正常输出目标 | 上限原则 |
|---|---:|---|
| 单次前台语义回合 | Patch、动作和对白合计通常 80～180 token | P95 与硬上限至少保留 30% 余量 |
| 独立短心智 Patch | 通常 20～100 token | 无变化必须极短 |
| 短 Critic | approve 通常低于 20 token；revise 通常低于 80 token | 不复制完整 Patch |
| 记忆草案 | 空结果低于 20 token；单条通常低于 100 token | 最多两条，不复制证据原文 |

前台正式验收必须同时记录：

- 静态短提示模型速度。
- 真实动态输入的首个 token 和完整输出。
- 玩家真正看到已提交回复的端到端延迟。
- 输入 token、输出 token、缓存命中和重试次数。
- 有状态变化与无状态变化两类回合。

## 9. 验证方法

使用同一套冻结输入比较三种协议：

```text
基线 A：当前长结构三段链
候选 B：短 Patch + 短 Critic + 纯文本 GAME_REPLY
候选 C：一次前台语义回合 + 必要时短 Critic
```

至少比较：

- 状态连续性正确率。
- 男主和世界事实一致性。
- 角色语言质量。
- 记忆提议准确率和重复率。
- 结构成功率与重试率。
- 首字、完整输出和玩家可见端到端延迟。
- 60 轮冻结工作负载完成率。
- 一小时队列、崩溃和恢复结果。

不能只因为候选 C 更快就采用；必须同时证明它仍然从更新后的自己出发回复，并且不会让状态、对白和原子提交发生分裂。

## 10. 待裁决问题

1. 正常前台终态是否确认采用一次语义回合，而不是固定三次模型调用。
2. 一次语义回合中最多允许多少个 `changes`。
3. 哪些字段属于高影响变化，必须触发语义 Critic。
4. Critic 在迁移期每轮执行，还是直接采用条件触发。
5. 女主动作候选是否与对白一起输出，以及每轮最大数量。
6. 记忆草案最小枚举集合如何定义。
7. 哪些游戏时间表达由程序确定性解析，哪些保持模糊。
8. 原子提交前是否始终缓冲完整对白；如果未来需要流式显示，应另行设计可恢复的显示与提交合同。

## 11. 建议决策顺序

1. 先确认“模型语义草案、Runtime 编译、持久化对象”三层边界。
2. 再确认前台采用一次语义回合还是短双阶段。
3. 冻结短心智、短 Critic、回复和记忆草案四个协议。
4. 回写 V6 权威设计和系统施工计划。
5. 施工后先做协议级冻结对比，再重跑同一 SYS-12 60 轮和一小时验收。

在以上设计获得裁决前，不应通过单纯提高 520/360 token 上限、扩大超时或增加重试次数来冻结发布栈。

## 12. 整体优化方案汇总

本节集中记录当前推荐的完整优化路线。M1/R1 的完整码表、输入输出合同、Decoder、缓存和日志要求统一收录在本文第 13～15 章，不再维护独立子提案。

### 12.1 重新划分模型与程序职责

核心原则：

> 模型只负责开放语义判断，程序负责确定性结构。

模型负责：

- 判断女主状态是否自然变化。
- 选择真正发生变化的状态。
- 生成变化后的心理、身体、活动、关系、动机或知识语义。
- 从更新后的自己出发生成自然回复。
- 判断已经发生的内容是否值得当前女主长期记住。
- 生成长期记忆的核心语义和必要关系。

程序负责：

- 存档、世界、男主和激活女主身份。
- 女主独立记忆 Repository 的选择和隔离。
- 快照 ID、父版本、目标版本和事务 ID。
- 精确游戏时间、世界版本和男主程序状态断言。
- 未变化状态从上一稳定状态继承。
- 证据别名到真实事件 ID、原文、位置和哈希的映射。
- 明确游戏时间表达的解析和 RFC3339 物化。
- 数据库对象、索引、原子提交和崩溃恢复。

程序不得根据关键词替模型决定情绪、关系、动机和记忆语义。模型也不再负责复制程序已经确定的数据。

### 12.2 合并正常前台模型调用

当前固定主干：

```text
TURN_MIND_ADVANCE
-> WORLD_CONTINUITY_REVIEW
-> GAME_REPLY
```

会让同一个本地模型多次读取相近上下文，并分别生成长结构。

推荐终态：

```text
上一稳定女主状态
+ 最新冻结世界状态
+ 男主当前对白
+ 当前女主相关记忆
        |
        v
一次前台语义调用
        |
        +-> 短状态变化
        +-> 女主动作候选
        +-> 从变化后的自己出发生成的回复
        |
        v
Runtime 编译完整 Patch 和世界断言
        |
        v
硬不变量校验
        |
        v
必要时短 Critic
        |
        v
原子提交状态与对白
```

模型输出顺序必须先包含状态变化，再包含回复。由于模型是自回归生成，后面的回复已经看见本轮变化结果，从而实现：

```text
上一刻的自己 + 当前对白 + 最新世界 + 相关记忆
-> 更新后的自己
-> 从更新后的自己出发回复
```

### 12.3 使用短心智 Patch

模型只输出真正变化的字段，不输出全部状态和大量 `null`：

```json
{
  "c": [
    [2, "有些担心，但不愿表现得太明显", [1]],
    [5, "提醒男主慢一点吃", [0, 1]]
  ],
  "r": "慢一点，别烫着。"
}
```

其中：

```text
2 -> emotion
5 -> immediate_intent
0 -> 本轮冻结世界快照
1 -> 男主当前对白
```

没有变化时：

```json
{
  "c": [],
  "r": "嗯，我在听。"
}
```

`c:[]` 表示模型明确判断无变化。程序只继承上一稳定状态，不能自行创造变化。

### 12.4 重构正式回复协议

`GAME_REPLY` 必须与心智和记忆一起重构。

推荐终态中，正式回复合并进一次前台语义调用，只输出自然对白字段 `r`。模型不再输出：

- `schema_version`
- `mode`
- `snapshot_id`
- `approved_mind_state_version`
- 男主位置和活动断言
- 世界版本
- 游戏时间
- 事务元数据

如果迁移期暂时保留独立 `GAME_REPLY`，也应只接收精简的动态 `ReplyFrame` 并输出纯女主对白，不再输出 JSON 元数据。

程序仍然在显示前执行原子提交。是否未来支持生成过程中的玩家可见流式回复，需要另行设计显示与事务恢复合同，不能在本次协议重构中静默改变。

### 12.5 连续性审查改为短协议和风险触发

程序每轮执行硬不变量校验：

- 禁止修改男主状态。
- 禁止修改游戏时间。
- 禁止修改客观世界事实。
- 禁止引用不存在的证据别名。
- 禁止访问其他女主记忆。
- 禁止输出未知状态字段和协议代码。

语义 Critic 不再复制完整修订 Patch，只输出短决定：

```json
{"d": 1}
```

或：

```json
{
  "d": 2,
  "drop": [1]
}
```

建议代码：

```text
1 -> approve
2 -> revise
3 -> reject
```

推荐终态中，语义 Critic 只在以下情况触发：

- 本轮确实存在心智变化。
- 关系阶段、信任等高影响字段变化。
- 一轮变化字段过多。
- 新旧状态存在潜在矛盾。
- 模型输出出现语义风险信号。
- 按固定比例进行质量抽样审计。

迁移期可以先保留每轮短 Critic，用冻结测试确认条件触发不会降低连续性质量，再切换到风险触发。

### 12.6 使用简单长期记忆草案

记忆模型只决定：

- 当前事件是否值得长期记住。
- 记忆的核心陈述。
- 记忆种类、主体、确定性和时间关系。
- 使用哪些来源事件。
- 是否替代、矛盾或细化已有记忆。

例如：

```json
{
  "m": [
    [2, "男主不吃香菜", 1, 1, 0, [0]]
  ]
}
```

解释：

```text
2 -> preference_boundary
1 -> protagonist
1 -> asserted
0 -> atemporal
[0] -> 来源事件 0
```

程序负责生成：

- `memory_id`、版本和女主独立 Repository 身份。
- 证据真实事件 ID、原文、位置和哈希。
- RFC3339 游戏时间、时区和精度。
- 提议批次、状态和数据库生命周期。
- Embedding、Reranker 索引和重建数据。
- 替代、矛盾和细化关系的最终物化。

模型不再输出完整时间对象、时区、证据原文副本、事件哈希、浮点置信度和为了满足 Schema 而生成的长 `semantic_reason`。

### 12.7 使用 M1 / R1 版本化码表

协议压缩采用：

```text
顶层短键名
+ 重复记录固定位置元组
+ 有限枚举数字代码
+ 开放语义自然语言
```

可以编码：

```text
5 -> immediate_intent
0 -> atemporal
2 -> preference_boundary
```

不能编码：

```text
“有些担心，但不愿表现出来”
“提醒男主慢一点吃”
“男主不吃香菜”
```

`M1` 和 `R1` 使用独立命名空间和 Decoder。未知版本、未知代码、错误数组长度和越界证据必须拒绝，不能猜测。

码表放入稳定系统前缀，不应每轮作为动态输入完整重复发送。已有版本的代码含义不得静默改变；不兼容变更必须建立 `M2` 或 `R2`。

### 12.8 压缩模型输入并优化稳定前缀

每轮只发送一份权威信息：

- 男主状态只发送一次，删除文本投影和结构对象之间的重复。
- 女主只发送当前有效状态，不发送数据库身份、版本和历史计数。
- 相关记忆只发送回答需要的语义陈述和短别名，不发送完整物化对象。
- 空的动机、知识和记忆字段允许省略。
- 角色正典、世界边界和 M1/R1 码表形成稳定前缀。
- 当前时间、当前状态、男主对白和相关记忆形成短动态帧。

Prompt Cache 不能只靠理论判断。需要在目标 `llama.cpp` 推理槽上测量不同模式切换是否破坏前台稳定前缀缓存，并决定是否需要前台专用槽或其他缓存隔离策略。

### 12.9 隔离后台失败

`MEMORY_PROPOSE`、回答后整理和五分钟整理属于后台派生任务。失败时：

```text
记录明确失败
-> 不产生错误状态或记忆
-> 放入去重的可恢复任务队列
-> 有界重试或与下一批事件合并
-> 前台对话继续
-> GameClock 和程序世界继续运行
```

后台异常不得突破 Worker 边界并终止前台 Runtime。失败时也不得通过关键词规则伪造角色心智或长期记忆。

### 12.10 冻结对比与验收

使用同一套冻结输入比较：

```text
A：当前长结构三段链
B：短 Patch + 短 Critic + 纯文本 GAME_REPLY
C：一次前台语义调用 + 条件短 Critic
```

M1/R1 协议内部再比较：

```text
A1：可读短对象
B1：短键名 + 数字枚举对象
C1：顶层短对象 + 固定位置元组
```

必须同时测量：

- 心智状态连续性和自然变化正确率。
- 男主、游戏时间和世界事实一致性。
- 回复角色质量和语言自然度。
- 记忆准确率、遗漏率、重复率和关系错误率。
- 协议结构成功率和重试率。
- 输入 token、输出 token 和缓存命中情况。
- 首 token、完整生成和玩家可见端到端延迟。
- 无变化和空记忆结果的稳定性。
- 60 轮冻结工作负载完成率。
- 一小时队列、崩溃、恢复和资源结果。

采用更短协议的前提是语义正确率和结构稳定性不下降。固定位置元组如果使 4B 模型明显混淆，应退回短键名对象，不为少量 token 牺牲角色和状态正确性。

### 12.11 当前推荐路线

当前综合推荐为：

```text
一次前台语义调用
+ M1 短心智与回复协议
+ Runtime 硬不变量校验
+ 条件触发短 Critic
+ 后台 R1 记忆语义草案
+ Runtime 编译完整状态与记忆对象
+ 后台失败隔离
```

该路线不是削弱人物心智和记忆能力，而是让模型集中处理不可预先枚举的语义判断，让程序承担它更擅长且可以完全确定的数据工作。

## 13. M1：前台心智与回复详细协议

### 13.1 协议定位

`M1` 对应推荐的一次前台语义回合：模型先输出本轮心智变化，再从变化后的自己出发输出正式对白。

`M1` 采用：

```text
顶层短键名 JSON 对象
+ 重复记录固定位置元组
+ 有限枚举数字代码
+ 开放语义自然语言
```

固定协议结构可以编码；人物心理、意图、动作和对白不能编码成规则枚举。

### 13.2 输入顶层键

| 键 | 含义 | 必需 |
|---|---|---|
| `p` | 协议版本，固定为 `M1` | 是 |
| `s` | 当前女主状态固定数组 | 是 |
| `o` | 当前动机列表 | 否 |
| `k` | 当前知识列表 | 否 |
| `w` | 本轮冻结世界状态固定数组 | 是 |
| `u` | 男主当前对白 | 是 |
| `m` | 本轮相关记忆列表 | 否 |

`o`、`k`、`m` 为空时可以省略。`s` 和 `w` 的位置定义固定，不能根据内容移动字段。

协议版本由请求路由和日志持有。为便于调试，候选协议暂在输入中保留 `p:"M1"`；正式冻结时应实测保留或移除这一字段对稳定性的影响。

### 13.3 女主状态数组 `s`

| 位置 | 完整字段 |
|---:|---|
| 0 | `form` |
| 1 | `body` |
| 2 | `emotion` |
| 3 | `attention` |
| 4 | `current_activity` |
| 5 | `immediate_intent` |
| 6 | `relationship.stage` |
| 7 | `relationship.trust` |
| 8 | `relationship.unresolved_tension` |

状态值使用简短自然语言。例如：

```text
emotion = 平静，和男主相处时稍微放松
immediate_intent = 安静陪着男主
relationship.trust = 对男主仍有戒备，但愿意接近
```

不能把情绪、信任和关系语义压缩成有限数字等级，否则会把开放心智重新退化成规则状态机。

### 13.4 世界状态数组 `w`

| 位置 | 含义 |
|---:|---|
| 0 | 当前游戏时间的模型可读短表示 |
| 1 | 当前场景名称 |
| 2 | 男主位置 |
| 3 | 男主活动 |
| 4 | 男主身体状态 |
| 5 | 女主位置 |
| 6 | 回答所需的场景简述 |

例如：

```json
[
  "D10 19:32",
  "出租屋餐桌旁",
  "餐桌旁",
  "正在吃面",
  "正常",
  "餐桌旁",
  "男主和白未晞坐在餐桌旁"
]
```

`D10 19:32` 只是模型可读的游戏时间短表示。Runtime 仍然持有精确、持续运行的权威 `GameClock`。

模型不接收也不回传：

- `save_id`
- `world_id`
- `snapshot_id`
- 世界版本
- 心智版本
- RFC3339 时间
- 数据库事务信息

这些信息由 Runtime 在模型调用外持有。

### 13.5 动机与知识列表

动机和知识使用键值元组：

```json
{
  "o": [
    ["home_need", "渴望拥有稳定的家"]
  ],
  "k": [
    ["food.no_coriander", "男主不吃香菜"]
  ]
}
```

动态键由 Runtime 管理，语义值由模型理解。正式协议需要限制列表数量，只发送本轮相关项，不发送全部动机和知识投影。

### 13.6 相关记忆列表 `m`

相关记忆使用：

```text
[证据别名, 记忆种类代码, 记忆陈述]
```

例如：

```json
{
  "m": [
    [2, 2, "男主不吃香菜"]
  ]
}
```

M1 证据别名分配：

| 别名 | 来源 |
|---:|---|
| 0 | 本轮冻结世界快照 |
| 1 | 男主当前对白 |
| 2 及以后 | `m` 中按顺序提供的相关记忆或事件 |

模型只输出数字别名。Runtime 将其映射回真实快照、事件和记忆 ID。

### 13.7 M1 完整输入例子

```json
{
  "p": "M1",
  "s": [
    "人形",
    "身体正常，坐在桌边",
    "平静，和男主相处时稍微放松",
    "留意男主",
    "坐在桌边看男主吃面",
    "安静陪着男主",
    "开始信任",
    "对男主仍有戒备，但愿意接近",
    "不习惯直接表达关心"
  ],
  "w": [
    "D10 19:32",
    "出租屋餐桌旁",
    "餐桌旁",
    "正在吃面",
    "正常",
    "餐桌旁",
    "男主和白未晞坐在餐桌旁"
  ],
  "u": "这面有点烫，不过挺好吃。"
}
```

### 13.8 输出顶层键

| 键 | 含义 | 必需 |
|---|---|---|
| `c` | 本轮状态变化列表；无变化时为 `[]` | 是 |
| `a` | 女主动作候选；没有动作时可以省略 | 否 |
| `r` | 唯一可见女主对白 | 是 |

保留必需的 `c:[]`，而不是用字段缺失表示无变化。这样可以区分：

```text
模型明确判断无变化
与
模型漏写变化字段
```

### 13.9 固定状态变化元组

普通字段变化：

```text
[字段代码, 新语义值, 证据别名数组]
```

字段代码：

| 代码 | 完整字段 |
|---:|---|
| 0 | `form` |
| 1 | `body` |
| 2 | `emotion` |
| 3 | `attention` |
| 4 | `current_activity` |
| 5 | `immediate_intent` |
| 6 | `relationship.stage` |
| 7 | `relationship.trust` |
| 8 | `relationship.unresolved_tension` |
| 9 | `motive_state` 中的动态键 |
| 10 | `knowledge_state` 中的动态键 |

代码 9 和 10 使用四项元组：

```text
[字段代码, 动态键, 新语义值, 证据别名数组]
```

例如：

```json
[9, "home_need", "更希望把这里当成自己的家", [1, 2]]
```

### 13.10 女主动作元组

动作使用：

```text
[动作描述, 证据别名数组]
```

例如：

```json
{
  "a": [
    ["把水杯轻轻推到男主手边", [0, 1]]
  ]
}
```

动作只是女主自己的动作候选：

- 不能替男主行动。
- 不能修改男主程序状态。
- 不能声称程序世界中尚未发生的客观结果已经完成。
- 原子提交后，动作表现如何进入游戏事件账本需要保留现有受控动作边界。

### 13.11 M1 完整输出例子

```json
{
  "c": [
    [5, "提醒男主慢一点吃，避免烫到", [0, 1]]
  ],
  "r": "烫就慢一点，没人和你抢。"
}
```

Runtime 解码：

```text
5 -> immediate_intent
0 -> 本轮冻结世界快照
1 -> 男主当前对白
```

然后由 Runtime：

- 从上一稳定状态继承所有未变化字段。
- 生成完整 `HeroineMindPatch`。
- 填充快照 ID、父版本和目标版本。
- 生成男主位置、活动、世界版本和游戏时间断言。
- 执行硬不变量与必要的连续性审查。
- 原子提交状态变化、动作和对白。

### 13.12 M1 无变化输出

```json
{
  "c": [],
  "r": "嗯，我在听。"
}
```

这表示模型明确判断当前稳定心智无需变化。程序不能根据对白关键词补造状态变化。

### 13.13 M1 输出边界

初步建议：

- 普通回合最多 3 个变化。
- 女主动作最多 2 个。
- 每个自然语言状态值设置合理字符上限。
- 回复长度按角色对话需求单独限制，不与 Patch 共用一个紧贴正常输出的 token 上限。
- 正常 P95 输出与硬 token 上限至少保留 30%～50% 余量。

以上数量属于待冻结参数，必须通过真实模型测试确认。

## 14. R1：长期记忆语义草案详细协议

### 14.1 协议定位

`R1` 只判断当前女主自己的独立记忆库中应增加什么长期语义，不直接生成最终数据库对象。

模型负责：

- 判断当前已提交事件是否具有长期价值。
- 生成简洁、可以独立理解的记忆陈述。
- 判断记忆种类、主体、确定性和时间关系。
- 选择来源事件。
- 必要时提出与已有记忆的语义关系。

Runtime 负责最终记忆身份、版本、证据、时间、生命周期和索引。

### 14.2 输入顶层键

| 键 | 含义 | 必需 |
|---|---|---|
| `p` | 协议版本，固定为 `R1` | 是 |
| `n` | 当前游戏时间的模型可读短表示 | 是 |
| `e` | 已提交来源事件列表 | 是 |
| `m` | 可能相关的现有记忆列表 | 否 |

来源事件元组：

```text
[事件别名, 说话者代码, 正文]
```

说话者代码：

| 代码 | 含义 |
|---:|---|
| 0 | 程序世界或客观事件 |
| 1 | 男主 |
| 2 | 当前女主 |
| 3 | 第三方角色 |

现有记忆元组：

```text
[记忆别名, 记忆种类代码, 记忆陈述]
```

事件别名和记忆别名属于不同字段命名空间：

- 证据只能指向 `e`。
- 记忆关系目标只能指向 `m`。

### 14.3 R1 完整输入例子

```json
{
  "p": "R1",
  "n": "D10 19:36",
  "e": [
    [0, 1, "以后煮面别放香菜，我一直都不吃香菜。"],
    [1, 2, "知道了。"]
  ],
  "m": [
    [0, 1, "男主喜欢吃面"]
  ]
}
```

### 14.4 记忆种类代码

| 代码 | 完整种类 |
|---:|---|
| 1 | `player_fact` |
| 2 | `preference_boundary` |
| 3 | `person_relation` |
| 4 | `shared_experience` |
| 5 | `relationship_meaning` |
| 6 | `future_event` |
| 7 | `unfinished_topic` |
| 8 | `character_self_claim` |

种类代码需要经过正式记忆测试集复核。当前集合继承现有记忆语义，不代表已经冻结。

### 14.5 主体代码

| 代码 | 完整主体 |
|---:|---|
| 1 | `protagonist` |
| 2 | `heroine` |
| 3 | `both` |
| 4 | `relationship` |
| 5 | `third_party` |

第三方主体的具体实体身份由输入事件和 Runtime 物化决定，不能只靠数字 5 丢失实体信息。涉及第三方时，记忆元组需要增加可选的主体名称或实体别名，具体格式待测试冻结。

### 14.6 确定性代码

| 代码 | 完整含义 |
|---:|---|
| 1 | `asserted` |
| 2 | `uncertain` |
| 3 | `hypothetical` |
| 4 | `joking` |
| 5 | `quoted` |

确定性是开放语义判断的一部分，必须由模型决定，Runtime 只能校验代码是否合法。

### 14.7 时间关系代码

| 代码 | 完整含义 |
|---:|---|
| 0 | `atemporal` |
| 1 | `past` |
| 2 | `present` |
| 3 | `future` |
| 4 | `unknown` |

`temporal`、`resolution`、`timezone`、`start_at` 和 `end_at` 不再由模型完整生成。模型只输出语义时间关系和必要的原始时间表达，Runtime 根据权威 `GameClock` 解析。

### 14.8 基础记忆元组

基础格式：

```text
[种类, 陈述, 主体, 确定性, 时间关系, 证据事件别名数组]
```

普通偏好：

```json
{
  "m": [
    [2, "男主不吃香菜", 1, 1, 0, [0]]
  ]
}
```

Runtime 解码：

```text
2 -> preference_boundary
1 -> protagonist
1 -> asserted
0 -> atemporal
证据事件 0 -> 男主原始对白
```

### 14.9 带时间表达的记忆元组

第七项只在存在有意义的时间原文时出现：

```text
[种类, 陈述, 主体, 确定性, 时间关系, 证据, 时间原文]
```

例如：

```json
{
  "m": [
    [6, "男主明天下午准备去咖啡厅", 1, 1, 3, [0], "明天下午"]
  ]
}
```

Runtime 根据当前游戏时间解析“明天下午”。如果表达无法唯一确定，则合法保存：

```text
relation = future
source_text = 过几天
resolution = ambiguous
start_at = null
```

模糊时间是合法语义，不能导致整条记忆提议失败。

### 14.10 与已有记忆的关系

第八项是可选关系元组：

```text
[关系代码, 目标记忆别名]
```

关系代码：

| 代码 | 含义 |
|---:|---|
| 1 | `supersedes` |
| 2 | `contradicts` |
| 3 | `refines` |

如果存在关系但没有时间原文，第七项必须显式为 `null`，避免位置歧义：

```json
{
  "m": [
    [2, "男主只是不吃生香菜，熟香菜可以接受", 1, 1, 0, [0], null, [3, 0]]
  ]
}
```

是否允许单条记忆同时提出多个关系，需要通过真实记忆案例决定。R1 初版建议最多一个关系，减少4B模型结构负担。

### 14.11 R1 空结果

```json
{"m": []}
```

这表示模型明确判断当前事件没有长期记忆价值。程序不得根据关键词自行制造记忆。

### 14.12 Runtime 记忆物化

Runtime 从 R1 草案生成完整记忆对象：

- 当前存档、世界和女主独立 Repository 身份。
- `memory_id`、版本、提议批次和顺序。
- 证据真实事件 ID、原文、角色、位置和哈希。
- 时间解析结果、游戏时区和精度。
- 生效、替代、矛盾和细化关系。
- Embedding、Reranker 索引和重建数据。

模型不再输出：

- RFC3339 时间。
- 时区。
- 证据原文的重复副本。
- 事件哈希。
- 数据库 ID 和版本。
- 浮点置信度。
- 为填充 Schema 而生成的 `semantic_reason`。

取消置信度和 `semantic_reason` 属于当前推荐，仍需使用现有记忆质量集验证是否会损失必要信息。

### 14.13 R1 输出边界

初步建议：

- 每批最多 2 条长期记忆。
- 每条记忆只保留一个核心陈述。
- 每条最多引用 2 个来源事件。
- 每条最多提出 1 个与已有记忆的关系。
- 无长期价值时必须稳定输出 `{"m":[]}`。
- 正常单条记忆输出应显著低于硬 token 上限。

这些参数属于待冻结配置，不是最终权威数字。

## 15. M1/R1 共同工程合同

### 15.1 协议三层结构

```text
模型协议 M1 / R1
  短、版本化、只包含语义决定
        |
        v
Protocol Decoder
  解码数字、验证位置、绑定证据别名
        |
        v
Runtime Compiler
  补齐身份、版本、时间、证据和事务信息
        |
        v
完整持久化对象
```

最终数据库结构可以保持完整，但不得反向要求模型逐字段生成相同结构。

### 15.2 独立代码空间

数字代码依赖协议、字段和位置解释：

```text
M1.s[2] 中的 2 是状态数组位置 emotion
M1.c[*][0]=2 表示修改 emotion
R1.m[*][0]=2 表示 preference_boundary
R1.m[*][2]=2 表示 heroine
```

数字可以在不同命名空间重复，但同一命名空间中的含义必须永久稳定。Runtime 不得脱离协议版本和字段位置解释数字。

### 15.3 版本规则

- `M1` 和 `R1` 一经冻结，已有代码含义不得修改。
- 新增不兼容字段时建立 `M2` 或 `R2`。
- Runtime 根据调用路由加载固定 Decoder。
- 请求、日志和模型工件 Manifest 必须记录协议版本。
- 未知版本或未知代码必须拒绝，禁止猜测。
- 同一正式发布版本不能长期并行维护两套具有相同职责的活跃协议。

### 15.4 结构校验

Decoder 必须校验：

- 顶层键只能来自当前协议定义。
- 固定数组长度和元素类型正确。
- M1 普通变化元组为 3 项，动态键变化为 4 项。
- R1 记忆元组只能使用规定的 6、7 或 8 项形式。
- 自然语言值非空且有长度上限。
- 数组数量不超过模式配置。

JSON Schema 应使用 `prefixItems` 校验固定位置数组，不能只靠 Prompt 要求模型遵守。

### 15.5 代码校验

- 字段、枚举和关系代码必须存在于当前协议版本。
- 未知数字直接返回协议错误。
- 不允许用 M1 字典解释 R1 代码，反之亦然。
- 动态动机和知识键必须符合 Runtime 允许的键格式。
- Decoder 只解码，不得替模型修正未知代码的语义。

### 15.6 证据校验

- M1 证据别名必须存在于本轮冻结输入。
- R1 证据只能引用本次 `e` 中的已提交事件。
- R1 关系目标只能引用本次 `m` 中当前女主已有记忆。
- Decoder 映射到真实 ID 后，继续执行现有证据边界校验。
- 任何证据越界都不得通过相似文本或关键词猜测修复。

### 15.7 语义硬边界

- M1 不得产生男主、游戏时间或客观世界 Patch。
- M1 只能表达当前激活女主自己的状态和动作。
- R1 只能访问和写入当前女主独立记忆库。
- R1 不得将其他女主私有记忆作为证据或关系目标。
- 程序只编译模型决定，不根据关键词补造情绪、关系和记忆。
- 编码压缩不能成为重新引入规则型人格状态机的理由。

### 15.8 Prompt 与缓存

推荐上下文结构：

```text
稳定系统前缀
  = 角色正典
  + 唯一游戏世界边界
  + M1 或 R1 固定码表
  + 固定输出规则

动态用户帧
  = 当前短状态
  + 最新冻结世界
  + 当前对白或已提交事件
  + 相关记忆
```

要求：

- 码表不能每轮在动态输入中完整重复。
- 角色和世界正典只保留回答需要的稳定表达，删除重复投影。
- 不同模式切换可能破坏前缀缓存，必须在目标 llama.cpp 配置上实测。
- 是否为前台 M1 保留专用推理槽或缓存区，必须通过显存和延迟共同裁决。
- 未来训练数据可以加入 M1/R1 样本，但训练前后必须使用相同冻结协议集对比。

### 15.9 可观测性

生产日志应保存：

```text
协议版本
模型原始短输出
Decoder 解码结果
Runtime 编译后的完整对象
输入和输出 token
首 token 与完整输出延迟
Prompt Eval 和可用缓存指标
重试次数
失败阶段和失败代码
```

人工调试页面默认展示解码后的可读字段，同时允许展开查看原始编码。否则数字协议会增加问题定位成本。

### 15.11 性能预期边界

按 SYS-12 中当前模型约 22 token/秒的生成速度估算：

```text
减少 100 个输出 token，理论上约减少 4.5 秒
减少 300 个输出 token，理论上约减少 13.5 秒
```

但 M1/R1 码表不能单独解决旧 520-token 心智结构。优化顺序必须是：

1. 删除不应由模型生成的确定性结构。
2. 合并正常前台模型调用，减少重复上下文处理。
3. 使用 M1/R1 压缩剩余语义协议。
4. 优化稳定前缀和真实缓存命中。

不能把旧长 Schema 原样换成数字字段后宣布重构完成。

### 15.12 M1/R1 冻结对比

使用相同冻结输入比较：

```text
A：可读短对象协议
B：短键名 + 数字枚举对象协议
C：顶层短对象 + 固定位置元组协议
```

分别测量：

- 输入和输出 token。
- 首 token 与完整输出延迟。
- JSON 与 Schema 成功率。
- 代码和位置混淆率。
- 证据别名错误率。
- 状态变化语义正确率。
- 回复角色质量和世界一致性。
- 记忆准确率、遗漏率、重复率和关系错误率。
- 无变化与空记忆输出稳定率。

冻结条件：

- C 的语义正确率不得低于 A。
- C 的协议成功率不得低于 A。
- C 必须带来可重复的端到端延迟收益，而不只是字符减少。
- 如果固定位置元组使 4B 模型明显混淆，则退回 B，不为少量 token 牺牲语义稳定性。

### 15.13 合并后的待裁决问题

1. 是否确认采用“顶层短对象 + 内部固定元组”的混合格式。
2. M1 是否正式采用一次前台语义回合，同时输出变化和对白。
3. M1 的 `s`、`w` 固定位置是否足够，是否缺少必需状态。
4. M1 一轮最多允许几个变化和动作。
5. 哪些 M1 变化属于高影响字段并触发 Critic。
6. R1 是否正式取消模型输出置信度和 `semantic_reason`。
7. R1 证据绑定完整来源事件是否足够，还是需要模型选择具体句段。
8. R1 的种类、主体、确定性、时间和关系枚举是否需要调整。
9. 第三方主体如何在不增加过多 token 的情况下保留实体身份。
10. 固定位置协议是否先作为候选 C 测试，通过后再成为正式合同。

## 16. 统一决策与实施顺序

1. 先裁决“模型语义草案、Runtime 编译、持久化对象”三层边界。
2. 再裁决正常前台采用一次 M1 调用还是短双阶段。
3. 冻结 M1、短 Critic 和 R1 的候选协议。
4. 使用可读对象、数字对象和固定元组三组冻结测试选择最终格式。
5. 回写 V6 权威设计、系统施工计划、RuntimeConfig 和正式 Schema。
6. 施工后先做协议级对比，再重跑同一 SYS-12 60 轮和一小时验收。

在上述设计获得裁决前，不应通过提高 token 上限、扩大超时或增加重试次数来冻结发布栈，也不应让 M1/R1 与当前旧 Schema 长期并列为两套正式协议。
