# 模型驱动持续当下认知方案调研

> 状态：研究提案 V1，非权威设计，不得直接施工；已由《模型驱动持续当下认知方案调研 V2》细化取代  
> 记录日期：2026-08-08  
> 研究问题：能否主要依靠模型，而不是持续扩张人工 schema 和规则，解决人物当前身心状态与世界当前状态的一致性问题。  
> 初步结论：可将主模型训练成“持续心智状态转换器”，由模型维护自然语言形式的当下自我与情境理解；程序只承担感知输入、持久化、外部事实来源和极少数安全不变量。状态变化权力、连续性否决权和事务提交权的具体划分以后续 V2 为准。

## 1. 对问题的重新定义

问题不应被定义为“系统还缺少多少状态字段”，而应定义为：

> 模型每次生成回复时，并没有真正继承上一时刻的内部处境，只是在重新阅读一批资料后临时扮演秦未晞。

普通聊天模型近似执行：

```text
persona + memories + user_message -> reply
```

它缺少明确的递归变量：

```text
previous_mind_state + new_observation -> next_mind_state + reply
```

因此“正在弹琴”“心情很好”“刚才被玩家惹恼”“今天是什么日期”都只是上下文中的若干文本，不是模型必须连续演进的自身状态。

## 2. 核心方案：持续心智表征

引入由模型维护的 `LivingMind`。它不是固定槽位表，也不是事实数据库，而是一段短小、自然语言、第一人称、可递归更新的内部处境描述。

示例：

```text
现在是周六晚上，我还坐在客厅钢琴前，刚把同一小节重复了几遍。
手腕有一点酸，但整体状态不错。我因为终于弹顺了一些而心情轻快，
注意力仍主要在琴上，也愿意听浩然说话。刚才没有发生让我情绪明显转坏的事。
我大概还会再弹一会儿，但没有必须完成的明确时间点。
```

这里没有要求开发者事先枚举“活动兼容矩阵”“情绪标签全集”或所有身体状态。模型依靠已经学到的语言、常识和人物逻辑理解：

- 弹琴和简短聊天可以同时发生。
- 弹琴和正在睡觉不能同时发生。
- 心情可以复杂、混合和逐渐变化。
- “把琴盖合上再去吃面”是合理过渡，不是冲突。
- 没有新的刺激时，不应毫无原因地从轻快跳到极度低落。

## 3. 模型成为状态转换器

每轮不再只要求模型生成回复，而是让模型完成一次心智推进：

```text
MindTransition(
    previous_living_mind,
    new_perception,
    selected_memories
) -> {
    next_living_mind,
    private_response_intent,
    visible_reply
}
```

### 3.1 输入：上一刻心智

`previous_living_mind` 是上一轮已经接受的自然语言状态。它代表模型此刻认为自己：

- 正在经历什么。
- 身体和注意力是什么状态。
- 对当前事件有什么感受。
- 如何理解玩家与周围环境。
- 接下来倾向做什么。
- 哪些事情不确定。

它不是永久事实；永久证据仍留在追加式账本。它相当于可以由历史重建的模型工作心境。

### 3.2 输入：新感知

程序不解释生活，只提供模型无法自行感知的观察：

```text
PerceptionPacket
- 当前绝对时间与时区
- 距离上次心智推进经过多久
- 玩家本轮原话
- 应用启动、恢复、关闭或交互事件
- 有可信来源的外部观察
- 本轮召回的相关经历
```

关键区别是：程序只告诉模型“看见了什么”，不告诉模型“应该如何感受、当前应该是什么活动、哪些生活动作互斥”。解释与演进交给模型。

### 3.3 输出：下一刻心智

模型先在内部形成 `next_living_mind`，再根据它回复。这样回复不是直接从零生成，而是从刚刚更新过的自身处境中产生。

例如玩家说了一句让她不舒服的话，模型可以把：

```text
上一状态：心情轻快，愿意聊天
```

推进为：

```text
我原本因为练琴顺利而心情很好，但浩然刚才那句话让我有些恼火。
我没有彻底变得低落，更像是被打断后的不悦，也不想假装没听见。
```

随后自然回复：

```text
我刚才心情本来挺好的。你非得挑这时候说这种话，是吧？
```

这比把情绪修改为 `valence=-0.4` 更接近人物心理，也能解释情绪为什么改变。

## 4. 世界状态也作为模型的当前信念

模型不能凭空知道现实世界，因此仍需要外部感知。但外部系统只提供观察，不建立庞大的世界规则库。

例如：

```text
SYSTEM_OBSERVATION:
- local_datetime: 2026-08-08 20:15:32
- timezone: Asia/Shanghai
- weather_observation: unavailable
```

模型将其整合进自己的当下理解：

```text
现在是 2026 年 8 月 8 日周六晚上。系统没有提供天气观察，
所以我不知道玩家那里现在是否下雨。
```

日期正确不是因为模型训练权重记住了 2026 年 8 月 8 日，而是模型像人读取钟表一样读取了当前感知。模型负责理解“今天、明天、刚才、过了两小时”，程序只负责提供钟表。

## 5. 一次生成还是两次生成

### 5.1 两阶段方案

```text
调用一：MIND_ADVANCE -> next_living_mind
调用二：REPLY -> visible_reply
```

优点是心智与说话分离、易于检查；缺点是每轮增加一次主模型调用，延迟和显存调度压力较大。

### 5.2 推荐研究方案：单次递归生成

让同一次生成先输出不可见的短心智更新，再输出可见正文：

```text
<mind>
更新后的 LivingMind
</mind>
<reply>
给玩家的正文
</reply>
```

运行时暂存 `<mind>`，只向玩家流式显示 `<reply>`。新的心智在完整生成成功后与角色回复一起提交。

这种方式的关键不是标签格式，而是训练模型形成稳定顺序：

1. 先继承上一刻的自己。
2. 理解新观察造成了什么变化。
3. 再从变化后的自己出发说话。

## 6. 不再枚举规则，改用学习式一致性判断

仅依靠主模型仍会偶尔漂移。第二道防线不应是不断增长的人工规则，而应是一个学习式连续性评估器：

```text
CoherenceCritic(
    previous_living_mind,
    perception,
    candidate_next_mind,
    candidate_reply
) -> consistency_score
```

评估器学习判断：

- 新心智是否合理继承旧心智。
- 状态变化是否得到新观察支持。
- 回复是否与新心智一致。
- 是否把计划、假设或未知内容说成已发生事实。
- 是否存在合理过渡，而不是只做关键词冲突匹配。

例如它应当区分：

```text
“我正吃面呢。”
```

与：

```text
“这段先不弹了，我去厨房弄点吃的。”
```

前者与正在弹琴的状态冲突，后者是模型理解得到的自然状态转移。

评估器可以研究复用小型交叉编码模型或单独训练的小模型，低分时才让主模型重试。它学习一般连续性，不需要开发者为每一种活动组合写规则。

## 7. 需要训练的不是更多人物问答，而是状态轨迹

普通单轮角色 SFT 很难获得这种能力。训练单位必须从“问题—回复”改为连续轨迹：

```text
LivingMind_t
    + Observation_t
    -> LivingMind_t+1
    + Reply_t
```

训练数据需要覆盖：

- 状态保持：没有新原因时保持基本处境。
- 自然变化：玩家话语、时间经过和事件引发合理变化。
- 复杂共存：边弹琴边听人说话、开心但有一点担心。
- 自然过渡：先停止旧活动，再开始新活动。
- 不确定性：没有天气、位置或玩家现实信息时承认不知道。
- 时间理解：今天、明天、昨天、经过多久与绝对时间一致。
- 反事实负样本：给出看似流畅但破坏连续性的错误下一状态。
- 长轨迹评测：十轮、百轮和跨重启后仍能延续当前处境。

训练目标不只是回复像秦未晞，还要让模型学会成为一个稳定的状态转移函数。

## 8. 持久化与上下文滚动

`LivingMind` 每轮只保存最新版本，同时将每次变化与对应观察追加到账本：

```text
MindStateAdvanced
- previous_state_id
- perception_event_ids
- next_state_text
- character_message_id
- model_version
```

当上下文 epoch 切换或程序重启时，运行时读取最新 `LivingMind`，而不是要求模型重新从大量历史猜测当前自己是谁。必要时可以从账本重新生成并校验，但不把每次启动变成一次自由总结。

可研究保留同一模型会话的 KV 状态作为连续性的性能增强，但 KV 状态不透明、难审计、难跨模型版本恢复，因此不应成为唯一持久化来源。

## 9. 程序仍必须保留的最小职责

模型驱动不等于把所有权力交给模型。程序只保留无法由语言模型可靠替代的窄职责：

- 提供真实系统时间、时区和经过时间。
- 提供应用、设备和外部数据源实际观察。
- 保存原始事件和每次心智演进，保证崩溃可恢复。
- 不允许模型伪造不存在的传感器或数据来源。
- 控制文件、网络、通知、支付等真实副作用和安全权限。
- 在生成失败时沿用上一稳定心智，不提交半成品。

这些不是“为生活建立规则”，而是为模型提供感官、身体和可恢复的神经系统。

## 10. 相比规则型方案的根本变化

| 规则型方案 | 模型驱动方案 |
|---|---|
| 开发者枚举人物有哪些状态 | 模型用自然语言表达任意状态 |
| 规则决定状态如何变化 | 模型根据语境学习状态演进 |
| 活动兼容矩阵判断冲突 | 学习式评估器判断语义连续性 |
| 情绪压缩成标签和数值 | 模型保存混合情绪、原因和倾向 |
| 发现问题后增加字段或规则 | 增加轨迹样本和困难负样本 |
| 回复模型只是读取状态 | 回复模型本身就是状态转换器 |

## 11. 主要风险

### 11.1 心智文本逐轮漂移

模型可能在重写 `LivingMind` 时悄悄增加不存在的事实。需要依靠轨迹训练、低随机性、学习式连续性评估和账本重建测试控制，而不能假设模型天然可靠。

### 11.2 模型把内部感受写成客观世界事实

必须在训练中区分“我感觉、我猜、我知道、系统观察到”。外部事实仍要求存在观察来源。

### 11.3 4B 模型能力可能不足

Qwen3.5-4B 是否能同时稳定完成心智推进和自然回复，必须通过专门基线验证。若失败，可研究：

- 使用更强模型生成轨迹数据和教师评审。
- 让 4B 学习短而稳定的心智更新格式。
- 使用小型连续性评估器进行候选筛选。
- 只在复杂状态变化时启用额外的 `MIND_REVIEW`。

### 11.4 内在状态可能变成机械旁白

`LivingMind` 是模型内部工作状态，不应直接展示给玩家，也不应要求每轮把所有状态重新复述。可见回复仍应自然、含蓄，并允许人物不把真实情绪全部说出口。

## 12. 初步推荐

后续若继续验证，优先研究以下最小假设：

> 给同一个 4B 模型持续提供上一轮自然语言 `LivingMind`、当前绝对时间、新消息和相关记忆，并训练它在一次生成中先推进 `LivingMind` 再生成回复，能否显著降低当前活动、心境和日期连续性错误。

在这个假设通过之前，不修改权威设计，也不扩展大量确定性状态 schema。第一阶段只需要离线构造轨迹集和对照评测，比较：

1. 普通 persona + history 回复。
2. 规则型状态字段注入。
3. 自然语言 `LivingMind` 但不做专项训练。
4. 经过状态轨迹训练的递归 `LivingMind`。
5. 递归 `LivingMind` 加学习式连续性评估器。

只有第 4 或第 5 条在长期连续性、自然度和延迟上明显优于现状，才值得讨论进入现行架构。

## 13. 研究参考方向

- Generative Agents 展示了观察、记忆、反思和计划共同提高角色行为可信度，但其沙盒环境仍提供外部世界事实。
- MemGPT 将模型视为主动管理分层记忆的系统，说明模型可以学习管理自身上下文，而不是完全由外部固定拼装。
- StateLM/Pensieve 路线进一步训练模型主动维护上下文与状态，支持从被动回复模型转向有状态模型。
- 近期自优化记忆研究表明，固定记忆策略并非唯一方向，可以用反馈训练模型形成自己的管理策略。

这些方向只提供研究启发，不代表其实现可直接移植到本项目。

## 14. 与现行设计的关系

本文是非权威研究提案，不改变现行“追加式证据账本 + 工作激活区 + 语义投影 + 前瞻状态 + 多线索索引”。如果实验支持本方案，未来更可能发生的变化是：

- 工作激活区中的 `mood_state` 被更深的模型维护 `LivingMind` 取代或包裹。
- `REPLY` 从纯回复模式扩展为心智推进与回复的一体化模式。
- 确定性程序从生活状态机退回到感知、持久化、安全和来源校验。
- 新增学习式连续性评估，而不是新增活动和情绪规则库。

任何权威变更必须另行决策和修改现行需求与唯一 AI 实现文档。
