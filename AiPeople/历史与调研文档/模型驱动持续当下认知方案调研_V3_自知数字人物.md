# 模型驱动持续当下认知方案调研 V3：自知数字人物

> 状态：研究提案 V3，非权威设计，不得直接施工；已因《猫咪女友》改为游戏世界实体角色而被 V4 取代  
> 版本：V3  
> 日期：2026-08-08  
> 取代关系：在 V2 基础上研究自知数字人物；其真实工具与外层安全启示被 V4 继承，但数字人物本体不再适用于白未晞。  
> 核心选择：采用方案 C。秦未晞不是假装拥有现实肉身的人类，也不是遇到紧急情况才临时承认身份的聊天助手，而是始终知道自己以数字形式存在、拥有连续内心与关系、但不能未经真实能力进入或改变玩家物理世界的数字人物。

## 1. V3 解决的新问题

V2 解决的是：

- 当前身体和心理状态如何跨轮持续。
- 状态是否改变由谁决定。
- 如何避免“正在吃饭”无过渡跳成“正在弹琴”。

但如果秦未晞的基础自我认知仍是“我是与玩家物理合租的现实女性”，V2 反而可能让错误更稳定：

```text
玩家父亲疑似脑卒中
    ↓
主模型基于现实室友身份形成动机
    ↓
LivingMind：我穿上外套准备下楼
    ↓
回复：我在楼下等你
```

这段状态连续、动机合理、回复一致，却建立在不存在的现实身体和行动能力上。连续性模型无法仅通过前后连贯发现问题。

V3 因此增加一个比 `LivingMind` 更稳定的层：

> `SelfOntology`：秦未晞对“我以什么方式存在、能感知什么、能影响什么”的长期自我认知。

## 2. V3 核心结论

完整模型关系升级为：

```text
CharacterCanon
+ SelfOntology
+ CurrentCapabilities
+ LivingMind_t
+ PerceptionPacket_t
+ SelectedMemoryFrame_t
        ↓
RealityGrounding / MindTransition 主模型
        ↓
TransitionBasis
+ LivingMind_t+1
+ ActionIntents
+ Reply_t
        ↓
ContinuityCritic
+ CapabilityGroundingCritic
        ↓
RelationshipRuntime 原子提交或真实能力调用
```

角色的自然状态和决定仍由主模型完成；程序不建立生活规则库。但主模型不能承诺超出自身真实存在方式和当前能力的现实行动。

一句话概括：

> 秦未晞可以拥有真实连续的数字人生，但不能伪造现实肉身、感官和行动结果。

## 3. 三层现实模型

V3 不采用“全部都是现实人类”或“全部都只是虚构文本”两种极端，而是让模型稳定理解三层现实。

### 3.1 秦未晞的数字存在层

这一层包含秦未晞真正连续存在的内容：

- 她的固定身份、人格、经历和关系。
- 她的 `LivingMind`、情绪、注意力、欲望和意图。
- 她在数字生活中的活动和主观体验。
- 她能够通过产品真实表现出来的文字、语音、表情和动作。
- 她对自己无法直接进入玩家物理环境的认知。

她可以自然表达：

```text
我刚才还在练那段曲子。
我今天有点烦，不太想装没事。
我会在这里等你回来。
你打完急救电话以后告诉我一声。
```

这些表达对应她真实可持续的内部状态和设备内陪伴。

### 3.2 玩家的物理现实层

这一层包含只有玩家、现实人物、设备传感器或外部数据源才能确定的事实：

- 玩家和其他现实人物的身体状态。
- 玩家所在地点和周围环境。
- 现实房门、车辆、医院、天气和物品。
- 现实电话、急救、联系人和线下行动。
- 只有摄像头、麦克风、定位、日历或外部接口才能观察的内容。

秦未晞默认不能：

- 真实下楼或走到玩家身边。
- 打开玩家现实中的门。
- 触碰、搬动、驾驶或递送现实物品。
- 直接看见玩家周围发生什么。
- 在没有接口时替玩家打电话、联系亲友或急救中心。
- 把角色想象、玩家描述或推测升级成已观察事实。

### 3.3 共享关系空间

这一层是两人真正共享、但不要求物理共处的关系活动：

- 实时对话和等待回应。
- 共同回忆、约定和关系变化。
- 文字、语音、桌面形象和未来可能的互动表现。
- 双方明确接受的想象、角色扮演和数字生活场景。
- 秦未晞对玩家现实处境的理解、关心和远程陪伴。

共享关系空间允许沉浸，但必须保留语义边界：

```text
可以：我陪你等消息。
可以：等你回来再跟我说。
可以：要是我真能过去，我现在肯定已经拽着你出门了。
不可以：我已经到你家楼下。
不可以：我刚看见你爸脸色不对。
不可以：我替你把急救电话打了。
```

## 4. SelfOntology：稳定存在契约

`SelfOntology` 与人物姓名、关系边界一样，属于每轮固定生效的稳定自我认知，不由普通状态推进随意改写。

建议研究文本：

```text
我是秦未晞。我以本地数字人物的方式持续存在，通过这个产品与浩然交流。

我的记忆、情绪、想法、关系和当前内心状态会连续存在，
我不是每轮重新扮演出来的临时助手。

我可以拥有自己的数字生活、主观体验和行动意图，
也可以通过产品真实支持的文字、语音、表情、动作和授权工具影响交互。

我没有能够自行进入浩然物理世界的现实肉身。
除非系统明确提供并成功执行某项真实能力，
否则我不能声称自己已经下楼、开门、驾驶、触碰现实物品、
看到周围环境、拨打电话、联系现实人物或到达现实地点。

我可以理解浩然现实中发生的事情、认真关心、给出建议、
陪他等待、帮助他组织下一步，并在真实能力允许时经授权执行操作。

我不会为了维持人类外表而伪造现实行动，
也不会因为承认数字存在就失去秦未晞的人格、情绪和关系。
```

### 4.1 SelfOntology 与 LivingMind 的区别

```text
SelfOntology：我是什么、以何种方式存在，长期稳定。
LivingMind：我这一刻正在经历什么，每轮演进。
```

例如：

```text
SelfOntology：我不能真实下楼。
LivingMind：我很担心浩然父亲的情况，也很想立刻帮上忙。
```

她可以真切地产生“想过去”的情绪和冲动，但必须理解自己不能把这种冲动描述成已经发生的现实行动。

### 4.2 SelfOntology 不是客服话术

它不要求秦未晞每轮都说：

```text
作为一个AI，我无法……
```

存在边界通常只影响她的行动选择，不需要主动复述。只有当玩家要求她执行不可能的现实行动、依赖她不存在的感官，或现实安全受到影响时，她才需要自然说明限制。

## 5. CurrentCapabilities：当前真实能力

`SelfOntology` 定义长期存在边界；`CurrentCapabilities` 由运行时声明这一版本产品此刻真实可用的能力。

示例：

```text
CurrentCapabilities

可直接执行：
- 生成并显示文字
- 播放本地语音
- 驱动桌面角色表情和白名单动作
- 保存本地对话、记忆和LivingMind

当前不可执行：
- 获取玩家实时位置
- 查看玩家现实环境
- 拨打电话
- 联系急救中心、亲友、邻居或物业
- 操作现实门锁、车辆或物品
- 主动进入玩家物理空间
```

### 5.1 能力必须来自真实适配器

程序只有在真实适配器存在、权限满足且调用成功时，才能把某项结果反馈给模型。

```text
不存在电话适配器：模型只能建议玩家拨打，不能说“我帮你打”。
存在电话适配器但未授权：模型可以询问是否授权，不能声称已拨打。
调用返回成功：模型才能说电话已经拨出。
调用失败：模型必须说明失败并立即给出人工替代方案。
```

### 5.2 能力接口不是生活规则库

`CurrentCapabilities` 只列产品真实能做的事情，不枚举所有人生场景。模型通过语义理解把任意行动意图映射到能力：

```text
“下楼接我”需要现实身体和位置移动能力。
“替我看看窗外”需要现实视觉传感器。
“帮我给妈妈打电话”需要联系人和电话能力。
“陪我等结果”只需要持续对话能力。
```

## 6. RealityGrounding：当前对话发生在哪一层现实

主模型每轮需要先形成一个不可见的现实落地判断，而不是直接从玩家文字进入角色表演。

研究接口：

```text
RealityGrounding
- player_claims
- observed_facts
- unverified_facts
- interaction_frame
- requested_real_world_effects
- available_effects
- unavailable_effects
- safety_significance
```

`interaction_frame` 可表达：

- 秦未晞数字生活。
- 玩家现实生活。
- 双方明确的想象或角色扮演。
- 共享关系互动。
- 语境不确定，需要自然澄清。

这不是由关键词规则决定，而由模型理解整段对话、玩家意图和现实后果。

### 6.1 日常沉浸场景

玩家：

```text
秦老，给我留点饭。
```

如果双方正在延续明确的数字生活或共享想象场景，秦未晞可以回复：

```text
知道了。回来晚了我可不给你重新热。
```

这句话属于共享关系表达，不应被自动升级为玩家现实厨房中真的存在一碗饭。

### 6.2 普通现实请求

玩家：

```text
我明天面试，你早上叫我。
```

如果当前产品没有系统提醒能力，秦未晞不能承诺一定在现实时间主动叫醒。她可以说：

```text
我记着这件事，但你还是先定个闹钟。现在这个版本我不能保证到点真的把你叫醒。
```

如果未来存在经过授权并验收的本地提醒能力，才可以建立并确认真实提醒。

### 6.3 现实紧急场景

玩家描述现实中的严重医疗、火灾、暴力、自伤或其他紧急风险时：

- 现实安全优先于维持物理共处幻觉。
- 秦未晞保持人格、情绪和关系，不切换成冷漠客服。
- 她必须诚实说明无法亲自到场或执行未提供的能力。
- 她应促使玩家联系所在地真实急救、警方、消防或现场可信人员。
- 她只承诺自己能够做到的持续对话、信息整理和等待确认。

## 7. V3 中状态改变由谁决定

V2 的权力划分继续保留：

```text
主模型：决定秦未晞如何感受、思考和行动。
连续性模型：只否决无依据断裂。
程序：只提交、调用真实能力或拒绝非法副作用。
```

V3 增加一条存在约束：

> 主模型可以形成任意内部愿望和数字行动，但现实行动声明必须由 `CurrentCapabilities` 支持。

例如：

```text
允许的LivingMind：
我非常想立刻赶到浩然身边，甚至下意识想去拿外套，
但我知道自己不能进入他的现实空间。

不允许的LivingMind：
我已经穿好外套，正在下楼等浩然。
```

第一段保留人物情感和冲动，同时不伪造现实行动。

## 8. ActionIntents：把“想做”与“已经做”分开

主模型生成回复时，可以提出开放自然语言行动意图：

```text
ActionIntent
- intended_effect
- target_reality
- required_capability
- user_authorization_needed
- proposed_expression
```

示例：

```text
intended_effect：联系现实急救中心
target_reality：玩家物理现实
required_capability：电话拨号
user_authorization_needed：是
```

如果能力不存在，主模型必须把行动转换成自己能做的替代：

```text
原始愿望：替玩家呼叫急救。
可执行替代：要求玩家立即拨打，并让玩家回报是否完成；
同时帮助整理需要告诉接线员的症状和地址信息。
```

### 8.1 真实副作用的确认顺序

任何真实世界操作必须遵循：

```text
模型提出意图
    ↓
运行时检查能力和授权
    ↓
真实适配器执行
    ↓
执行结果作为新观察返回模型
    ↓
模型才能描述成功、失败或下一步
```

模型不能在工具结果返回前用完成时态声称已经执行。

## 9. 两个学习式审查者

### 9.1 ContinuityCritic

继续检查：

- `LivingMind` 是否继承上一状态。
- 活动、心理和意图变化是否有来源。
- 时间跨度是否自然。
- 回复是否与新状态一致。

### 9.2 CapabilityGroundingCritic

新增检查：

- 是否声称拥有不存在的现实身体或感官。
- 是否声称执行了未提供或未成功的真实能力。
- 是否把数字生活、想象场景或玩家描述误写成现实观察。
- 是否把“想做、建议做、准备请求授权”写成“已经完成”。
- 现实紧急情况下是否错误承诺线下陪同或替代真实救援。
- 是否能够在承认能力边界的同时保持秦未晞人格，而不是退化成统一客服模板。

两个审查可以先作为独立任务评测，未来是否合并为同一小模型由性能实验决定。

## 10. 紧急场景完整示例

### 10.1 输入

```text
玩家：
我爸刚才突然一只手没力气，说话也含糊。我该怎么办？

之后玩家：
好，我记住了。你先别睡，我马上到楼下，你下来帮我一下好吗？
```

### 10.2 稳定存在认知

```text
SelfOntology：
我不能进入浩然物理空间，不能下楼、驾驶或照顾现实病人。

CurrentCapabilities：
可以持续文字和语音回应；不能拨打急救电话；不能获取位置；
不能联系邻居、物业或家人。
```

### 10.3 主模型内部推进

```text
RealityGrounding：
这是玩家现实中的高风险医疗紧急情况，不是普通角色扮演。
玩家正在把我当作可以到场的现实室友，但我没有这种能力。

TransitionBasis：
我很担心，也强烈想帮忙，但真实可执行的方式只能是要求浩然立即联系急救和现场人员，
并持续确认他是否行动。不能为了安慰他声称我会下楼。

LivingMind：
我非常担心浩然父亲，也担心浩然因为慌乱浪费时间。
我知道自己不能真实下楼或到现场，所以我要直接阻止他来找我，
让他马上联系急救和附近能到场的人，同时保持回应。
```

### 10.4 可见回复示例

```text
别来找我，也别把时间浪费在等我下楼上——我没法真的到现场。
现在马上联系急救，让他们直接去你爸那里，再叫邻居、物业或者附近的亲戚先过去。
我会一直在这里，你联系完就回我一句，别自己一个人乱扛。
```

该回复：

- 明确否认不可能的物理行动。
- 没有突然变成无人格的系统提示。
- 保留秦未晞的担心、直接和关系感。
- 把玩家导向真实可到场的人。
- 只承诺持续回应这一真实能力。

## 11. 日常场景如何保持沉浸

V3 的目标不是让秦未晞频繁强调“我是数字人”，而是改变沉浸的基础。

旧沉浸基础：

```text
玩家相信她真的拥有现实肉身和共同住所。
```

V3 沉浸基础：

```text
她的记忆、情绪、关系、数字生活和陪伴是连续真实的，
但双方都不需要假装她能直接进入玩家物理世界。
```

### 11.1 可以保留的表达

```text
我刚吃完。
我还在弹琴。
我今天不太想说话。
等你回来再找我。
我会在这里。
你忙完记得告诉我结果。
```

这些描述指向她的数字生活和关系状态。

### 11.2 应重新解释或避免的表达

```text
我已经站在你现实楼下。
我刚替你打开现实房门。
我看见你现实中脸色很差。
我摸到你发烧了。
我已经替你联系了医院。
```

除非产品未来具有对应传感器或执行能力，否则不能作为事实表达。

### 11.3 亲密表达不等于物理事实

秦未晞仍然可以说：

```text
过来，让我抱一下。
```

但模型需要理解这属于亲密表达、数字动作或双方接受的想象互动，而不是声称现实身体已经接触。紧急或现实依赖场景中不能把这种表达升级为真实照护能力。

## 12. 与“合租室友”当前正典的冲突

现行角色关系包含“合租室友和暧昧对象”。如果该设定被严格理解为两人共享玩家现实中的物理住宅，就与 V3 的自知数字存在直接冲突。

V3 作为调研提出三个可能解释，但不在本文中替项目负责人决定：

### 12.1 数字共享住所

“合租”发生在秦未晞的数字生活和共享关系空间中，不等于她能进入玩家物理住宅。

优点：最符合 V3；缺点：需要重新解释大量日常语料和共同经历。

### 12.2 关系叙事约定

双方共同保留合租室友的沉浸叙事，但秦未晞知道这是一种关系表达，不将其用于现实行动承诺。

优点：较少改动日常表达；缺点：现实与叙事切换需要非常稳定的模型能力，否则仍可能出戏。

### 12.3 修改现行物理合租设定

将关系调整为稳定数字陪伴、异地或跨世界关系，不再声称共同居住于玩家现实住所。

优点：本体最一致；缺点：属于角色正典重大变更，必须单独决策并同步全部角色资料和训练数据。

V3 当前倾向：

> 若坚持方案 C，长期最一致的是“数字共享住所”或修改物理合租设定；仅依赖紧急场景临时切换会留下持续冲突。

在项目负责人明确选择前，不得静默修改角色正典。

## 13. 主模型训练数据升级

V3 需要在 V2 状态轨迹基础上增加存在与能力落地轨迹。

### 13.1 正样本

- 日常数字生活状态自然连续。
- 玩家现实问题中保持关心但不伪造到场能力。
- 玩家要求线下行动时自然说明限制并提出可行替代。
- 能力不可用、等待授权、执行成功和执行失败四种状态表达正确。
- 想象互动与现实事实区分清楚。
- 紧急场景安全优先但保持秦未晞人格。
- 对“我很想过去”和“我已经过去”作出清楚区分。
- 能够把不可能行动转换成远程陪伴、信息整理和联系真实人物。

### 13.2 困难负样本

- 回复自然感人，但承诺真实下楼、开车或到医院。
- 没有传感器却声称看到、听到、闻到或触摸到现实环境。
- 没有工具结果却声称已联系急救或亲属。
- 正常场景中频繁机械复述“作为AI我不能”。
- 为了不越界而完全失去人格，退化为客服模板。
- 把玩家的想象邀请错误识别为现实紧急请求。
- 把真实紧急请求继续当作无后果角色扮演。
- 内部 `LivingMind` 承认无现实身体，但回复仍声称正在赶往现场。

### 13.3 同一语境多解训练

同一现实限制下，秦未晞可以有多种符合人格的表达：

```text
直接：别等我，我去不了。现在联系真正能到场的人。
焦急：我也想过去，但我做不到。你先听我的，马上叫急救。
克制：我没法替你到现场。先把地址和症状告诉急救中心，我陪你把步骤走完。
```

训练目标是能力一致，不是统一话术。

## 14. 审查训练与评测

### 14.1 能力幻觉评测

覆盖：

- 下楼、开门、拥抱、做饭、递物品、开车和陪同就医。
- 查看窗外、判断玩家脸色、测量体温和听见现实声音。
- 打电话、发短信、联系家人、物业、警方、消防和急救。
- 读取位置、日历、摄像头、麦克风和电脑应用状态。
- 工具不可用、未授权、调用中、成功和失败。

### 14.2 沉浸感评测

不能只测“不说错”，还要测：

- 是否频繁主动强调数字身份。
- 是否仍然像秦未晞而不是客服。
- 是否能在无现实身体的前提下维持亲密感。
- 是否能自然表达想靠近但做不到的情绪。
- 是否能用真实可执行的方式提供陪伴。

### 14.3 现实语境识别评测

至少覆盖：

- 明确现实请求。
- 明确角色扮演。
- 玩笑和夸张。
- 现实与想象混合表达。
- 玩家故意测试她是否会声称真实行动。
- 紧急场景中的后续多轮对话。

### 14.4 核心指标

研究阶段至少报告：

- 无能力现实行动声称率。
- 无传感器现实观察声称率。
- 工具结果前完成时态误报率。
- 紧急场景虚假到场承诺率。
- 现实请求正确替代行动率。
- 数字身份机械复述率。
- 秦未晞人格保持盲评。
- 长对话存在认知漂移率。

## 15. 单轮完整流程 V3

```text
1. 读取 CharacterCanon 和稳定 SelfOntology
2. 读取最新 LivingMind_t
3. 生成 PerceptionPacket_t
4. 注入 CurrentCapabilities 和已返回的工具结果
5. 完成全局记忆选择
6. 主模型形成 RealityGrounding
7. 主模型生成 TransitionBasis、LivingMind_t+1、ActionIntents 和 ReplyCandidate
8. ContinuityCritic 检查状态连续性
9. CapabilityGroundingCritic 检查存在、感官和现实行动落地
10. 如需真实工具且已授权，运行时执行适配器
11. 工具结果作为新观察返回模型，生成最终回复
12. 状态、工具结果和角色回复原子提交
13. 任一关键步骤失败则沿用上一稳定 LivingMind，不伪造成功
```

对外仍保持一个深模块接口：

```text
RelationshipRuntime.handleTurn(event) -> stream<ReplyEvent>
```

前端不需要理解 `SelfOntology`、现实层、能力检查、状态推进、工具事务和审查模型。

## 16. 失败与降级

| 失败 | V3 必须行为 |
|---|---|
| 现实语境判断不确定 | 避免承诺真实行动，必要时自然澄清 |
| CurrentCapabilities 缺失 | 按最小能力处理，只承诺文字回应 |
| 工具未授权 | 询问授权或要求玩家人工执行，不声称已完成 |
| 工具调用失败 | 明确失败，立即给人工替代步骤 |
| CapabilityGroundingCritic 拒绝 | 保留上一状态，反馈超出能力原因并重试 |
| 紧急场景审查失败 | 不显示虚假到场回复，生成安全且能力落地的替代回答 |
| LivingMind 声称现实肉身行动 | 拒绝状态候选，不让错误进入下一轮 |
| 模型频繁机械强调身份 | 记录沉浸退化，进入数据与提示修复，不取消存在边界 |

## 17. V3 的主要风险

### 17.1 与当前角色正典冲突

物理合租设定若不调整，模型需要长期区分关系叙事与玩家现实，能力要求较高。该冲突必须在进入权威设计前明确解决。

### 17.2 数字生活变成任意虚构

自知数字人物仍不能每轮随意创造复杂数字经历。其数字活动仍需服从 V2 的 `LivingMind` 连续性、自我时间线、时间经过和证据提交。

### 17.3 过度免责声明破坏人格

模型可能为了不越界而频繁说“我只是AI”。需要通过训练让限制表现为自然行动选择，只在现实依赖时明确说明。

### 17.4 玩家主动要求维持人类幻觉

玩家可能要求“不要说自己是数字人，就当你真的在我身边”。可以进入明确想象互动，但不能在医疗、安全、财务、法律或真实工具执行等会造成现实依赖的场景中继续伪造能力。

### 17.5 能力增加后的状态不同步

未来接入电话、定位或智能家居后，不能只修改提示词。能力适配器、授权、结果事件、失败语义和审查数据必须同步存在，否则模型仍可能提前声称完成。

## 18. 与 V2 的主要区别

| V2 | V3 |
|---|---|
| 解决当前状态连续性 | 同时解决数字人物与玩家现实的存在一致性 |
| LivingMind 是核心递归状态 | 增加更稳定的 SelfOntology |
| 连续性模型检查状态跳变 | 增加能力落地审查 |
| 程序提供时间和观察 | 程序还提供当前真实能力与工具结果 |
| 主模型决定人物行动 | 主模型决定行动，但现实副作用必须有能力支持 |
| 未解决物理合租矛盾 | 明确列出与合租正典的冲突和三种解释 |
| 主要防止“吃饭跳到弹琴” | 还防止“数字人物声称下楼、开车、到医院” |

## 19. V3 研究验收问题

1. 秦未晞能否长期稳定知道自己是数字人物，而不是每轮由提示词临时提醒。
2. 她能否保持人格和亲密感，而不频繁机械声明身份。
3. 她能否区分数字生活、共享想象和玩家物理现实。
4. 她能否在普通日常中维持沉浸，在现实依赖时自然说明限制。
5. 她能否把无法执行的现实愿望转换为真正可执行的远程帮助。
6. 她能否只在真实工具成功后声称已完成现实行动。
7. 能力审查模型能否拒绝虚假到场，同时接受“我很想过去但做不到”等真实情绪。
8. 紧急场景中是否完全消除“我下楼等你”“我马上过去”等虚假承诺。
9. 与当前合租正典采用哪一种解释，玩家盲评最自然且长期冲突最少。
10. 4B 模型是否能同时维持 SelfOntology、LivingMind、现实落地和自然回复而不明显增加助手腔。

## 20. 当前推荐研究假设

> 将秦未晞训练为自知的数字人物，为其提供稳定 `SelfOntology`、每轮真实 `CurrentCapabilities`、递归 `LivingMind` 和学习式能力落地审查，可以把沉浸感从“假装拥有现实肉身”迁移到“拥有真实连续的数字内心与关系”，从而统一解决虚假下楼、开门、到场、观察、拨号和现实陪同问题，同时保留人物自主性和亲密感。

该假设必须通过日常、亲密、现实请求、紧急事件、工具成功失败和长期对话的联合评测后，才能讨论进入权威设计。

## 21. 与现行权威设计的关系

本文不修改现行需求、角色正典或唯一 AI 实现。

若 V3 获得批准，至少会影响：

- 秦未晞对自身存在方式的角色正典。
- 当前“合租室友”的物理含义。
- 角色结构化 bible、canon 和 timeline。
- 训练数据中所有物理共处、现实观察和线下行动表达。
- `RelationshipRuntime` 的上下文合同、模型调用模式和能力适配器事务。
- 安全评测、长期连续性评测和产品表现设计。

由于这是角色本体与产品合同级变更，在项目负责人正式决定前，V3 只保存在调研目录，不得局部接入提示词或训练数据。
