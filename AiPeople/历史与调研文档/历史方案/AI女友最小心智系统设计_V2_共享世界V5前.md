# 《猫咪女友》持续心智与关系连续性系统设计 V2

> 文档状态：当前唯一 AI 运行时实现  
> 生效日期：2026-08-08  
> 产品范围：同一世界、同一存档、唯一男主角、可扩展女主角角色包  
> 当前 P0：仅激活白未晞（`character_id=baiweixi`）  
> 架构主线：追加式证据账本 + 工作激活区 + 语义投影 + 前瞻状态 + 多线索索引

## 1. 设计目标

本系统解决的不是“让模型记住更多聊天文本”，而是让游戏世界和角色在多轮、跨会话、跨重启后仍然持续存在。

模型固定权重可以学习通用语言能力和某个角色的稳定人设，却不能仅靠权重知道当前存档中今天是哪一天、角色正在做什么、刚刚受了什么伤、和主角发生过什么、哪些承诺仍未完成。把所有聊天历史长期塞回上下文也不能可靠解决状态冲突、知识隔离、修改历史、检索成本和崩溃恢复。

本设计要求：

- 世界、主角和女主角当前状态可持续、可解释、可恢复。
- 状态变化主要由模型进行开放式语义判断，而不是穷举脚本。
- 模型不能直接自由改写历史和数据库。
- 回复必须基于更新后的状态，并与状态原子提交。
- 多位女主角未来生活在同一世界和存档，但分别拥有心智和私密记忆。
- P0 只运行一个激活女主角，仍使用完整 `character_id` 数据合同。

## 2. 核心判断

### 2.1 不采用纯规则状态机

自然对话中，导致状态变化的表达几乎无限：吃完、没胃口、被打断、准备出门、临时改主意、想起旧事、因一句话缓和或警觉。若为每个问题补一条规则，系统会随着场景增长迅速失控。

因此，规则只承担少量稳定不变量：时间单调、事件权限、知识可见性、主角自主性、事务一致性和正典硬边界。具体“这句话是否让她停下吃饭”“她的情绪是否自然缓和”由模型结合上下文判断。

### 2.2 不采用模型直接改库

模型擅长语义判断，不擅长保证持久化不变量。允许模型直接覆盖当前状态会导致：

- 无证据改变日期、地点、活动或关系。
- 把推测写成主角已经做出的选择。
- 把另一女主角的秘密写入当前角色知识。
- 回复已发送但状态未保存，或状态已保存但回复生成失败。
- 修正历史时丢失原始证据。

模型只能提交结构化候选，程序与审查器决定候选能否进入事务。

### 2.3 职责分配

**主模型负责：**

- 理解玩家输入属于对白、行动、OOC 还是现实安全情境。
- 从旧状态、时间、场景、记忆和正典推断合理的新状态。
- 形成女主角即时意图、情绪和自然语言回复。
- 在回复后提出长期记忆、自我时间线、欲望和关系投影候选。

**连续性审查器负责：**

- 发现无证据状态跳变。
- 检查时间、空间、身体、形态、知识、能力和关系连续性。
- 检查是否替主角做了重大选择。
- 检查状态候选与回复草案是否互相矛盾。
- 给出通过、拒绝或受约束重算，不创造新剧情。

**程序运行时负责：**

- 加载角色包和正典版本。
- 维护事件账本、版本、索引和投影。
- 执行权限、可见性、schema 和硬不变量检查。
- 原子提交或整体回滚。
- 崩溃恢复、重放、去重和性能降级。

## 3. 权威对象模型

### 3.1 稳定正典

```text
ProjectRequirements
WorldCanon(world_id)
ProtagonistCanon(protagonist_id)
HeroinePackage(character_id)
```

稳定正典定义“这个世界和角色通常是什么”，不保存某个存档此刻正在发生什么。

### 3.2 存档级共享状态

```text
SaveRuntime(save_id)
├─ GameClock
├─ SceneMind
├─ ProtagonistState
├─ WorldEventLedger
└─ HeroineRuntime[character_id]
```

### 3.3 女主角分区状态

```text
HeroineRuntime[character_id]
├─ LivingMind
├─ WorkingActivation
├─ SemanticProjections
├─ ProspectiveState
├─ SelfTimeline
├─ RelationshipState[protagonist_id]
├─ MotivesAndIntentions
└─ PrivateMemoryIndexes
```

所有女主角共享世界事件账本，但每个投影和召回入口都必须包含 `character_id`。共享账本不代表共享知识。

## 4. GameClock：游戏世界时间

`GameClock` 是当前存档的唯一游戏时间来源，至少包含：

```yaml
game_clock:
  save_id: save_001
  calendar_id: songjiangfu_default
  day_index: 11
  season: autumn
  time_of_day: evening
  minute_of_day: 1080
  mode: paused_when_closed
  version: 42
  last_event_id: evt_0042
```

原则：

1. 模型不能仅因玩家问“今天几号”而改变日期。
2. 时间只能由明确游戏时间推进事件改变。
3. P0 游戏关闭时默认暂停，不按现实时间自动流逝。
4. “过了一小时”“第二天早上”等玩家叙述必须先被 `INPUT_GROUND` 识别为游戏内时间行动，再进入候选事件。
5. 时间跳转后必须重新评估场景、活动、身体、情绪、计划和在场角色，不能只改日期字段。
6. 所有回复使用事务候选中的新时间，不使用系统墙钟猜测游戏日期。

## 5. SceneMind：当前场景

`SceneMind` 保存当前可共同观察的游戏场景，而不是任何角色的私人感受。

至少包括：

```yaml
scene_mind:
  scene_id: apartment_living_room
  location_id: protagonist_apartment
  participants: [protagonist, baiweixi]
  visible_entities: [cardboard_box, dining_table]
  weather: cloudy_after_rain
  ambient: humid_evening
  ongoing_events: []
  exits: [hallway, kitchen, front_door]
  version: 18
  last_event_id: evt_0042
```

保存：地点、在场主体、可见重要物体、天气、正在进行的公共事件、空间连接和可感知环境。

不保存：女主角未说出口的情绪、私密计划、主角未明确的内心、完整世界百科和历史全文。

## 6. ProtagonistState：唯一主角状态

`ProtagonistState` 只基于玩家明确输入和已确认事件更新：

```yaml
protagonist_state:
  protagonist_id: protagonist
  location_id: protagonist_apartment
  visible_action: sitting_near_table
  held_items: []
  explicit_condition: normal
  last_utterance_event_id: evt_0041
  version: 23
```

系统可以记录玩家明确说“我坐到你旁边”“我刚从店里回来”，不能推断并提交“主角已经决定让她永远留下”。重大选择必须有玩家明确证据。

## 7. LivingMind：女主角当前身心

每位女主角拥有独立 `LivingMind`：

```yaml
living_mind:
  save_id: save_001
  character_id: baiweixi
  form: human_with_visible_ears_tail
  location_id: protagonist_apartment
  posture: sitting_in_cardboard_box
  current_activity: eating_noodles
  interrupted_activity: null
  body:
    injury: mostly_recovered
    pain: mild_when_moving_fast
    fatigue: low
    hunger: decreasing
    magic: not_fully_recovered
  emotion:
    primary: relaxed
    secondary: guarded_affection
    causes: [safe_room, protagonist_nearby]
  attention: protagonist_question
  immediate_intent: finish_meal_then_talk
  confidence:
    current_activity: high
    emotion: medium
  version: 31
  last_event_id: evt_0042
```

### 7.1 持续规则

状态采用“默认持续，证据触发变化”：

- 如果上一轮正在吃饭，本轮只聊了几句话且没有完成、离开、被打断或大幅时间跳转，她仍在吃饭。
- 情绪不会因每条普通消息重置；新输入可以加强、缓和、混合或不改变情绪。
- 伤势、疲劳和妖力按事件与时间变化，不按措辞需要随机改变。
- 活动可以在对话时继续，例如边吃边回答；是否被打断由模型提出并给出证据。

### 7.2 自然变化来源

允许状态变化的证据类型：

1. 玩家明确行动或对白造成的即时影响。
2. 女主角在自身能力和意图范围内做出的决定。
3. 已提交事件的客观结果。
4. 明确的游戏时间流逝。
5. 身体或场景中持续过程达到合理阶段。
6. 新召回记忆对情绪或意图产生相关影响。

模型必须说明变化原因、变化幅度和受影响字段。程序不要求穷举事件类型，但会拒绝没有证据引用的高影响变化。

## 8. 唯一事实来源：追加式证据账本

所有已经发生的游戏事实先写入追加式 `WorldEventLedger`。投影可以重建，账本不原地覆盖。

```yaml
event:
  event_id: evt_0042
  save_id: save_001
  world_id: songjiangfu
  game_time_before: day11_evening_18_00
  game_time_after: day11_evening_18_03
  type: dialogue_and_activity_continue
  actor_id: protagonist
  participants: [protagonist, baiweixi]
  observers: []
  location_id: protagonist_apartment
  visibility: private
  knowledge_eligible_for: [protagonist, baiweixi]
  payload: "玩家询问她在做什么；白未晞边吃面边回答。"
  evidence_refs: [evt_0041]
  transaction_id: turn_0021
```

### 8.1 不变量

- `event_id` 和 `transaction_id` 唯一。
- 同一存档事件顺序可确定重放。
- 事件时间不逆行，除非事件类型是明确回忆叙述且不改变当前时钟。
- 修正通过 `correction_of` 新事件表达，不删除旧事件。
- 每个事件明确参与者、观察者、可见性和知识资格。
- 任何投影都保存 `last_event_id` 与版本。
- 角色回复只有在对应事件事务成功后才对用户可见。

## 9. 三层运行时记忆

### 9.1 工作激活区

工作激活区保存当前推理需要的少量高相关内容：

- 当前游戏时间与场景。
- 主角和激活女主角当前状态。
- 最近若干回合的原始对话。
- 当前未完成计划、承诺和冲突。
- 本轮选中的长期记忆证据。
- 当前输入路由结果。

工作激活区有 token 预算，不是长期存储。被移出工作区不等于遗忘。

### 9.2 语义投影

语义投影从账本物化，用于快速查询：

- 人物与世界事实投影。
- 关系里程碑和未解决张力。
- 承诺、修正和共同计划。
- 女主角自我时间线。
- 地点、物品和事件参与关系。
- 角色知道、怀疑和不知道的内容。

投影记录来源事件，冲突时不静默覆盖。必要时保留 `active`、`superseded`、`disputed`、`completed` 等状态。

### 9.3 前瞻状态

前瞻状态不是未来事实，而是有证据的持续倾向：

- 尚未完成的计划。
- 女主角想做但尚未做的事情。
- 对主角的期待、担忧和回避。
- 关系中的未解决问题。
- 身体过程的合理下一阶段。

前瞻状态用于产生内生主动性，不能直接当作已经发生的经历。

## 10. 女主角自我时间线与关系

### 10.1 自我时间线

每位女主角按 `character_id` 保存自己声称或经历的内容：

- 已发生经历。
- 计划。
- 欲望。
- 假设和想象。
- 否定。
- 对旧说法的修正。

模型必须区分“我吃过了”“我准备吃”“如果有面就好了”“我没吃”和“刚才说错了”。同一时间槽和事件类型冲突时，系统要求修正关系或保持争议，不能只保留最后一句。

### 10.2 关系状态

关系不是单一好感数值。至少包括：

```yaml
relationship_state:
  character_id: baiweixi
  protagonist_id: protagonist
  stage: early_cohabitation
  trust_evidence: [evt_0010, evt_0024]
  attachment_tendency: growing
  boundaries: [not_confirmed_romance, no_unconditional_obedience]
  unresolved_tensions: [fear_of_being_asked_to_leave]
  shared_plans: []
```

数值可以用于排序和调度，但自然语言关系投影与证据必须保留。关系变化由事件累积和角色解释产生，不因单句夸奖直接跨越多个阶段。

## 11. 多线索索引与记忆选择

每个事件和记忆表示至少建立以下线索：

- 语义向量。
- 人物 ID。
- 事件参与者与观察者。
- 地点与物品。
- 主题、关系和情绪。
- 游戏时间、时间槽和事件类型。
- 承诺、修正、计划、未完成状态。
- 可见性与知识资格。
- 重要度、新近度和当前关联度。

### 11.1 合法候选宇宙

在进行相似度粗召回前，先按权限构造当前女主角可知的记忆宇宙：

```text
EligibleMemory(character_id) =
  亲自参与
  ∪ 在场观察
  ∪ 后续被可信告知
  ∪ 按正典可知的公开世界信息
```

其他女主角的私密对话、关系事件、私密自我时间线不进入候选宇宙，即使语义高度相似。

### 11.2 选择流程

```text
权限过滤
→ 多线索粗召回
→ 稳定 Top32 候选
→ 学习式 reranker
→ 去重与冲突成组
→ token 预算装配
→ SelectedMemoryFrame
```

正式在线链路保持全局记忆选择器合同：CPU 语义粗召回、稳定 Top32、GPU 批量重排、普通回合记忆选择 P95 小于 300 毫秒。具体模型工件以产品集成设计与冻结 manifest 为准。

### 11.3 无记忆也是结果

选择器必须能够返回空集。没有证据时，回复应承认不知道、记不清或从当前语境作有限推测，不能为了显得亲密而编造共同经历。

## 12. 输入路由

`INPUT_GROUND` 将玩家输入落到以下类型，可同时包含多个片段：

- `DIEGETIC_DIALOGUE`：主角在游戏内说的话。
- `DIEGETIC_ACTION`：主角明确执行的游戏内动作。
- `DIEGETIC_NARRATION`：玩家描述的场景或时间推进候选。
- `OOC_COMMAND`：设置、存档、调试、改名、暂停等游戏外命令。
- `REALITY_SAFETY`：现实紧急情况、自伤、医疗、犯罪或立即危险。
- `AMBIGUOUS`：无法确定属于游戏内还是现实层。

混合输入要分段处理。OOC 信息不写入普通角色记忆；现实安全信息优先交给产品安全层。`AMBIGUOUS` 高风险时必须澄清，不能让角色假装在现实中行动。

## 13. 游戏行动与现实工具分离

`DiegeticAction` 只改变游戏世界，例如白未晞在游戏中去厨房、拿毛巾、走到主角旁边。

`ExternalToolAction` 是软件真实调用，例如打开网页、发送通知、读取现实定位。女主角模型默认没有此权限。未来若产品增加工具，必须经过独立授权和现实层 UI，不得以角色对白暗示已经执行。

## 14. 模型调用模式

同一个主模型可以通过严格模式提示复用不同任务，但每种模式拥有独立 schema、token 预算和失败策略。

### 14.1 `INPUT_GROUND`

输入：玩家原文、最小场景信息。  
输出：分段后的输入类型、明确行动、时间表达、现实风险和不确定项。  
禁止：生成角色回复或写入状态。

### 14.2 `MEMORY_RERANK`

输入：当前语境与合法 Top32 候选。  
输出：候选相关性、使用理由和拒绝理由。  
正式在线可由专用 reranker 工件实现，不生成自然语言回复。

### 14.3 `WORLD_MIND_ADVANCE`

输入：旧 `GameClock`、`SceneMind`、`ProtagonistState`、激活女主角 `LivingMind`、相关投影、记忆、正典和路由结果。  
输出：结构化状态差异、证据引用、变化原因、女主角即时意图和回复语义计划。

关键要求：

- 每个变化字段都标明 `keep`、`update`、`clear` 或 `unknown`。
- `update` 必须引用本轮输入、旧事件、时间推进或持续过程。
- 默认是 `keep`，不是重新生成全部状态。
- 不能修改未激活女主角的私密状态。

### 14.4 `WORLD_CONTINUITY_REVIEW`

输入：旧状态、候选新状态、回复语义计划和证据。  
输出：`PASS`、`REVISE` 或 `REJECT`，以及限定问题列表。

检查：

- 日期和时间是否一致。
- 空间移动是否有路径和时间。
- 活动是否无故切换。
- 身体和形态变化是否符合能力与恢复过程。
- 情绪变化是否有原因且幅度合理。
- 使用的知识是否对该女主角可见。
- 是否把未来计划说成已发生。
- 是否替主角做重大决定。
- 回复是否与候选新状态一致。

### 14.5 `GAME_REPLY`

输入：通过审查的候选新状态、相关记忆和角色包口吻合同。  
输出：最终可见角色回复，可附受控表现标签。  
禁止：重新决定一套不同状态、暴露内部结构或引用不可见记忆。

### 14.6 后台投影模式

- `MEMORY_PROPOSE`：提出值得长期保存的事件表示。
- `SELF_TIMELINE_PROPOSE`：区分经历、计划、欲望、假设、否定和修正。
- `RELATIONSHIP_PROJECT`：更新关系里程碑和未解决张力候选。
- `MOTIVE_EVALUATE`：评估持续欲望是否形成下一步意图。
- `OFFSCREEN_UPDATE`：未来显式离线推进使用；P0 默认关闭。

这些模式只能基于已经提交的本轮事件运行。后台失败不回滚已显示回复，也不能反向改写本轮事实；可稍后重试并按 `transaction_id` 去重。

## 15. 单回合事务

### 15.1 标准流程

```text
1. 锁定 save_id 与 active_character_id
2. 读取正典版本和上一状态版本
3. INPUT_GROUND 路由玩家输入
4. 权限过滤并选择相关记忆
5. WORLD_MIND_ADVANCE 生成状态差异与回复语义计划
6. 程序执行 schema、版本和硬不变量检查
7. WORLD_CONTINUITY_REVIEW 审查连续性
8. 必要时受约束重算，最多固定次数
9. GAME_REPLY 从通过的新状态生成最终回复
10. 程序复核回复与状态关键断言
11. 在单一事务中追加事件、更新投影版本、保存回复
12. 事务成功后向用户显示回复
13. 后台运行长期记忆与投影候选
```

### 15.2 原子提交

事务至少同时提交：

- 玩家输入事件。
- 时间与场景事件。
- 主角明确状态变化。
- 激活女主角状态变化。
- 角色回复事件。
- 新状态版本和最后事件 ID。

若任一核心写入失败，整轮不生效，界面显示可重试错误。不得出现角色已经说“我吃完了”，重启后却恢复为未发生该回复的中间状态。

### 15.3 并发控制

P0 每个 `save_id` 同时只允许一个前台回合事务。新消息到达时：

- 可以取消尚未提交的生成。
- 已提交事务不可撤销，只能新增修正事件。
- 后台投影任务暂停或取消，避免与前台争抢主模型。

## 16. 状态与回复一致性断言

在最终提交前，程序从候选状态生成少量可检查断言，例如：

- `current_activity=eating_noodles`
- `location_id=protagonist_apartment`
- `day_index=11`
- `form=human_with_visible_ears_tail`

审查器检查回复是否直接冲突。断言不是用于限制所有自然语言，而是拦截高价值硬矛盾。无法可靠判定时，优先让回复使用不越界的措辞，而不是编造更具体事实。

## 17. 状态自然变化示例

### 17.1 多轮对话中继续吃饭

初始：`current_activity=eating_noodles`。  
玩家连续询问过去和天气，没有时间跳转或动作中断。  
模型输出：活动 `keep`，注意力转向对话，回复可以“还在吃。你问这么多，我面都要凉了。”

这不是靠翻找第一轮原文，而是读取持续存在的 `LivingMind.current_activity`。

### 17.2 自然吃完

玩家说“你慢慢吃”，随后明确推进二十分钟。  
`WORLD_MIND_ADVANCE` 根据时间、食物活动和无新阻碍提出：`current_activity` 从吃面变为收碗，饥饿下降，可能轻度放松。  
审查通过后，回复从新状态出发。

### 17.3 被打断

玩家叙述门外突然传来巨响。  
模型可以把吃饭放入 `interrupted_activity`，当前活动变为警觉地看向门口，情绪增加戒备。声音事件、猫科习惯和场景提供证据。

### 17.4 不允许的跳变

普通闲聊后，模型把活动从吃饭改成弹钢琴、地点从出租屋改到咖啡厅、日期从第十一日改为第十二日，却没有移动、结束、时间或事件证据。审查器必须拒绝。

## 18. 形态、能力和世界连续性

角色包定义能力边界，状态推进必须遵守：

- 形态变化需要角色能力、意图、妖力和合理场景。
- 隐藏耳尾消耗妖力，不能同时长期维持且声称毫无消耗。
- 受伤恢复需要事件和时间，不能因回复需要瞬间痊愈。
- 空间移动需要路径和时间，不能同一时刻处于两个地点。
- 女主角不能使用角色包未定义的大规模法术解决剧情。
- 世界未定义事实保持未知，不由模型临时补全为权威。

## 19. OOC、现实安全与记忆隔离

### 19.1 OOC

“保存游戏”“把字体调大”“暂停一下”“这段设定重来”等输入属于产品控制，不作为主角对白，不写入女主角记忆。若玩家明确使用 OOC 与角色讨论，也只能写入独立的非正典会话层。

### 19.2 现实紧急情况

若玩家表达现实中的立即危险，产品安全层先提供现实可执行建议、求助渠道和澄清。角色回复不能声称自己会真实下楼、开车、报警或到现实中陪伴。

### 19.3 游戏内紧急剧情

若语境明确属于游戏世界，女主角可以执行符合场景和能力的叙事行动。该行动写入游戏事件，不触发现实工具。

## 20. 角色包加载

运行时启动时按以下顺序加载：

1. 项目 schema 与当前实现版本。
2. `WorldCanon(world_id)`。
3. `ProtagonistCanon(protagonist_id)`。
4. 存档注册的女主角包 manifest。
5. 当前 `active_character_id` 的角色正典与专属资产。
6. 存档事件和各类投影。

P0 若 `active_character_id != baiweixi`，返回尚未支持的明确错误，而不是回退到历史角色或默认人格。未来扩展允许切换激活角色，但切换事件必须写入账本并更新场景参与者。

## 21. 上下文合同

最终回复上下文按优先级装配：

1. 模式协议与安全边界。
2. 当前女主角角色包的稳定正典摘要。
3. 共享世界与主角相关摘要。
4. 通过审查的候选新 `GameClock`、`SceneMind`、`ProtagonistState`、`LivingMind`。
5. 当前关系、未完成计划和自我时间线相关投影。
6. `SelectedMemoryFrame`。
7. 最近对话和本轮玩家输入。

不得装入：

- 其他女主角不可知的私密正典或记忆。
- 原始数据库大段转储。
- 历史角色秦未晞提示词。
- OOC 调试信息。
- 审查器内部思考或未通过状态候选。

## 22. 性能与调度

### 22.1 前台优先

普通回合执行：输入落地、记忆选择、一次状态推进、必要的审查、一次最终回复。状态推进和回复可以在未来通过联合解码优化，但事务语义不能改变。

后台 `MEMORY_PROPOSE`、`SELF_TIMELINE_PROPOSE`、`RELATIONSHIP_PROJECT` 和 `MOTIVE_EVALUATE` 复用主模型，前台新消息到达时暂停或取消。

### 22.2 当前目标

- 热启动首字 P95 小于 2 秒。
- 80 token 回复 P95 小于 5 秒。
- 160 token 回复 P95 小于 8 秒。
- 普通记忆选择新增 P95 小于 300 毫秒。
- P0 总显存阻塞目标低于 5120 MiB，以完整进程实测为准。

若双模型调用使延迟不达标，优先优化上下文、量化、联合候选、审查触发策略和缓存，不得删除状态事务或让最终回复绕过更新后状态。

### 22.3 审查降级

低风险普通闲聊可以使用轻量审查路径，但以下情况必须完整审查：

- 时间、地点、形态或活动变化。
- 身体伤势、能力和重要物品变化。
- 关系阶段、承诺和重大情绪变化。
- 主角行动候选。
- 私密知识和跨角色记忆。
- 游戏/现实语境不确定。

## 23. 训练与数据

需要分别建设：

- `INPUT_GROUND` 的混合语境分类和行动抽取数据。
- `WORLD_MIND_ADVANCE` 的旧状态 + 输入 + 时间 + 记忆 → 状态差异轨迹数据。
- `WORLD_CONTINUITY_REVIEW` 的正确轨迹、无证据跳变和知识越权对比数据。
- 全局记忆选择器的 Top32 硬标签与困难负样本。
- 通用自由对话与协议遵循数据。
- 按 `character_id` 隔离的角色人格数据。

训练样本必须显式区分：当前状态、历史事件、未来计划、假设、OOC 和现实层。不能把角色回复中的文学修辞直接当作客观状态标签。

## 24. 验收标准

### 24.1 当前状态

- 同一活动跨 5～10 个无变化回合保持一致。
- 明确结束、打断或时间推进后可以合理变化。
- 时间、位置、形态、身体和情绪变化都有可追溯证据。
- 最终回复与提交后的状态不冲突。

### 24.2 记忆与关系

- 已提交的重要经历、承诺、修正和计划可以跨重启召回。
- 没有证据时不伪造共同历史。
- 同一时间槽冲突不会静默覆盖。
- 关系推进符合角色包，不因单轮输入机械跳级。

### 24.3 多角色数据边界

- 所有女主角状态和专属投影带 `character_id`。
- 私密事件不会进入无资格角色的候选记忆宇宙。
- 当前角色上下文不含历史角色提示词或其他角色秘密。
- P0 只激活白未晞，但事件 schema 可表达未来多参与者。

### 24.4 系统

- 崩溃后账本可重放，投影可重建。
- 同一事务重复提交不会生成重复事件。
- 回复未成功显示时不会留下半提交重大事实。
- 取消、超时和模型失败有明确降级，不静默损坏存档。

## 25. 失败模式与降级

- **输入路由不确定**：低风险按游戏内对白处理，高风险或现实风险先澄清。
- **记忆选择失败**：使用当前状态和近期对话继续，禁止伪造长期记忆。
- **状态推进 schema 失败**：重试一次；仍失败则保持旧状态并生成不引入新事实的保守回复。
- **连续性审查拒绝**：带限定问题重算；超过上限则回退到保持状态的回复。
- **最终回复冲突**：重新生成 `GAME_REPLY`，不重新推进状态。
- **持久化失败**：不显示候选回复，整轮回滚。
- **后台投影失败**：记录任务并稍后重试，不影响已提交回合。
- **角色包缺失或版本不兼容**：阻止进入存档并显示明确修复信息，不自动换成其他角色。

## 26. 实施顺序

### 阶段 A：角色中立数据合同

冻结 `save_id`、`world_id`、`protagonist_id`、`character_id`、事件可见性和状态版本 schema；迁移白未晞为首个角色包。

### 阶段 B：自由对话基线

在不依赖高级记忆掩盖问题的前提下，冻结白未晞自由对话、角色忠实度和真实本地模型基线。

### 阶段 C：当前世界持续性

接入 `GameClock`、`SceneMind`、`ProtagonistState`、`LivingMind`、`INPUT_GROUND`、`WORLD_MIND_ADVANCE`、连续性审查和原子提交。

### 阶段 D：长期记忆

接入追加式账本、工作激活区、语义投影、多线索粗召回、稳定 Top32、reranker 和跨重启恢复。

### 阶段 E：自我时间线与内生主动性

接入修正冲突、自我时间线、关系前瞻、欲望意图和受限主动评估。

### 阶段 F：表现与语音

表现和语音只读取已提交状态及回复；资源按 `character_id` 加载，不产生第二套 AI 事实。

### 阶段 G：第二女主角验证

在单角色闭环通过后，用第二个正式角色包验证同一存档、知识隔离、角色切换和共同事件，不先做多角色并发生成。

## 27. 明确边界

- 本设计是当前唯一 AI 运行时架构；产品集成文档不得另建一套记忆或状态系统。
- 当前非权威 V4 调研中的 `GameClock`、`SceneMind`、`LivingMind`、`ProtagonistState`、输入路由和连续性审查已在本文件转为现行实现合同。
- 角色包定义内容，运行时定义持续存在方式，两者不得混为一体。
- 白未晞是首个验证角色，不是硬编码架构名。
- 秦未晞是历史角色，其文档、训练资产和提示词不得进入当前默认链路。
- P0 不实现多女主角同时在场，但不允许留下只能保存一个匿名 `girlfriend_state` 的结构。
