# CHAT-02E：回复模型路线比较——基座上下文、角色微调与云端 GPT-5.6

> 状态：技术评估与决策实验，不替代现行本地产品需求  
> 日期：2026-08-06  
> 依据：CHAT-02D 自动基线、CHAT-02E 40 条人工盲评、现行项目需求与最小心智系统  
> 本文不启动训练、不接入云 API、不修改现行唯一记忆架构

## 1. 要回答的问题

本次评审提出了三个合理问题：

1. 如果未训练的 Qwen3-4B 基座加人格上下文已经不弱于旧 LoRA，回复模型是否可以不训练？
2. 如果人格可以通过上下文建立，是否应直接使用能力更强的通用模型？
3. 如果使用 GPT-5.6 这类云端顶级模型，我们自己的模型与运行时还有没有价值？

结论先行：

- **当前应暂停继续训练回复模型，先完成基座 + 上下文路线的独立基线。**
- **当前证据只能否定旧 v1 的 295 条训练方案，不能证明所有微调都无价值。**
- **云端 GPT-5.6 Sol 很可能提供最高的单轮理解和稳健性上限，但不是现行“完全本地、断网可用、默认不上传”产品的直接替代品。**
- **无论使用本地基座、微调模型还是 GPT-5.6，关系连续性运行时都不能删除。模型能力越强，越能利用正确记忆；它不会自动拥有本地账本中的长期经历。**
- **当前最优工程路线是：GPT-5.6 作为质量上限、评审器和数据教师；Qwen3-4B 基座 + 上下文先作为本地正式候选；只有测出明确且稳定的人格缺口后，才训练新的回复 LoRA。**

这里的“暂停训练”只指秦未晞回复大模型的 LoRA。全局记忆选择器中的关系重排器属于另一项模型任务，是否训练仍由其独立冻结评测决定；两者不能混为一谈。高质量角色数据也仍然需要，只是优先用于冻结评测、prompt 示例、教师改写和缺口覆盖，而不是默认全部送入 SFT。

## 2. 评审结果真正说明了什么

本轮被比较的训练模型高置信来自旧 v1：295 条 ShareGPT 会话、266 条实际训练记录、600 iterations，而不是当前 2500 条 v4 数据。

40 条人工盲评：

| 指标 | Qwen3-4B 基座 + 同一运行时人格锚 | 旧秦未晞 LoRA + 同一人格锚 |
|---|---:|---:|
| 胜出题数 | 16 | 14 |
| 六维均分 | 4.029 | 3.925 |
| relevance | 3.600 | 3.075 |
| correctness | 3.650 | 3.025 |
| persona_fit | 4.100 | 4.200 |
| relationship_naturalness | 4.275 | 4.350 |
| emotion_fit | 4.300 | 4.425 |
| naturalness | 4.250 | 4.475 |
| fact_error | 11 | 19 |
| off_topic | 5 | 11 |
| fabricated_reality | 1 | 4 |
| assistant_tone | 3 | 0 |

这说明：

- 基座通过上下文已经能表现出较强的秦未晞人格，并保留了更好的理解和事实能力。
- 旧 LoRA 的主要收益是口语、情绪、关系感和消除助手腔。
- 旧 LoRA 的代价是相关性、正确性和现实证据边界退化。
- “训练后有风格变化”不等于“训练后产品质量更好”。

但这组结果**没有**证明：

- 2500 条清洗后的新数据也会失败，因为它尚未训练。
- 基座 + 当前 prompt 已经达到产品质量闸门，因为双方仍有 7 条都不可接受。
- 只靠一个固定 system prompt 就能维持几个月关系连续性。
- GPT-5.6 在秦未晞任务上一定获胜，因为尚未用同一冻结集实测。

## 3. 上下文设定能替代什么

“上下文设定”不是只写一句“你是秦未晞”。在本项目中，合格的每轮输入应由以下部分组成：

```text
稳定人格合同
+ 当前关系阶段与身份锚
+ 最近对话原文
+ 当前工作状态
+ 本轮召回的有证据记忆
+ 必要的安全和输出边界
-> 通用基座生成回复
```

它可以替代或显著减少微调承担的内容：

- 角色姓名、年龄、职业、关系阶段等显式事实。
- 不使用助手腔、不编造现实、不机械任务化等行为合同。
- 当前心情、话题、称呼倾向和关系状态。
- 本轮真正相关的玩家记忆和共同经历。
- 少量风格示例与输出长度要求。

它不能独自解决：

- 数月原始聊天永久保存。
- 在有限上下文中从全部历史找出正确经历。
- 玩家纠正旧事实后的版本关系。
- 重启后的连续性。
- 计划、承诺和共同约定的可靠状态转换。
- 上下文没有提供的信息。

所以“基座 + 上下文”可以替代回复 LoRA 的一部分职责，但不能替代 RelationshipRuntime。

## 4. 三条正式路线比较

| 维度 | 本地基座 + 上下文 | 本地角色 LoRA + 上下文 | 云端 GPT-5.6 Sol + 上下文 |
|---|---|---|---|
| 当前实测质量 | 略胜旧 LoRA | 旧版整体略输基座 | 尚未实测，理论上限最高 |
| 中文理解/常识 | 保留基座能力 | 可能因 SFT 退化 | 通常最强 |
| 人格鲜明度 | 依赖 prompt、示例和记忆 | 可把稳定风格写入权重 | 强模型通常能很好遵循角色合同 |
| 长期记忆 | 仍需 RelationshipRuntime | 仍需 RelationshipRuntime | 仍需 RelationshipRuntime |
| 无证据编造 | 由模型能力 + 上下文边界决定 | 数据不佳会把编造写入权重 | 能力更强但仍可能编造，必须提供证据边界 |
| 严肃支持 | 基座当前明显优于旧 LoRA | 需要高质量情境数据 | 预计最好，必须实测 |
| 首字延迟 | 本机已测约几十毫秒级服务响应 | 与基座接近，回复更短 | 网络 + 排队 + 推理，波动更大 |
| 单轮成本 | 购置硬件后的边际成本低 | 同左，另有训练成本 | 按 API 输入、输出及可能的推理 token 持续计费 |
| 隐私 | 对话不离开设备 | 对话不离开设备 | 需要上传本轮对话和选中记忆，必须单独评估数据条款与配置 |
| 离线 | 支持 | 支持 | 不支持 |
| 可复现性 | 模型文件和参数可冻结 | 模型、adapter、数据和参数都需冻结 | 服务模型可能更新，必须记录实际返回模型和请求合同 |
| 8GB 显卡 | 符合现行目标 | 符合现行目标 | 本地显卡不承担主模型推理 |
| 开发复杂度 | 最低 | 数据、训练、导出和回归链路最高 | API、鉴权、费用、网络故障和隐私同意链路 |
| 现行需求符合度 | 完全符合 | 完全符合 | 不符合“正式核心完全本地”的当前要求 |

## 5. 是否可以完全不训练

### 5.1 现在可以暂停训练

现阶段没有理由立刻把 2500 条 v4 送去训练。正确顺序应是：

1. 用未训练 Qwen3-4B 基座建立完整的“人格锚 + 最近对话 + 工作状态 + 召回记忆”基线。
2. 修正 prompt，但不针对冻结测试答案逐题打补丁。
3. 重新执行 CHAT-01/02 自动评测、40 条盲评和长对话。
4. 只有基座路线存在稳定、可复现且 prompt 无法解决的人格缺口，才决定训练。

这能避免把训练当作默认步骤，也能避免新 LoRA 再次损伤基座能力。

### 5.2 现在不能宣布永远不训练

微调仍可能在以下条件下有价值：

- 基座持续出现助手腔，而更强 prompt 会显著增加上下文或造成机械回答。
- 基座在长对话压力下逐渐丢失角色口吻和独立立场。
- 角色特有的语用行为无法靠少量示例稳定触发。
- 希望缩短固定人格 prompt，降低本地首字延迟和上下文占用。
- 未来多个角色共用同一基座，需要用 adapter 低成本切换稳定风格。

但训练必须满足一个原则：**只训练已经测出的稳定缺口，不再把整个角色人生和所有行为一股脑灌进权重。**

新 LoRA 更适合学习：

- 克制的说话节奏和句式分布。
- 非助手式但仍准确承接的表达方式。
- 严肃、日常、冲突、害羞等情境中的人格调节。
- 不编造共同经历、信息不足时保持未知等行为边界。

不适合写入权重的内容：

- 玩家部署后产生的个人事实和共同经历。
- 会变化的关系状态、计划、承诺和时间信息。
- 为修单个评测题添加的固定答案。

## 6. 使用 GPT-5.6 会不会更好

### 6.1 单纯看回答质量：很可能更好

根据当前 OpenAI 模型资料，`gpt-5.6` 是指向 `gpt-5.6-sol` 的最新旗舰别名；Sol 面向质量优先和困难推理工作。关系聊天并不需要最高推理强度，首轮测试应显式使用低延迟设置，例如 `reasoning.effort: none` 或 `low`，不能因为“最高级”就默认开到最大推理。

相对本地 Qwen3-4B，GPT-5.6 Sol 的潜在优势是：

- 对含糊表达、反讽、情绪和复杂指代的理解更强。
- 更能同时遵守“有人格、准确承接、不编经历、严肃时克制”等多重约束。
- 常识、安全、写作变化和长上下文利用能力更强。
- 更少需要通过 LoRA 弥补基础能力不足。

但“很可能”不能替代实测。恋爱角色不是通用榜单任务，顶级模型也可能：

- 过于圆滑、礼貌或像心理咨询师。
- 安全策略过度显眼，破坏亲密对话自然度。
- 在长 prompt 下逐渐遵循最近指令而淡化角色。
- 生成更长、更完整但不够像真人聊天的回答。
- 因服务更新产生行为漂移。

### 6.2 它不是 ChatGPT 客户端的直接嵌入

产品里应使用 OpenAI API 模型 ID，例如显式的 `gpt-5.6-sol`；“ChatGPT”是面向用户的产品。ChatGPT 订阅不能直接视为桌面宠物的 API 调用额度，API 鉴权、账单、限额和数据设置需要独立处理。

### 6.3 超大上下文不等于把全部人生塞进去

GPT-5.6 Sol/Terra 的资料快照显示其上下文规模可达约一百万 token，但这不意味着应该每轮上传全部聊天：

- 输入越长，费用和延迟越高。
- 大量无关历史会稀释当前问题和真正相关记忆。
- 全量上传扩大隐私暴露范围。
- 长期关系中的修正、冲突和有效状态仍需结构化管理。

正确做法仍然是本地保存全部账本，每轮只向云模型发送稳定人格锚、最近对话和本轮相关记忆。云端只替换 `REPLY` 模型，不替换记忆系统。

## 7. GPT-5.6 对现行产品需求的影响

现行需求明确规定：

- P0 核心断网后仍可使用。
- 对话与语音默认不上传。
- 不使用云端推理作为正式产品的必要依赖。
- 首字延迟 P95 小于 2 秒。

因此 GPT-5.6 不能在不修改需求的情况下成为唯一正式回复模型。可选定位有三种：

| 定位 | 是否改变需求 | 建议 |
|---|---|---|
| 开发期质量上限/教师/评审器 | 否 | 立即采用，价值最高 |
| 用户主动开启的云端增强模式 | 需要补充隐私、费用和降级要求 | P0 本地通过后再评估 |
| 唯一正式回复模型 | 是，直接取消完全本地核心 | 当前不建议 |

如果项目负责人决定把产品从“完全本地 AI 女友”改为“联网 AI 女友”，这是产品战略变更，需要同时修改需求、隐私政策、部署设计、成本模型、故障降级和验收标准，不能只把模型 ID 换掉。

## 8. 推荐的四路决策实验

为了避免继续凭感觉讨论，下一步应使用完全相同的冻结输入比较：

| 候选 | 目的 |
|---|---|
| A：Qwen3-4B 基座 + 当前上下文 | 保留当前基线 |
| B：Qwen3-4B 基座 + 改进后的最小人格/证据上下文 | 判断不训练的本地质量上限 |
| C：GPT-5.6 Sol + 与 B 语义等价的上下文 | 建立云端质量上限 |
| D：GPT-5.6 Terra + 与 B 语义等价的上下文 | 比较更合适的延迟和成本档位 |

旧 LoRA 作为历史对照保留，不再作为未来候选。2500 条 v4 不训练，直到 A-D 结果出来。

### 8.1 必须控制的变量

- 同一套角色正典、关系阶段、最近对话和 SelectedMemoryFrame。
- 相同最大回复长度和输出格式。
- 云模型显式固定 reasoning effort，首次用 `none`，再按需要测试 `low`。
- 不向模型发送评测 rubric、禁答清单或参考答案。
- 记录实际返回模型 ID、首字延迟、总延迟、输入/输出/推理 token 和失败率。
- 本地与云端都做 40 条冻结盲评、严肃支持、无证据记忆、现实未知和长对话。
- 评审时隐藏模型身份，至少两名独立评审。

### 8.2 决策指标

质量优先级：

1. `fabricated_reality` 和事实错误。
2. 当前问题承接与严肃支持。
3. 人格自然、关系感和非助手腔。
4. 长对话中的角色漂移与记忆误激活。
5. 首字延迟、总延迟、费用和可用性。

不能用一个总平均分掩盖 P0 失败。任何候选若在健康、安全、现实编造或关系边界上出现阻断，即使人格分高也不能通过。

## 9. 决策规则

实验后按以下规则决策：

### 情况一：本地 B 达到质量闸门

正式产品采用“Qwen3-4B 基座 + RelationshipRuntime + 最小人格上下文”，取消当前回复 LoRA 前置要求。2500 条数据保留作测试、示例筛选和未来缺口修复，不直接训练。

### 情况二：本地 B 只在人格/助手腔上稳定落后，通用能力合格

针对明确缺口制作小而高质量的行为数据，训练最小 LoRA；每次训练必须证明人格收益没有换来事实、相关性和安全退化。

### 情况三：GPT-5.6 明显领先，但本地 B 未达标

不立即取消本地产品。将 GPT-5.6 用作教师生成候选、困难样本改写和盲评质量上限，再训练或蒸馏本地模型。是否增加用户自愿云模式作为独立产品决策处理。

### 情况四：项目决定云端质量优先于本地性

正式修改需求后，采用“本地 RelationshipRuntime + GPT-5.6 API REPLY + 本地基座离线降级”。仍不应把全部记忆上传，也不能删除本地证据账本。

## 10. 当前建议

当前最合理的施工决策是：

1. 暂停 2500 条回复模型训练。
2. 不删除训练管线，只把它从默认路线改成“评测证明有必要后才启用”。
3. 先完成 Qwen3-4B 基座 + 最小上下文的 CHAT-02 新候选。
4. 接入 GPT-5.6 Sol/Terra 仅用于同题质量上限实验；在用户明确批准修改产品需求前，不作为正式依赖。
5. 保留并继续实现 RelationshipRuntime，因为它与选择哪个回复模型无冲突。
6. 用四路盲评结果决定是否训练，而不是用“模型越大”或“数据越多”的直觉决定。
