# 权重 NPC vs 快轨 NPC：全用方案二 vs 中间路线 分析

> 性质：决策分析文档（非实现）。回答"既然两路线差别不大，能否全用快轨+prompt 锚方案二"。
> 结论：不建议全用方案二。推荐"2-3 个 hero + 其余方案二"的中间路线。
> 日期：2026-08-01。

---

## 0. 前提澄清

在我们方案里，"权重 NPC（hero）"**不是纯权重**，而是 **per-NPC LoRA（稳定人格/口吻在权重）+ 快轨记忆（易变事实/经历）**；"背景 NPC"是 **快轨记忆 + prompt 锚（人格在 prompt）**，两者共享同一"通用角色能力 SFT"基座。

所以真正对比的是：**hero（权重+快轨）vs 背景（快轨+prompt）**，共同部分（基座、快轨）剥离后，差异集中在下表。

---

## 1. 真实差别表（剥离共享部分）

| 维度 | Hero(权重+快轨) | 背景(快轨+prompt锚) | 差别 |
|---|---|---|---|
| 口吻保真度 | 高（口吻/口头禅/节律在权重） | 中（prompt 软指令） | 明显 |
| 长对话/上下文重置后是否漂 | 不漂 | 会漂（锚被历史挤掉） | **关键** |
| 抗"助手腔"残留 | 强（训练时一致性检查硬卡 <5%） | 弱（靠 prompt 约束，易漏） | 明显 |
| 改人格 | 重训 LoRA | 改 prompt | 方案二优势 |
| 每 NPC 额外显存 | +~56MB(adapter) | 0 | 方案二优势 |
| 动态性/反应力（像活人） | 一样 | 一样 | 无差 |

"差别不大"只对**短对话、口吻要求不高、上下文不爆**的场景成立。全用方案二，主要赌三件事不出问题：① 长对话漂移 ② 助手腔漏 ③ 口吻保真。

---

## 2. 全用方案二会怎样（逐项研究）

### 2.1 长对话/上下文重置漂移——方案二最大结构性弱点

prompt 锚在对话变长时被挤进历史深处，注意力稀释，人格漂。缓解手段与天花板：
- 锚放 system 且每轮重复：有效但吃 token（每轮 +200-400 token），且 >8k 上下文后 system 影响力仍衰减。8GB 卡上下文本就短(2k)，挤掉锚更严重。
- 压缩对话历史：延缓不根治。
- 快轨"自我提醒"：把 persona 关键点当记忆检索注入——本质是"用记忆补权重的活"，每轮多一次检索+拼装，且记忆里的人格描述 ≠ 权重固化的人格，仍可能矛盾。

**结论**：漂移可缓解不可消除。短交互背景 NPC 无所谓；玩家长期对话的主角会出戏。hero tier 不是锦上添花，是长对话保真的结构性保障。

### 2.2 助手腔残留——方案二更脆

基座做角色 SFT 后助手腔已大幅压住，方案二有底。但 prompt 锚对"别像 AI"这类反向指令约束力弱于权重——权重是正面积淀"此人怎么说话"，prompt 是禁止"别那样说话"，后者在长上下文/边界情况更易漏。权重训练时一致性检查把助手腔当命门硬卡（<5%），是 prompt 给不了的保险。

**结论**：基座角色 SFT 后方案二助手腔可控但更脆，长对话更易漏出。主角级 NPC 不宜赌。

### 2.3 口吻保真度

prompt 描述口吻（"温和、偏书面、爱用省略号"）能引导但达不到权重级细腻——口头禅频率、句长分布、犹豫词节律，prompt 描述不准也约束不严。短对话看不出，长期相处的 NPC 会"串味"。

**结论**：背景 NPC 够；主角"这个人的质感"会打折。

---

## 3. 全用方案二的可行性（分场景）

| 场景 | 全用方案二可行? | 翻车点 |
|---|---|---|
| NPC 都只短交互（路边、商店） | ✅ 完全可行 | 无 |
| 玩家长期对话少数 NPC（剧情主角） | ⚠️ 能跑但体验降级 | 长对话漂移、口吻串味 |
| "NPC 个性是卖点"的游戏 | ❌ 不建议 | 主角分不清、助手腔漏出 |
| 8GB 卡想最大化 NPC 数 | ✅ 性能最优 | 无（这正是方案二价值） |

---

## 4. 全用方案二的真实代价

1. **主角失去识别度**：权重 NPC 口吻长期稳定可识别，玩家会和"那个人"建立关系。全 prompt NPC 跑久后所有主角趋于平均口吻（共享基座+相似 prompt 结构），瓦解"让 NPC 像特定的人"的初衷。
2. **失去项目差异化**：全方案二只剩快轨记忆成长——恰是 mem0/Letta/AIRI/ACE 都在做的事，退回同质化，丢失《技术路线对比》里核心价值（hero 反射闭环 + 集体演化共享固化层）。
3. **省下的显存有限**：hero adapter ~56MB/个，3 个才 0.17GB。8GB 卡上为省这点显存放弃主角质感不划算——瓶颈是 KV-cache（每 NPC 144-288MB）和游戏渲染占显存，不是 adapter。

---

## 5. 判断条件

**全用方案二合理的条件**（任一）：
- NPC 都是短交互、没有玩家长期相处的角色
- 单卡预算极紧、且接受主角质感打折换更多 NPC
- 不追求"NPC 个性是核心卖点"

**不该全用方案二**（任一）：
- 有玩家长期对话的剧情主角（hero 的长对话抗漂是结构性的）
- NPC 个性/人格是游戏卖点（全 prompt 会串味、助手腔易漏）
- 想保留项目差异化（权重成长 + 反射闭环）

---

## 6. 推荐：中间路线

**2-3 个 hero + 其余全方案二** 的极简 tier：
- **2-3 个 hero**（玩家长期相处的主角）：per-NPC LoRA，保口吻+抗漂+权重成长。代价仅 ~0.17GB 显存。
- **其余所有 NPC**：方案二（快轨+prompt锚），拿最大数量与灵活。
- **基座**都做角色 SFT（杀助手腔，是方案二能用的前提）。

8GB 卡上：hero 显存代价几乎可忽略，却保住主角体验和项目差异化，又拿到方案二"背景 NPC 最大化"的好处。比"全用方案二"只多 ~0.17GB，但避免它在主角上的三个翻车点。

---

## 7. 一句话结论

不建议全用方案二。全用方案二在背景 NPC 上完全可行且是性能最优解，但对玩家长期对话的主角会翻车（长对话漂移、口吻串味、助手腔更易漏），且会让项目失去"人格在权重+权重成长"的差异化、退回与 mem0/Letta/ACE 同质化的位置。最佳是 **2-3 个 hero + 其余全方案二**——hero 的显存代价（~0.17GB）远小于它守住的主角体验与差异化价值。
