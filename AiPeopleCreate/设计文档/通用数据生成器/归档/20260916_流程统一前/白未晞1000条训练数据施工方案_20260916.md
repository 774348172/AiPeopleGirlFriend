# 白未晞 1,000 条训练数据施工方案

版本：2026-09-16

状态：施工方案。本文只规定生产候选和验收，不启动训练。

## 一、目标和边界

目标是生产 1,000 条可进入回复生成阶段的冻结输入，并在此基础上生成、审核 1,000 条女主回复候选。最终进入训练池的数量以人工和机器审核结果为准，不能把“生成 1,000 条”当成“合格 1,000 条”。

正式生产只允许使用：

- Codex 预先编排并审核的完整组件；
- `run_curated_candidate_batch.py` 的正式回复入口；
- 共享 `convert → model_view → GAME_REPLY_CONTEXT_V1` 渲染链。

不得使用：

- `run_mixed_candidate_batch.py` 的正式生产功能；
- `prepare_expanded_batch_seeds.py` 产生的占位种子；
- 任何包含“待编剧生成相关原话”或“待编剧生成自然承接的当前发言”的输入；
- 旧批次的自动审核结果作为新的输入审核凭证；
- 旧批次重试结果与原批次重复合并。

## 二、统一数据结构

每条输入在冻结前必须具备：

1. 唯一 `sample_id` 和 `family_id`；
2. 一个固定权威场景和当前快照：时间、天气、地点、男女主位置和状态、相关设备或物品状态；
3. 与当前问题有关的冻结事件。过去事实必须由事件支持，事件必须有 `current_fact_ids`、`actors`、`known_by` 和时间；
4. 4 条相关记忆对白；
5. 4 条最近对白；
6. 当前男主发言；
7. 明确的已知事实、明确未知和女主知情边界；
8. Codex 外部输入审核记录，包含 `provenance=external_codex_review`、`review_run_id`、审核结论、事实依赖和 `component_sha256`；
9. 通过正式渲染后的完整 `GAME_REPLY_CONTEXT_V1`，以及冻结哈希。

历史对白只承担对话连续性，不能单独证明事实。没有冻结事件支持的“上次、昨天、刚才做过”必须改成假设、主观意见或明确未知。

## 三、数量规划

先按 5 个场景均衡分配：

| 场景 | 输入目标 |
|---|---:|
| 家中 | 200 |
| 街角咖啡店 | 200 |
| 邻里便利店 | 200 |
| 百花里小街逛街途中 | 200 |
| 心愿咖啡馆 | 200 |
| 合计 | 1,000 |

建议每个场景包含 100 条闲聊、50 条情绪或关系交流、50 条事实问答。事实问答必须登记需要的事实或有意未知；闲聊不能为了凑状态变成状态查询。

同一对话家族最多 4 个变体。变体必须改变场景时间、天气、意图或对话走向，不能只改编号、标点或一个形容词。

## 四、分阶段施工

### 阶段 0：施工前锁定

确认当前权威角色锚、五个场景设定、世界状态字段、渲染器哈希和聊天模板哈希。建立新批次目录，不复用暂停批次作为输出目录。

产物：

- `batch_manifest.json`；
- 权威来源哈希；
- 场景与任务分配表；
- 本批禁止使用的旧目录清单。

验收：来源变更、字段缺失或目录与批次不匹配时停止。

### 阶段 1：编排 20 条输入

由 Codex 逐条编排完整组件和输入审核记录。每条都先确定权威快照和冻结事件，再写历史对白和当前问题。不得先写对白再补状态。

使用正式转换器检查最终消息，确认模型实际看到：

- 当前权威事实；
- 明确未知；
- 女主设定；
- 男主可公开资料和保密资料边界；
- 相关记忆；
- 最近对白；
- 当前问题。

验收门槛：20 条全部有完整组件和外部审核记录；输入通过率必须达到 90% 以上；所有占位对白、字符串 `"null"`、话题漂移和无事件事实均隔离。

### 阶段 2：编排 50 条输入

只有阶段 1 通过后才进行。新增 30 条必须与前 20 条做完整历史去重和场景覆盖检查。

验收门槛：输入通过率 ≥90%，五个场景均有样本，单一对话家族不超过 4 条，失败原因分布没有集中在同一个结构性问题。

### 阶段 3：编排 200 条输入

按五个场景各 40 条进行。先完成全部输入审核，再生成任何回复。建立整批输入审核摘要：尝试数、通过数、失败数、失败原因、`review_run_id`、通过样本 ID 和失败样本 ID。

验收门槛：输入通过率 ≥90%；权威来源哈希一致；没有占位内容；没有跨场景状态串用；历史事件和对白的时间顺序全部通过。

### 阶段 4：生成和审核 200 条回复

使用 `run_curated_candidate_batch.py`。该入口只读取冻结输入，Qwen 只输出最终女主回复；本地审核器固定采用默认 `gemma4:31b-it-qat`，审核历史、事实覆盖、回复质量和事实支持，程序保留请求、原始响应、审核结果和失败原因。

回复阶段禁止：重新编排世界、重新编历史、根据回复反向补事实、用语义重采样掩盖失败。

验收门槛：空回复、截断和格式错误为失败；事实错误和话题漂移隔离；自动通过不等于训练放行。Codex 对完整批次进行独立复核，再通过 `build_pending_human_review.py` 将机器/程序隔离项、Codex语义疑点、边界及分歧项合并为人工审核页。全量页仅备查，不再要求用户逐条重复审核整个批次。未判断项必须保持待审；人工意见另存，不能覆盖原审核结论。

2026-09-16 当前进度：同一100条候选已完成Gemma31B QAT审核及Codex文件复核，24条进入人工裁决。该100条不等于本阶段200条验收已完成。人工回传后先整理误判、漏判及边界标准，再按冻结输入要求补齐200条试产和验收；验收未完成前不直接启动1000条。完成200条也不能仅凭机器通过率宣称可扩产，需检查人工纠错和结构性回归。

### 本次人工校准与200条试产的执行补充

人工24条已回传：17好、7坏，原始文件与原机器判断分开保存。005、011、016、017、018、052、091维持人工拒绝；其中052的拒绝理由为空，不能擅自归纳为“短答一律不合格”。不同完整输入得到相同短答不自动判坏；完全相同的输入与回复组合仍去重，输入链近重复和同族上限检查继续保留。

审核使用Gemma 31B QAT和`human24_calibration_v1`标准，区分客观状态、假设创作和口语表达。不能凭“刚才”“没看到”关键词直接判捏造，也不能因此放过新增具体巡查或行为；有歧义转人工。稳定偏好若用于较早对话，必须具备早于该对话的获知时间。普通当前状态仍不能证明旧事件。

试产组成是原100条加新编排100条，后者位于`训练数据/calibrated_add100_20260916`。100条输入均有逐条编排审核、冻结哈希和完整正式消息，不由本地模型自动补历史。新增回复首轮有效98条，两条仅做格式重试后达到100条有效回复；内容拒绝不通过重抽来消除。新增Gemma机器放行87条、隔离13条；这不是人工准确率。

原24条另用校准后的Gemma回放检验，因它们参与过标准修订，只能称为校准集表现，不是独立验证准确率。原100条保留原审核和人工覆盖，新100条是前瞻试产，不宣称全200条已按新规则统一重新机器审核。Codex逐条语义复核另存，机器失败、语义疑点和分歧合并为待人工队列，已裁决24条不重复送审。

最终汇总目录为`训练数据/calibrated_trial200_20260916`，数量、校准效果、待审清单和用量以其中报告为准。此阶段交付200条候选和验收材料，人工裁决未回传前，状态仍为`awaiting_human_acceptance`，`released_training_rows=0`，不启动1000条。

### 阶段 5：扩展到 1,000 条

2026-09-16用户后续明确授权覆盖此前候选生产等待条件：暂缓23条人工裁决，先生产1000条候选，每批100条共10批。候选生产可开始，但不代表200条已验收通过；既有23条仍待裁决，训练导出放行条件不变。此次目录为`训练数据/candidate1000_20260916`，原200条不计入1000目标。每批仍需Codex提前编排、逐条自审、冻结、正式预检；批次结束汇总用量并核对集中性错误后再推进，不允许复制输入或本地模型自动编排。当前只有batch01已完成100条输入冻结，其他批次不能冒称已排队生成。

只有 200 条阶段的输入和回复质量都达到门槛后，才按 5 个独立 200 条批次扩展。每个批次使用独立目录、独立 `review_run_id` 和独立 token/耗时账本。

每个 200 条批次完成后先停下来统计：

- 输入通过率；
- 有效回复率；
- 自动审核通过率；
- Codex 拒绝率和待人工率；
- 空回复、事实捏造、历史不连续、重复回复数量；
- 本地 Qwen/Gemma token 和耗时。

任何一项出现集中性回归，立即停止后续批次，修复模板或规则后从新的批次目录重跑，不在原目录覆盖。

## 五、正式命令边界

冻结输入完成后，正式回复阶段使用：

```text
python tools/run_curated_candidate_batch.py \
  --input <冻结组件.json> \
  --approvals <外部输入审核.json> \
  --input-review-summary <整批审核摘要.json> \
  --output-root <本批正式输出目录>
```

20 条及以上批次必须提供整批摘要。摘要必须包含 `review_run_id` 和 `approved_ids`，且 `approved_ids` 必须与冻结组件的 `sample_id` 集合完全一致；每条 approval 的 `review_run_id` 必须与摘要一致。摘要中的 `approved` 必须等于冻结组件数量，`approved / attempted` 必须不低于 0.90。

`run_mixed_candidate_batch.py` 只保留为历史实验复盘入口。它拒绝正式 `seed-input` 和旧 `retry-input`，不得用于本施工方案。

## 六、目录和交付物

每个批次至少保留：

- `components.json`：冻结前组件；
- `input_approvals.json`：外部 Codex 输入审核；
- `input_review_summary.json`：整批通过率摘要；
- `inputs/frozen_inputs.json`：实际发送给模型的完整消息；
- `preflight_report.json`：字段覆盖和哈希检查；
- `requests/`：实际本地模型请求与响应；
- `results.json`：逐条结果；
- `report.json`：数量、失败、审核和耗时；
- `review.html`：人工审核页面；
- `token_usage.json`：Codex 和本地模型分开记账；
- `验收结果.md`：本批最终结论。

任何批次的 `released_training_rows` 在用户人工确认前必须为 0。

## 七、最终训练放行条件

1. 1,000 条输入全部来自冻结组件，不含占位内容；
2. 每条都有外部 Codex 输入审核记录；
3. 每个 200 条批次的输入通过率达到 90% 以上；
4. 所有正式消息通过 `GAME_REPLY_CONTEXT_V1` 完整性检查；
5. 回复阶段没有空回复、截断回复或未隔离的失败；
6. 自动审核、Codex 复核和用户人工审核结果全部可追溯；
7. 训练导出前重新执行训练包 preflight；
8. 用户明确批准后才把合格行写入训练包。

在以上条件全部满足前，数据只能称为候选或隔离样本，不能称为正式训练数据。
