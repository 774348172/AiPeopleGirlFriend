## 1. 结论先行

V5 不推翻 V4 的通用生成框架，而是在 V4 中新增一条独立的、可审计的 `runtime_grounded_reply` 生产路径。

V5 的核心变化只有一句话：

> 程序先确定世界、历史、事实来源、主体和正确处理方向，教师模型只负责把这些确定内容写成自然角色对白。

V5 明确禁止继续让同一次教师调用同时自由编写玩家台词、动态事实、历史变化和角色答案。教师可以决定措辞，不得决定事实。

V5 不引入运行时 ReplyFocus，不增加玩家聊天时的模型调用链。全部场景规格、事实标签、生成审核和发布门禁都发生在离线数据生成阶段。

## 2. 问题定义与直接证据

### 2.1 当前产品问题

现有 LoRA 在多轮聊天中出现以下问题：

1. 玩家明确提问后没有回答关键事实。
2. 当前事实已更新，回复仍复活旧事实。
3. 玩家纠正角色后，角色继续坚持旧说法。
4. 玩家、女主、物品和第三人的事实发生主体错位。
5. 单句语法通顺，但句内前后关系不成立。
6. LoRA 回复质量明显低于同一裸基座，说明训练改变破坏了基座已有能力。

典型错误：

```text
玩家：我泡茶还是不要糖，你记得吧？
错误回复：记得。我从来不吃甜的东西。
```

问题不是“糖”这个案例未被训练覆盖，而是模型没有稳定保持：

- 事实主体是玩家；
- 属性是喝茶时的加糖偏好；
- 当前玩家自述对其个人偏好具有权威性；
- 回复必须确认玩家偏好，不能转移成女主偏好。

### 2.2 现有数据结构缺口

白未晞 V4 训练集共 1973 条，经直接检查：

| 运行时字段或标记 | 训练数据命中数 |
|---|---:|
| `[当前世界]` | 0 |
| `item_states` | 0 |
| `pending_actions` | 0 |
| `selected_memory_frame` | 0 |
| `recent_dialogue` | 0 |
| 运行时“只输出说出口的话”协议 | 0 |

`reply_correction` 只有 29 条，且混合了“角色纠正玩家”和“角色接受玩家最新更新”两个方向相反的任务。当前配方权重为 0.01。

### 2.3 根因判断

按当前证据，剩余质量问题的主要原因排序为：

1. 训练输入与生产推理输入不一致。
2. 动态事实、主体、有效期和纠正方向没有进入数据合同。
3. 教师同时编写条件和答案，造成自洽但不受权威状态约束的对话。
4. 事实审核只覆盖教师自报命题，不覆盖完整回复。
5. Judge 缺少当前事实、旧事实、主体和必答信息轴。
6. 已修复的全 assistant 监督问题曾是重要原因，但不足以解决上述结构问题。
7. 模型容量影响上限，但不是 LoRA 相对裸基座退化的首要解释。

## 3. 目标与非目标

### 3.1 V5 目标

1. 训练模型根据来源、主体、有效期和当前状态处理事实，而不是背具体句子。
2. 训练输入与 `JUDGE_TURN` 的事实上下文同构。
3. 动态场景由确定性规格产生，可重放、可组合、可留出评测。
4. 教师只负责自然语言实现，不拥有世界事实编辑权。
5. 完整回复中的事实主张全部接受审核。
6. 新 Adapter 在事实能力上不劣于裸基座，并保持角色风格收益。
7. 通过未见对象、时间、主体和组合验证泛化，而不是用随机同分布切分制造高分。

### 3.2 V5 非目标

1. 不训练 `action_id`、工具列表、动作参数或 `mind_patch` 输出格式。
2. 不把运行时动作白名单写进训练输入。
3. 不用数据生成器替代游戏世界状态或动作执行。
4. 不在运行时增加 ReplyFocus、规划模型或固定语义规则链。
5. 不承诺有限训练数据覆盖所有自然语言句子。
6. 不直接清洗并覆盖原 1973 条数据。
7. 不通过角色专属关键词穷举事实正确性。

---

## 4. V5 不变量

以下规则是施工和评审不得改变的硬约束：

1. **游戏是客观世界事实唯一来源。** 位置、时间、物品、进行中动作和已发生结果以冻结游戏投影为准。
2. **事实权威按领域和主体判断。** 不使用一个覆盖所有事实的简单全局来源排序。
3. **条件由程序生成。** 当前世界、历史、旧事实、玩家输入和纠正方向均来自冻结 `ScenarioSpec`。
4. **教师只实现答案。** 教师不得新增或改写场景事实、历史消息和事实有效期。
5. **结构化 claim 与自然语言分离。** claim 用于生成和审核，不作为训练目标输出。
6. **训练输入与运行时上下文同构。** 允许省略动作清单与结构化动作输出，不允许省略事实判断所需的世界、记忆和历史。
7. **每个状态节点独立监督。** 一个 runtime-grounded 样本只监督当前 assistant 回复；历史 assistant 只作为条件。
8. **审核完整回复。** 教师自报 claim 不能代替对最终文本的独立提取和审核。
9. **事实硬门不能被风格分补偿。** 人设自然不能抵消事实错误、主体错误或答非所问。
10. **旧数据不可变。** V4 数据和 Adapter 保留哈希与 lineage，只能派生新版本。
11. **先小门，后完整训练。** 冻结专项门未通过时，不运行完整训练和 60 轮人工评测。
12. **核心保持多角色通用。** 角色事实放入 ProfilePackage 或场景资源，不进入共享核心的关键词分支。

## 6. 事实权威模型

### 6.1 为什么不能只做全局来源排序

“当前玩家原话永远最高”是错误的，因为玩家可以说错物品位置；“世界状态永远覆盖玩家”也不完整，因为游戏通常不能替玩家决定其口味、主观感受和临时意愿。

V5 使用 `subject_domain + source + recency + status` 共同决定权威性。

### 6.2 领域与权威来源

| 事实领域 | 例子 | 首要权威来源 | 玩家当前说法的地位 |
|---|---|---|---|
| 客观世界 | 时间、地点、物品位置、动作完成 | 当前游戏投影 | 普通主张，不得覆盖快照 |
| 男主自身偏好 | 不喝甜茶、喜欢清淡 | 男主当前明确自述 | 对其自身偏好具有权威性 |
| 男主主观感受 | 疼、冷、害怕 | 男主当前明确自述 | 原则上接受，除非安全场景要求澄清 |
| 男主计划和选择 | 周六去、暂时不买 | 男主当前明确自述或游戏确认 | 当前自述可更新旧对话 |
| 女主内在状态 | 女主心情、动机、意愿 | 女主状态和女主自身表达 | 玩家推测不能直接覆盖 |
| 女主身份正典 | 姓名、年龄、能力边界 | ProfilePackage 正典 | 玩家说错时应纠正 |
| 共同历史 | 曾经发生的事件 | 已确认事件、有效记忆 | 无证据的玩家前提不能自动成立 |
| 第三人事实 | 第三人的偏好或行为 | 当前世界、有效事件证据 | 玩家说法按证据状态处理 |

### 6.3 事实状态

每条用于判断的事实必须具有以下状态之一：

- `current`：当前有效。
- `stale`：过去有效、现在失效。
- `false`：已被权威来源否定。
- `unknown`：没有充分依据。
- `contested`：来源冲突且无法仅凭当前上下文解决。

禁止用 `supported` 一个标签同时表示当前、历史和纠正方向。

### 6.4 冲突处理矩阵

| 当前情况 | 期望处理 |
|---|---|
| 玩家说法与客观游戏快照冲突 | 以快照为准，自然纠正玩家 |
| 玩家更新自己的偏好、感受或计划 | 接受最新自述，旧对话标记 stale |
| 玩家错误描述女主正典 | 女主纠正玩家 |
| 旧记忆与当前世界冲突 | 当前世界优先，旧记忆不得复活为当前事实 |
| 两条非权威历史相互冲突 | 表达不确定或请求澄清 |
| 当前事实明确而问题为确认问句 | 先给明确“是/不是”，再补关键事实 |
| 当前上下文无答案 | 说明不知道，不补造具体时间、位置或因果 |

### 7.1 双视图原则

一个 `ScenarioSpec` 同时包含：

- `model_view`：训练和教师可见的生产同构上下文。
- `oracle_view`：只供生成器审核和评测使用，绝不进入模型训练输入。

这样可以避免把答案标签、禁止事实或权威排序泄漏给被训练模型。

### 7.3 必填字段

所有 runtime-grounded 场景至少必须具有：

- 唯一 `scenario_id`。
- `task_type`。
- 完整 `model_view`。
- 至少一个带主体的 `current` 或 `unknown` 判断依据。
- `correction_direction` 或明确的 `answer_shape`。
- `required_assertions`。
- `forbidden_assertions`，允许为空数组但不得缺失。
- `response_contract`，三项字段必须完整，不允许依赖默认值发布数据。
- `split_anchors`。

`model_view` 不是 V5 自创的近似上下文。它必须通过当前生产 `judge_payload` 的版本化投影 schema 校验，字段名称、嵌套、类型和顺序以冻结运行时合同为准。V5 只允许从该投影中删除 `available_actions`，以及删除只用于声明结构化输出格式的 schema 文本；不得把 `snapshot`、`selected_memory_frame` 或 `recent_dialogue` 改造成生成器专用结构。

### 7.4 回复行为合同

`oracle_view.response_contract` 固定为：

```json
{
  "unknown_acknowledgement": "required|not_applicable",
  "subject_proposition_binding": "required|not_applicable",
  "unsupported_expansion_policy": "reject"
}
```

其任务一致性由程序检查：

- `reply_insufficient_information` 必须令 `unknown_acknowledgement=required`；其他任务为 `not_applicable`。
- `reply_subject_attribution` 必须令 `subject_proposition_binding=required`；其他任务为 `not_applicable`。
- 所有 runtime-grounded 场景都必须令 `unsupported_expansion_policy=reject`。
- unknown 合格回复必须明确表达当前不知道、不清楚、不确定或没有可靠记录；只反问玩家不算完成目标。
- 主体归属合格回复必须联合保留原说话人和 `required_assertions` 中的命题内容；只答人名、只答事实或改成“我说的”均不合格。
- 回复不得把一次、当前或有限事实扩展为“每天、每次、一直、永远、都会、都有”，也不得新增没有来源的确认、通知、联系、安排、查询或执行动作。

`response_contract` 只存在于 oracle 侧，不进入训练输入。它用于约束教师目标、候选审核和评测标签，不要求本地聊天模型在运行时生成中间标签。

### 7.5 禁止字段

`model_view` 禁止包含：

- `required_assertions`。
- `forbidden_assertions`。
- `correction_direction` 标签。
- 参考答案。
- Judge 评分和审核原因。
- `available_actions` 动作清单。
- 训练目标 JSON schema。

## 8. 任务类型重构

### 8.1 废止混合任务

V5 新数据不再使用含义混杂的 `reply_correction`。V4 中已有该标签只用于旧数据追溯。

### 8.2 V5 核心任务

| 任务类型 | 训练目标 | 主要负例 |
|---|---|---|
| `reply_accept_authoritative_update` | 接受玩家对自身偏好、感受、计划的最新更新 | 坚持旧对话、转移到女主 |
| `reply_reject_stale_claim` | 拒绝已失效事实并给出当前事实 | 复活旧时间、旧位置、旧状态 |
| `reply_correct_false_premise` | 根据权威证据纠正玩家错误前提 | 顺着错误前提编造 |
| `reply_resolve_world_memory_conflict` | 当前世界优先于旧记忆 | 把回忆当成当前事实 |
| `reply_confirm_current_state` | 准确确认当前状态 | 含糊回应、遗漏关键值 |
| `reply_subject_attribution` | 保持玩家、女主、物品、第三人主体 | 把“你”说成“我” |
| `reply_insufficient_information` | 信息不足时保持未知或追问 | 编造具体细节 |
| `reply_direct_answer` | 对明确问题先作明确回答 | 只安慰、只调侃、不回答 |

一个场景可以有一个主任务和多个能力标签，但发布统计以主任务为准，能力标签用于覆盖报告和切分。

### 8.3 组合维度

每个任务至少沿以下维度组合：

- 主体：玩家、女主、物品、第三人、共享事件。
- 谓词：时间、位置、归属、数量、偏好、状态、完成情况、计划。
- 来源：世界快照、游戏反馈、当前玩家自述、有效记忆、旧历史。
- 冲突：无冲突、当前覆盖旧值、来源冲突、信息不足。
- 问法：确认、反问、纠正、含蓄提醒、直接提问。
- 回复长度：极短明确、短句说明、必要澄清。

核心生成器不得为“衣柜、抽屉、牙医、糖”等具体名词编写语义规则。这些只是 fixture 变量。

## 9. 确定性场景生成

### 9.1 场景来源

场景必须来自以下两类资源：

1. 通用合成 fixture：使用无角色专属含义的对象、时间、位置、偏好和状态模板。
2. 角色/产品 fixture：由 ProfilePackage 和游戏接口提供合法场景值。

教师模型不得创建 fixture。

### 9.2 状态轨迹

多轮场景使用状态轨迹表示：

```text
S0 初始事实
 -> 玩家/游戏事件 E1
S1 更新后的当前事实，S0 对应值变 stale
 -> 玩家确认、误述或纠正 E2
S2 需要生成回复的判断节点
```

每一步必须记录：

- 哪个 fact 发生变化。
- 变化前后的值。
- 变化来源。
- 受影响主体。
- 旧值为何失效。
- 当前回复需要完成的语义动作。

### 9.3 单变量与组合变化

首批数据以单变量变化为主，确保归因清晰；通过小门后再增加两个变量同时变化的困难样本。禁止第一批就让时间、位置、人物、关系和动作同时变化，导致无法判断错误来源。

### 9.4 防止模板背诵

场景切分不按最终自然语言随机切分，而按语义组合切分：

- 留出未见对象。
- 留出未见时间表达。
- 留出未见主体和谓词组合。
- 留出未见冲突来源组合。
- 同一轨迹家族不得跨训练集和测试集。

## 10. 教师生成合同

### 10.1 教师输入

教师接收：

- ProfilePackage 中与当前表达相关的角色风格。
- `model_view` 的完整上下文。
- `oracle_view` 的回答义务。
- spoken-only 输出要求。

`oracle_view` 只用于教师生成和离线审核，不进入最终训练输入。

### 10.2 教师输出

教师只输出：

```json
{
  "reply": "不是，星期五下午那个时间已经作废了。你要星期六上午十点去。",
  "declared_claims": [
    {
      "subject": "protagonist.dentist_appointment",
      "predicate": "not_scheduled_at",
      "object": "星期五下午"
    },
    {
      "subject": "protagonist.dentist_appointment",
      "predicate": "scheduled_at",
      "object": "星期六上午十点"
    }
  ]
}
```

`declared_claims` 是审计辅助字段，不可信，也不进入训练目标。最终回复仍必须由独立审核器重新提取 claim。

### 10.3 教师禁止事项

- 不得生成或改写玩家消息。
- 不得生成额外历史轮次。
- 不得改变 current/stale/unknown 状态。
- 不得新增时间、位置、人物、物品、因果或共同经历。
- 不得用动作旁白代替对白。
- 不得只用“嗯、别想太多、按时去”回避必答事实。
- 不得为了表现人设而降低事实明确性。
- unknown 场景不得用反问替代明确的未知承认，也不得补造具体日期、位置、状态或原因。
- 主体归属场景不得拆开“说话人 + 原命题”，不得只回答其中一半。
- 不得新增 oracle 没有授权的频率、持续性、确认、通知、联系、安排、查询或执行动作。

### 10.4 教师模型要求

教师和语义审核器属于离线数据生产资源，可以使用强模型。它们不进入本地聊天运行时，因此不增加玩家侧首字延迟。V5 不要求待训练的 7B/12B/14B 模型自己生成中间标签。

## 11. 训练渲染合同

### 11.1 两条 REPLY 路径

| 路径 | 用途 | 上下文 | 监督范围 |
|---|---|---|---|
| `static_persona_reply` | 人设、口吻、关系和普通闲聊保持 | 静态角色锚 + 对话 | 每条合法 assistant 均可监督 |
| `runtime_grounded_reply` | 当前事实、多轮状态、纠正和主体 | 生产同构上下文 + 当前玩家输入 | 只监督当前最后一条 assistant |

不得用静态 REPLY 代替 runtime-grounded REPLY。

### 11.2 运行时同构字段

`runtime_grounded_reply` 至少渲染：

1. 角色身份与风格锚。
2. 当前世界状态。
3. 男主状态。
4. 女主状态。
5. 记忆召回。
6. 进行中动作。
7. 游戏反馈。
8. 最近对话。
9. 当前玩家输入。

训练输入不渲染 `available_actions`，训练目标不出现 `actions`、`action_id`、`mind_patch` 或 `JUDGE_TURN` JSON。动作协议继续由生产 prompt 零样本提供。

### 11.3 共享渲染来源

训练和运行时不得各维护一套手写字段名称与顺序。施工时应从运行时冻结 fixture 或抽取共享的纯数据序列化合同，生成器只允许过滤明确禁止进入训练的动作清单和输出 schema，不允许自由重写事实区块。

### 11.4 监督 mask

每个 runtime-grounded 记录必须自动验证：

- system 和 user token 不参与 loss。
- 历史 assistant token 不参与当前样本 loss。
- 当前最后一条 assistant 全部参与 loss。
- 特殊 token、拼接边界和截断不改变上述结果。
- 每个行为类型输出样本数、监督消息数和监督 token 数。

任一核心任务监督数为零，训练包构建必须失败。

## 12. 完整回复事实审核

### 12.1 双来源 claim

审核同时比较：

1. 教师自报的 `declared_claims`。
2. 独立语义审核器从最终 `reply` 提取的 `extracted_claims`。

两者不一致时不得默认相信教师，应拒绝或进入人工复核。

### 12.2 每条 claim 的最小结构

```json
{
  "subject": "player|heroine|world.entity|third_party|shared_event",
  "predicate": "规范化关系",
  "object": "值",
  "polarity": "positive|negative",
  "temporal_status": "current|past|future|unknown",
  "source_fact_ids": ["fact_id"]
}
```

### 12.3 审核问题

对完整回复逐项回答：

1. 是否包含全部 `required_assertions`。
2. 是否包含任何 `forbidden_assertions`。
3. 是否把 stale 或 false 事实说成 current。
4. 是否出现主体错位。
5. 是否新增 oracle 不支持的具体事实。
6. 是否明确回答当前问题。
7. 是否出现内部前后矛盾。
8. 是否只输出角色说出口的话。
9. required unknown 是否有明确未知承认，而不是仅反问或回避。
10. required 主体归属是否在同一完整回答中同时保留说话人和原命题。
11. 是否把有限事实扩展成无限频率/持续状态，或新增无来源动作。

### 12.4 确定性检查与语义检查边界

确定性检查负责：

- schema、字段、ID、来源和状态转换完整性。
- required/forbidden 中可精确匹配的值。
- 动作旁白标记、空回复、格式和长度异常。
- split 泄漏和 lineage。

强语义审核负责：

- 自然语言同义表达。
- 主体、否定、时间状态和含蓄断言。
- 句内逻辑和答题完整性。
- 无依据新增事实。

禁止用两字符子串匹配代替语义事实审核。

## 13. V5 硬门与软 Judge

### 13.1 Runtime-grounded 专用硬门

为避免与 V4 现有 G0-G8 编号混淆，V5 新门使用 `RG` 前缀：

| 门 | 含义 | 失败处理 |
|---|---|---|
| RG0 | ScenarioSpec schema 完整 | 拒绝 |
| RG1 | fixture、package lock、source ID 可追溯 | 拒绝 |
| RG2 | 事实状态转换合法，current/stale 不冲突 | 拒绝 |
| RG3 | 运行时上下文字段覆盖完整 | 拒绝 |
| RG4 | 教师只生成一个当前回复 | 拒绝 |
| RG5 | required assertions 全部满足 | 拒绝 |
| RG6 | forbidden/stale/unsupported assertions 为零 | 拒绝 |
| RG7 | 主体归属正确 | 拒绝 |
| RG8 | 纠正方向与 answer shape 正确 | 拒绝 |
| RG9 | 明确回答且无动作旁白 | 拒绝 |
| RG10 | 独立 claim 提取与教师声明一致 | 拒绝或人工复核 |
| RG11 | split、去重和家族隔离正确 | 拒绝 |

三项回复合同映射到既有硬门，不新增空转编号：unknown 承认失败归入 RG8；主体与命题任一缺失归入 RG5/RG7；未授权频率、持续性、确认或执行动作归入 RG6。关键词检查只负责确定性高精度拒绝，未命中关键词不等于语义通过；无来源动作和含蓄扩展仍必须经过完整回复语义审核。

事实硬门失败不能通过重试 Judge 分数补偿。重试只能让教师在相同 ScenarioSpec 上重新表达，不得修改场景。

### 13.2 新 Judge 维度

硬门通过后才计算软质量分：

- `direct_answer_quality`
- `persona_naturalness`
- `relationship_fit`
- `language_coherence`
- `style_restraint`
- `brevity_fit`

以下能力保留为报告轴，但必须达到硬阈值，不能仅作加权软分：

- `current_fact_adherence`
- `stale_fact_rejection`
- `subject_attribution`
- `unsupported_assertion_absence`

V4 的 `conversational_progress` 不再要求所有回答“不能单句终结”。明确确认题允许一句话正确结束，对话长度必须服从当前任务。

## 14. 数据配比与覆盖下限

### 14.1 总体混合建议

首个 V5 试验版本使用以下范围，而不是立即冻结单点比例：

| 数据域 | 建议占比 |
|---|---:|
| 审核通过的静态人设、口吻和关系保持数据 | 35% 至 45% |
| runtime-grounded 事实与状态数据 | 55% 至 65% |

试验结果决定最终比例，但 runtime-grounded 数据不得再次降为装饰性少数。

### 14.2 Grounded 域内部覆盖下限

| 能力 | Grounded 域最低占比 |
|---|---:|
| 普通当前状态承接与确认 | 20% |
| 接受玩家对自身信息的最新更新 | 15% |
| 拒绝 stale 或 false 前提 | 15% |
| 世界与记忆/历史冲突 | 15% |
| 主体归属专项 | 10% |
| 信息不足与澄清 | 10% |

剩余比例用于组合困难样本。一个样本可以同时覆盖多个能力，但主任务计数不得重复。

### 14.3 平衡要求

发布报告至少统计：

- 每个 task_type 的场景数和训练记录数。
- 每类主体的数量。
- 每类谓词的数量。
- 每类权威来源和冲突组合的数量。
- current/stale/false/unknown/contested 的数量。
- 明确问句、纠正句、含蓄问句的数量。
- 每种行为的实际监督消息数和 token 数。

## 16. 切分与封存评测

### 16.1 三种切分

1. **训练集**：用于 Adapter 训练。
2. **开发集**：用于数据配比、训练超参数和早停选择。
3. **封存测试集**：生成后冻结哈希，训练过程不可读取答案。

### 16.2 语义家族隔离

- 同一状态轨迹模板。
- 同一事实组合。
- 同一对象、谓词和冲突方向组合。
- 同一自然语言改写家族。
- 60 轮人工脚本中的原始场景。

### 16.3 封存专项套件

至少建立：

- `subject_attribution_sealed_v1`
- `accept_authoritative_update_sealed_v1`

- `world_memory_conflict_sealed_v1`
- `direct_answer_completeness_sealed_v1`
- `unsupported_assertion_sealed_v1`
- `heldout_semantic_combinations_sealed_v1`
- `base_adapter_non_inferiority_sealed_v1`

`profile_evaluation_suites` 和 `sealed_evaluation_refs` 为空时禁止发布 V5 训练包。

2. 所有核心 task_type 有非零监督样本和监督 token。
3. 训练输入运行时字段覆盖率为 100%。
4. 动作清单、`action_id`、`mind_patch` 在 REPLY 训练目标中为零命中。
5. 动作旁白为零。
6. 封存评测引用非空且哈希冻结。
7. 人工抽检覆盖每个 task_type、主体和冲突方向。
8. 三项 `response_contract` 字段覆盖率为 100%，任务一致性错误为零。
9. required unknown 承认、required 主体+命题联合输出和 unsupported expansion 拒绝门均实际执行，且具有正反例合同测试。

### 17.2 小规模训练门

先训练受控试验 Adapter，不直接消耗完整训练预算。试验必须比较：

- 裸基座。
- 旧 Adapter。
- 新 V5 试验 Adapter。

- 严重事实错误为零。
- 主体错位为零。
- 新 Adapter 不低于裸基座的直接回答和逻辑连贯能力。

小门失败时只允许回到场景、数据、配比或训练设置诊断，不得直接跑 60 轮寻找偶然好结果。

### 17.3 完整发布目标

候选 Adapter 进入完整 60 轮人工评测前，封存专项集应满足：

- 当前事实与纠正综合正确率目标不低于 95%。
- 主体归属正确率目标不低于 98%。
- stale 事实复活率不高于 2%。
- unsupported assertion 严重错误率为 0，普通错误率不高于 2%。
- 相对裸基座的通用逻辑能力通过非劣化门。

95% 是发布目标，不得通过删除困难测试或把测试改写进训练集实现。

| 角色 fixture | `profiles/<profile_id>/` 下的角色资源 |

| 生产同构渲染 | renderer 新入口，复用冻结运行时字段合同 |
| RG0-RG11 | 独立 runtime-grounded gates |
| claim 独立提取 | 语义审核 adapter |
| 数据混合 | recipe 新数据域和配比 |
| 封存评测 | profile evaluation suites + release refs |
| 旧数据派生 | 新 migration manifest，不覆盖原文件 |

是否命名为 `data_gen_v5` 目录由施工计划决定，但 schema_version、dataset_id 和 manifest 必须明确为 V5，不能继续冒用 V4 版本。

## 21. 设计自审与风险

### 21.1 教师仍可能写错

风险：强教师也可能漏答、反转否定或增加细节。

控制：条件固定、答案义务结构化、独立 claim 提取、RG 硬门、候选重生成和分层人工抽检。不得因为教师强就跳过审核。

### 21.2 语义审核器也可能误判

风险：同义表达、含蓄否定和中文省略主语可能导致误判。

控制：确定性检查与强语义审核组合；不一致样本进入拒绝或人工复核，不自动放行；封存集校准 Judge 的漏判率和误杀率。

### 21.3 训练输入与生产输入再次漂移

风险：运行时字段或顺序变化，生成器仍使用旧副本。

控制：共享字段合同或运行时 fixture；CI 比较训练渲染与生产 payload 的结构覆盖；字段增删必须触发合同测试失败。

### 21.4 事实数据压制角色风格

风险：大量短而明确的纠正数据使角色变机械。

控制：保留审计后的 persona anchors；所有 grounded 回复仍经过角色风格实现；事实硬门之后再做自然度选择；用多候选表达提高措辞多样性。

### 21.5 模型容量仍有上限

风险：小模型即使数据正确，复杂组合仍可能低于目标。

控制：先证明新 Adapter 不破坏裸基座，再比较不同基座；数据、训练方法和模型容量分开做 A/B，不用换模型掩盖坏数据。

### 21.6 95% 目标被同分布测试虚高

风险：训练和测试只换了措辞，模型靠记忆取得高分。

控制：按语义家族和组合留出；封存未见对象、时间和主体组合；人工 60 轮脚本不进入训练。

### 21.7 只训练回复仍不能绝对保证运行时正确

风险：SFT 提升概率，不提供形式化保证。

控制：V5 的目标是达到封存正确率与非劣化门，而不是宣称所有输入绝不错误。若发布目标仍无法达到，再根据实测决定是否启用当前程序已有的定向 Critic；不得在没有数据证据前重建长运行时链。

## 22. 施工顺序

V5 施工必须按以下顺序，不能先写生成 prompt：

1. 冻结 ScenarioSpec、claim 和事实状态 schema。
2. 编写 schema、状态转换和主体权威的合同测试。
3. 建立小型手写黄金 fixture 与反例集。
4. 实现确定性 scenario builder。
5. 实现生产同构 renderer 和 mask 测试。
6. 实现教师 realizer，限制为单条当前回复。
7. 实现独立 claim 提取与 RG0-RG11。
8. 接入新版 Judge 和人工复核出口。
9. 建立封存评测和 release 引用。
10. 生成小批数据并人工逐条审查。
11. 构建试验训练包并输出监督覆盖报告。
12. 训练小 Adapter，执行裸基座/旧 Adapter/新 Adapter 冻结小门。
13. 小门通过后再扩大数据、完整训练和 60 轮评测。

## 23. 设计验收清单

在编写施工计划前，评审者必须能对下列问题给出唯一答案：

- [ ] 玩家更新自己的口味时，哪个来源有权威性？
- [ ] 玩家说错物品位置时，哪个来源有权威性？
- [ ] 旧记忆与当前世界冲突时，哪个值进入回复？
- [ ] 教师模型能否改变玩家台词或世界状态？
- [ ] 训练模型能否看到 required/forbidden assertions？
- [ ] 历史 assistant 在 grounded 样本中是否参与 loss？
- [ ] 如何发现“你的偏好”被回答成“我的偏好”？
- [ ] 如何发现一句回复前半正确、后半新增错误因果？
- [ ] 哪些错误必须硬拒绝，不能被人设分补偿？
- [ ] 如何证明测试组合没有泄漏进训练？
- [ ] 如何证明新 Adapter 没有破坏裸基座逻辑能力？
- [ ] 哪个门不通过时必须停止完整训练？

本文已对上述问题给出设计答案。后续施工方案若改变这些答案，必须先修订本文版本并重新评审，不得由代码实现隐式改变权威设计。

## 24. 最终决策

V5 采用以下正式路线：

> V4 通用框架保留；新增确定性 ScenarioSpec 驱动的 runtime-grounded REPLY；事实权威按主体和领域解析；教师只负责自然语言实现；完整回复经过独立 claim 审核；新数据通过封存组合测试和裸基座非劣化门后才允许完整训练。

在 V5 小规模 Adapter 通过冻结小门之前：

- 不继续扩充旧 `reply_correction`。
- 不用原 1973 条数据直接再次全量训练。
- 不把 60 轮人工脚本加入训练数据。
- 不以更换更大模型代替生成器修复。
- 不新增运行时 ReplyFocus 或长串行判断链。
