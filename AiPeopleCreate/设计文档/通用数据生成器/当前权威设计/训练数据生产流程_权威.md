# 白未晞训练数据生产流程

版本：2026-09-19，流程统一、生活场景及显式连续窗口编排版。

本文是候选生产的当前权威流程，覆盖旧《提前编排输入与本地回复分工》和《1000条施工方案》中冲突的分工、顺序和批次推进条件。角色与场景内容仍以`世界设定/松江府`的正式设定为准。用户后续明确指令优先于本文。

## 一、默认流程和职责

**Codex编排完整输入并逐条自审 → 程序编译、检查并冻结 → Qwen生成回复 → 程序校验格式 → Gemma审核 → 程序分流、统计及生成疑点网页。**

人工可稍后裁决隔离项，不默认阻止其他已授权候选批次生产。训练导出与开始训练另行授权，不属于候选生成。

| 环节 | 执行者 | 产出与边界 |
|---|---|---|
| 编排输入 | Codex | 联合规划人物知情、世界快照、必要旧事件、旧对白、最近对白、当前问题 |
| 输入自审 | 同一Codex | 逐条检查来源、连续性、人物归属、已知/未知；留下具体理由，非独立第二模型审核 |
| 编译与冻结 | 程序 | 转正式model_view及完整消息，检查字段覆盖、对话重复、审核记录和哈希 |
| 回复生成 | 本地Qwen `qwen3.5:27b` | 只生成最终女主reply，不改世界、不补历史、不自动编排输入 |
| 格式与有效性检查 | 程序 | 空回复、无效JSON、生成过程文字等不计为有效回复 |
| 内容审核 | 本地Gemma `gemma4:31b-it-qat` | 核对历史证据、话题、事实、角色和自然度，程序核对引用与结论 |
| 分流与记账 | 程序 | 保存机器通过、内容隔离、技术失败；统计token并建立疑点审核页 |
| 疑点裁决 | 用户 | 好/差结果另存；未审维持待审，既有裁决不反复送审 |

**Codex回复语义复核不是默认环节，也不是下一批启动条件。** 用户明确要求对比模型、复盘漏判或检查特定样本时才执行专项回复复核。Codex查看运行统计、排查程序异常，与逐条判定回复内容是两回事。

## 二、每条输入的组成

输入必须一次性绑定以下信息，再生成回复：

1. 女主正式角色锚；男主基础资料按知情边界投影，未披露资料只给作者检查，不冒充女主记忆。
2. 固定场景：家庭、街角咖啡店、便利店、逛街途中、心愿咖啡馆，以及楼下与楼道、青禾菜市场、榕荫小园、邻家小馆；设施存在不等于设备运行或当日供应。
3. 当前快照：时间、天气、人物位置与活动，以及本题需要的具体物品、设备、人员、订单等状态。已知有来源，未知用结构化null并在对白上下文显示为中文未知。
4. 相关旧对白：当前100条编译入口使用4句，即两个来回。它们是提前选择的模拟记忆片段，不宣称已执行真实向量召回。
5. 最近对白：4句，即两个来回，推进同一话题并自然引出当前男主发言。
6. 旧新事实关系：过去事件在回复前冻结，带时间、主体和知情者；对白能证明说过什么，不能单凭对白证明某事件真的发生。纯假设、主观闲聊不强制凑历史事件。
7. 本题事实需求：明确哪些已知，哪些有意未知；新增字段先注册，禁止看答案后倒填依据。

### 历史声明编排（2026-09-17补充）

新编排批次在world_plan.json启用`require_history_claims: true`，并填写`history_claims`：样本序号→对白键（如memory_turns:0、recent_turns:2）→`{kind, scope, evidence_ids}`。每句都登记；scope具体描述证明什么及不证明什么，不能复制万能通过理由。旧冻结输入兼容，不回写此字段。

| 编排类型kind | 证据及表达边界 |
|---|---|
| self_report | 人物自述自身习惯、偏好和感受；不要求外部事件，但只证明此人如此表达，不证明每次如此，也不用于付款、第三方行为等客观事件 |
| knowledge_limit | 本人目前不知道；不证明外部事件未发生。例如“我不知道多久上菜”不等于“服务员没说过” |
| subjective | 主观看法、明确假设和未执行计划，不附会事实 |
| world | 绑定正式fact_id，值不得未知；旧会话不能引用本轮无获知时间的动态快照 |
| event | 绑定冻结历史事件source，检查事件时间早于或等于原话、说话者确实知情 |
| conversation | 绑定更早的memory_turns:N或recent_turns:N，只证明原话存在，不能证明原话声称的外部事件 |

没有第三方告知情况的证据时，编排为人物自己的知情范围，不写“店员没说”“店员保证”等外部行为。若情节确实需要第三方告知，应先编排对应事件及实际知情范围，再编译对白；禁止看回复后补事实。编译器检查完整性和引用；不能自动理解无限多句子的语义，分类适当性仍须Codex逐句自审并由Gemma独立判断。history_claim_plan只用于编排检查和追溯，不作为独立事实证据输入审核器，也不篡改实际模型上下文。

正式链路为`component → convert → scenario.model_view → build_messages → GAME_REPLY_CONTEXT_V1`。审核页完整消息须来自保存的实际请求，不能拿说明摘要冒充模型输入。

## 三、默认批次策略

既有1000条任务按10批、每批100条推进，旧200条不计入目标。编译器默认五个场景各20条，按每场景10闲聊、5情绪交流、5事实问答组成100条。新批可通过world_plan.json的scene_groups选择已注册场景；group_counts按源文件名显式指定每组条数，省略时每组20条。task_types按样本序号指定闲聊、情绪或事实问答类型，省略保持旧分配。小批同样经过逐条输入自审、完整消息检查和正式冻结，不另设简化入口。

每批必须先有真实Codex编排及输入自审。当前门禁要求整批通过率至少90%，批准集合、运行ID与哈希一致；通过率仅描述冻结版本，不假装初稿零修改。不得自动制造“Codex审核通过”的语义结论。

生成完成后，只需程序运行完整性检查与Gemma分流，不等待Codex再审全部回复，也不因存在人工待审队列就默认暂停候选生产。下一批输入未编排时应继续编排，不得宣称剩余条目已排队。

哈希变化、缺字段、重复输入、模型服务不可用、证据映射错误等会使结果无效的技术问题应先处理。Gemma内容拒绝项隔离保存，不凭单条拒绝停止整个任务；若报告显示同类技术故障集中出现，暂停受影响阶段并说明具体原因。本文不新增未经确认的内容通过率停机阈值。

单批入口仅运行一批。2026-09-16新增`run_reviewed_campaign_queue.py`顺序执行已冻结批次：上一批机器处理完成就接续下一批，不等待回复语义复核；缺少后续输入时显示`waiting_authored_input`，不会自行编排。Codex仍需持续完成剩余输入，不能把目标数量冒称为已排队数量。队列实际状态保存在任务根目录`queue_status.json`。

2026-09-17起，队列仅接收完成正式预检、实际消息哈希一致性核对后最后发布的`sealed_ready.json`；启动前再次核对其四份冻结文件哈希。仅有审核批准文件不代表冻结完成，避免提前启动。

## 四、审核、重试和去重

### 显式对话链的连续窗口（2026-09-19）

同一条新编排长对话可取最多4个连续窗口，不能只改时间或名词复用同段历史。`expand_authored_dialogue_windows.py`读取Codex实际写好的`authored_episodes.yaml`：每个episode包含4句相关旧对白、11句连续新对白、15句声明类型、4个任务类型、预先规划的状态及4份独立输入审核理由。它只按顺序切出最近4句与下一句男主问题，序列化已写好的审核结论；不会生成对白、推断语义批准或调用本地模型编剧。

每片100条可由25条新长链产生，也可以像既有入口一样逐条写100条。必须如实统计独立family数，不能称25条长链为100条独立情节。每个窗口单独检查连续性、证据与人物边界，再走原正式compiler、model_view、实际messages检查和seal。后续窗口里的女主历史句仍是预先编排的模拟对白，不是前一窗口Qwen实际回复，也不宣称是真实向量召回或闭环生成结果。

连续窗口的旧记忆时间保持一致，重叠最近对白的时间必须相同，前一窗口当前男主问题在后一窗口对应历史位置出现。新入口显式设定`recent_minutes_ago=2`及逐分钟快照；旧入口未提供此参数仍用原默认4分钟，不回写旧冻结输入。`inspect_authored_window_messages.py`只做完整消息和时间重叠检查，不产生语义批准。

编排装配器将同一任务已编译组件和指定既有任务组件纳入跨批去重。先完成全部1000条输入自审冻结，再启动一个覆盖10批的顺序队列和一个等待队列完成的收尾进程，可避免后台中途因Codex未编排而断供；候选完成后仍按机器审核分流，不自动进入训练库。

当前状态渲染中，值为null的物品状态只能进入中文未知区，不再以`None`混入已知事实区。此修正只影响新编译消息；旧冻结消息及已发布训练输入原样保留。

- 审核报告新增dimensions：审核有效性、历史输入、当前问题、最终回复分别记录；issue_categories区分audit_invalid、history_input_issue、question_input_issue、reply_content_issue、reply_needs_review。整体仍须全部通过才能机器放行。一条可有多类问题，分项计数不能相加当样本数。
- 审核输出无效时，各内容维度记unresolved，不用矛盾结果宣称回复合格或错误。有效审核中历史失败而最终回复合格，可以明确显示“历史输入待修正，最终回复机器通过”；原始status兼容保留content_rejected，页面和报告用细分原因解释。所有内容结论仍是机器判断。
- history负责历史输入，coverage负责当前问题与依据，facts/style负责最终回复；最终回复错误使用历史时才计入回复问题，不把历史缺陷重复算成回复错误。人工作出的好评独立于机器结论保存，不倒改机器记录或自动导出训练。

- 2026-09-17起，先核对审核输出本身是否有效：历史汇总与主体、直接对白、支持度、连续性分项须一致；证据不能引用自身、未来对白或用对白自证客观事实。矛盾结论及非法引用分为audit_invalid（审核结果无效），保持隔离，不计为已证实内容错误，也不自动通过。
- content_rejected表示通过审核输出一致性检查后仍被模型或程序拒绝，依然是机器判断，不冒称人工金标准。audit_failed表示调用或格式失败；三种状态在报告和人工页面分别提示。旁白与证据不足分别显示具体句子或断言，不再合并为一个泛化错误。
- 已明确授权的审核纠错可以只重审指定队列；必须新建输出目录，保留原回复、实际生成消息、原审核和来源哈希。只调用Gemma一次，不重新生成回复，不自动循环到通过；无效结果仍进入人工疑点页。原批已通过且不在指定队列内的记录原样保留。

- 空回复与格式错误不通过。首轮完成后仅对没有有效目标的生成失败槽位做至多一次显式格式重试，输入不变，保留首轮及重试记录。内容拒绝的有效回复不反复抽样刷通过率。
- 当前输入去重工具拒绝完全相同及近重复的整段历史，同族上限4条是上限，不代表相同历史天然可以复制4次。
- 完全相同的完整输入和回复组成重复训练对，应拦截；不同上下文的相同短答仅记频次，不直接判错。
- Gemma沿用`human24_calibration_v1`标准：不以“刚才”“没看到”单个词判捏造；真实行动需要依据，假设创作与主观偏好可以自然表达。
- 默认人工页仅收录Gemma或程序未通过项。机器通过可能存在漏判，未进入队列不等于人工认可；不宣称队列覆盖所有坏样本。
- 空回复不可被网页标为好。人工裁决另存，不覆盖原机器结论；已有24条或23条历史队列保持各自来源和状态。

## 五、正式命令

在仓库根目录`D:/AIPeopleGit/ai-girlfriend`执行。下面的`<批次目录>`用本批真实路径替换，不直接复制占位符。

```powershell
python -X utf8 AiPeopleCreate/tools/build_codex_authored_input_batch.py compile --output-root <批次目录>
# 读取draft_inputs.json及inspection.md，Codex逐条写input_review_notes.txt后：

python -X utf8 -u AiPeopleCreate/tools/run_candidate_campaign_batch.py --batch-root <批次目录>
```

`seal_authored_notes.py`仅绑定已写好的具体审核记录，不执行语义审核。编排格式和字段以`build_codex_authored_input_batch.py`、本批`source/world_plan.json`为准；沿用格式不等于复用旧对白。已冻结批次不覆盖修改。

格式重试和补算用量按实际需要执行：

```powershell
python -X utf8 AiPeopleCreate/tools/retry_curated_format_failures.py --output-root <批次目录>/formal_run
python -X utf8 AiPeopleCreate/tools/summarize_curated_reply_usage.py --output-root <批次目录>/formal_run
```

重试后的队列应从最新results生成新目录，避免展示已修复的旧失败：

```powershell
python -X utf8 AiPeopleCreate/tools/build_pending_human_review.py --results <批次目录>/formal_run/results.json --output-root <新审核目录>
```

默认不传`--semantic-results`，不启动`run_mixed_candidate_batch.py`自动编排实验入口。

审核纠错专用入口（须明确指定已授权的原疑点队列）：

```powershell
python -X utf8 -u AiPeopleCreate/tools/reaudit_invalid_candidates.py --source <原results.json> --queue <原疑点目录/queue_manifest.json> --output-root <新的重审目录>
```

该入口不生成回复。新目录results.json为合并结果，report.json单列重审数量与分类，human_review_pending仅包含最新未放行项；原目录不修改。修订审核合同后不直接续写旧正式运行目录，因为配置版本已经变化。

顺序队列入口如下；启动前确认没有其他队列持有相同批次，不重复运行。`--wait-for-previous`等待前一批单独运行的进程完成。缺输入时等待并明确报告，前一批技术失败时退出报告错误，不自动反复重试。

```powershell
python -X utf8 -u AiPeopleCreate/tools/run_reviewed_campaign_queue.py --root <任务目录> --first 3 --last 10 --wait-for-previous
```

## 六、状态与可追溯性

### 全部输入冻结后的后台收尾（2026-09-18）

`finalize_reviewed_campaign.py`只适用于已经授权、每批100条且全部发布`sealed_ready.json`的任务。它不是新的编排器，也不启动第二条回复生成队列：先逐批校验冻结文件哈希和跨批样本ID，等待原队列完成，然后仅对无有效回复且未重试的槽位调用既有一次格式重试入口，补算本地用量，合并结果并生成仅含机器/程序未放行项的人工页。内容拒绝的有效回复保持原样，不增加Codex回复复核，不导出训练包。

```powershell
python -X utf8 AiPeopleCreate/tools/finalize_reviewed_campaign.py --root <任务目录> --check
# 上一步为只读检查；确认没有同任务收尾进程，再后台启动：
python -X utf8 -u AiPeopleCreate/tools/finalize_reviewed_campaign.py --root <任务目录>
```

收尾状态与结果保存在`campaign_finalization/`。原队列失败、冻结哈希不符或结果ID不完整时记录失败，不把失败伪装成完成。默认最多等待24小时，超时需检查实际进程再续接。启动队列或收尾进程都不等于1000条已处理完；实时进度仍以原队列、批次报告和收尾状态为准。全部输入真实冻结后，本地进程才能独立消费完整目标；若尚缺Codex输入，不能用此入口代替继续编排。

分别报告：目标数量、已编排、已冻结、生成尝试数、有效回复数、机器通过数、内容隔离数、技术失败数、人工已判数、训练已放行数。不得用“处理100条”代替“100条合格”。

保留source、逐条审核理由、冻结组件及完整消息、配置哈希、requests、checkpoints、results、report、queue_manifest和token_usage。本地Qwen/Gemma token来自Ollama响应，Codex计費用量无可靠接口时记null，不记零、不按字符数伪造。检查原报告的重试字段是否是总量子集，避免重复相加。
