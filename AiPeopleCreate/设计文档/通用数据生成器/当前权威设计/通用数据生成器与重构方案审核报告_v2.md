# 通用数据生成器与重构方案审核报告（v2）

> 日期：2026-08-07  
> 状态：审核结论，未批准施工  
> 审核对象：`data_gen_v4/`、`gen_qin_v4.py`、`profiles/qinweixi/`、`数据生成规则重构方案_v1.md`、现有 997+119 条数据及训练打包路径  
> 当前结论：**不建议按《数据生成规则重构方案_v1.md》施工。**  
> 文档关系：本报告替代 `通用生成方案审核报告_v1.md` 的审核结论；旧报告保留作为历史草稿，待项目负责人确认后归档。

## 1. 执行结论

《数据生成规则重构方案_v1.md》正确识别了现有系统的表面问题：规则补丁不断增加、词法检查无法覆盖开放语义错误、失败重试缺少有效反馈。但它给出的目标态仍然是：

```text
规划 JSON
→ 写作 JSON
→ 元数据比对
→ critic
→ rewrite
→ 旧 checker 预筛
→ taxonomy 回流 prompt/schema
```

这不是生成范式变化，而是把原有“单次生成 + 规则过滤”扩展成更长的补丁链。它仍然缺少四个决定训练数据是否有效的核心能力：

1. **候选池**：同一训练目标生成多个真正独立的 Candidate，而不是失败后重试同一稿。
2. **数据集级选择**：联合考虑质量、目标覆盖、语义多样性和风险，而不是逐条通过即入库。
3. **训练后效用闭环**：用固定模型、固定训练配置和冻结评测合同测量新增数据的边际收益。
4. **不可变发布**：证据、模型、prompt、validator、split、人工审核和 manifest 共同决定 DatasetRelease。

因此，本报告建议停止继续扩展现有规则层，也不直接施工 v1 的 plan/write/critic 链。目标应改为：

> **目标驱动的数据搜索与发布 Module**：从目标模型的行为缺口出发，生成多样 Candidate，经过硬约束、校准评审和数据集级选择后发布；再通过小批训练和冻结评测判断这些数据是否值得保留。

在新的发布合同完成前：

- 现有 997 条应标记为 `candidate_unreviewed`，不能因“已导出”视为正式 release。
- 现有 119 条行为矩阵应标记为 `human_review_incomplete`，不能宣称全部人工复核通过。
- 不应继续基于现有管线扩大数据规模。
- 不应在 v1 阶段 2/3 完成后直接全量重跑；先完成选择和训练后效用闭环，再决定是否重生成。

## 2. 审核依据与方法

### 2.1 当前权威合同

本报告按以下当前文档判断训练任务和发布要求，不把历史方案或生成器自己的声明当作上位合同：

1. `需求文档/项目框架需求.md`
2. `设计文档/AI设计/当前权威设计/AI女友最小心智系统设计.md`
3. `设计文档/AI设计/当前权威设计/本地AI恋爱桌面宠物产品集成设计.md`
4. `eval/training_contract/freeze02_contract_v1.json`
5. 秦未晞当前角色正典及结构化正典

关键要求包括：

- 首个约 1000 条工程候选只允许可见 `REPLY` 数据。
- 可见回复、后台结构化模式、关系记忆 selector 数据必须物理分离。
- 后台结构化数据在 mode schema 冻结前不得发布。
- train/dev/test 必须按 conversation、leakage group、source record 等锚点隔离。
- 每次迭代必须保存数据版本、模型哈希、prompt、采样配置、训练配置和评测报告。
- 条数不是质量通过标准。

### 2.2 本地只读检查

本次进行了以下只读检查：

- 审阅生成器 core、mode Adapter、model Adapter、gate、compiler、sink、exporter 和生产入口。
- 实际编译秦未晞 package，检查 plan、lock、risk、review、evidence 和 candidate 配置。
- 审阅 release、recipe、protocol 和 FREEZE-02 的合同传递情况。
- 统计最终 997 条及 119 条矩阵的数据分布、属性复读、场景坍缩和 family/split 泄漏。
- 回溯最终数据到 shard metadata 和 gate report。
- 检查人工复核表、验收报告和训练包 README 的状态一致性。
- 运行核心测试：`215 passed`。

测试通过仅说明现有测试所覆盖的行为未失败；当前测试没有覆盖数量兑现、risk 继承、非空证据、完整发布门、真实模型 lineage、人工复核状态和 family-aware split。

### 2.3 联网研究

联网核验了 Self-Instruct、Evol-Instruct、Magpie、Persona Hub、DEITA、LESS、UltraFeedback、Tulu 3、LLM-as-a-Judge、MDS、KITE 等论文或官方仓库，并复核了 v1 引用的论文是否真的支持其论点。研究结论见第 6 节。

### 2.4 数据统计限制

- exact duplicate 使用去空白后的完整 human/assistant 对话统计。
- near duplicate 使用字符 trigram Jaccard，阈值检查到 0.70；这是词法近似，不等于语义聚类。
- 没有在本次审核中运行 embedding 或 LLM 聚类，因此语义重复结论是保守下界。
- 高频短语统计只证明分布偏斜，不单独判定每一条样本错误；代表样本另行人工核对。

## 3. 阻断问题

### P0-1：ReleasePolicy 没有控制实际发布

**代码事实**

- `profiles/qinweixi/release.yaml:12-28` 要求 G0-G7、profile validator、protocol validator 和人工审核规则。
- `gen_qin_v4.py:330-336` 将 G3/G4 注入为无条件通过。
- `gen_qin_v4.py:355` 和 `gen_qin_v4.py:411` 实际只启用 G0/G1/G2/G5/G6/G8。
- 现有 shard gate report 只包含 G0/G1/G2/G3/G5/G6，缺少 G4/G7；历史与当前脚本均没有兑现完整 release 合同。
- `CandidateRecordV4.review_status` 固定为 `pending`，pending Candidate 仍可直接导出。

**风险合同丢失**

- recipe 中 `reply_safety` 是 `risk_level: high`、`review_requirement: full`。
- `RecipeDrivenItemFactory` 构造 item 时没有把 strata 的 risk/review/candidate 配置传给 sample。
- 实际编译的 24 条 safety 全部变成 `risk_level=low`、`required_review=auto`。

**影响**

当前 gate report 只能证明“运行过某些检查”，不能证明“满足 ReleasePolicy”。`accepted=true` 不能等价于正式可训练或可发布。

### P0-2：证据链为空，G2 对无证据样本直接批准

实编译结果：

| 指标 | 结果 |
|---|---:|
| PlanItem 总数 | 2674 |
| `source_refs` 为空 | 2674 |
| `support_spans` 为空 | 2674 |
| safety 条目 | 24 |
| safety 编译为 `low/auto` | 24 |

`data_gen_v4/core/gates.py:106-115` 在 `support_spans` 为空时直接批准 G2。`RecipeDrivenItemFactory` 又没有填充 `source_refs/support_spans`，因此 evidence 字段目前是装饰性合同，不是发布事实。

这意味着：

- “角色事实来自 canon”没有逐条 evidence packet 证明。
- “没有编造”主要依赖 prompt 和文本启发式检查。
- v1 新增 `used_facts` 只会得到模型自报的 ID，仍不能证明正文被来源蕴含。

### P0-3：复现锁与真实模型 lineage 不成立

`data_gen_v4/core/compiler.py:259-275` 生成的 lock 中：

```yaml
prompt_refs: {}
validator_refs: {}
adapter_revisions:
  core: ...
```

同时：

- Candidate 写入的是抽象 `reply-teacher/v1`，不是真实 provider/model revision。
- `ModelPool` 遇到 dict 型 model spec 时使用 CLI 注入的 `default_model`。
- reply Adapter 生成字符串 seed，真实 Adapter 只向 provider 传整数 seed。
- reply 和 structured protocol Adapter 均返回空 `calls`，Candidate 的 `provenance.calls` 因而为空。
- resume 只比较旧 lock hash，却可接收新的 ModelPool，无法保证恢复时模型和 Adapter 未改变。

当前 lineage 无法回答：某条 Candidate 由哪个真实模型、哪个 prompt、哪次调用、哪些采样参数生成。

### P0-4：`candidate_count` 是死字段，没有 Candidate 选择

recipe 声明 `candidate_count=2/3`，PlanItem 也持有该字段；但 Engine 只循环 `max_attempts`：

```text
尝试生成
→ 失败则重试
→ 第一个成功立即写 c1 并返回
```

所有 Candidate 都是 `candidate_no=1`。系统没有：

- 同一目标的 N 个独立候选；
- best-of-N；
- 成对比较；
- quality/diversity 联合选择；
- rejected Candidate 与 winner 的完整关系；
- 数据集级 coverage 优化。

失败重试与 Candidate 搜索不是同一件事。重试解决“能否生成合法对象”，候选选择解决“哪个对象最值得训练”。

### P0-5：冻结训练合同没有进入生成器 Seam

当前唯一 AI 设计要求分离：

1. 可见 `REPLY/PROACTIVE_REPLY`；
2. `MEMORY_PROPOSE/SELF_TIMELINE_PROPOSE/OFFSCREEN_UPDATE/MOTIVE_EVALUATE`；
3. 独立关系记忆 selector 数据。

但 V4 ProtocolBundle 只有：

- `REPLY`
- `RECALL_PLAN`
- `MEMORY_PROPOSE`

FREEZE-02 又明确规定：

- 首个工程候选只允许 `REPLY`；
- 后台结构化 mode 在 schema 冻结前 `blocked_until_mode_schemas_frozen`；
- selector 在 SELECT-01 前 `blocked_until_select01`。

现有 Generator Interface 无法根据冻结训练合同返回 `AdmissionBlocked`，也无法保证不同数据家族物理隔离。v1 仍只重构普通 reply 写作，没有先重定训练任务合同。

## 4. 重要但非阻断的问题

### P1-1：core 与通用 Adapter 被生产角色知识污染

以下内容位于通用 Implementation：

- `core/compiler.py`：秦未晞专属事实字段中文标签。
- `core/gates.py`：异世界秘密词和中文急救词表。
- `adapters/modes/reply.py`：秦未晞姓名、怕冷、数学、航天基地、防空洞等补丁。
- `prompts/reply_merge.txt`：生产角色名、玩家名和专属事件规则。

这直接违反 V4 自己的“不通过条件”：core 中不得出现生产角色名、专属事实或专用问题池，checker 不得通过全局硬编码判断角色事实。

真正通用的 Locality 应是：

- 角色事实和风格只改 ProfilePackage；
- 安全知识只改有来源、版本化的 ProtocolBundle；
- mode 行为只改 TaskContract/Mode Adapter；
- 发布阈值只改 ReleasePolicy；
- core 不随角色变化。

### P1-2：顶层 Module 太浅，调用方承担实际 Implementation

生产入口必须手工组装：

```text
PackageSet
→ Registry
→ SourceLoader
→ ItemFactory
→ Compiler
→ ModelPool
→ Engine
→ Sink
→ Gate
→ Renderer
→ Exporter
```

调用方需要知道过多内部 ordering、错误恢复、gate 注入和导出细节。删除顶层 Generator 后，复杂度不会重新出现在多个调用点，因为复杂度本来就已经在调用点；这是浅 Module。

`--count` 也没有兑现调用合同：

| 请求 | 实际选中 |
|---:|---:|
| 20 | 13 |
| 100 | 91 |
| 1000 | 492 |

成功结果应满足精确数量，或返回类型化 `QualifiedSampleShortfall`，不能静默少产。

### P1-3：所谓语义检查仍是词法启发式

`ReplyModeAdapter` 的关键检查包括：

- 命题只要任意三字片段出现在 assistant 文本即视为落地。
- 事实主张只要数字命中或存在二字公共子串即视为有支撑。
- 共同经历依赖 bigram 匹配。
- 身份、属性、秘密和安全依赖不断扩张的词表。

这些规则会同时产生：

- **误放**：文本共享常见片段但语义不相同。
- **误杀**：自然同义表达没有共享指定片段。
- **生成诱导**：教师为了通过检查，主动朗读身份和属性。
- **补丁增长**：每次误判继续加例外词、场景词和前缀。

硬规则仍有价值，但只适合结构、来源存在性、禁止泄漏和已审定安全协议等可机械验证事项。开放语义不应伪装成确定性字符串问题。

### P1-4：权威正典存在副本漂移

文件哈希检查显示：

- `人物设定/秦/bible.yaml` 与 profile 副本相同。
- `人物设定/秦/canon.json` 与 profile 副本不同。
- `人物设定/秦/timeline.yaml` 与 profile 副本不同。
- 权威 `canon.json` 已有 `capability_boundary`，profile 副本缺失该条。

v1 把“新增能力边界”列为施工项，但真正问题是生成器读取复制品，而不是从唯一权威源编译不可变 snapshot。继续给副本补字段只会扩大漂移面。

### P1-5：失败恢复依赖 plan 下标，崩溃窗口不可可靠重放

- `--retry-from` 从旧 plan ID 尾部提取索引，再映射到新编译 plan。
- recipe、pool 或编译顺序变化后，索引可能指向不同目标。
- 外部调用完成后先写 CallRecord，再写 Candidate；两次 append 之间崩溃会重新调用模型。
- CallRecord 只有 output hash，没有可重放原文或 blob ref。

复现非确定性外部模型的正确含义应是“重放已保存的原始响应”，不是再次请求模型并假设得到同一结果。

## 5. 对《数据生成规则重构方案_v1.md》的逐项判定

### 5.1 可以保留

| 内容 | 处理方式 |
|---|---|
| 错误 taxonomy | 保留为不可变 observation 分类，不直接等同于 prompt 补丁队列 |
| 带失败原因的 retry/rewrite | 保留为有界 repair；必须创建 child Candidate 并保留 parent lineage |
| 属性能力边界和反例 | 保留；从唯一权威正典编译，不维护第二份属性库 |
| 现有 checker | 仅保留可解释、低成本的 early rejection；不得批准 release |
| 规划轨迹 | 仅在能产生可验证 artifact 时保留，例如 evidence ID、protocol action ID |
| 高风险人工审核 | 保留并由 ReleasePolicy 强制，不能靠调用方选择是否执行 |

### 5.2 必须删除的论断

| v1 论断 | 判定 |
|---|---|
| 结构化轨迹让语义错误“事前不可能” | 错。schema 只能约束结构，不能保证自然语言事实正确或关系自然 |
| `used_facts` 自报可以证明事实落地 | 错。自报可漏报、错报，也无法发现规划外编造 |
| `used_attributes ⊆ attribute_plan` 能根治属性朗读 | 错。开放文本不是属性白名单语言；隐含表达和不合时宜使用都无法由集合包含判断 |
| `safety_actions` 出现在消息即可替代安全校验 | 错。动作词出现不代表顺序、条件、剂量和处置正确 |
| critic 必须强于 teacher | 不是普遍定律；必须与强 teacher 直出做对照实验 |
| 逐轮 critic 等于过程监督 | 错误外推；MATH 的推理步骤监督不能直接证明角色对话逐轮审查更优 |
| taxonomy 回流 prompt/schema 即形成飞轮 | 不完整；没有训练后效用反馈仍是生成器内部自循环 |

### 5.3 必须改写

| v1 内容 | 改写为 |
|---|---|
| 两阶段规划+写作是主架构 | named WorkflowPolicy 中的一种可消融生成策略 |
| critic 是终审 | critic 只产生 ReviewEvidence；批准权属于 ReleasePolicy + 硬门 + 校准阈值 + 必需人工审核 |
| used_facts 是事实依据 | used_facts 仅作 provenance；事实通过来自 claim extraction + evidence entailment/人工 oracle |
| safety 由 teacher 自由生成再检查 | 安全处置骨架来自经审核、版本化的 ProtocolBundle；teacher 只做角色化表达 |
| 属性密度限频 | 数据集级分布约束 + 情境触发覆盖，不在每条回复里机械配额 |
| 每批 taxonomy 聚类后改 prompt | 先关联 `behavior_gap_id`、Candidate、训练版本和评测 delta，再决定改来源、蓝图、生成策略或选择器 |

## 6. 联网研究结论

### 6.1 可迁移的方法

| 来源 | 核心方法 | 对本项目的正确用法 | 不应误用为 |
|---|---|---|---|
| [Self-Instruct](https://arxiv.org/abs/2212.10560) | 从 seed 生成 instruction/input/output，再过滤无效与近重复 | 建立可扩展的场景蓝图池 | 证明模型自产数据天然可靠 |
| [Evol-Instruct](https://arxiv.org/abs/2304.12244) | 对 seed 做深度和广度演化 | 演化玩家处境、证据状态、关系难度和反事实 | 演化角色 canon 或凭空增加事实 |
| [Magpie](https://arxiv.org/abs/2406.08464) | 生成 400 万候选，选择 30 万高质量实例 | 先扩大 Candidate pool，再做质量和多样性选择 | 单条规划比候选选择更重要 |
| [Persona Hub](https://arxiv.org/abs/2406.20094) | 用多样 persona 扩展问题视角 | 生成玩家侧职业、处境、表达习惯和关系视角 | 强化多个秦未晞人格或属性朗读 |
| [DEITA](https://arxiv.org/abs/2312.15685) | complexity、quality、diversity 三维选数；6K 可胜十倍数据 | 先质量阈值，再做覆盖和多样性选择 | complexity 越高越适合角色对话 |
| [UltraFeedback](https://arxiv.org/abs/2310.01377) | 多候选、多 rubric 反馈、best-of-N、偏好数据 | 同 prompt 生成 N 个候选并构造高置信 pair | 单 judge 分数可以当真值 |
| [LESS](https://arxiv.org/abs/2402.04333) | 用目标验证样本和训练影响选择数据；5% 可优于全量 | 第二阶段研究目标能力的边际数据效用 | 首版必须直接实现昂贵梯度选择 |
| [Tulu 3](https://arxiv.org/abs/2411.15124) | SFT/DPO/RLVR、开发集、未知评测、去污染和完整 recipe | 建立数据、训练、评测和发布的一体化实验账本 | 只复制某种训练算法 |
| [MDS](https://arxiv.org/abs/2604.07892) | 按整段多轮对话的覆盖、结构和信息进展选择 | conversation-level selection，避免只看逐轮分数 | 每轮 critic 足以代表整段质量 |
| [KITE](https://arxiv.org/abs/2607.17043) | 失败驱动生成、能力边界附近的不确定性选择 | 根据冻结评测的行为失败簇采集下一批数据 | 让生成器读取 sealed 测试题原文 |

### 6.2 v1 引用纠偏

#### 《A Critical Evaluation of AI Feedback》

[论文](https://arxiv.org/abs/2402.12366) 的结果是：常见 RLAIF 的收益很大程度来自 critic 比 SFT teacher 强；直接使用 GPT-4 作为 teacher 的 SFT 可以优于更复杂的“弱 teacher + GPT-4 critic”流程。

因此它不支持“critic 必须强于 teacher”作为架构定律，反而要求本项目至少比较：

- 强 teacher 直接生成；
- 弱 teacher + 强 critic；
- 强 teacher + 校准 selector。

#### 《Let's Verify Step by Step》

[论文](https://arxiv.org/abs/2305.20050) 比较的是 MATH 数据集上的人工步骤监督和结果监督。它不能推出“逐轮审角色对话一定优于整段终检”。角色对话的自然度、关系一致性和信息进展往往需要整段判断。

#### 《The Format Tax》

[论文](https://arxiv.org/abs/2604.03616) 支持把推理与序列化解耦，但同时指出较新的闭源模型格式税很小。它不支持：

- 把 JSON 称作自由文本；
- 认为所有生成都必须先自由规划；
- 认为规划 JSON 能提高事实正确性。

#### 《The False Promise of Imitating Proprietary LLMs》

[论文](https://arxiv.org/abs/2305.15717) 说明 imitation 容易学到风格，却难以补齐训练数据未覆盖的基座能力。它没有证明过滤无用，也没有证明事实问题只能在生成源解决。

#### LLM-as-a-Judge

[LLM-as-a-Judge](https://arxiv.org/abs/2306.05685) 和 [FairEval](https://arxiv.org/abs/2305.17926) 明确记录位置、冗长、自增强等偏差。Judge 可扩展，但必须：

- 隐去 Candidate 来源和模型名；
- pairwise 换序复判；
- 使用人工 gold 校准误报和漏报；
- 允许 abstain 和进入人工复核队列；
- 不让同一 judge 独立决定正式 release。

## 7. 推荐目标态：目标驱动的数据搜索与发布 Module

### 7.1 核心流程

```text
冻结 DatasetObjective、开发集与 sealed holdout
→ 对目标模型运行基线评测
→ 只输出行为族级 gap vector，不向生成器暴露 sealed 原文/oracle
→ BehaviorPlanner 按失败簇、风险和覆盖缺口分配预算
→ 生成玩家侧场景蓝图和最小反事实 family
→ 每个目标生成 N 个 Candidate
→ schema / evidence / safety / contamination 硬校验
→ 校准的 judge panel 做多轴评分和 pairwise 比较
→ 按质量阈值、行为覆盖和语义多样性进行数据集级选择
→ family-aware split、近重复检查、人工复核
→ 原子发布 SFT / preference / structured artifact
→ 固定模型与训练配置进行小批训练
→ 在冻结开发集、未知评测和人工盲测上测 delta
→ 只针对仍失败的行为簇继续采集
```

### 7.2 场景蓝图，而不是角色属性配额

蓝图应围绕运行时需要的行为合同组织，例如：

| 行为族 | 最小对照 |
|---|---|
| 事实使用 | 有 evidence / 无 evidence / conflicting evidence |
| 记忆边界 | supported / insufficient / false premise / corrected |
| 可见性 | public / private / profile_secret |
| 能力属性 | 属性被话题触发 / 无关场景不得主动朗读 |
| 严肃支持 | 普通负面情绪 / 高风险健康或安全 |
| 关系边界 | 自然暧昧 / 明确拒绝越级 / 玩家纠正 |
| 主动行为 | 有合法意图 / cooldown 抑制 / quiet hours / 自然消退 |
| 后台结构化 | 正结果 / 空结果 / 否定 / 冲突 / 假设 |

Persona Hub 类方法只用于扩展玩家侧视角，不用于创造多个角色 canon。Evol 类方法只能演化场景、证据状态、表达方式和难度，不得演化正典事实。

### 7.3 Candidate 质量向量

每个 Candidate 不应只有 `approved/rejected`，而应保存不可变质量向量：

```yaml
hard:
  schema_valid: true
  evidence_valid: true
  safety_protocol_valid: true
  sealed_contamination: false
soft:
  instruction_fulfillment: 0.91
  persona_naturalness: 0.84
  relationship_fit: 0.88
  conversational_progress: 0.79
  style_restraint: 0.93
selection:
  semantic_cluster: cluster-...
  novelty: 0.71
  coverage_contribution:
    - gap:serious_support:no_self_centering
review:
  judge_agreement: 0.86
  human_required: false
```

硬约束不可被软分数补偿。软分数用于排序和选择，不直接证明事实或安全正确。

### 7.4 SFT、preference 与 rejected 数据

- 每个蓝图的最佳 Candidate 可进入 SFT 候选池。
- 只有同 prompt、换序一致、跨 judge 达成 agreement 且 margin 足够的 pair 才可进入 preference 数据。
- 普通 rejected Candidate 只进入审计账本，不能自动当 DPO 负样本。
- 安全样本的动作骨架来自审核过的协议知识；teacher 只负责角色化表达。
- 约 1000-2500 条规模下，DPO 是否优于高质量 SFT 必须通过消融决定，不能默认启用。

## 8. 推荐的深 Module Interface

### 8.1 方案比较

本次对三种 Interface 取向进行了比较：

| 取向 | Interface | Depth | Locality | 主要问题 |
|---|---|---|---|---|
| 默认调用最简单 | `build_dataset(...)` | 高 | 高 | 复杂实验矩阵表达较弱 |
| 最小生产 Interface | `build(...)`、`resume(...)` | **最高** | **最高** | 每次实验需要先形成版本化 request |
| 研究灵活性最大 | `compile(...)`、`execute(...)`、`materialize(...)` | 中 | 中 | 容易把内部 DAG 和因子组合泄漏给调用方 |

推荐采用混合方案：

- 正式外部 Seam：`DatasetGenerator.build/resume`。
- 普通调用便利函数：`build_dataset(...)`，内部转成 BuildRequest。
- `compile/execute/materialize` 作为内部 DatasetLab，不进入常规生产 Interface。

### 8.2 外部 Interface

```python
@dataclass(frozen=True)
class BuildRequest:
    recipe_ref: PackageRef[DatasetRecipe]
    objective_ref: PackageRef[DatasetObjective]
    destination: Path
    seed: int
    budget: RunBudget


@dataclass(frozen=True)
class RunBudget:
    max_external_calls: int
    max_cost: Decimal | None
    deadline: datetime | None
    concurrency: int = 8


@dataclass(frozen=True)
class DatasetRelease:
    release_id: str
    manifest_path: Path
    manifest_hash: Sha256
    package_lock_hash: Sha256
    split_counts: Mapping[str, int]


@dataclass(frozen=True)
class IncompleteRun:
    run_id: str
    reason: FailureSummary
    resumable: bool


BuildOutcome = DatasetRelease | IncompleteRun


class DatasetGenerator:
    def build(self, request: BuildRequest) -> BuildOutcome: ...
    def resume(self, run_id: str, *, budget: RunBudget | None = None) -> BuildOutcome: ...
```

普通调用：

```python
result = build_dataset(
    profile="profiles/qinweixi",
    objective="behavior-contract.chat01.v5",
    count=1000,
)
```

调用方不再学习 PlanItem、Candidate、Gate、Sink、Renderer、Exporter、split ordering 或 retry index。

### 8.3 Interface 不变量

1. 所有 PlanItem 在首次外部调用前编译并冻结。
2. profile、protocol、recipe、release、training contract、真实模型 revision、prompt、validator、schema、rubric、sampling 和 exporter 全部进入 lock。
3. 成功必须发布精确 count；不足返回 `QualifiedSampleShortfall` 或 `IncompleteRun`。
4. teacher、critic 和 generator 均无权写 approved。
5. 每个 Candidate 绑定真实 call IDs、parent Candidate、PlanItem 和 evidence packet。
6. repair 创建 child Candidate，不原地覆盖。
7. sealed suite 原文和 oracle 永不进入 teacher、critic、embedding 或 prompt 调试。
8. safety 等 high-risk 不允许调用方降级 review。
9. family、question family、scene family、semantic cluster 和 source anchors 整组 split。
10. 只有全部硬门、覆盖、去重、split、人工审核和 manifest 事务成功，才能返回 DatasetRelease。
11. 外部模型非确定性时，复现依赖保存并重放原始响应，不依赖重新生成相同文本。
12. 未冻结的 mode 必须返回 `AdmissionBlocked`，不能静默生成或混训。

### 8.4 Ordering

```text
resolve root recipe
→ validate dependency closure
→ check training admission
→ snapshot and lock
→ compile PlanItems and split anchors
→ generate K Candidates
→ deterministic hard validation
→ independent ReviewEvidence
→ deterministic dataset selection
→ bounded repair
→ global dedup / coverage / split
→ required human review
→ atomic manifest and release
```

### 8.5 依赖与 Adapter

| 依赖类别 | 内容 | 处理方式 |
|---|---|---|
| in-process | 规划、schema/evidence 校验、选择、coverage、split | 作为深 Module 的 Implementation，不暴露 Adapter |
| local-substitutable | package、source、SQLite ledger、manifest、embedding cache | 内部 Seam；生产 filesystem/SQLite Adapter，测试 temp/in-memory Adapter |
| remote but owned | 本地模型、冻结评测 runner | typed port；生产 HTTP/进程 Adapter，测试 replay Adapter |
| true external | aihub teacher、critic、embedding、人工审核 | 注入 typed port；生产 Adapter + strict scripted test Adapter |

建议替换当前通用 `ModelPool.resolve(dict)`：

```python
class TeacherPort(Protocol):
    def generate(self, tasks: Sequence[GenerationTask]) -> Sequence[Draft]: ...


class CriticPort(Protocol):
    def assess(self, tasks: Sequence[ReviewTask]) -> Sequence[ReviewEvidence]: ...


class EmbeddingPort(Protocol):
    def embed(self, texts: Sequence[str]) -> EmbeddingBatch: ...
```

这些是真实 Seam，因为每个都至少存在 production、local/replay 和 test Adapter。Planner、Selector 和 Splitter 不需要为了测试而成为外部 port。

## 9. 现有实现的处置建议

### 9.1 可复用

- package schema 和依赖引用概念；需改为封闭合同并完整进入 lock。
- append-only sink 思路；需保存原始模型响应或 blob ref。
- deterministic seed 派生；需确保真实 provider 接收的 seed 被记录。
- mode-specific render/export；保留为内部真实 Seam。
- gate reason code；升级为版本化 Observation，不直接批准 release。
- pool 中的 required/forbidden behavior；升级为 DatasetObjective 的行为蓝图输入。
- ProfilePackage、ProtocolBundle、DatasetRecipe、ReleasePolicy 四类知识归属。

### 9.2 应删除或收回内部

- 从外部 Interface 删除 `SourceLoader`、`PlanItemFactory`、`ModelPool`、`ModeAdapter`、`ValidatorAdapter`、`PackageRegistry`。
- 删除 `ReleaseQualityGate.set_injected`；validator 必须由锁定 package 解析。
- 删除 no-op validator 和静默 gate 降级。
- `candidate_count` 要么真正实现 K Candidate + selector，要么删除。
- 删除恒定 `review_status=pending` 作为表面状态字段；用 record 类型和 ReviewDecision 表达状态。
- 删除 core 和通用 reply Adapter 中的秦未晞专属词表与分支。
- 删除依赖 plan 全局下标的 retry/regen Interface。
- 删除把完整 ReleasePolicy 交给 teacher/critic 的做法，避免 sealed ref 暴露。

### 9.3 作为 legacy WorkflowPolicy 保留

当前 V4 可封装为：

```text
workflow:legacy.reply.v4
```

它用于：

- 复现实验基线；
- 迁移期间读取旧 package；
- 与新目标驱动流程做等预算消融。

不应继续直接扩展旧主流程，也不应把 legacy WorkflowPolicy 当作正式发布路径。

## 10. 迁移顺序

### 阶段 0：冻结现状

- 停止扩大现有数据规模。
- 997 标记为 `candidate_unreviewed`。
- 119 标记为 `human_review_incomplete`。
- 保存当前数据、脚本、模型、训练配置和评测结果作为 legacy baseline。
- 不删除旧数据，不在本阶段重生成。

### 阶段 1：修复合同完整性

- ProfilePackage 直接编译唯一权威 canon，删除生产 source 副本。
- lock 覆盖 prompt、validator、真实模型、rubric、sampling、schema、exporter。
- risk/review/candidate 配置从 recipe 正确传递到 PlanItem。
- FREEZE-02 admission 进入 Generator Seam。
- ReleasePolicy 不允许调用方 no-op 或漏执行。

### 阶段 2：统一 Candidate Ledger

- 保存原始外部响应和完整 CallRecord。
- 实现 K Candidate、parent/child repair 和 winner lineage。
- transient provider error 与 semantic failure 分开处理。
- resume 从 ledger 恢复，不重新请求已完成调用。

### 阶段 3：硬校验与数据集级选择

- 建立 evidence packet 和 claim-level validation。
- 安全知识进入审核过的 ProtocolBundle。
- 实现质量向量、pairwise judge、换序一致性和 abstain。
- 先过质量阈值，再做 coverage/diversity 选择。

### 阶段 4：去污染、整组切分和原子发布

- normalized exact hash。
- n-gram MinHash。
- embedding 近邻检查。
- family + semantic cluster 连通分量切分。
- sealed suite 只提供单向 contamination check 和聚合 gap，不提供原文。
- manifest 事务成功后才产生 DatasetRelease。

### 阶段 5：训练后效用闭环

- 固定 Qwen3.5-4B revision、LoRA 配置、token budget 和训练步数。
- 运行小批训练。
- 在开发集、未知评测、diagnostic120 和人工盲测上比较 delta。
- 只有目标能力改善、安全不退化、通用能力不退化的数据版本才能晋升。
- 失败只回流为 `behavior_gap_id + evidence + model_delta`，不直接新增关键词规则。

## 11. 最小验证实验

### 11.1 四组等预算消融

| 组 | 生成策略 | 选择策略 |
|---|---|---|
| A | 当前 V4 pool + checker | 首个合法 Candidate |
| B | v1 plan/write | critic rewrite 后首个合法 Candidate |
| C | 目标驱动蓝图 + 强 teacher，N=1 | 硬门 + 数据集级 coverage/diversity |
| D | 目标驱动蓝图 + 强 teacher，N=4 | 硬门 + 校准 pairwise + coverage/diversity |

控制变量：

- 相同外部调用/token/金额预算；
- 相同目标条数；
- 相同基座模型 revision；
- 相同 LoRA 配置和训练 token；
- 至少 3 个训练 seed；
- 相同冻结评测和人工盲测流程。

### 11.2 预注册指标

| 类型 | 指标 |
|---|---|
| 硬门 | schema、evidence、secret、安全、数据家族隔离、sealed contamination |
| 行为 | 严肃支持不自我中心、事实边界、未知保持、关系边界、自然度 |
| 通用能力 | 常识、计算、指令跟随、安全问题、误拒率 |
| 数据集 | coverage、语义 cluster 数、最大 cluster 占比、跨 split 近重复 |
| judge | gold precision/recall、换序一致率、abstain 率、人机一致性 |
| 训练效用 | 目标评测 delta、最差行为簇 delta、跨 seed 方差 |
| 成本 | 生成 token、评审 token、人工分钟、每个有效增益样本成本 |

### 11.3 晋升条件

建议首轮以以下条件为准，而不是“生成成功率”或“条数达到 1000”：

1. safety blocker 通过率 100%。
2. sealed contamination 0。
3. family/semantic cluster 跨 split 泄漏 0。
4. 目标行为族在至少 2/3 seed 中稳定改善。
5. 通用能力和误拒率不显著退化。
6. 人工盲测不低于当前最佳基线。
7. 完整 release manifest 可从 ledger 重建。

## 12. 必须新增的测试

### Interface 测试

- `count=20/1000`：精确发布或返回类型化 shortfall。
- 修改真实模型、prompt、validator、canon、schema 任一字节必须改变 lock。
- 未冻结 mode 必须返回 `AdmissionBlocked`。
- budget 用尽返回 `IncompleteRun`，不得静默换模型或降低审核级别。

### Candidate 测试

- `candidate_count=3` 必须生成三份可追踪 Candidate。
- selector 必须记录所有 Candidate、winner 和选择证据。
- repair 必须创建 child Candidate，parent 不可变。
- semantic failure 不得仅升温盲重试。

### Evidence 与安全测试

- 角色事实主张缺 Evidence ID 必败。
- 空 `support_spans` 在需要 evidence 的任务中必败。
- 自报 `used_facts` 与正文不一致必败。
- safety 缺审核来源、缺 full review 或被降级均阻断。

### Release 测试

- G0-G7、profile/protocol validator 和人工审核缺一项均不得发布。
- pending Candidate 不得进入正式 DatasetRelease。
- split 必须使用全部 family/source/semantic anchors。
- 精确和近重复注入必须阻断跨 split 发布。
- 中断续跑与一次完成应得到相同 manifest。
- sealed suite 原文不得出现在捕获的 teacher/critic/embedding 请求中。

### Protocol 测试

- visible reply、background structured、memory reranker 物理隔离。
- `REPLY` 和 `PROACTIVE_REPLY` 使用可见文本 schema。
- 后台 mode 使用各自冻结 JSON schema，允许合法空结果。
- selector 数据包含困难负样本和全拒绝标签，不得由普通 reply SFT 代替。

## 13. 最终建议

1. **否决按现稿施工 v1。** 不再把主要资源投入 plan/write/critic 补丁链。
2. **先修发布真实性。** risk、evidence、lock、gate、review、split 任一失真时，生成质量讨论没有可靠基础。
3. **建立一个深 DatasetGenerator Module。** 外部只暴露 `build/resume`；普通用法由 `build_dataset` 包装。
4. **把 Candidate 选择提升为核心能力。** 生成合法样本不是目标，选择最有训练价值的数据才是目标。
5. **让训练后的目标能力增益决定下一批数据。** taxonomy 只是 observation，不是自动加规则的指令。
6. **安全和事实使用权威来源。** teacher 负责表达，不负责发明安全处置或决定正典真值。
7. **先做等预算消融，再决定是否保留两阶段规划、critic 或 preference 训练。** 方法必须靠本项目目标模型的实际 delta 晋升。

本报告只形成审核结论和推荐目标态，不修改生成器代码、训练数据、模型或当前权威架构。任何施工应在项目负责人确认目标态后另立施工文档，并同步更新受影响的权威合同。
