## 1. V4 的通用范围

V4 所称“通用数据生成器”是：

> 同一套生成核心无需修改代码，只通过加载不同的角色包、协议包、数据配方和发布策略，即可为不同角色生成可追溯、可审核、可切分和可训练的对话与运行时协议数据。

它必须支持：

- 不同姓名、身份、关系、世界观和时间线。
- 有时间线或没有时间线的角色。
- 第一人称、第三人称、正式、口语等不同表达合同。
- 不同公开/私密/秘密可见性和披露策略。
- 不同标签集合、回复长度、轮数和场景分类。
- 不同数据 mode 和严格输出 schema。
- 不同模型提供方、critic、embedding、导出格式和训练配比。
- 不同 checker、评测集和发布阈值。

V4 首版的业务范围仍是“角色对话与记忆协议数据”。它不声称是图像、语音、代码、工具轨迹等任意模态的万能合成平台。未来要支持其他数据域，必须新增相应 `ModeAdapter` 和 `ExportAdapter`，而不是把非文本需求塞进角色 profile。

## 2. V3 为什么不是通用生成器

V3 的 provenance、证据 fixture、追加式记录和质量闭环可以复用，但其具体设计仍绑定单一角色：

- 权威源路径、checker 和时间矛盾写死。
- 固定为 18 条静态记忆。
- 口吻、关系、秘密、能力反差和场景直接进入生成逻辑。
- Protective 问题和拒答数量直接绑定单角色需求。
- 回复轮数、标签分布、数据配额和评测域写成全局常量。
- 训练包、system anchor 和发布目标直接指向单角色。

仅把角色名替换成变量仍然不通用，因为场景、秘密、标签、事实来源、披露边界和质量标准也会变化。V4 必须重新放置这些知识，而不是继续给核心增加条件分支。

V4 的决策：

| V3 中的内容 | V4 归属 |
|---|---|
| 追加式 record、幂等恢复、失败语义 | 生成核心 |
| `family_id`、证据状态、来源追踪 | 共享 schema |
| 人物事实、时间线、关系和秘密 | `ProfilePackage` |
| `REPLY/RECALL_PLAN/MEMORY_PROPOSE` | AiPeople 默认 `ProtocolBundle` |
| 轮数、数量、对照矩阵、拒答比例 | `DatasetRecipe` |
| 口吻、标签、长度和披露规则 | `ProfilePackage` / `DatasetRecipe` / `ReleasePolicy` |
| checker、事实门和风格门 | `ValidatorAdapter` + `ReleasePolicy` |
| exact/MinHash/embedding 参数 | `CurationPolicy` |
| ShareGPT、协议 SFT 等训练格式 | `ExportAdapter` |
| 角色专用封存测试 | `EvaluationSuite` |

## 3. 通用性硬标准

V4 只有同时满足以下条件，才能称为通用：

1. 新增角色不修改 `core/`、内置 mode adapter 或共享 schema。
2. 新角色只新增或组合 package、recipe、validator 和 evaluation suite。
3. 核心代码、默认模板和核心测试中不得出现任何生产角色名、专属事件、口头禅或文件路径。
4. 角色包可以没有 timeline、秘密、标签或情感关系，核心仍能运行。
5. 至少两套差异显著的测试角色使用同一核心完成全流程：
   - Profile A：第一人称、口语、有私密时间线和表现标签。
   - Profile B：第三人称、正式、无时间线、无秘密、另一套标签或无标签。
6. 两个 profile 的事实、风格、prompt 和评测不得交叉污染。
7. 删除任一 profile 后，核心及其他 profile 的测试仍然通过。
8. package 不完整、版本不兼容或来源矛盾时，核心必须在调用模型前失败。
9. 同一冻结 plan、package snapshot、模型 revision 和 seed 能重放出等价 lineage。
10. 通用性由 contract test 证明，不以“代码里有 `profile_id` 参数”作为证明。

## 4. 系统分层

```text
ProfilePackage       ProtocolBundle       DatasetRecipe
      |                     |                    |
      +---------------------+--------------------+
                            |
                      PackageSetV4
                            |
                            v
                    GenerationPlanCompiler
                            |
                     Immutable Plan JSONL
                            |
                            v
                     GenerationEngineV4
                   /          |           \
          ModeAdapter    ModelAdapter    AppendSink
                   \          |           /
                            v
                     Candidate Records
                            |
                   ReleaseQualityGate
                            |
           CurationPolicy -> GroupSplitter -> ExportAdapter
                            |
                      Dataset Manifest
                            |
               Training / Sealed Evaluation
```

### 4.1 生成器本体

生成器本体只包括：

- package 解析后的不可变输入。
- 生成计划编译。
- mode adapter 调度。
- 模型调用、候选生成和 candidate prefilter。
- call/candidate/failure 逐条追加。
- 幂等恢复和定向重试。

### 4.2 生成器本体之外

以下能力属于数据系统，不属于生成器 interface：

- 角色设定创作与正典决策。
- package 人工批准。
- 独立发布门。
- 去重、聚类、整组切分。
- 训练序列化、训练和模型导出。
- 封存测试和模型消融。

这些环节仍在 V4 文档中定义合同，因为缺少它们无法证明生成数据有效；但实现和产物必须与生成器分离。

## 5. 四类版本化 package

V4 用一个 `PackageSetV4` 绑定本次运行所需的四类 package：

```text
PackageSetV4
- profile_package_ref
- protocol_bundle_ref
- dataset_recipe_ref
- release_policy_ref
- package_lock_hash
```

所有 package 都必须具有：

```text
package_id
package_type
schema_version
package_version
content_hash
compatible_core_range
dependencies[]
created_at
status                  draft | approved | deprecated
```

只有 `status=approved`、依赖闭合且版本兼容的 package 能进入正式生成计划。package 内容改变必须产生新版本和新 hash，不能用相同 ID 静默替换。

`package_lock_hash` 不只覆盖四个顶层 manifest，还覆盖递归依赖、source snapshot IDs、schema、prompt、validator、adapter revision 和内容 hash。任何被解析资源变化都会得到新的 lock。

### 5.1 `ProfilePackage`：谁在说话

`ProfilePackage` 只包含会随角色变化的知识：

```text
ProfilePackage
- profile_id
- locale
- identity_sources[]
- canon_sources[]
- timeline_sources[]             optional
- memory_sources[]               optional
- relationship_model             optional
- visibility_model
- style_contract
- disclosure_policy              direct_allowed | hint_only | withhold
- label_schema                   optional
- capability_traits[]
- source_validators[]
- style_validators[]
- profile_prompt_fragments[]
- profile_evaluation_suites[]
```

它不包含：

- 模型 API 密钥。
- 训练机器路径。
- 全局 retry 和持久化策略。
- core 内部类型名。
- 某次数据批次的固定数量。

### 5.2 `ProtocolBundle`：生成什么协议

`ProtocolBundle` 注册本批可用 mode：

```text
ProtocolBundle
- protocol_bundle_id
- modes[]
  - mode_id
  - mode_adapter_id
  - input_schema_ref
  - target_schema_ref
  - grammar_ref                optional
  - render_profile_id
  - scheduling_semantics
  - failure_policy
```

核心不硬编码 mode 枚举。AiPeople 首版提供默认 bundle：

```text
relationship-runtime-v1
- REPLY
- RECALL_PLAN
- MEMORY_PROPOSE
```

其他项目可以只启用 `REPLY`，或注册新的结构化 mode；未注册 mode 在 plan 编译期失败。

### 5.3 `DatasetRecipe`：生成哪些数据、多少数据

`DatasetRecipe` 定义数据组成，不进入角色事实：

```text
DatasetRecipe
- recipe_id
- strata[]
  - task_type
  - mode_id
  - target_count
  - min_family_count
  - evidence_state_distribution
  - policy_distribution
  - candidate_count
  - risk_level
  - review_requirement
- contrast_suites[]
- memory_selection_policy
- refusal_bounds
- training_mix
```

去重与切分参数不在 recipe 中：它们属于 `ReleasePolicy.curation_policy` / `ReleasePolicy.split_policy`（§5.4），随 release policy 版本化并参与 lock hash。消融组不在 recipe 中定义：每组消融由独立实验层 manifest 定义（§16.3），跨 release 引用，生成配方无法预先承载。

“闲聊 100 条”“真正拒答约 20 条”“记忆全部全审”等数字只能出现在具体 recipe 或 release policy，不得成为核心常量。

### 5.4 `ReleasePolicy`：什么才算可发布

`ReleasePolicy` 组合通用门与业务门：

```text
ReleasePolicy
- required_core_gates[]            G0-G3 必过且不可裁剪；G4-G7 由本字段选择启用
- required_profile_validators[]
- required_protocol_validators[]
- human_review_rules[]
- metric_thresholds[]
- sealed_evaluation_refs[]
- allowed_export_profiles[]
- curation_policy
  - exact_normalization
  - ngram_range
  - minhash_params
  - embedding_model_ref
  - allowed_dedup_modes
- split_policy
  - initial_ratios
  - max_component_ratio
```

`curation_policy` 与 `split_policy` 是 ReleasePolicy 的组成部分，随 release policy 版本化并参与 `content_hash` 与 lock hash；`DatasetRecipe` 不再单独引用它们。core gates 中 G0-G3（§14.1）对任何 profile 都必过，ReleasePolicy 只能选择 G4-G7 的启用集合，不能裁剪 G0-G3。

核心只保证记录完整、来源可解析和生命周期正确；“像不像某角色”“能否披露某秘密”“标签频率是否合格”由绑定的 profile/release policy 决定。

### 5.5 引用与 lockfile 规则（阶段 0 冻结）

package 引用语法：

```text
pkg:<package_id>@<package_version>
```

解析 package ref 时必须校验目标 `package_version` 与 `content_hash` 和 lockfile 记录一致；版本不匹配、hash 不一致或 `status != approved` 时编译失败，错误码 `package_incompatible` / `package_invalid`，且必须在模型调用前失败。

每个正式运行冻结一份 `PackageLockV4`（schema：`data_gen_v4/schemas/lock_v4.schema.json`）：

```text
PackageLockV4
- lock_hash
- packages{}            package_id -> {package_version, content_hash, status}
- source_snapshots{}    snapshot_id -> {source_adapter_id, content_hash}
- schema_refs{}         schema 文件 id -> {content_hash}
- prompt_refs{}         prompt 模板 id -> {template_version, content_hash}
- validator_refs{}      validator id -> {content_hash}
- adapter_revisions{}   mode/model/source/export adapter id -> {revision}
- created_at
```

`package_lock_hash = SHA-256(按 key 排序后的全部 pin 的规范 JSON)`。任何被解析资源（package、source snapshot、schema、prompt、validator、adapter revision）变化都会产生新的 lock；同一 lock 下 `resume` 不允许更换任何 pin。run、plan、candidate 和 release 全部绑定 `package_lock_hash`，不允许以“最新”浮动引用替代。

## 6. 规范化来源模型

不同角色可能使用 JSON、YAML、Markdown、数据库或人工表格。核心不能认识这些文件格式中的角色字段，必须通过 `SourceAdapter` 转成统一的 `EvidenceUnitV4`。

### 6.1 `SourceAdapter` interface

```text
load(source_ref, snapshot_policy) -> SourceSnapshot
normalize(snapshot)              -> EvidenceUnitV4[]
resolve_span(source_ref, span)    -> string
validate(snapshot)                -> ValidationResult[]
```

首版至少有两个真实 adapter 才形成有效 seam：

- `StructuredFileSourceAdapter`：JSON/YAML。
- `MarkdownCanonSourceAdapter`：带稳定段落/字段 ID 的 Markdown。

数据库或远程文档 adapter 以后按相同 interface 增加。

### 6.2 `EvidenceUnitV4`

```text
EvidenceUnitV4
- source_kind              identity_fact | canon_fact | timeline_event |
                           memory_event | runtime_event | runtime_claim |
                           runtime_plan | custom
- source_id
- profile_id
- snapshot_id
- field_pointer
- value
- occurred_at              optional
- valid_from               optional
- valid_to                 optional
- visibility_scope
- knowledge_scope               optional
- disclosure_policy
- supersedes_source_id     optional
- tags[]
- metadata
```

稳定 ID 不能由日期、数组下标或显示文本临时充当。相同显示日期允许有多个事件；内容移动位置后 ID 仍保持稳定。

### 6.3 可见性和披露

V4 标准化以下概念，但具体规则由 profile 提供。三个字段各自独立取值：

`visibility_scope`（证据对外的可见性；candidate 至少一个值）：

| 值 | 含义 |
|---|---|
| `profile_public` | 角色知道且目标受众可直接获知 |
| `profile_private` | 角色知道，但只有特定受众或条件可披露 |
| `profile_secret` | 角色知道，当前条件不可直接披露 |

`knowledge_scope`（知识来源）：

| 值 | 含义 |
|---|---|
| `runtime_evidence` | 只能由当前运行时事件或 RecallFrame 支持 |
| `general_knowledge` | 不依赖角色正典的通用能力 |
| `realtime_external` | 当前离线模型无法自行获取的现实状态 |
| `safety_critical` | 安全优先处理的信息 |

`disclosure_policy`（披露策略）：

| 值 | 含义 |
|---|---|
| `direct_allowed` | 可直接披露 |
| `hint_only` | 只允许暗示 |
| `withhold` | 当前条件不得披露 |

Profile 可以增加 namespaced scope，例如 `project_x:faction_private`，但不能重新定义标准 scope 的语义。

秘密必须表示为：

```text
visibility_scope = profile_secret
evidence_state = supported
desired_policy = withhold
```

不能把“知道但不能说”编码成 `insufficient`。

## 7. 生成核心的深模块 interface

### 7.1 `GenerationPlanCompiler`

```text
compile(run_spec, package_set, source_snapshots)
    -> CompileResult<ImmutableGenerationPlan>
```

调用方只需提供 run spec 和批准的 package 引用。编译器内部负责：

- package 依赖和版本检查。
- source adapter 调用和 snapshot hash。
- profile preflight。
- strata、family 和 contrast 编排。
- seed 派生。
- fixture 引用。
- split anchor 初始标注。
- 风险和人工审核要求。

编译失败不产生部分可执行 plan。需要允许部分角色数据继续生成时，必须在 recipe 中把批次拆成明确的独立 partition，而不是运行时跳过失败项。

### 7.2 `GenerationEngineV4`

```text
execute(plan_ref, package_lock, model_pool, sink)
    -> GenerationRunResult

resume(run_id, package_lock, model_pool, sink)
    -> GenerationRunResult
```

不变量：

- `plan_ref`、package lock 和所有 snapshot hash 必须完全匹配。
- resume 不能换 profile、协议、recipe、prompt 或模型 revision。
- 任何有意变更都创建新 run，并通过 lineage 指向旧 run。
- engine 只产出 pending candidate，不能批准样本。
- engine 不调用训练、切分或封存测试。

### 7.3 `ModeAdapter`

```text
prepare(plan_item, package_set)          -> ModeJob
generate(mode_job, call_executor)         -> CandidatePayload | ModeFailure
render_training(candidate, package_set)  -> TrainingRecord
```

`call_executor` 由 `GenerationEngineV4` 注入，负责解析 `ModelAdapter`、追加每个 `CallRecord` 和执行超时/重试。Mode adapter 可以在一次 `generate` 内完成语义骨架、风格改写和 critic 等多阶段调用，但调用方不需要学习其内部状态机。

`render_training` 产出 TrainingRecord 语义层：messages、mode discriminator、system anchor、`supervised_message_indexes` 和 loss mask 信息。它是训练序列化的唯一来源；`ExportAdapter` 只把 TrainingRecord 序列化为具体文件格式并做往返验证（§15.3），不再自行构造监督信息。

`ModeAdapter` 隐藏：

- input/target schema。
- prompt 顺序。
- grammar 和解析。
- 内容骨架与表现实现。
- mode 专用 candidate prefilter。
- training messages 和 loss mask。

核心不判断“4-8 轮”“必须是 JSON”“允许哪些标签”。这些是 mode contract 和 recipe 的知识。

### 7.4 `ModelAdapter`

```text
generate(ModelCallSpec) -> ModelCallResult
```

`ModelCallSpec` 完整记录：

- provider/model/revision。
- role：generator、rewriter 或 critic。
- rendered prompt hash。
- sampling parameters。
- seed 或 `unsupported`。
- timeout、max tokens、response format。

model adapter 不知道角色事实；它只接收已经渲染的 job。三次失败后必须返回显式错误，不能把 mock 写入真实 candidate 路径。

### 7.5 `AppendSink`

```text
append(record, idempotency_key) -> DurableAppendResult
read_progress(run_id)           -> RunProgress
```

正式 adapter 必须提供：

- 单写者或文件锁。
- 原子追加。
- flush + OS fsync 或等价事务持久化。
- 幂等键去重。
- 崩溃恢复。

内存或 mock sink 只用于测试，产物不能进入 release 路径。

## 8. V4 追加式记录合同

### 8.1 判别联合

```text
V4Record = RunEvent | CallRecord | CandidateRecord |
           FailureRecord | GateDecisionRecord | ReleaseRecord
```

共享 header：

```text
LineageHeaderV4
- schema_version
- record_type
- record_id
- run_id
- plan_id
- package_lock_hash
- profile_id
- profile_snapshot_id
- protocol_bundle_id
- recipe_id
- mode
- task_type
- family_id
- generator_version
- created_at
```

Run-level record 的 `plan_id/mode/task_type/family_id` 可以为 null；Call/Candidate/Failure/GateDecision 必须按自己的判别 schema 补齐关联字段。`package_lock_hash/profile_id/profile_snapshot_id` 对 candidate 必填，不能依赖运行目录推断。

### 8.2 `CandidateRecordV4` 必填字段

| 字段 | 类型 | 不变量 |
|---|---|---|
| `sample_id` | string | 全局唯一，不原地复用 |
| `family_id` | string | 对照和切分的主 family |
| `question_family_id` | string/null | 问题族 |
| `scene_family_id` | string/null | 场景族 |
| `mode` | string | 必须由 protocol bundle 注册 |
| `task_type` | string | 必须由 recipe 声明 |
| `profile_id` | string | 角色包 ID，不允许隐式默认角色 |
| `profile_snapshot_id` | string | 冻结角色来源快照 |
| `protocol_bundle_id` | string | 冻结协议包 |
| `recipe_id` | string | 冻结数据配方 |
| `run_id` / `plan_id` | string | 绑定运行和计划 |
| `attempt_no` / `candidate_no` | integer | 修复与候选编号 |
| `parent_sample_id` | string/null | 修复 lineage |
| `fixture_id` / `fixture_hash` | string/null | 运行时 fixture 引用 |
| `source_refs` | object[] | 类型化来源 |
| `source_event_ids` | string[] | event 来源的查询投影，可为空 |
| `support_spans` | object[] | 可机械验证的精确支持范围 |
| `knowledge_scope` | string[] | 标准或 namespaced knowledge scope |
| `visibility_scope` | string[] | 至少一个标准或 namespaced visibility 值；秘密样本含 `profile_secret` |
| `evidence_state` | string | 主证据状态 |
| `desired_policy` | string | 主策略 |
| `required_behaviors` | string[] | 必须完成的组合行为 |
| `forbidden_behaviors` | string[] | 禁止行为和命题 |
| `expected_outcomes` | object[] | claim/行为逐项 gold |
| `input` | object | mode schema 决定 |
| `target` | object | mode schema 决定 |
| `model` | object | 主生成调用模型信息 |
| `prompt_hash` | string | 实际 target-producing prompt hash |
| `prompt_template_version` | string | 实际模板版本 |
| `config_hash` | string | mode/profile/recipe 合并后的生成配置 hash |
| `render_profile_id` | string | mode 专用 prompt/training renderer |
| `representation_ids` | string[] | 实际注入的批准记忆/风格表示 |
| `seed` | integer/string | seed 或 `unsupported` |
| `review_status` | string | candidate 固定为 `pending` |
| `provenance.calls` | string[] | 完整 call record 引用 |

V3 中用户要求的 `family_id/source_event_ids/support_spans/knowledge_scope/evidence_state/desired_policy/model/prompt_hash/seed/review_status` 在 V4 全部保留，并增加 profile/protocol/recipe lineage，确保同一个通用核心能区分不同角色包。

### 8.3 span 规范

```text
SupportSpanV4
- source_kind
- source_id
- snapshot_id
- field_pointer
- offset_unit              unicode_code_point
- start                    inclusive
- end                      exclusive
- quote
- supported_claim_id
- evidence_role            support | contradict | correction
```

校验器按 snapshot 和 field pointer 取字符串，再按 Unicode code point 的 `[start,end)` 比对 quote。不得用 UTF-8 byte、UTF-16 code unit 或模糊搜索替代。

### 8.4 gate decision

```text
GateDecisionRecord
- subject_sample_id
- subject_candidate_record_id
- gate_id
- decision                 approved | rejected | needs_revision
- reason_codes[]
- validator_id
- reviewer                 optional
- reviewed_at
```

accepted release 由全部必需 gate 的最新有效 decision 物化。generator、teacher 和 critic 都不能直接写 approved。

## 10. 默认 `relationship-runtime-v1` 协议包

本节是 AiPeople 的默认 `ProtocolBundle`，不是 V4 核心硬编码。删除或替换此 bundle 后，核心仍应运行其他已注册 mode。

### 10.1 `REPLY` adapter

输入可组合：

- profile identity anchor。
- 当前 epoch 历史。
- 工作状态。
- RecallFrame。
- 当前用户输入。
- profile 的 style、label 和 disclosure contract。

输出由 profile/recipe 决定：

- 纯文本或带白名单标签的文本。
- 单轮或多轮。
- 第一人称或其他叙述视角。
- 不同长度、语气和标签分布。

AiPeople recipe 可以要求 4-8 条严格交替消息，但核心不能把 4-8 写死为所有 profile 的规则。

内容与风格分两阶段：

```text
plan item
  -> grounded semantic skeleton
  -> candidate prefilter
  -> profile style realization
  -> semantic preservation check
```

style realization 不得增加新的事实命题。user simulator 只能看到 `audience_view`，不能看到角色秘密或 oracle state。

### 10.2 `RECALL_PLAN` adapter

只生成受约束的检索计划，不生成回忆答案。它读取 model-visible cue，oracle ledger 只供验真。合法输出必须允许：

- 多线索 search。
- ask clarification。
- `NO_OP`。
- miss policy。

具体 JSON schema、grammar 和 token 上限由 protocol bundle 版本控制。

### 10.3 `MEMORY_PROPOSE` adapter

只提出带证据的派生候选：

- fact。
- preference。
- relationship。
- episode。
- correction/conflict。
- `NO_OP`。

它不能删除历史、覆盖事件或直接提交 active fact。计划状态仍由确定性前瞻状态模块管理；除非未来协议明确新增 prospective proposal schema，否则不能把计划转换偷渡进该 mode。

### 10.4 双视图 fixture

```text
EvidenceFixtureV4
- fixture_id
- fixture_hash
- fixture_schema_version
- model_input
  - mode_system_input
  - visible_events
  - visible_state
  - current_input
- oracle_state
  - events
  - existing_claims
  - claim_evidence
  - plans
  - expected_retrieval_ids
  - expected_outcomes
```

`model_input` 逐字符等同于生产 renderer 可见视图；`oracle_state` 永不进入 prompt。fixture 由协议 adapter 解释，核心只校验 ID、hash 和引用完整性。

## 11. 通用记忆表示与批准

### 11.1 不固定记忆数量

V4 不假设角色一定有 18 条、17 条或任何固定数量。`DatasetRecipe.memory_selection_policy` 决定：

- 哪些 source kind 可参与记忆表达。
- 选多少事件。
- 是否生成 detail。
- 是否允许 summary-only。
- 哪些风险必须人工全审。

### 11.2 记忆表示合同

```text
MemoryRepresentationV4
- representation_id
- profile_id
- source_refs
- support_spans
- representation_type       summary | detail | cue | style_hint
- text
- knowledge_scope
- disclosure_policy
- profile_snapshot_id
- model
- prompt_hash
- seed
- review_status
- reviewer
- reviewed_at
```

状态流转：

```text
draft -> pending -> approved
                 -> needs_revision -> new version
                 -> rejected
```

已批准表示不可原地编辑。detail 无法在不增加事实的情况下产生时，review policy 可以批准 summary-only；具体批次是否允许 summary-only 由 recipe 决定。

### 11.3 通用扩写规则

允许：

- 叙述视角的确定性转换。
- 不改变真值的改写。
- profile style contract 允许的非命题性语气。

禁止：

- 新增人物、物品、地点、动作、对话、因果、时间或结果。
- 把模型补写内容反向注册为 canon。
- 以生成出的 representation 验证自身。
- 注入 pending、rejected、快照失效或披露策略不匹配的表示。

### 11.4 注入条件

`ApprovedRepresentationPack` 必须记录 pack ID、profile snapshot、成员 ID 和 hash。只有 recipe 选中的每个 source 都达到要求的人工/自动终态，pack 才能冻结。生成样本记录实际注入的 representation IDs，repair 不得重新抽取。

## 12. 通用知识边界与成组对照

V4 将 Protective 一般化为 `ContrastSuite`。它不是某个角色的问题池，而是可配置的策略矩阵。

### 12.1 标准证据状态

```text
supported
insufficient
false_premise
conflicted
not_required
```

### 12.2 标准目标策略

```text
answer
answer_with_uncertainty
ask_for_evidence
correct_premise
surface_conflict
withhold
safety_first_answer
refuse_unsafe_and_redirect
no_op
```

Profile/Protocol 可以增加 namespaced policy，但 release validator 必须认识其语义。

### 12.3 成组规则

一个 contrast family 至少包含：

- `positive_control`：可答时正确完成。
- `boundary_variant`：只改变一个关键变量后采用另一策略。

标准可选矩阵：

| 变体 | 目标 |
|---|---|
| 有充分证据 | 正确回答 |
| 缺少证据 | 追问或表达不确定 |
| 错误前提 | 纠正后回答可答部分 |
| 证据冲突 | 展示冲突，不静默选边 |
| 已知但不可披露 | 保留信息，不伪装成无知 |
| 安全帮助 | 给出完整安全建议 |
| 危险请求 | 拒绝危险部分并给安全替代 |

每个 recipe 自己设置适用状态、family 数和 accepted bounds；`refusal_required` 写入每个 plan item（§9）。核心按 `refusal_required=true` 的 accepted 样本机械统计真正拒答，误拒答由 release 阈值判定。核心不预设“20 条真正拒答”，但必须能机械统计真正拒答和误拒答。

### 12.4 能力与人设分离

Profile 中的“不擅长、害怕、讨厌、自嘲”等 trait 默认只影响表达，不能自动覆盖任务能力。只有 recipe/policy 明确声明且与产品需求相容时，trait 才能改变目标答案。

安全、常识、计算、明确指令和实时未知分别建 family，不把它们合并成“角色不会”。

## 13. 生成生命周期

```text
resolve package set
  -> validate package lock
  -> compile immutable plan
  -> append run_started
  -> append call records
  -> append candidate or failure
  -> append generation_completed
  -> independent gate decisions
  -> append gates_completed
  -> append release_created
```

### 13.1 幂等键

```text
(run_id, plan_id, attempt_no, candidate_no, stage)
```

`GateDecisionRecord` 通过 `subject_candidate_record_id` 精确关联候选，不能用“同 plan 最新一条”推断。

### 13.2 显式失败

标准错误：

```text
package_invalid
package_incompatible
source_snapshot_failed
precondition_failed
mode_not_registered
provider_error
timeout
truncated_output
parse_error
schema_error
unsupported_claim
policy_mismatch
style_failure
no_acceptable_candidate
```

Failure 不要求 target。重试耗尽后保留 failure，不返回 mock、解析失败占位或伪造成功。

### 13.3 定向修复

- schema 错误只修结构。
- 事实错误回到 semantic skeleton。
- 风格错误只重做 realization。
- policy 错误读取原 plan，不允许 critic 改题。
- package 问题不重试模型，直接阻断。
- 每次修复产生新 attempt、call records、seed 和 parent lineage。

## 14. 独立质量门

```text
ReleaseQualityGate.evaluate(candidate_ref, package_lock)
    -> GateDecisionRecord[]

ValidatorAdapter.validate(candidate, validation_context)
    -> ValidationResult[]
```

`ReleaseQualityGate` 只负责编排已锁定的 validators 和人工审核要求；角色或协议知识由 adapter 提供。它不能调用生成器重写 candidate，修复请求必须回到新 attempt。

### 14.1 通用核心门

所有 profile 必须通过。G0-G3 为不可裁剪的必过门，任何 ReleasePolicy 都不得关闭；G4-G7 由 `ReleasePolicy.required_core_gates[]` 选择启用（§5.4）。

```text
G0 record/schema integrity
G1 package and snapshot integrity
G2 source ID and support span validity
G3 mode input/target schema
G4 desired policy and expected outcomes
G5 safety                      必过硬门：安全处置正确、危险请求拒绝合理
G6 structural completeness
G7 required human review
```

硬门不能平均：G2（来源与 span 事实）或 G5（安全）失败的样本，不得因风格或其他轴分数高而通过。

### 14.2 Profile 门

由 profile validators 检查：

- identity/canon/timeline 一致性。
- 叙述视角。
- 风格和禁用表达。
- 关系阶段。
- visibility/disclosure。
- 标签白名单和分布。
- profile 专用能力边界。

checker 必须接收 `profile_snapshot_id`，不得在实现中硬编码角色事实。新增 profile 时只注册 validator package。

### 14.3 Protocol 门

由 mode adapter 检查：

- JSON/grammar/schema。
- 角色文本与协议 JSON 隔离。
- event/claim/plan ID 权限。
- `NO_OP` 合法性。
- loss mask 和 training renderer 往返一致。

### 14.4 审核策略

`ReleasePolicy` 按风险设置：

- 100% 人工审核。
- family 分层抽审。
- 语义簇抽审。
- 自动门通过。

发现系统性错误时回溯整个 profile、source、family、prompt version 或 model revision，不只修单条。

## 15. 通用整理、切分与导出

### 15.1 `CurationPolicy`

去重实现是 adapter/config，不硬编码中文：

1. normalized exact hash。
2. locale-aware n-gram/MinHash。
3. embedding candidate clustering。

Profile locale 决定 normalization 和 n-gram 策略。中文可用字符 3-5 gram；其他语言可使用适合的 token/character 策略。MinHash 和 embedding 只召回疑似近重复，删除或保留对照由 policy 决定。

### 15.2 split anchor

```text
split_anchor_ids
- family:<id>
- question_family:<id>
- scene_family:<id>
- primary_source:<id>
- trajectory:<id>
- confirmed_duplicate:<id>
```

公共 profile fact、次要证据和纯风格相似默认不形成 hub。连通分量整组进入 train/validation/test。最大分量超过 release policy 阈值时阻断并检查 anchor 设计。

所有消融组必须复用同一 profile-family partition。

### 15.3 `ExportAdapter`

```text
render(training_record, export_profile) -> SerializedRecord
validate_roundtrip(serialized)          -> ValidationResult
```

ExportAdapter 只消费 `ModeAdapter.render_training` 产出的 TrainingRecord（§7.3），负责格式序列化与往返验证，不构造监督信息或 loss mask。

首版可有：

- `ShareGPTReplyExportAdapter`
- `StructuredProtocolSFTExportAdapter`
- `RawAuditJsonlExportAdapter`

export adapter 必须保留 mode discriminator、system anchor、消息顺序、协议版本和 assistant-only loss mask。不得截断 target、JSON 尾部、证据 ID 或 support span。

3. 建立跨 profile 的协议 fixture 和 sealed suite。
4. 验证计划状态没有混入 MEMORY_PROPOSE。

### 阶段 5：迁移生产角色

1. 从 V3 提取生产 profile、recipe、validator 和 evaluation suite。
2. 先解决该 profile 自身的正典矛盾和 source ID。
3. 生成批准的 representation pack。
4. 用 V4 重测旧基线和新数据消融。
5. 对 adapter、merged 和最终部署格式做同集验证。

### 阶段 6：文档迁移

1. V4 获批后同步需求、唯一 AI 实现、产品集成和 README 中的数据合同。
2. 将 V2/V3 移入历史方案或实例设计归档目录。
3. 更新文档索引，保证当前设计目录只有一个通用生成器方案。

## 21. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 把配置化误当通用化 | 双 profile、无 core diff、删除测试作为硬门 |
| Package interface 过大 | Profile/Protocol/Recipe/Release 分离，调用方只学习各自职责 |
| 为未来 mode 过早抽象 | 首版用 REPLY 和 structured protocol 两类真实 adapter 验证 seam |
| Profile 偷带核心配置 | schema 明确禁止 provider secret、retry 和训练机器路径 |
| 通用 validator 太弱 | core gate + profile validator + protocol validator 分层 |
| Profile checker 再次硬编码旧角色 | validator 必须接收 snapshot；交叉 profile contract test |
| mode JSON 污染回复 | mode adapter、renderer、loss mask 和 exporter 分离 |
| 配置组合爆炸 | package lock、compatibility range 和预编译 plan |
| 近重复策略不适合语言 | locale-aware CurationPolicy adapter |
| 单角色数据证明不了通用性 | Alpha/Beta fixture 先于生产 profile 迁移 |
| 通用核心演变成第二套 AI 架构 | runtime 行为只由 ProtocolBundle 映射现行唯一实现 |

## 22. V4 验收定义

### 22.1 设计可以进入施工

- 用户确认“通用”指跨角色/Persona 的文本对话与记忆协议生成。
- 四类 package 职责和 adapter seam 获批。
- AiPeople 三 mode 被确认是默认协议包，不是核心固定枚举。
- V3 被确认只作为生产 profile 迁移来源。
- “V4 首版只支持文本角色/协议数据”边界已冻结（§1）；新增数据域必须新增 `ModeAdapter` / `ExportAdapter`，不得把非文本需求塞进角色 profile。

### 22.2 V4 实施完成

- Alpha 和 Beta 无 core 修改完成端到端生成。
- 两个 profile 的事实、风格、标签和可见性无交叉污染。
- 新增/删除 profile 不影响 core 和其他 profile。
- package/version/source 错误均在模型调用前失败。
- 所有 candidate 带完整 profile/protocol/recipe/provenance 字段。
- mode adapter 能独立序列化并通过往返测试。
- generator 逐条 durable append，失败和恢复可审计，无 mock 泄漏。
- 独立质量门、去重、整组切分和 export manifest 完整。
- 生产 profile 通过自身 sealed suite，且不要求 core 加专用条件分支。
- base、训练权重和最终部署格式使用同一固定集对照。

### 22.3 不通过条件

出现任一情况即不能称为 V4 通用生成器：

- core 中出现生产角色名、专属事实、固定记忆数量或专用问题池。
- 新角色需要复制并修改 generator 主流程。
- checker 通过全局硬编码判断角色事实。
- mode schema、prompt 或 loss mask 依赖角色名分支。
- 配额和拒答数量只能改代码，不能通过 recipe 改。
- 一个 profile 的数据、prompt、source 或评测进入另一个 profile 的 release。

在这些条件满足前，只能称为“V4 通用化设计或候选实现”，不能称为已验证的通用数据生成器。

## 24. 增补：记忆类型轴（2026-08-14）

> 本增补不改写 §1-23 冻结内容，只登记后续生效的扩展合同；完整方案见
> `训练数据记忆类型分类方案_20260814.md`（当前权威设计）。

### 24.1 memory_type（生成计划视角的记忆分类）

`memory_type` 是 plan item 的可选标注，与 task_type（行为轴）正交，取值：

| 值 | 含义 | 知识来源 |
|---|---|---|
| `persona` | 人设记忆（身份/性格/关系/能力/秘密边界） | identity_fact / canon_fact |
| `item` | 物品记忆（现代物品/设施知识状态：会用/在学/不知道） | canon + 日常池 |
| `general` | 通识记忆（不依赖角色正典的通用能力） | knowledge_scope=general_knowledge |
| `special` | 特殊记忆（角色专属经历） | timeline_event |

池条目显式声明优先；未声明时由 `RecipeDrivenItemFactory` 按 task_type 通用推断表兜底
（identity/canon_qa→persona；general/safety→general；reply_memory→special；reply_item→item；
其余不标注）。推断表是通用规则，不内置角色知识。未标注条目不参与记忆类型统计。

### 24.2 timeline 注入 REPLY（special 记忆对话生成）

§11 记忆表示合同与 §12.1 证据状态增补一条注入路径：`DatasetRecipe.memory_selection_policy`
可允许 `timeline_event` 进入 REPLY 生成（新 task_type `reply_memory`），注入规则：

- 蒸馏复用 `MemoryRerankAdapter.distill_candidates` 的过滤口径（timeline_event、去重、occurred_at）；
- `visibility_scope == profile_secret` 的事件不注入；
- `disclosure_policy == hint_only` 的事件只配 `desired_policy == hint_only` 的 item；
- 回忆类事实主张须由注入事件支撑（`_check_memory_grounding`，无支撑即重试），
  `_check_shared_history` 对 `reply_memory` 放行；
- 锚结构不变（记忆证据规则沿用 protocol `reply_runtime_rules`，注入事件即"明确可回证据"）。

### 24.3 新 task_type 命名空间

- `reply_item`：物品记忆问答（行为边界：不会就说不确定/认真观察提问，不装懂）；
- `reply_memory`：特殊记忆回忆（行为边界：只答注入的已发生事件，不编造细节、不升级承诺）。

两者均属 REPLY 模式，行为约束经 recipe strata 的 required/forbidden_behaviors 声明，
不在 core 中新增角色专属分支。
