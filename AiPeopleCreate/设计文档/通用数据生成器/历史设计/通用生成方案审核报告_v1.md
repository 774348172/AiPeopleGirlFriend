# 通用数据生成方案审核报告（v1）

> 2026-08-07 | 审核框架：《数据生成规则重构方案_v1.md》（两阶段+结构化+评审+飞轮）
> 审核对象：data_gen_v4 现状（gen_qin_v4.py + reply.py + gates.py + prompts）

---

## 一、审核框架（目标架构五层）

```
L0 生成之前（约束输入）→ L1 规划（可校验）→ L2 写作（受约束+结构化）
→ L3 评审（更强模型逐轮）→ L4 飞轮（错误分类回流）
```

## 二、逐层对照审核

### L0 · 生成之前（约束输入）

| 审核项 | 现状 | 判定 | 差距 |
|---|---|---|---|
| 事实来源单一化 | canon.json（带澄清句）✅ | **达标** | — |
| 事实带 ID 引用 | canon 有 key（facts:xxx），**但未进入 prompt 引用体系** | ⚠ 部分 | 教师自由引用事实，无法机械校验"引用了哪个事实" |
| 人设属性能力边界 | capability_boundary 澄清句（P2 已加"数学差是自嘲不影响思考"） | ⚠ 部分 | 只有数学一条；怕冷/记性等未边界化；属性无 ID |
| 宪法条款（原则清单） | 无（规则散落在 prompt 段落 + 检查器代码） | ❌ 缺失 | 原则不可被评审模型复用 |

### L1 · 规划层

| 审核项 | 现状 | 判定 | 差距 |
|---|---|---|---|
| 独立规划阶段 | **无**——propositions 与 messages 同一次调用生成 | ❌ 缺失 | 规划的"规划"（属性清单/事实引用）无法独立校验 |
| 规划可校验 | propositions 事后检查（语义保持/grounding） | ⚠ 部分 | 是"结果检查"不是"规划校验"——教师规划错误时无中间拦截 |
| 规划含引用信息 | propositions 无事实 ID/属性 ID | ❌ 缺失 | grounding 靠 bigram 猜，才出现"以前→1"误判类问题 |

**关键事实**：现有 prompt 的 `assistant_propositions` 就是规划雏形——但和 messages 一起生成（同一调用），等于**规划与执行无隔离**。重构方案 A 的第一刀就是把它拆成两次调用。

### L2 · 写作层

| 审核项 | 现状 | 判定 | 差距 |
|---|---|---|---|
| 受规划约束写作 | propositions 逐字保留要求（软约束） | ⚠ 部分 | 无 used_facts/used_attributes 自报，无法比对 |
| 结构化输出 | messages 数组（JSON），**无引用元数据** | ⚠ 部分 | 无约束解码/强 schema（parse_error 历史 672 次） |
| 比对器 | 无（grounding bigram 近似替代） | ❌ 缺失 | 核心差距 |

### L3 · 评审层

| 审核项 | 现状 | 判定 | 差距 |
|---|---|---|---|
| 更强模型评审 | **无评审模型**——7 层检查器全是规则 | ❌ 缺失 | 词法规则拦不住语义错误（拍背吐水） |
| 逐轮评审 | 无（整段终检） | ❌ 缺失 | 中间轮错误漏检 |
| critique→rewrite | 无——盲重试（同 prompt 重试 3 次） | ❌ 缺失 | 教师不知道错在哪，防空洞重试 3 次仍错 |
| 规则降级预筛 | 规则是唯一防线（承担终审） | ❌ 反向 | 规则检查器承担了不该承担的责任 |

### L4 · 飞轮

| 审核项 | 现状 | 判定 | 差距 |
|---|---|---|---|
| 错误分类学 | gate_report 的 reason_codes 有类别（secret_leak/safety_action/属性朗读…） | ⚠ 部分 | 是**拒绝码**不是**错误分类学**——无统计聚合、无回流机制 |
| 错误回流 | 无（每个错误手动加规则） | ❌ 缺失 | 补丁循环的根源 |

## 三、关键差距（按严重度排序）

| # | 差距 | 后果 | 改造难度 |
|---|---|---|---|
| 1 | **无评审层（L3 全缺）** | 语义错误（安全/事实/一致）永远靠规则兜底 | 中（依赖更强模型可得性） |
| 2 | **规划与执行不隔离（L1）** | 教师边规划边执行，错误无中间拦截点 | 低（拆调用即可，API 成本 ×1.5） |
| 3 | **无引用元数据/比对器（L2）** | grounding 靠文本猜测（bigram/数字归一化），"以前→1"类误判是必然 | 中（prompt 输出 schema 扩展） |
| 4 | **盲重试（L3 相关）** | 同错误重复 3 次，浪费 API 且产出率低（safety 62%） | 低（重试时附错误信息） |
| 5 | **无错误回流（L4）** | 补丁循环：每个新错误加一条规则 | 低（taxonomy 统计脚本） |

## 四、意外发现（现有资产可复用）

1. **propositions 机制 = 规划雏形**——重构不是从零写，而是把它拆开 + 加引用信息
2. **reason_codes = taxonomy 雏形**——gate_report 已有拒绝原因码，加聚合统计就是飞轮第一步
3. **P3/P4/P1 检查器逻辑可平移**——朗读/共同经历/安全动作的规则直接变成 L1 规划校验器和 L2 比对器的规则
4. **池条目（required/forbidden_behaviors）= 行为合同**——已有结构化约束输入，可升级为"宪法条款"

## 五、改造建议（分三批）

### 第一批（低成本高收益，不依赖更强模型）
1. **错误回流启动**：写 taxonomy 统计脚本（聚合 gate_report 的 reason_codes → 每批错误分布报告）
2. **盲重试→带反馈重试**：_ModeFailureSignal 的错误信息注入重试 prompt（"上次失败原因：xxx，请修正"）——成本几乎为零
3. **重试上限利用**：当前重试 3 次无反馈，带反馈后产出率可显著提升（safety 62% → 预计 85%+）

### 第二批（方案 A 核心，两阶段）
4. **规划阶段独立调用**（plan_merge.txt：plot_points/attribute_plan/fact_refs/safety_actions）
5. **规划校验器**（引用存在性检查——编造变成"引用不存在的 ID"，机械可查）
6. **写作阶段 + used_facts/used_attributes 自报 + 比对器**（确定性三方比对，替代 60% 检查器）

### 第三批（方案 B/C，依赖外部条件）
7. **更强模型评审**（需确认 aihub 可用模型；不可得则抽样人工评审 + taxonomy）
8. **属性能力边界全面化**（怕冷/记性等 + 属性 ID 入库）

## 六、结论

- **现有方案在 L0 和池设计上基础扎实**（canon 单一事实源/池行为合同/门禁体系），但 **L1-L4 四层全部缺失或薄弱**——这正是"补丁循环"的架构根源
- **第一批的三项改造零依赖、立即见效**（尤其"带反馈重试"几乎零成本）
- **第二批（两阶段）是根治关键**，但改动面大（prompt 重构 + 检查器迁移），建议在 3060 包小批量上先做原型验证
- 在 L1-L4 落地前，**997 条维持待重生成状态**（与重构方案结论一致）
