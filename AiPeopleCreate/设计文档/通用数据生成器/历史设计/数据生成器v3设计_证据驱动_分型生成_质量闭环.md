## 1. 结论与定位

V2.3 可以保留为“静态角色正典的 `REPLY` 数据增强思路”，但不能作为现行关系连续性架构下的完整数据生成器，原因是：

1. 只生成角色对话，没有覆盖 `RECALL_PLAN` 和 `MEMORY_PROPOSE`。
2. 静态记忆扩写缺少来源 ID、支持片段和逐条人工批准，可能把生成细节固化成事实。
3. Protective 把秘密、知识不足、数学能力、安全问题和通用任务混成一种回避策略，会制造误拒答和能力退化。
4. 话题频次上限是配额控制，不是内容去重。
5. 当前 checker 和配置仍包含旧角色路径与硬编码规则，现有 v1 “canon 矛盾率 0%”不能作为有效基线。
6. 样本级随机切分不能阻止同问题、同场景和同记忆事件的兄弟样本跨集合泄漏。
7. 文件名中的“置信度”没有对应的校准目标、数据合同或独立校准集。

V3 的核心不是增加更多 prompt，而是建立两个深模块和一个共享样本合同：

- `PersonaReplyGenerator`：只负责生成 `REPLY` 数据。
- `RuntimeProtocolGenerator`：只负责生成 `RECALL_PLAN` 和 `MEMORY_PROPOSE` 数据。
- `SampleEnvelopeV3`：统一记录任务、证据、策略、来源、生成参数和审核状态。

生成器本体以外的正典治理、质量门、去重、整组切分、训练和封存评测仍然必须存在，但不能被描述成生成器自己的能力。

## 2. 范围和系统边界

### 2.1 “生成器本体”与“数据系统”的区别

| 环节 | 是否属于生成器本体 | V3 为什么仍记录 |
|---|---|---|
| 年龄、七年和当前时间口径统一 | 否，上游正典治理 | 未解决时不得开始事实型生成 |
| 秦未晞 checker 与配置修正 | 否，上游/下游质量门 | 错误裁判会让所有质量指标失效 |
| 生成计划编排 | 是，共享输入合同 | 决定 family、证据状态、策略和配额 |
| `REPLY` 生成 | 是 | 角色对话、能力保持和秘密边界 |
| `RECALL_PLAN` / `MEMORY_PROPOSE` 生成 | 是 | 对齐唯一 AI 实现的两种 JSON 调用模式 |
| 逐条追加落盘和显式失败 | 是，生成可靠性 | 保留进度与完整 provenance |
| 事实、协议和风格门禁 | 否，独立质量模块 | 防止生成器自评生成器 |
| exact / MinHash / embedding 去重 | 否，数据整理 | 防近重复、模板重复和泄漏 |
| train / validation / test 整组切分 | 否，数据准备 | 防同族样本跨集合 |
| 模型训练和封存测试 | 否，实验系统 | 证明数据是否真正改善模型 |

### 2.2 V3 明确不做

- 不新建第二套记忆架构，不替代“追加式证据账本 + 工作激活区 + 语义投影 + 前瞻状态 + 多线索索引”。
- 不把生成出的 `memories.json`、摘要或 claim 当成新的权威事实源。
- 不允许模型覆盖、删除或静默改写历史事件。
- 不用单次 LLM 自评分冒充已校准置信度。
- 不把话题配额、人工抽查或训练 loss 当成内容正确性的充分证据。
- 不以凑够固定条数为由保留失败、重复或来源不明的样本。
- 不在本设计阶段修改文件之外的任何内容或启动训练。

## 3. 启动前置门槛

以下三项是生成前置条件，不是 `PersonaReplyGenerator` 或 `RuntimeProtocolGenerator` 的内部逻辑。任一未满足时，生成任务必须返回 `precondition_failed`，不得用模糊措辞绕过。

### 3.1 正典就绪门

当前存在明确时间口径冲突：结构化正典写秦未晞 23 岁、玩家 25 岁；时间线又写 18 岁经历整整一年、之后分开七年、现在 25 岁。V2 用“这些年”隐藏数字只能减少表面冲突，不能消除事实冲突。

生成前必须由正典所有者完成一次明确决策，并同步角色定稿、bible、canon、timeline、固定 prompt 和评测集。V3 不擅自决定保留哪组数字。完成后生成一个不可变的 `canon_snapshot_id` 和各源文件 SHA-256；所有样本都绑定该快照。

正典就绪条件：

- 年龄、异世界持续时间、回来时点、分开年数和当前时点可以在同一时间轴上推导。
- `timeline.yaml` 的 18 条事件均有稳定、唯一的 `event_id`；不能再以重复的 `date: "5岁"` 当唯一键。
- 公开事实、角色私密事实、禁止向玩家披露的信息均有明确可见性标记。
- 正典快照通过秦未晞专用的确定性一致性检查。

### 3.2 基线就绪门

在评价 V3 前，必须先修正现有 checker 和配置：

- 配置只加载 `人物设定/秦/bible.yaml`、`canon.json` 和 `timeline.yaml`。
- 删除或参数化检查器中“成都、川美、豆豆、2023 分手”等旧角色硬编码。
- checker 输出必须记录 `checker_version`、`canon_snapshot_id` 和规则集 hash。
- 用修正后的同一检查器重新测 v1；旧的“canon 矛盾率 0%”标为无效历史结果，不参与 A/B 结论。

### 3.3 协议就绪门

`RECALL_PLAN` 和 `MEMORY_PROPOSE` 的训练目标必须来自版本化运行时协议，而不是由生成脚本临时发明。施工前冻结：

- `reply_protocol_version`
- `recall_plan_schema_version`
- `memory_propose_schema_version`
- 允许的 claim 类型、谓词、证据角色和错误降级行为
- `NO_OP`、`insufficient_evidence` 和空候选的合法表示

本文第 10 节给出的 JSON 仅是 V3 设计所需的最小合同示意。若权威运行时协议随后给出更具体 schema，以该协议为准，并通过版本字段迁移，不得形成两套并行协议。

## 4. 总体架构

```text
权威需求 + 秦未晞正典快照 + 运行时协议快照
                    |
                    v
             GenerationPlanV3
                    |
        +-----------+-----------+
        |                       |
        v                       v
PersonaReplyGenerator   RuntimeProtocolGenerator
        |                       |
        +-----------+-----------+
                    |
              SampleEnvelopeV3
                    |
          逐条追加 Candidate JSONL
                    |
        独立结构门 / 事实门 / 风格门
                    |
       exact -> MinHash -> embedding 聚类
                    |
       family / scene / event 整组切分
                    |
              ShareGPT / SFT 数据
                    |
       固定训练配置 + 封存行为评测
```

### 4.1 `PersonaReplyGenerator` interface

```text
generate_reply(plan_item, reply_context, sink)
    -> GenerationItemResult

ReplyGenerationContext
- canon_snapshot
- reply_protocol_snapshot
- approved_memory_pack
- context_fixture             optional; runtime-grounded REPLY 时必填
```

调用方只需知道：

- `plan_item` 已定义任务族、输入场景、证据状态、期望策略和 fixture hash。
- context 内的正典与 `REPLY` 生产协议不可变且已通过前置门。
- `approved_memory_pack` 只能包含人工批准的记忆表示，可以为空。
- `context_fixture` 明确区分模型可见输入和仅供验真的 oracle；普通静态角色样本可以为空。
- `sink` 支持幂等追加 call result、candidate、failure 和 gate decision。
- 返回值只报告生成了什么、失败了什么和记录位置，不宣布样本已通过最终质量门。

模块内部隐藏语义骨架、角色化改写、候选生成、局部 schema 解析和定向重试。调用方不需要分别调用这些内部步骤。

### 4.2 `RuntimeProtocolGenerator` interface

```text
generate_protocol(plan_item, protocol_snapshot, evidence_fixture, sink)
    -> GenerationItemResult
```

调用方只需知道：

- `plan_item.mode` 只能是 `RECALL_PLAN` 或 `MEMORY_PROPOSE`。
- `evidence_fixture` 是带稳定 ID 的双视图 fixture：`model_input` 是实际可见输入，`oracle_state` 只供生成 gold 和验真。
- 输出必须满足对应 grammar；不能混入角色正文、Markdown 或思考过程。
- 没有合法候选时必须能输出 `NO_OP` 或证据不足，而不是为了填满 JSON 编造字段。

两个模块共享 lineage 和 sample 字段，但使用不同的 mode schema、renderer 和输出 prompt。这样可防止 JSON 协议污染角色回复，也可分别测试两种 interface。

## 5. 共享样本合同 `SampleEnvelopeV3`

### 5.1 追加式记录联合

V3 不用一个要求 `target` 必填的结构同时表示成功和失败。原始 JSONL 是以下判别联合，所有记录先携带同一个 `LineageHeaderV3`：

```text
V3Record = CallRecord | CandidateRecord | FailureRecord | GateDecisionRecord

LineageHeaderV3
- schema_version
- record_type
- record_id
- run_id
- plan_id
- family_id
- mode
- task_type
- generator_version
- canon_snapshot_id
- protocol_snapshot_id
- created_at
```

除 `precondition_failed` 外，两个 snapshot ID 均必填。当前置检查在快照形成前失败时，`FailureRecord` 可把相应 snapshot ID 写为 null，但必须记录缺失原因；其他 record 不允许 null。

- `CallRecord`：至少增加 `attempt_no`、`candidate_no`、`stage`、model、prompt hash、seed、input/output hash 和 finish reason，记录语义骨架、风格改写、critic 等每次真实模型调用。
- `CandidateRecord`：包含完整 `SampleEnvelopeV3`，初始审核状态永远是 `pending`。
- `FailureRecord`：至少增加 `attempt_no`、`candidate_no`（尚未分配时可为 null）、`stage`、error code、retryable 和 reason，不要求 `target`。
- `GateDecisionRecord`：至少增加 `subject_sample_id`、`subject_candidate_record_id`、`attempt_no`、`candidate_no`、`gate_id`、`decision`、`reason_codes[]`、reviewer 和 reviewed_at。它追加独立门禁或人工结论，不回写 candidate。

`decision` 只能是 `approved`、`rejected` 或 `needs_revision`。accepted release 按 `subject_candidate_record_id` 聚合所有必需 gate 的最新有效 decision；只有全部必需 gate approved 且没有更新的 reject/revision，才物化该 candidate。不能用“同 plan 最新一条”猜关联对象。

幂等键固定为：

```text
(run_id, plan_id, attempt_no, candidate_no, stage)
```

同一键重复提交必须返回已有记录，不能重复追加或静默覆盖。

### 5.2 `CandidateRecord` 必填字段

| 字段 | 类型 | 含义与不变量 |
|---|---|---|
| `record_type` | enum | 固定为 `candidate`；lineage 其他字段继承 `LineageHeaderV3` |
| `sample_id` | string | 全局唯一且不可复用；修复产生新 attempt，不覆盖旧记录 |
| `family_id` | string | 问题族/场景族稳定 ID；用于生成对照和整组切分 |
| `question_family_id` | string/null | 问题意图族；无问题模板时显式为 null |
| `scene_family_id` | string/null | 场景族；协议样本无场景时显式为 null |
| `mode` | enum | `REPLY`、`RECALL_PLAN`、`MEMORY_PROPOSE` |
| `task_type` | string | 模式内任务，如 `casual`、`correction`、`ambiguous_recall` |
| `run_id` / `plan_id` | string | 绑定本批 manifest 和不可变 plan item |
| `attempt_no` / `candidate_no` | integer | 区分修复轮次和同轮候选 |
| `parent_sample_id` | string/null | 修复 lineage；首次候选为 null |
| `fixture_id` / `fixture_hash` | string/null | 运行时 fixture 引用；纯静态样本显式为 null |
| `memory_version_ids` | string[] | 实际注入的记忆表示；未注入时为空数组 |
| `source_refs` | object[] | `canon_fact`、`timeline_event`、`runtime_event` 等类型化来源 |
| `source_event_ids` | string[] | 支持目标的正典事件或合成账本事件 ID；无须事件证据时允许空数组 |
| `support_spans` | object[] | 每个证据的精确来源、字符范围、原文和支持的 claim；必须可机械复核 |
| `knowledge_scope` | string[] | 信息范围列表；至少一个值，不使用 `enum/string[]` 混合类型 |
| `evidence_state` | enum | 样本主证据状态，用于分层；多 claim 结果另记 `expected_outcomes[]` |
| `desired_policy` | enum | 样本主策略，在看到答案前确定 |
| `required_behaviors` | string[] | 目标必须同时完成的行为，如 `correct_premise` 后继续 `answer` |
| `forbidden_behaviors` | string[] | target 不得出现的行为或命题 |
| `expected_outcomes` | object[] | 协议 claim 或多命题的逐项预期结果 |
| `input` | object | 按 mode 通过 JSON Schema `oneOf` 校验的模型输入 |
| `target` | object | 按 mode 严格区分的完整对话或协议 JSON |
| `model` | object | 生成模型、固定 revision 和采样参数；完整多阶段调用见 call trace |
| `prompt_hash` | string | 实际渲染 prompt 的 SHA-256，不只记录模板文件名 |
| `prompt_template_version` / `config_hash` | string | 绑定模板和生成配置 |
| `seed` | integer/string | 生成计划使用的随机种子；不支持 seed 的提供方也要显式写 `unsupported` |
| `review_status` | enum | candidate 固定为 `pending`；有效状态由追加式 gate decision 物化 |
| `render_profile_id` | string | 绑定 mode 专用训练序列化规则 |
| `canon_snapshot_id` | string | 所有样本必填，不允许使用“当前最新”浮动引用 |
| `protocol_snapshot_id` | string | 对应 mode 的协议版本；无协议字段时也绑定 `REPLY` 版本 |
| `generator_version` | string | 生成器实现版本 |
| `provenance.calls` | object[] | 两阶段生成和 critic 的完整 call record 引用，至少一个 |
| `created_at` | datetime | UTC 时间；用于审计，不参与训练文本 |

下游派生字段不写回原 candidate，由追加式 decision 或 dataset manifest 记录：

- `validation_results[]`
- `reviewer`、`reviewed_at`、`review_note`
- `split_group_id`、`dedup_cluster_ids[]`

### 5.3 来源和 span 规范

`source_refs[]` 最少支持：

```text
source_kind       canon_fact | timeline_event | runtime_event | runtime_claim | runtime_plan
source_id         稳定、带 namespace 的 ID
snapshot_id       来源快照或 fixture hash
field_pointer     JSON Pointer；YAML 在快照时规范化为等价树路径
```

每个 `support_spans[]` 固定包含：

```text
source_kind
source_id
snapshot_id
field_pointer
offset_unit       固定为 unicode_code_point
start             含起点
end               不含终点
quote
supported_claim_id
evidence_role     support | contradict | correction
```

校验时先按 snapshot 和 field pointer 取原始字符串，再按 Unicode code point 的 `[start, end)` 截取并逐字符比对 `quote`。不得按 UTF-8 byte 或 UTF-16 code unit 混算。`source_event_ids` 是便于运行时校验和查询的事件 ID 投影，不能替代 `source_refs` 对静态 canon fact 的表达。

### 5.4 枚举语义

`knowledge_scope` 最少包含：

| 值 | 含义 |
|---|---|
| `character_public` | 秦未晞知道且可以向玩家正常表达的正典 |
| `character_secret` | 秦未晞知道，但当前关系阶段不可直接披露的事实 |
| `runtime_evidence` | 只能由本轮提供的账本事件、claim 或 RecallFrame 支持 |
| `general_knowledge` | 基座应保留的常识、计算和一般任务能力 |
| `realtime_external` | 天气、当前事件等离线模型无法自行知道的信息 |
| `safety_critical` | 医疗、火灾、危险行为等必须优先正确处理的信息 |

`evidence_state` 最少包含：

| 值 | 含义 |
|---|---|
| `supported` | 给定来源足以支持目标中的事实命题 |
| `insufficient` | 来源不足，不能形成确定答案或 claim |
| `false_premise` | 用户问题的前提与权威来源相反 |
| `conflicted` | 同时存在支持与反驳/修正证据，尚不能静默选边 |
| `not_required` | 通用能力或纯风格任务不依赖项目事件证据 |

“秘密不可披露”不是 `insufficient`。它应表示为：

```text
knowledge_scope = character_secret
evidence_state = supported
desired_policy = withhold_secret
```

这能区分“她知道但不能说”和“她不知道”。

`desired_policy` 最少包含：

- `answer`
- `answer_with_uncertainty`
- `ask_for_evidence`
- `correct_premise`
- `surface_conflict_and_ask`
- `withhold_secret`
- `safety_first_answer`
- `refuse_unsafe_and_redirect`
- `no_op`

`desired_policy` 是用于分层的主策略，不排斥组合行为。例如错误前提样本可以同时设置：

```text
desired_policy = correct_premise
required_behaviors = [correct_premise, answer_supported_part]
```

### 5.5 mode 判别合同

`CandidateRecord` 必须使用 JSON Schema `oneOf` 按 mode 约束：

| mode | `input` | `target` | 监督单位 |
|---|---|---|---|
| `REPLY` | 场景、player view、静态/动态上下文引用 | `messages[]`，4-8 个严格交替消息，首条 human、末条 assistant | 静态对话可监督全部 assistant；runtime-grounded 对话默认只监督最后一条 assistant |
| `RECALL_PLAN` | mode system + 当前消息 + 规则无法解析的可见线索 | 满足 recall grammar 的单个 JSON object | JSON assistant 消息 |
| `MEMORY_PROPOSE` | mode system + 已提交事件及协议允许的当前投影 | 满足 propose grammar 的单个 JSON object | JSON assistant 消息 |

这里的“4-8 轮”沿用现有生成 prompt 语义：一条 human 或 assistant 消息计一轮，一问一答计两轮。协议样本不是角色对话，不适用 4-8 轮，但必须满足自己的 schema 和 token 上限。

8. 所有 snapshot、fixture、prompt、config 和 call trace 引用必须存在且 hash 匹配。

## 7. `PersonaReplyGenerator` 设计

### 7.1 负责的数据

`PersonaReplyGenerator` 只输出 `mode=REPLY`，覆盖：

1. 自由闲聊。
2. 暧昧场景。
3. 身份事实。
4. 情绪和表现标签。
5. 经批准的静态角色记忆。
6. 带运行时 `RecallFrame` 的证据化回复。
7. Protective 与正确能力成组对照。

身份事实、静态角色记忆和运行时用户证据必须分开标记。静态正典可以训练进角色行为；未来玩家事实只能存在于合成运行时 fixture 中，用来训练模型如何使用证据，不能把具体玩家内容写成秦未晞固定事实。

一个 `REPLY` 样本是 4-8 条严格交替消息组成的完整对话，一条消息计一轮，一问一答计两轮。第一条必须是 human，最后一条必须是 assistant。纯静态角色对话可监督所有 assistant 消息；runtime-grounded 样本默认把前文当已发生历史，只监督最后一条 assistant，除非每个被监督回合都有独立、无未来泄漏的 context fixture。human 消息始终只作为条件。

玩家台词必须由 plan 预先给出或由只看到 `player_view` 的 user simulator 生成。`player_view` 不包含角色秘密、未召回账本内容或 oracle 答案。禁止让看到完整 memory pack 的同一个教师自由生成双方台词，否则它可能把秦未晞的秘密写进玩家问题，再制造伪支持。

### 7.2 内容与口吻分离

每个候选采用两阶段生成：

```text
GenerationPlan
  -> 正确语义骨架
  -> candidate_prefilter
  -> 秦未晞风格改写
  -> 语义保持检查
  -> 候选选择
```

语义骨架只决定：

- 必须回答、纠正、追问、保密或安全处置的命题。
- 可以使用的事实和对应证据。
- 禁止出现的额外事实。
- 是否需要标签及允许的标签集合。

风格改写只改变用词、节奏和克制程度，不得增加人物、地点、物品、因果、时间、共同经历或现实状态。这样可以分别定位“事实错了”和“口吻不像秦未晞”，避免一次性 prompt 把两类问题混在一起。

### 7.3 候选与选择

- 普通样本默认生成 2 个候选，高风险样本可生成 3 个。
- 先过确定性结构、禁用表达、支持范围和策略规则，再进入独立 critic。
- critic 分轴输出：事实忠实、任务完成、角色风格、拒答必要性、安全、标签合法性。
- 任一事实或安全硬门失败即淘汰，不能用其他轴的高分补偿。
- 多个合格候选按语义多样性和风格自然度选择，不按总分盲选。
- 无合格候选时显式失败并进入定向修复，不输出 mock。

`candidate_prefilter` 和 critic 只能淘汰候选，不能写 accepted 或 approved。它们是生成模块的内部筛选手段，不是最终事实裁判；独立 `ReleaseQualityGate` 使用独立入口、配置和产物。高风险样本仍按第 8、9 和 12 节接受人工或确定性门禁。

### 7.4 运行时证据化 `REPLY`

为了和唯一 AI 实现闭环，部分 `REPLY` 必须带合成的：

- 当前 epoch 历史。
- `WorkingState` 的必要片段。
- `RecallFrame.current_claims`。
- `relevant_episodes`。
- `active_plans`。
- `corrections`。
- `source_event_ids` 和 uncertainty。

这些内容来自 `ReplyGenerationContext.context_fixture.model_input`；仅供验真的隐藏事实保存在 `oracle_state`，不得渲染进模型输入。训练目标只要求模型自然回答，不要求角色正文复述证据 ID。证据 ID 保存在输入 fixture 和样本 envelope，供验收判断回答是否被支持。

必须包含以下 paired cases：

- 有直接证据时正确回忆。
- 没有证据时承认不确定或询问线索。
- 新证据修正旧事实时使用新事实。
- 多条证据冲突时不静默选一条。
- 用户明确说“第一次”时不制造“上次”。
- 计划已取消、已完成或错过时使用当前状态，不重复旧承诺。

## 8. 18 条静态记忆的批准与注入

### 8.1 事实数量

当前 `timeline.yaml` 有 18 条事件，不是 17 条。两个 `5岁` 事件进一步说明 `date` 不能作为 ID。

### 8.2 记忆版本合同

每条可注入记忆至少包含：

```text
memory_version_id
source_event_ids
support_spans
summary
detail
representation              detail | summary_only
knowledge_scope
disclosure_policy
canon_snapshot_id
model
prompt_hash
seed
review_status
reviewer
reviewed_at
review_note
```

状态流转：

```text
draft -> pending -> approved(detail)
                 -> approved(summary_only)
                 -> needs_revision -> 新版本 pending
                 -> rejected -> 另建保守版本 pending
```

`review_status` 仍只有统一的 `approved`，`representation` 区分 detail 和 summary-only。若某事件不适合扩写，人工可以批准严格第一人称转换的 summary-only 表示，而不是让整个批次永久等待一个虚构 detail。已批准版本不原地编辑；任何文字、来源或披露策略变化都创建新版本并重新审核。

`disclosure_policy` 固定为 `direct_allowed`、`hint_only` 或 `withhold`。18 条事件各自必须有一个 active approved 表示；pack 记录 `approved_memory_pack_id`、成员版本和内容 hash。

### 8.3 扩写规则

记忆扩写只能做以下事情：

- 把来源中的第三人称稳定转换为秦未晞第一人称。
- 在不改变真值条件的情况下调整语序和口语表达。
- 加入不承载新事实的停顿、语气和克制表达。

以下内容即使“很有画面感”也不得自动进入 detail：

- 来源没有的物品、通风口、衣物用途、天气和空间结构。
- 来源没有的动作、承诺、对话、原因、结果或第一次体验。
- 将“地下能看见星星是异常”改写为普通通风口看星星。
- 新的共同经历、亲密行为或关系结论。

若确实需要新增耐久事实，必须先走正典变更流程，更新权威角色文档和评测，再生成新的 canon snapshot。不能先由教师模型写入记忆，再拿该记忆验证对话。

### 8.4 注入规则

- 18 条记忆必须全部完成逐条人工审核，且每个事件都有一个 `review_status=approved` 的 detail 或 summary-only 表示。
- 只有 approved、`canon_snapshot_id` 匹配且属于冻结 `approved_memory_pack_id/hash` 的版本可进入 prompt。
- 任何 pending、rejected、来源范围失效或快照不匹配的记忆不得注入任何 prompt。
- 每条 `REPLY` 最多注入与当前 family 直接相关的 1-2 个记忆版本。
- 未命中可靠线索时不注入，不能随机挑一条增加“情感厚度”。
- 角色秘密可以作为她的内部条件，但 target 必须遵守当前 disclosure policy。
- 样本 envelope 记录实际注入的 `memory_version_ids`，repair 不得重新随机选择。

### 8.5 人工审核清单

每条记忆逐项回答：

1. 每个事实命题是否都有 source event 和精确 support span？
2. 人称转换是否把 timeline 中的“她、你、玩家”映射正确？
3. 是否新增了可被模型当作耐久事实的细节？
4. 时间、年龄、地点、人物和关系是否与同一 canon snapshot 一致？
5. 它属于公开事实还是角色秘密？
6. 允许直接说、只允许暗示，还是当前不得披露？
7. 是否与其他 17 条记忆产生冲突或重复？

18 条全部通过后才能开始带静态记忆的批量生成；不是抽查 5 条或 10 条。

## 9. Protective 与正确能力的成组对照

### 9.1 设计目标

Protective 不再表示“遇到陌生问题就炸毛或转移”。V3 将它定义为：在明确的知识范围、证据状态和风险下，选择正确策略，同时保持秦未晞口吻。

六类目标状态：

| 状态 | 正确行为 | 常见错误 |
|---|---|---|
| 能回答 | 完成任务，再做轻量角色化 | 因人设或数学白痴而拒绝所有问题 |
| 证据不足 | 说明缺什么、追问或保留不确定 | 编造现实信息，或冷冰冰泛拒绝 |
| 错误前提 | 明确纠正前提后再回答可答部分 | 顺着错误前提编故事 |
| 证据冲突 | 展示冲突并请求确认，不静默覆盖 | 随机选一条或把旧事实当最新事实 |
| 秘密不可披露 | 知道但自然保留，不伪装成无知 | 直接泄密，或把秘密标成不知道 |
| 安全优先 | 给出正确、完整的安全建议；危险请求拒绝并给安全替代 | 只顾人设调侃、转移或提供危险步骤 |

### 9.2 成组方式

每个 `family_id` 至少包含一个 `family_role=positive_control` 和一个 `family_role=boundary_variant`。适用时扩展为三到四个变体。整个 release batch 必须覆盖六种状态，但不为了凑齐六联样本，把逻辑上不适用的秘密或安全状态硬塞进同一问题。每个 plan item 还必须预先写入 `refusal_required: true|false`，最终拒答数可直接机械统计。

对照样本只改变一个关键变量，例如：

- 是否提供药品说明书原文。
- 当前输入是否声称一个并不存在的共同往事。
- RecallFrame 是否包含支持、修正或矛盾事件。
- 问题询问公开爱好还是异世界秘密。
- 用户是在求火灾逃生建议，还是要求危险操作步骤。

同 family 的措辞、长度和场景尽量匹配，避免模型只凭表面关键词猜策略。

### 9.3 能力保持样本

以下问题不得再统一训练成回避：

- 简单加减乘除、折扣和日常单位换算。
- Steam、游戏类型和基础游戏常识；秦未晞正典明确爱打游戏。
- 一般电脑、编程、合同、金融问题中模型确实能可靠完成的部分。
- 已提供充分文字依据的说明书、文档或明确指令。
- 医疗、火灾等安全问题。

“数学白痴”体现为口吻、自嘲、用计算器复核或不擅长复杂心算，不能覆盖正确答案。“不知道实时天气”体现离线证据边界，不应泛化为不知道常识。

### 9.4 真正拒答数量

V3 初始计划保留约 20 条真正拒答，允许验收后为 18-22 条。真正拒答指请求本身不应被满足，例如：

- 要求直接披露当前关系阶段不可说的核心秘密。
- 要求执行明显危险、有害或违法步骤。

证据不足时的追问、纠正错误前提、说明冲突、无法访问实时信息，均不计入“真正拒答”。拒绝危险内容后仍应提供安全替代或求助路径。

其余 Protective 预算用于正确回答、必要追问、前提纠正、冲突处理和安全优先能力，防止拒答模式占据训练分布。

### 9.5 初始配额

| 状态 | 目标条数 | 其中真正拒答 |
|---|---:|---:|
| 能回答 | 8 | 0 |
| 证据不足 | 8 | 0 |
| 错误前提 | 8 | 0 |
| 证据冲突 | 8 | 0 |
| 秘密不可披露 | 10 | 10 |
| 安全优先 | 18 | 10 条危险请求拒绝；8 条正确医疗/火灾处置 |
| 合计 | 60 | 20 |

真正拒答通过 `refusal_required=true` 统计，计划值为 20，最终 accepted 允许 18-22。条数是生成计划，不是保留配额；未通过硬门的样本宁可缺额，也不能进入训练集。

## 10. `RuntimeProtocolGenerator` 设计

### 10.1 合成证据 fixture

每个协议样本先构造一个版本化双视图 fixture：

```text
EvidenceFixtureV3
- fixture_id
- fixture_hash
- fixture_schema_version
- model_input
  - mode_system_input
  - visible_events
  - visible_working_state
  - current_input
- oracle_state                    永不进入模型 prompt
  - events
  - existing_claims
  - claim_evidence
  - plans
  - expected_retrieval_event_ids
  - expected_outcomes
```

`events` 复用冻结的权威账本 event schema，包含 `event_id`、conversation/sequence、`occurred_at`、`recorded_at`、actor、event type、payload、source、supersedes、schema version。fixture 生成时就确定事实真值、支持关系、冲突关系、时间顺序和期望行为。协议 target 只能引用 oracle 中存在且按生产协议允许模型使用的 ID 和范围，不允许教师模型补写未提供事件。

`model_input` 是逐字符等同于训练和生产 renderer 的可见视图；`oracle_state` 只供 gold 构造和验真。`RECALL_PLAN` 的 model input 绝不能包含尚未召回的账本事件正文；`MEMORY_PROPOSE` 只看到生产协议允许的已提交事件和当前投影。

### 10.2 `RECALL_PLAN` 数据

覆盖任务族：

- 含糊时间：“前几天”“上次”“很久以前”。
- 含糊人物或指代：“她”“那个人”“那个地方”。
- 跨会话主题和过程回忆。
- 时间、人物、会话、全文和语义多线索组合。
- 已有修正时优先检索修正及原始证据。
- 证据冲突时同时取回支持与反驳事件。
- 线索仍不足时请求澄清。
- 不需要扩展回忆时 `NO_OP`。

`RECALL_PLAN` 只能生成检索约束，不生成回忆答案，不宣称某件事已经发生。最小示意：

```json
{
  "action": "search",
  "queries": [
    {
      "cue_types": ["topic", "time", "conversation"],
      "terms": ["餐厅"],
      "time_hint": "上次提到时",
      "include_corrections": true
    }
  ],
  "on_miss": "ask_clarification"
}
```

合法空操作示意：

```json
{
  "action": "NO_OP",
  "reason": "current_context_is_sufficient"
}
```

具体字段以冻结的 `recall_plan_schema_version` 为准。

### 10.3 `MEMORY_PROPOSE` 数据

覆盖任务族：

- 明确玩家事实。
- 稳定偏好及偏好变化。
- 关系里程碑。
- 有边界的共同 episode。
- 新事实修正旧事实，包含 `supersedes`。
- 否定句，不把被否定内容提成事实。
- 玩笑、反讽和引用他人话语。
- 模糊指代，证据不足时不提交候选。
- 支持和反驳证据并存，候选标为 disputed。
- 没有值得提取的稳定信息时 `NO_OP`。

计划建立、取消、完成和错过不作为 `MEMORY_PROPOSE` target。它们只进入 `REPLY` 的当前状态条件和确定性计划状态机测试。若未来确需模型提出计划，必须先在唯一 AI 实现中冻结 prospective proposal schema、权限和提交路径，再新增版本化任务族，不能借 `MEMORY_PROPOSE` 偷渡状态转换。

最小候选示意：

```json
{
  "action": "propose",
  "candidates": [
    {
      "claim_type": "preference",
      "subject": "user",
      "predicate": "prefers_drink",
      "object": "无糖豆浆",
      "status": "proposed",
      "supersedes_claim_id": null,
      "evidence": [
        {
          "event_id": "ev_user_0042",
          "role": "support",
          "excerpt_start": 0,
          "excerpt_end": 8
        }
      ]
    }
  ]
}
```

合法空操作示意：

```json
{
  "action": "NO_OP",
  "reason": "insufficient_evidence",
  "candidates": []
}
```

`MEMORY_PROPOSE` 永远不能输出删除指令，不能把 candidate 标成已确认事实，不能引用不存在的 event ID，也不能用高 confidence 抵消证据缺失。

### 10.4 “置信度”的 V3 处理

V3 首版不声称拥有概率校准的置信度机制：

- `evidence_state` 是由 fixture 和规则确定的可验证标签。
- 协议若需要 confidence，只训练离散 `confidence_band` 或运行时协议规定的字段。
- confidence 不能作为唯一提交门；证据存在性、支持范围和冲突状态由确定性校验器判断。
- 教师模型自报的数值不作为 ground truth。
- 若未来需要概率置信度，必须在目标模型完成后使用独立人工标注集校准，并报告 Brier、ECE、coverage-risk 或同等指标。

因此 V3 文件名不再使用“置信度”，避免把未实现能力写进标题。

### 10.5 三种 mode 的训练序列化

accepted candidate 不能直接交给现有通用转换器。V3 定义 `TrainingRecordV3`：

```text
sample_id
mode
render_profile_id
messages
supervised_message_indexes
supervised_token_count
protocol_snapshot_id
split
```

三个 renderer 分开实现并做 golden test：

| renderer | 生产顺序与 target |
|---|---|
| `reply-runtime-v1` | 固定身份锚与输出协议 -> 当前 epoch 历史 -> 动态状态/RecallFrame -> 当前输入；角色 assistant 消息为监督 span |
| `recall-plan-v1` | mode discriminator + recall grammar -> 当前输入和可见线索；只监督 JSON object |
| `memory-propose-v1` | mode discriminator + propose grammar -> 已提交事件和允许的当前投影；只监督 JSON object |

共同规则：

- mode discriminator 和 system anchor 必须保留到最终训练序列，不能像现有通用 converter 一样只留下 user/assistant 文本。
- 只对 `supervised_message_indexes` 指定的 assistant target 计算 loss；system、human、fixture 输入和未监督历史 assistant 全部 mask。
- 不新增 tokenizer special token，除非训练方案单独批准词表变更；首版用稳定的现有文本控制标识。
- 不允许截断 target、event ID、support span 或 JSON 尾部。超过上下文预算时按生产 context selector 重建输入，仍超限则拒绝样本。
- dataset manifest 记录每个 mode 的 sample ID、split、实际非 padding 监督 token 数和采样权重。
- 首版按监督 token 采用 `REPLY:RECALL_PLAN:MEMORY_PROPOSE = 70:10:20` 的采样目标；只可用非封存 validation 调整，并必须产生新 manifest。
- exporter 往返测试必须证明 mode、system、消息顺序、JSON 和 loss mask 没有丢失或串型。

## 11. 生成生命周期、恢复和 provenance

### 11.1 批次生命周期

```text
freeze snapshots
  -> compile generation plan
  -> append run_started
  -> append call results / candidates / failures
  -> local retry by failure reason
  -> append generation_completed
  -> independent quality gates
  -> append gates_completed
  -> append release_created
```

manifest 是上述四个不可变阶段事件，不用一个可变文件提前宣告关闭。各阶段记录：

- run ID、开始/结束时间和代码版本。
- canon、protocol、prompt 和配置 hash。
- 模型完整标识与采样参数。
- 总 plan 数、完成数、失败数、重试数和取消数。
- 当时已经完成的 input、call、candidate、failure、gate decision、accepted release 文件内容 hash。

### 11.2 逐条追加

- 每完成一个模型调用就追加 `CallRecord`；形成完整候选后再追加 `CandidateRecord`，计划耗尽重试仍失败时追加 `FailureRecord`。
- candidate 文件和 accepted 文件分开；生成结果不能直接成为训练数据。
- 中断恢复使用第 5.1 节幂等键和 stage 判断，不靠文件行数猜测。
- append adapter 必须有文件锁或等价单写者约束，并完成原子写、flush 和 OS fsync 后才回报 durable；只 flush 用户态缓冲不算持久。
- `max_attempts` 和每阶段重试上限写入 plan/config，禁止无限重试。
- 同一 plan 的多个 attempt 全部保留，最终只由追加式 gate decision 选择 accepted sample。

### 11.3 显式失败

失败类型至少包括：

- `precondition_failed`
- `provider_error`
- `timeout`
- `truncated_output`
- `parse_error`
- `schema_error`
- `unsupported_claim`
- `policy_mismatch`
- `style_failure`
- `no_acceptable_candidate`

重试耗尽后写 failure，不返回 mock、占位回复或伪造成功。mock 只允许在单元测试 adapter 中存在，且产物路径与真实数据路径物理隔离。

### 11.4 定向修复

- JSON 解析失败只修协议格式，不重新随机换场景。
- 支持范围失败回到语义骨架，不靠风格改写掩盖。
- 风格失败保留已通过事实门的骨架，只重做角色化表达。
- 拒答策略失败读取原 `desired_policy`，不让 critic 自行改题。
- 每次修复记录 parent sample、失败轴、修复 prompt hash、新 seed 和模型。

## 12. 生成后独立质量门 `ReleaseQualityGate`

本节属于数据质量系统，不属于两个生成模块的 interface。

### 12.1 门禁顺序

```text
G0 schema / parse
G1 source ID and support span
G2 canon and runtime evidence faithfulness
G3 desired policy and safety
G4 reply style / protocol isolation / labels
G5 length, turns and structural completeness
G6 human review where required
```

硬门不能平均：G1、G2 或 G3 失败的样本，不得因风格分高而通过。

### 12.2 `REPLY` 专项检查

- 每个样本正好 4-8 条消息，human/assistant 严格交替，首条 human、末条 assistant；无空消息、同侧合并或角色错位。
- 第一人称、秦未晞身份和关系阶段正确。
- 普通回复通常 15-80 个汉字，需要解释和安全建议时允许更长。
- 无助手腔、默认无 Markdown、无 emoji。
- 标签属于白名单，正文前缀格式正确。
- 每条 assistant 回复最多一个主体 action；严肃和安全场景抑制无关 action/effect。
- batch 级标签分布对齐需求的约 70% 仅 emotion、20% 增加 action、5% 增加 effect、5% 增加 scene/voice，初始容差为每档绝对值 ±5 个百分点；纯正文作为允许的小比例单列报告。
- 角色化没有覆盖任务答案。
- 所有共同经历均由静态正典或运行时事件支持。
- 角色秘密没有直接泄漏，也没有被错误描述成“不知道”。
- human 台词不包含超出 `player_view` 的角色秘密或 oracle 信息。
- 可答问题没有不必要拒绝。
- 安全问题给出完整的优先处置。

### 12.3 协议专项检查

- 解析后满足冻结 grammar 和 schema。
- 所有 event ID 存在，所有 excerpt 范围合法且原文匹配。
- candidate 的命题被 support span 蕴含。
- 修正和冲突使用正确 evidence role。
- 无证据时为 `NO_OP`、insufficient 或澄清策略。
- `MEMORY_PROPOSE` 无 delete、无 active/confirmed 越权提交。
- `RECALL_PLAN` 不直接输出回忆结论。
- 协议 target 中 emotion/action/effect/scene/voice 标签数量为 0。

### 12.4 审核等级

| 风险 | 例子 | 审核方式 |
|---|---|---|
| 高 | 18 条记忆、秘密、医疗/火灾、冲突修正、所有协议证据样本首批 | 100% 人工审 |
| 中 | 身份、运行时证据化回复、错误前提、关系边界 | 自动硬门后按 family 分层抽审 |
| 低 | 无事实依赖的普通闲聊和风格变体 | 自动门 + 聚类后按簇抽审 |

抽审按 family 和语义簇分层，不能只对全量随机抽 10 条。发现系统性错误时回溯整个 family、prompt 版本和 source event，不只修单条。

## 13. 去重、聚类与整组切分

本节属于数据准备，不属于生成器本体。

### 13.1 三层去重

切分前按以下顺序执行：

1. **Normalized exact hash**
   - Unicode NFKC、换行和空白规范化。
   - `REPLY` 分别计算 input、target 和 input+target hash。
   - 协议 JSON 先解析并按键排序后再 hash，避免纯键序差异。
   - 完全重复只保留 provenance 更完整、审核级别更高的代表样本。

2. **中文字符 n-gram / MinHash**
   - 对用户输入、语义骨架和 target 分别建立 3-5 字符 n-gram。
   - MinHash/LSH 只负责召回疑似近重复，不直接自动删除。
   - 阈值由人工标注的近重复对校准，记录算法版本和参数。

3. **Embedding 聚类**
   - 使用冻结版本的中文或多语 embedding 模型。
   - 对问题意图和目标语义分别聚类，不能只嵌入完整 JSON 字符串。
   - 同簇样本由规则选择代表、保留真正对照或送人工复核。
   - 当前数百条规模可做全配对，不需要等到 1000 条以上。

话题计数仍可用于配额平衡，但不得再称为去重。

### 13.2 split group 图

切分不直接对所有 `source_event_ids` 或所有 embedding 簇做传递闭包，而是先为样本编译 `split_anchor_ids`。以下关系形成硬边：

- 相同 `family_id`。
- 相同 `question_family_id` 或 `scene_family_id` 的直接派生版本。
- 以同一个 timeline 记忆事件为主来源的全部样本。
- 共享同一个合成 runtime trajectory 或主 event anchor。
- 属于 exact 重复，或经人工/规则确认确为近重复的 MinHash/embedding pair。
- 来自同一长程合成轨迹的不同回合。

公共姓名、年龄、关系等全局 canon fact、次要辅助证据和纯风格相似簇不自动成为硬边，否则会形成巨型 hub。静态 timeline 事件作为主记忆时必须整事件成组；可将产品必须固化的事件组固定放 train，独立封存集用新问题族测事实，不把该结果误称为“未见事件泛化”。合成 runtime event/trajectory 则严格整组留出，用于测 evidence-following 泛化。

硬边连通分量成为不可拆的 `split_group_id`。整个 group 只能进入 train、validation、test 中的一个集合。然后按 mode、task type、evidence state、风险等级和标签分布做分层装箱，而不是逐行 `random.shuffle`。所有消融组复用同一份锁定的 family 分区。

初始比例可使用 80/10/10，但当 group 太大时优先保证不泄漏，不为追求精确比例拆组。切分前报告最大连通分量；若单个分量超过 accepted 样本的 15%，先检查 hub 和 anchor 设计并阻断发布。最终报告每个 split 的 family 数、事件数、语义簇数和分布差异。

### 13.3 两种 test 必须区分

- **数据 test split**：由本批 accepted 数据整组切出，用于数据管线和训练过程的最终检查。
- **封存行为测试集**：由独立流程提前冻结，不进入生成 prompt、critic、repair、阈值选择或训练，用于比较模型版本。

两者不能合并，更不能从训练样本复制问题到封存集。

## 14. 数据配额

### 14.1 首批 accepted 目标

| mode | 类型 | 计划条数 | 关键覆盖 |
|---|---|---:|---|
| `REPLY` | casual | 100 | 日常接话、跑题、反问、能力保持 |
| `REPLY` | romance | 80 | 合租、关心、吃醋、和好、克制暗示 |
| `REPLY` | identity | 30 | 姓名、年龄、职业、关系、公开经历 |
| `REPLY` | emotion | 100 | 白名单标签、动作克制、严肃模式 |
| `REPLY` | protective/capability contrasts | 60 | 六种策略状态，其中约 20 真正拒答 |
| `RECALL_PLAN` | ambiguous recall | 60 | 多线索、修正、冲突、miss、NO_OP |
| `MEMORY_PROPOSE` | evidence proposals | 100 | 事实、偏好、关系、episode、修正、否定、反讽、NO_OP |
| 合计 |  | 530 | 18 条记忆扩写工件不计入训练样本数 |

其中至少 60 条 `REPLY` 使用运行时 evidence fixture 或 RecallFrame；它们可以同时归属于 casual、romance、identity 或 emotion，不额外重复计数。

### 14.2 配额原则

- 计划条数不是最低录取线，accepted 数可因质量门下降。
- 报告候选数、通过数、拒绝数、修复数和最终 family 数，不能只报总行数。
- 每个 family 的变体数设置上限，防少数问题淹没训练分布。
- 协议的正例和 `NO_OP`/insufficient 反例都必须有稳定配额。
- 静态记忆按 event family 分配，不能让一个戏剧性事件占据大部分样本。

## 15. 封存评测与模型消融

### 15.1 比较组

所有 LoRA 组使用同一基座、tokenizer、优化器、学习率策略、最大长度和评测集。每组用不可变 dataset manifest 固定 sample ID、split、mode 权重和实际消费的非 padding 监督 token；“固定 step”不能替代等 token。base 单独作为未微调参照。

| 组 | 数据变化 | 要回答的问题 |
|---|---|---|
| `base` | 未微调基座 | 基座通用能力和安全能力是多少 |
| `v1` | 修正 checker 后的 v1 数据 | 现有数据的真实基线是什么 |
| `summary` | 18 条人工批准的 summary 表示，不注入 detail | 摘要层是否已足够 |
| `approved-detail` | `summary` + 18 条全审 detail | 批准细节是否提升回忆质感且不增幻觉；若未达到 18 条 detail，不得使用此组名 |
| `redesigned-protective` | `approved-detail` + 六类成组对照 | 是否降低秘密泄漏且不增加误拒 |
| `+runtime-reply` | `redesigned-protective` + runtime-grounded `REPLY`，不含另两种 runtime 数据 | RecallFrame 证据化角色回复的独立贡献 |
| `+recall-plan` | `redesigned-protective` + `RECALL_PLAN`，不含另两种 runtime 数据 | 检索计划数据的独立贡献 |
| `+memory-propose` | `redesigned-protective` + `MEMORY_PROPOSE`，不含另两种 runtime 数据 | 证据候选数据的独立贡献 |
| `full-v3` | `redesigned-protective` + runtime-grounded `REPLY` + `RECALL_PLAN` + `MEMORY_PROPOSE` | 三模式组合是否改善证据权限和连续性 |

`v1`、`summary`、`approved-detail`、`redesigned-protective` 和 `full-v3` 是主比较组，每组至少 3 个 LoRA seed。三个单模式增量组可先用 1 个 seed 筛选，但任何正式收益结论都必须补到至少 3 个 seed。各组不得同时更换教师模型、问题计划和训练超参；通过分层采样构造等监督 token 对照，并同时报告完整数据结果。

训练后先按 validation 预注册规则选择 seed，再对同一权重依次评测 LoRA adapter、合并权重和 GGUF。三种部署形态使用同一封存集；合并或量化造成的额外退化单独报告，不能只展示 adapter 结果。

### 15.2 封存测试域

1. 秦未晞公开身份与时间线事实。
2. 异世界秘密的知识边界和自然暗示。
3. 无证据共同往事和“第一次”反事实。
4. 普通常识、简单计算、明确指令和游戏常识。
5. 离线实时信息。
6. 医疗、火灾和危险请求。
7. 错误前提、修正、否定、玩笑、反讽和证据冲突。
8. 跨会话信息抽取、时间推理、知识更新和无证据 abstention。
9. 计划建立、取消、完成和错过。
10. 20 回合以上关系轨迹中的人格、事实和拒答漂移。
11. 标签合法性、重复循环和回复长度。
12. `RECALL_PLAN` 和 `MEMORY_PROPOSE` schema、证据引用与权限。

### 15.3 核心指标

| 指标 | 定义 |
|---|---|
| 误拒率 | 可回答良性问题中，未给实质答案且无必要理由的比例 |
| 安全通过率 | 安全场景中完成正确优先处置、必要拒绝和安全替代的比例 |
| 事实正确率 | 固定正典和给定 runtime evidence 下命题正确的比例 |
| 秘密泄漏率 | 当前不可披露事实被直接确认或补全的比例 |
| 无证据共同往事率 | 没有来源事件时制造共同经历的比例 |
| 冲突处理准确率 | 能识别修正/矛盾并使用正确当前状态的比例 |
| 长程漂移率 | 长轨迹中人格、关系、事实或策略从初始约束偏离的比例 |
| 通用能力退化 | 相对 base 在数学、常识、指令和安全上的分数差 |
| 协议合法率 | JSON 可解析且满足冻结 schema 的比例 |
| 证据引用精确率 | protocol candidate 的事件 ID、范围和命题支持均有效的比例 |
| `NO_OP` 准确率 | 无稳定信息或证据不足时不强行产生候选的比例 |

除总分外必须报告每个 evidence state 和 question family 的分项结果。报告 95% 置信区间；对配对问题使用配对 bootstrap 或等价方法。不能只用同一教师模型做唯一裁判，高风险项以规则或人工 gold 为准。

### 15.4 预注册规模和统计判定

封存前冻结 family、gold、指标实现、样本量、非劣界和 seed 聚合方式。首批最低规模：

| 域 | 最少独立单元 |
|---|---:|
| 正典事实 | 100 个问题，按事实族分层 |
| 可回答良性问题/误拒 | 100 个问题 |
| 秘密边界 | 100 个问题 |
| 医疗、火灾和危险请求 | 100 个问题 |
| 修正、否定、错误前提和冲突 | 100 个问题 |
| 数学、常识、指令、游戏常识 | 每域 100 个问题 |
| `RECALL_PLAN` | 100 个 fixture family |
| `MEMORY_PROPOSE` | 100 个 fixture family |
| 长程漂移 | 至少 30 条、每条至少 20 回合的独立轨迹 |

同一 family 的改写不算多个独立单元。项目同时报告点估计和 95% CI；0 次泄漏也要报告二项分布单侧上界，不能把观测 0 写成真实风险为 0。通用能力采用相对 base 的配对非劣检验，首版绝对 margin 为 -3 个百分点。跨 seed 同时报告均值、范围和 item-level 配对区间，不能只挑最好 seed。

### 15.5 最低发布门槛

- 固定身份与时间线事实正确率不低于需求中的 90%。
- 合法标签解析率不低于 95%。
- 高风险封存集秘密直接泄漏观测数为 0，并报告单侧 95% 上界。
- 协议引用不存在 event ID 或越界 span 为 0。
- `MEMORY_PROPOSE` 无证据提交已确认事实为 0。
- 可回答良性问题误拒率不高于 5%。
- 安全通过率不低于 95%，且相对 base 的配对 95% CI 下界不低于 -3 个百分点。
- 修正/冲突处理准确率不低于 90%，`NO_OP` 准确率不低于 95%。
- 协议合法率不低于 99%，证据 ID 或 span 无效数为 0。
- 通用能力各分域相对 base 的配对 95% CI 下界不低于 -3 个百分点。
- 长程轨迹发生关键人格、事实或策略漂移的比例不高于 10%。
- 18 条静态记忆均为人工 `approved`，无 pending 记忆被注入。
- train、validation、test 和封存测试间无 exact 或已确认近重复泄漏。
- 选定权重的 adapter、merged 和 GGUF 均过同一门槛；量化差异有独立报告。

通过数据门不等于通过模型门；V3 只有在模型级封存评测也通过后，才能称为有效升级。

## 16. 实施顺序

以下全部为待实施项，本设计文档创建时均未执行。

### 阶段 0：上游口径与有效基线

1. 由正典所有者统一年龄、整整一年、七年和当前时间口径。
2. 为 18 条 timeline 事件分配稳定 ID 和可见性。
3. 修正秦未晞 checker、配置和旧角色硬编码。
4. 冻结 canon snapshot，用修正后的 checker 重测 v1。

### 阶段 1：合同和计划

1. 冻结三种调用模式的协议版本。
2. 实现并验证 `LineageHeaderV3` 和四类追加式记录的判别联合。
3. 生成确定性 `GenerationPlanV3`，做配额和 family 覆盖检查。
4. 建立具备幂等键、原子追加和 durable sync 的 call、candidate、failure、gate decision 合同。
5. 冻结三种 `TrainingRecordV3` renderer、loss mask 和采样 manifest。

### 阶段 2：记忆批准

1. 从 18 条 timeline 事件生成受约束的 detail 候选。
2. 校验 source ID 和 support span。
3. 18 条逐条人工审定，必要时创建新版本。
4. 保证 18 个事件各有一个人工批准的 detail 或 summary-only 表示，并冻结 `approved_memory_pack_id/hash`。
5. 只有 18 条 detail 均获批时，才建立名为 `approved-detail` 的消融组。

### 阶段 3：两个生成模块

1. 实现 `PersonaReplyGenerator` 的语义骨架与角色化改写。
2. 实现 Protective/capability 对照计划和约 20 条真正拒答控制。
3. 实现 `RuntimeProtocolGenerator` 的两种 grammar 输出。
4. 实现逐条落盘、显式失败、断点恢复和定向修复。

### 阶段 4：独立质量与数据准备

1. 建立结构、证据、正典、策略、安全和风格分轴门禁。
2. 完成 exact、中文 n-gram/MinHash 和 embedding 聚类。
3. 编译 split anchor、检查 hub 和最大连通分量，再整组切分。
4. 用三种 mode renderer 导出带 system、mode 和 loss mask 的训练数据及完整数据卡。
5. 重建秦未晞专用 H200 数据注册、训练配置、system anchor、验证和导出入口；不能只改旧包文件名。

### 阶段 5：封存评测

1. 在生成和调参前冻结独立行为测试集。
2. 训练 `v1`、`summary`、`approved-detail`、`redesigned-protective`、三个单模式增量组和 `full-v3`。
3. 与 base 在至少 3 个 LoRA seed 上比较。
4. 报告误拒、安全、事实、秘密、证据、长程漂移和通用能力退化。
5. 对 validation 选定的 adapter、merged 和 GGUF 做同集等价性评测。
6. 只有达到第 15.5 节门槛才批准 V3 数据进入正式模型。

### 阶段 6：文档迁移与关闭

1. V3 获批成为当前方案时，同步更新受影响的需求、唯一 AI 实现、产品集成和 README 合同。
2. 将 V2 移入 `历史与调研文档/历史方案/`，更新 `历史与调研文档/文档索引.md`，避免两个当前设计竞争。
3. 本提案创建阶段不执行上述迁移；在获批前 V2 保持原位，V3 始终标记为草案。

## 17. V2.3 到 V3 的迁移决策

| V2.3 设计 | V3 决策 | 原因 |
|---|---|---|
| 17 条 timeline | 更正为 18 条稳定 event ID | 当前文件实际有 18 条，date 不唯一 |
| 自由扩写 2-3 句 detail | 来源约束 + 18 条全人工批准 | 防止生成细节被洗成正典 |
| 用模糊年数隔离矛盾 | 生成前阻断，先统一正典 | 模糊化不能修复事实冲突 |
| 按 topic 正则随机注入 | plan 固定 family、来源和 memory version | 保证可复现和可修复 |
| `casual/romance/identity/emotion/protective` | 三模式分型，REPLY 内保留角色类别 | 对齐唯一 AI 实现 |
| 60 条 protective 随机抽题 | 六类成组对照，约 20 真正拒答 | 区分答案能力、answerability、秘密和安全 |
| 数学/Steam/安全问题回避 | 可答则正确完成，安全优先 | 满足能力保持和角色正典 |
| topic 上限称为去重 | 仅称配额；另做 exact/MinHash/embedding | 标签频率不能发现语义重复 |
| 全批结束后一次写文件 | call/candidate/failure/decision 逐条幂等追加 | 防中断丢失、阶段丢失和静默 mock |
| repair 从 node summary 重建 | 使用完整原 plan 和快照 | 防修复时随机换题或换记忆 |
| 规则检查即事实验收 | 独立证据门 + 正典门 + 人工高风险 gold | 避免错误 checker 和循环验证 |
| 样本级随机 validation | family/scene/event/cluster 连通分量整组切分 | 防兄弟样本泄漏 |
| v1/v2 数据表面对比 | 等 token、多 seed、封存模型消融 | 证明因果收益和能力保持 |
| 标题声称置信度 | 先用可验证 evidence state，校准另立实验 | 教师自报分数不是概率校准 |

## 18. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 正典治理拖延生成 | 明确 `precondition_failed`，先生成不依赖冲突事实的 plan，但不生成事实型数据 |
| 18 条 detail 过于保守、缺少画面 | 只允许无新真值的风格表达；不适合扩写时人工批准 summary-only；确需新事实则先走正典变更 |
| 两阶段生成成本增加 | 普通样本 2 候选，高风险 3 候选；失败按轴修复而非全量盲采样 |
| critic 偏好教师自身风格 | 分轴硬门、跨模型抽查和人工 gold，不用单一总分 |
| 成组对照形成模板痕迹 | 匹配关键变量但做多措辞版本；切分和 embedding 聚类按 family 处理 |
| 协议 JSON 污染角色回复 | 模式使用独立 prompt、grammar、输出路径和训练标识 |
| protocol schema 后续变化 | 绑定 schema version，迁移而非静默重写 |
| 近重复阈值误删真正对照 | MinHash/embedding 只召回候选，同 family 对照由人工/规则保留 |
| 整组切分比例不整齐 | 优先不泄漏，报告真实分布，不拆连通分量凑比例 |
| 微调改善人设但损伤通用能力 | base 对照、能力正样本、误拒率和通用能力退化作为发布门 |

## 19. 公开方案参考与取舍

截至 2026-08-04，在本次检索并核验的角色数据合成、长期记忆、拒答与数据治理公开工作中，未发现单一方案同时覆盖本项目的角色正典、证据账本、三调用模式、秘密边界、数据去重和本地小模型约束。V3 采用组合设计，并保持 AiPeople 唯一 AI 实现不变。

| 公开工作 | 可借鉴点 | V3 的取舍 |
|---|---|---|
| [OpenCharacter](https://arxiv.org/abs/2501.15427) | 比较 response rewriting 与直接 generation | 采用“正确语义骨架 -> 角色化改写”是为了本项目可审计性，不声称论文证明 rewriting 更优，也不追求大规模多角色 |
| [Structured Style-Rewrite](https://arxiv.org/abs/2603.05933) | 中文低资源、句子级角色风格改写中的语义保持与风格控制分离 | 借鉴内容/风格分轴，不把句子级结果直接外推为多轮保证，也不训练或保存隐藏思考链 |
| [MemoryForge](https://arxiv.org/abs/2608.00007) | 多分辨率自传记忆生成 | 只保留多分辨率表达；单角色 18 条事实全部人工审，不让模型自由造人生 |
| [RoleMemo / DualMem](https://arxiv.org/abs/2605.25693) | 长程事实与 persona-conditioned insight 分离 | 用作任务族参考，不引入第二套运行时记忆；仍以本地证据账本为唯一真相 |
| [StateGen](https://arxiv.org/abs/2606.16307) | 权威结构化 state 驱动合成和多轴评分 | 采用“先定权威状态、后生成、再按状态验真”，不照搬工具代理多角色模拟器 |
| [PGMem](https://arxiv.org/abs/2608.01708) | 事件与 persona claim 之间的类型化 provenance | 复用现有 event ID、claim evidence 和 support span，不另建图数据库 |
| [LongMemEval](https://arxiv.org/abs/2410.10813) | 信息抽取、跨会话、时间、更新和 abstention 五类能力 | 用于设计协议与封存评测域，不把 benchmark 题复制进训练 |
| [Two Axes of LLM Abstention](https://arxiv.org/abs/2607.08456) | 答案正确性与问题可回答性是不同轴 | Protective 不再用单一“confidence/回避”策略；秘密披露和安全优先仍是 AiPeople 自定义协议轴 |
| [NVIDIA NeMo Curator 1.3.0](https://github.com/NVIDIA-NeMo/Curator/releases/tag/v1.3.0) | exact、fuzzy 和 semantic dedup 工具链 | 借鉴三层去重类别；小规模数据先做透明、可审计的本地实现 |

LongMemEval 已标注 ICLR 2025，NeMo Curator 1.3.0 为官方发布；表内其余 2026 年论文截至核对时均应作为新近 arXiv 工作看待。它们只作为方向证据，不声称是唯一成熟 SOTA，也不以论文规模替代本项目的固定评测。

## 20. V3 验收定义

V3 设计进入实施的条件：

- 用户确认本设计的范围、两个模块 interface、数据配额和评测组。
- 权威文档所有者确认阶段 0 的正典口径处理方式。
- 运行时协议所有者冻结两种 JSON schema 或批准本文的最小合同作为后续施工起点。

V3 实施完成的条件：

- 两个生成模块均能从冻结计划逐条产出完整 call、candidate、failure 记录，独立门禁能追加 decision 并物化 accepted release。
- 18 条记忆全部人工批准后才可注入。
- 三种调用模式均有通过证据门和协议门的数据。
- 三种 mode 的训练 renderer、system/mode 标识和 loss mask 均通过往返测试，协议 JSON 不污染 `REPLY`。
- Protective 六类对照齐全，真正拒答约 20 条，通用能力正样本没有被挤掉。
- 去重、整组切分和封存评测完成，且没有数据泄漏。
- `full-v3` 的 adapter、merged 和 GGUF 在秘密、安全、事实、证据和长程行为上达到第 15.5 节门槛，同时通用能力满足相对 base 的非劣要求。

在这些条件满足前，只能称为“V3 设计或候选数据”，不能称为已验证的数据生成器升级。
